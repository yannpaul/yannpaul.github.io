Go Programs Beyond One main.go

Learn packages, libraries, and multiple binaries by fixing a real structural problem in burrow, the CLI tool from Go CLI Basics: everything it does still lives in one main.go, thirteen lessons later. Same format as the other Go workspaces — a checklist, not a script, with code hidden behind collapsed disclosures until you're stuck.

Seven lessons, each a self-contained page. Every lesson (from Lesson 2 on) opens by making you redo everything structural from prior lessons before teaching anything new. Only Lessons 1–2 are written so far; the rest are scoped below and will be built out in future sessions. This workspace assumes you already have a working burrow — built across Go CLI Basics' lessons — on your own machine; Lesson 2 on tells you what to change in that existing code.

Lessons

  1. Packages Beyond main — what makes a directory a package, the exported/unexported visibility rule, and importing one package from another inside the same module, on a small standalone demo before touching burrow
  2. A Library Package and a Second Binary — extract real logic out of burrow's main.go into an importable scanner package, confirm the existing CLI still behaves identically, then build a second, independent binary that reuses it
  3. Coming up — internal/ and What It Actually Enforces — the directory convention the Go compiler itself checks, not just a naming suggestion, for code that shouldn't be imported from outside the module
  4. Coming up — Multiple Binaries, One Module — a deeper look at the cmd/ layout now that two binaries already exist, and what go build ./... actually does across all of them
  5. Coming up — Sharing Config and Version Info Across Binaries — a small pattern for constants (like a version string) shared between multiple binaries without duplicating literals
  6. Coming up — Testing a Library Package in Isolation — table-driven tests against the extracted package directly, no CLI framework or os.Args parsing involved
  7. Coming up — Capstone — pull every technique together and defend every package-boundary decision in the finished layout
