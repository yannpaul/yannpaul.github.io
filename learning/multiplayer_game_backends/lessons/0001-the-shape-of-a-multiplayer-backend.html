The Shape of a Multiplayer Backend

One authoritative server, a fixed simulation rate, and a boundary the client is never allowed to cross.

Strip away the graphics, the matchmaking screen, the cosmetics store — the backend of almost every competitive multiplayer game is one specific shape: a server that owns the real copy of the game world, ticking forward at a fixed rate, and a set of clients that render a best guess of that world and send it their intentions.

That's the whole shape. Every lesson after this one is either zooming into one piece of it (how the server hides its own latency from the player, Lesson 2) or explaining when a game deliberately breaks the pattern (peer-to-peer rollback in fighting games, Lesson 4). If you already think in distributed-systems terms, this lesson is mostly a vocabulary translation exercise — the ideas underneath will feel familiar fast.

The client-server model, and why it wins

A multiplayer game backend needs to answer one question first: who decides what's true? There are two broad answers.

Client-server: one machine — a dedicated, authoritative server — runs the real simulation. Every client sends it inputs ("I pressed forward," "I fired") and receives back the results. No client ever talks directly to another client. This is the dominant model for competitive shooters, MOBAs, and battle royales — Counter-Strike, Overwatch, Valorant, Fortnite all work this way.

Peer-to-peer: there is no separate server; the players' own machines coordinate directly, sometimes with one peer acting as an informal "host." This shows up in some genres (notably fighting games, which Lesson 4 covers in depth) but is rare wherever cheating or "who's actually right" matters competitively, for a reason this workspace returns to repeatedly: a peer is also a player, and a player has every incentive to lie about the world state in their own favor.

Distributed systems parallel

An authoritative server is structurally a single primary in primary-replica replication. Clients are replicas — but unlike a normal read replica, a game client is never trusted to have been an honest replica in the first place. Peer-to-peer is closer to a leaderless, quorum-free system: every node just believes its own state unless corrected, which is exactly why it's a poor fit whenever one participant might be adversarial.

Why do most competitive multiplayer games use a client-server model instead of peer-to-peer, even though peer-to-peer avoids the cost of running dedicated servers?

  • Peer-to-peer connections use too much bandwidth for real-time games to function.
  • A player's own machine has an incentive to lie about game state in peer-to-peer, and there's no independent arbiter to catch it.
  • Peer-to-peer always has higher latency than talking to a dedicated server.
  • Only a dedicated server is powerful enough to render the game's graphics.

Tick rate: the server's own clock

An authoritative server doesn't react to input the instant it arrives and continuously stream updates. Like almost all real-time simulations, it runs a game loop that advances the world by one fixed step — a tick — some fixed number of times per second, called the tick rate.

Tick rate is a real, expensive design decision, not a free dial to max out. Riot Games' own account of building Valorant is a good grounded example: they chose 128 Hz server ticks — double the 64 Hz that had been the genre standard (Counter-Strike's competitive servers, for instance) — specifically to shrink "peeker's advantage," the edge a player gets by being the one to round a corner first. But every doubling of tick rate roughly doubles the CPU cost of hosting each match: at 128 ticks per second, the server has under 7.8 milliseconds to finish all the work for one tick before the next one is due, and a data center hosting thousands of concurrent matches needs that math to work out per core, not just per match.

Why this isn't "just turn it up"

A higher tick rate makes the game feel more precise, but it costs real money at scale — more CPU per match means fewer matches per server means more servers. Every tick-rate decision in a shipped game is a trade between game feel and hosting cost. Keep this in mind for Lesson 6, when hosting cost comes back as its own topic.

Distributed systems parallel

Tick rate is a lot like choosing a fixed consensus round interval or a database's commit batching window: shorter intervals mean fresher, more precise state, at a direct throughput/CPU cost per unit of freshness gained. The novelty in games isn't the trade-off shape — it's that the "freshness" being bought is felt by a human in real time, in milliseconds, rather than measured as a system metric.

What the server actually sends back

Each tick, the server broadcasts the result — the current state of every relevant object in the world — back out to clients. A client never gets to just "ask a question and get the real answer instantly": there's always at least one full round trip (client → server → client) of network latency between an input and its confirmed result. That unavoidable delay, round-trip time (RTT), is the entire reason Lesson 2 exists — an authoritative server that simply waited for confirmation before showing anything would feel unbearably sluggish, so real games hide that latency instead of eliminating it.

That's the shape: authoritative server, fixed tick rate, an RTT floor no one can engineer away. Everything from here is either working around that floor (Lesson 2) or scaling this one shape up to millions of concurrent matches (Lessons 5–7).
