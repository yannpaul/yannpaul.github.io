Event-Driven Architecture · Lesson 3 of 6

The Shadow Side of Every Strength

Each weakness here is the same design decision from Lesson 2, seen from the other side.

Decoupling, scale, and durability weren't free in Lesson 2 — they were traded for something. This lesson names exactly what.

1. You traded ACID for eventual consistency

In a request-driven system, one database transaction can update several related rows atomically. In an event-driven system spanning services, there is no such transaction — each service reacts to an event on its own schedule. The system is only eventually consistent: correct once every consumer has caught up, with no promised bound on when "eventually" arrives.

Concretely: a payment service publishes "payment succeeded," but the order service hasn't consumed it yet. For some window of real time, the order genuinely looks unpaid to anyone who checks — and that window has no fixed ceiling.

2. The dual-write problem

A service usually needs to do two things when something happens: update its own database, and publish an event about it. Those are two separate operations against two separate systems — they are not atomic. If the database commit succeeds but the publish fails (network blip, broker unavailable), every downstream consumer never learns the change happened at all. Silent, hard-to-detect data drift is the result.

A service commits a database write, then the process crashes before it publishes the corresponding event. What's the direct consequence?

  • Kafka rolls back the database write to stay consistent.
  • Kafka's replication reconstructs the missing event from broker logs.
  • The event publishes automatically on the next database write.
  • Every downstream consumer silently never learns the change occurred.

3. Ordering is per-partition, not per-topic

Kafka guarantees order only within a single partition. Two events for the same entity (say, two updates to order 42) will be processed in order only if they're routed — by key — to the same partition. Get the partitioning key wrong, or need order across entities, and events can be processed out of sequence with no error raised anywhere. This is invisible until it causes a bug: "the shipment event was processed before the order-creation event" is a class of failure with no stack trace.

4. Rebalancing pauses the thing it's protecting

Lesson 2's resilience story — a crashed consumer gets its partitions picked up by others — runs on a mechanism called rebalance. But a rebalance briefly pauses consumption for the affected partitions while assignments are recalculated. In the older "eager" rebalancing strategy, that pause hits the whole group, not just the changed partitions — so a single flaky consumer restarting can spike consumer lag across an entire group, on every restart.

5. Debugging a flow you can't see end-to-end

In a request-driven call chain, a stack trace shows you the path. In an event-driven system, an event can trigger a consumer, which publishes another event, which triggers another consumer — a chain with no single process holding the whole picture. Without deliberate work (correlation IDs threaded through every event, distributed tracing, dead-letter monitoring), a production incident becomes "which of our 40 services touched this event, and in what order?" This effect compounds with scale — practitioners call the resulting sprawl of hard-to-track flows event entropy.

Order-creation and shipment events for the same order end up on different partitions and are processed out of order downstream. What does Kafka do about it?

  • Kafka reorders them automatically to match creation time.
  • Kafka raises an ordering-violation alert for the consumer.
  • Nothing: cross-partition order was never a guarantee here.
  • The consumer group rejects the out-of-order shipment event.

The pattern across all five

None of these are bugs in Kafka. They're the honest cost of the design in Lesson 1: decoupled, asynchronous, partition-parallel systems give up the single-transaction, single-call-stack guarantees a monolith gets for free. Lesson 4 is about paying that cost deliberately instead of discovering it in production.

If any of these feels abstract — especially the dual-write problem or partition ordering — ask for a walk-through with concrete service names before Lesson 4. The mitigations only make sense once the failure they're patching is vivid.
