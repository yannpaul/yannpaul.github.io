Flipping the Outbox: When the Topic Is the Truth

Yes, people build it this way — but the consistency is not the same, and here's precisely why.

In Lesson 4, the database was the source of truth and the outbox got events out of it reliably. This lesson answers a sharper question: what if you flip that — the topic is the source of truth, and a service's own database is just a materialized view it builds by consuming its own topic, exactly like every other consumer?

Yes — this is a real, named pattern

It's not exotic. It's the combination of event sourcing (an entity's true state is the sequence of events that happened to it, not a row that gets overwritten) with CQRS (the write path and the read path are different things, connected by the log). Kafka Streams formalizes it directly: a KTable is state built by folding a topic, and Kafka's own internal-data-management documentation is explicit about which side is authoritative — "the changelog topic is the source of truth for the state ... RocksDB is used as a (non-fault-tolerant) cache." The local database is the cache. The log is the record.

The clearest articulation of this as a general architecture — not just a Kafka Streams implementation detail — is Martin Kleppmann's "Turning the Database Inside Out," built around Apache Samza (LinkedIn's own stream processor, a sibling to Kafka). His framing: make changes in one place — the log — and treat every database, index, or cache as a materialized view derived from it. There can be many such views (a key-value store, a search index, a graph index), and critically, a service consuming its own topic to build its local view is not a special case — it's just one more derived view, architecturally identical to any dependent's.

In the reversed pattern, what does a service's local database actually contain?

  • A derived, rebuildable view folded from replaying its own topic.
  • The authoritative record, with the topic as a side effect.
  • An independent copy, entirely unrelated to the topic's own state.
  • Nothing at all, since single-partition topics need no local view.

So is the consistency the same? No — and here's the specific reason

Walk through what changes for the writer itself, since that's where the asymmetry lives:

Outbox (Lesson 4): the service writes to its own database and inserts the outbox row in one local transaction. That database write is synchronous and immediate. The service — and anyone querying its database a moment later — sees the change instantly. Only downstream consumers wait on the relay, bounded by its lag.

Log-as-truth (this lesson): there is no separate synchronous database write anymore. The only durable commit is the produce to the topic. The service's own local materialized view is populated by consuming that topic back — on the same consumer machinery, with the same lag characteristics, as every other consumer. The service has lost its special status. It is now just another eventually-consistent reader of its own write.

This is a known, named problem, not a hypothetical: practitioners call it the read-your-writes problem in Kafka-backed event-sourced systems. One well-documented critique of using Kafka this way puts the fix bluntly: "make the producer a consumer of its own events and block until the event is committed and available" — and notes that doing so "would have severe impact on performance." That's the trade laid bare: you can get read-your-writes back, but only by paying for it explicitly, per request.

The direct answer to your question

No, it would not be the same. Durability is arguably better in the reversed pattern — there's only one system of record, so the dual-write problem doesn't just get mitigated, it's structurally impossible (nothing to desynchronize from). But per-request consistency for the writer gets worse: the outbox pattern gives the writer free, instant read-your-own-writes; the reversed pattern demotes the writer to eventual consistency along with everyone else, unless you deliberately re-engineer that guarantee back in.

Getting read-your-writes back, if you need it

  • Block until caught up — after producing, wait until the local consumer's offset passes the produced offset before responding to the caller. Correct, but adds latency proportional to consumer lag, which is exactly the cost the quote above warns about.
  • Optimistic local apply — update an in-memory or provisional view immediately on produce, before the log round-trip confirms it, and reconcile if the eventual replay disagrees. Fast, but now you're maintaining two notions of "current state" during the gap.
  • Accept it in the UI — show the write as pending/processing rather than pretending it's instantly final. Cheapest to build, and honest about what actually happened, but it's a product decision as much as an engineering one.

None of these are free. That's the same shape of trade-off as every mitigation in Lesson 4: you're not eliminating the cost, you're choosing which cost you pay.

Why most CRUD services still don't do this

Two costs keep the plain outbox pattern more common than log-as-truth for ordinary services: the read-your-writes cost above, and the loss of ad-hoc querying — a relational database answers a new filter or join today; a log-as-truth system needs a purpose-built materialized view (a new KTable, a new index) for each query shape you didn't already plan for. Log-as-truth earns its keep where the audit trail is the product (financial ledgers, event-sourced domain aggregates) or where a stream-processing platform (Kafka Streams, ksqlDB) is already doing the folding for you as infrastructure, not bespoke code per service.

If you're weighing this for a specific service you're designing, tell me what it needs to query and how fresh a write needs to look to the person who just made it — that's usually enough to tell which side of this trade-off you're on.
