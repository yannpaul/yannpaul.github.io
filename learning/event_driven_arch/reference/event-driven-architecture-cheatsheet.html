Event-Driven Architecture · Reference

EDA / Kafka Cheat Sheet

Compressed from Lessons 1–8. Designed to print on one or two pages — this is what you come back to, not the lessons themselves.

Core mechanisms

TermWhat it is
TopicA named, durable, append-only log of events. Not deleted on read.
PartitionAn ordered slice of a topic. Order is guaranteed within a partition only.
OffsetA consumer's position in a partition's log — enables resume, rewind, replay.
ProducerPublishes events. Never knows who (if anyone) consumes them.
ConsumerSubscribes to and processes events, independently of the producer's lifecycle.
Consumer groupA set of consumers splitting a topic's partitions between them — one partition, one consumer per group, at a time.
In-sync replica (ISR)A replica fully caught up with the partition leader; eligible for promotion on leader failure. min.insync.replicas sets how many must ack a write under acks=all.
RebalanceReassigning a consumer group's partitions when membership changes — pauses affected consumption while it runs.
Consumer lagGap between the latest offset written and the offset a consumer has processed. The primary "are we falling behind" metric.
Schema registryStores and enforces event-schema compatibility, so producers/consumers evolve independently without breaking each other.

Concepts

TermWhat it is
Eventual consistencyAll consumers converge on the same state eventually — no bound on how long "eventually" takes.
Event entropyEvent flows multiplying faster than any team can track their intent, order, and causality, absent deliberate governance.
SagaA cross-service business transaction as a sequence of local transactions, each with a compensating action.
Compensating actionAn explicit "undo" step for a saga stage that already committed and can't be rolled back transactionally.
Event sourcingAn entity's true state is the full sequence of events that happened to it, not a row that gets overwritten in place.
Materialized viewA derived, rebuildable read model (a database table, an index, a Kafka Streams state store) folded from replaying a log. The log is authoritative; the view is a cache.
CQRSWrite path and read path are different things, connected by the log — writes append events, reads query a materialized view built from them.
Read-your-writes problemWhen the writer's own local view is just another consumer of the log, it no longer sees its own write instantly — it waits on the same lag as everyone else.
Aggregate (entity)The largest unit that can be updated atomically — one service, one local transaction. Called an "entity" in Pat Helland's distributed-systems framing; never atomically updated across another aggregate.
ActivityCoordination between separate aggregates/entities, necessarily via at-least-once messaging (retries, dedup, out-of-order arrival) since no transaction can span them.

Strengths → weaknesses → mitigations, at a glance

StrengthShadow weaknessMitigationCost of the mitigation
Decoupled in time & space Eventual consistency, not ACID Idempotent consumers + sagas with compensating actions Compensating logic to write and maintain; some actions can't be undone cleanly
Producer doesn't know consumers Dual-write problem (DB write + publish aren't atomic) Transactional outbox + relay Extra table + relay process; small publish delay
Parallel scaling via partitions Order guaranteed per-partition only Partition by a stable business key Hot partitions on skewed keys; repartitioning is a migration
Resilience via consumer-group failover Rebalance pauses consumption Cooperative rebalancing + static membership Real crashes take longer to detect and recover from
New consumers attach with no coordination No single stack trace across services (event entropy) Correlation IDs, schema registry, lag alerting, dead-letter topics Governance and tooling overhead, owned by someone

Decision checklist

Lean toward EDA when

Multiple independent consumers need the same facts (now or later) · producers and consumers release on different schedules · brief inconsistency between services is tolerable for the business process.

Lean away from EDA when

A single, all-or-nothing, immediately-consistent operation is all you need — a local ACID transaction is simpler and more correct than sagas and outboxes bolted on to fake it back.
