Upgrading to errgroup

Rebuild Lesson 7's worker-pool duTop from memory first. Then delete most of it, and let a well-tested library carry the parts you've been hand-writing since Lesson 2.

Look back at what Lesson 7 actually built: a jobs channel, a fixed number of workers, a WaitGroup, a second goroutine just to close results at the right time. Every piece was worth learning, because you'll recognize this shape everywhere in real Go code — but almost nobody hand-writes it from scratch anymore. golang.org/x/sync/errgroup is the standard answer: a small, official-adjacent library that does exactly this, with the error-handling Lesson 2's mutex was protecting built in from the start. This is the same move Go CLI Basics made when Lesson 11 replaced by-hand dispatch with Cobra.

Warm-up — repeat from Lessons 1–7
  • Checkpoint

    go run -race . du top --path scratch --n 10 prints your known-good sorted lines, no warnings — this is what you're about to replace.

New: errgroup.Group

An errgroup.Group is a sync.WaitGroup that also knows how to collect an error. Call g.Go(func() error { ... }) instead of go func() { ... }(), and instead of wg.Add(1)/defer wg.Done(), the group tracks the goroutine for you. Call g.Wait() instead of wg.Wait(), and it returns the first non-nil error any of your functions returned — no mutex, no firstErr variable, built into the type itself. g.SetLimit(n) caps how many of your functions run at once, replacing Lesson 7's entire jobs-channel-plus-worker-loop mechanism with one method call.

  • Stuck? Show the command 
    go get golang.org/x/sync/errgroup

    Despite the golang.org/x import path, this isn't part of the standard library you get for free — it's a separate module, maintained by the Go team, that you add like any other dependency.

  • Stuck? Show the function 
    import "golang.org/x/sync/errgroup"

const maxWorkers = 4

func duTop(root string, n int) error {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return err
	}

	dSizes := make([]dirSize, len(dirs))
	var g errgroup.Group
	g.SetLimit(maxWorkers)

	for i, d := range dirs {
		g.Go(func() error {
			p := filepath.Join(root, d.Name())
			s, err := sizeOf(p)
			if err != nil {
				return err
			}
			dSizes[i] = dirSize{p, s}
			return nil
		})
	}

	if err := g.Wait(); err != nil {
		return err
	}

	sort.Slice(dSizes, func(i, j int) bool { return dSizes[i].Size > dSizes[j].Size })
	n = min(len(dSizes), n)
	for _, d := range dSizes[:n] {
		fmt.Printf("%10d %q\n", d.Size, d.Name)
	}
	return nil
}

    Notice i and d are used directly inside the closure passed to g.Go, with no func(i int, name string) { ... }(i, d.Name()) wrapper like every earlier lesson needed. Since Go 1.22, each loop iteration gets its own copy of i and d automatically — the classic "closure captures the loop variable and every goroutine sees the last value" bug is gone. On an older Go version this same code would be a real bug; if you're ever unsure which behavior you're getting, the explicit-parameter version from Lessons 2–7 always works regardless of version.

    go build ./... succeeds with all of that gone — errgroup.Group was doing the job of every piece you just deleted.

  • Checkpoint

    Same sorted output as Lesson 7, every time, -race silent. Fewer moving parts, identical guarantee: at most maxWorkers entries are being sized at once, indexed writes mean no two goroutines ever touch the same slice slot, and the first real error — try pointing --path at a directory you can't read — comes back from g.Wait() exactly like firstErr used to.

Idiom

This is a pattern worth internalizing beyond just duTop: learn the primitives by hand first — go, WaitGroup, channels, select, a worker pool built from scratch — so that when you reach for a library that packages them up, you know exactly what it's doing underneath and can debug it when something goes wrong. errgroup isn't magic; it's a WaitGroup, a mutex-protected error, and (with SetLimit) a semaphore, wearing a smaller API. Reaching for the library first, without having built the primitives yourself even once, is how you end up unable to explain why your own code works.

You've now rebuilt duTop five times: serial, indexed-writes-plus-mutex, channel-based, worker-pool, and errgroup. Lesson 9 puts a number on why any of this mattered in the first place, and asks you to defend the final version's every synchronization choice from memory.
