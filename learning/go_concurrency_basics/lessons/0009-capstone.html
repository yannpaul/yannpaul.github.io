New: putting a number on it

Every lesson so far has argued concurrency helps without measuring it. On a small scratch directory with three or four entries, a parallel duTop and a serial one finish close enough in time that you can't feel the difference — the real payoff shows up on work that's actually slow per item. Rather than fighting with a real slow disk again, write a tiny standalone benchmark using a fake slow task, so the timing difference is unambiguous and reproducible on any machine.

  • Stuck? Show the code 
    package main

import (
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func slowTask(n int) int {
	time.Sleep(200 * time.Millisecond)
	return n * n
}

func serial(inputs []int) []int {
	out := make([]int, len(inputs))
	for i, n := range inputs {
		out[i] = slowTask(n)
	}
	return out
}

func parallel(inputs []int) []int {
	out := make([]int, len(inputs))
	var g errgroup.Group
	g.SetLimit(4)
	for i, n := range inputs {
		g.Go(func() error {
			out[i] = slowTask(n)
			return nil
		})
	}
	g.Wait()
	return out
}

func main() {
	inputs := []int{1, 2, 3, 4, 5, 6, 7, 8}

	start := time.Now()
	serial(inputs)
	fmt.Println("serial:  ", time.Since(start))

	start = time.Now()
	parallel(inputs)
	fmt.Println("parallel:", time.Since(start))
}
    Checkpoint

    serial takes roughly 1.6 seconds — 8 tasks times 200ms each, one after another. parallel takes roughly 400ms — 8 tasks through 4 workers means two batches of 4 running at once, 200ms per batch. That ratio (4x here, bounded by SetLimit(4), not by the input size) is the entire, concrete payoff of everything this course covered. go run -race . stays silent on both.

Idiom

Notice the parallel version isn't 8x faster, it's roughly maxWorkersx faster — bounded concurrency trades some theoretical speed for a predictable ceiling on resource use. If duTop ran one goroutine per entry with no limit at all (Lesson 2 through 6's approach), a directory with 8 entries would look 8x faster in a toy benchmark like this — but that number stops meaning anything once the directory has thousands of entries and the bottleneck becomes the disk itself, not the number of goroutines. Lesson 7's maxWorkers and Lesson 8's SetLimit exist for exactly that gap between a toy benchmark and reality.

Recap — from memory, no hints

Answer each question before checking — this is retrieval practice, not a reading exercise. Every option gets an explanation once you answer, right or wrong.

1. In Lesson 1, go func() { fmt.Println("hi") }() followed immediately by main returning often prints nothing at all. Why?

  • Incorrect — it's a stdout buffering issue specific to goroutines.
  • Incorrect — the goroutine never actually starts running.
  • Correct — the program exits as soon as main returns, and nothing forces main to wait for the goroutine to run first.
  • Incorrect — fmt.Println can't be safely called from inside a goroutine.

2. Lesson 2's duTop wrote to dSizes[i] from multiple goroutines with no mutex, and -race stayed silent. Why was that safe?

  • Incorrect — it was actually unsafe, the test fixture was just too small to trigger it.
  • Correct — every goroutine wrote to a distinct index into a slice that was already sized to fit all of them, so no two goroutines ever touched the same memory.
  • Incorrect — Go slices have built-in per-element locking.
  • Incorrect — the sync.WaitGroup in that version was what made the writes safe.

3. Lesson 3 replaced the mutex-protected firstErr with a channel. What specifically made receiving from that channel exactly len(dirs) times sufficient to replace wg.Wait()?

  • Correct — receiving a value only completes once some goroutine has actually sent one, so finishing len(dirs) receives is only possible once every goroutine has finished and sent.
  • Incorrect — channels automatically track how many goroutines are still running.
  • Incorrect — the channel's buffer size was set to match the number of goroutines.
  • Incorrect — a sync.WaitGroup was still running quietly behind the scenes.

4. In Lesson 4, the broken append-based duTop sometimes printed 8 lines and sometimes 7, with no crash and no error message. What does that intermittent behavior tell you about a data race?

  • Incorrect — since it worked most of the time, it was mostly safe with just an occasional cosmetic glitch.
  • Incorrect — Go always panics immediately when two goroutines write to the same slice concurrently.
  • Incorrect — this kind of bug is undetectable by tooling and can only be found by manual review.
  • Correct — a data race produces undefined behavior whose visible effect depends on scheduling timing, so it can look fine on many runs and wrong on others, with no reliable warning either way.

5. Lesson 5's scratch demo showed a goroutine's "send completed" print appearing immediately with a buffered channel, but only after main's sleep with an unbuffered one. What's the underlying rule?

  • Incorrect — unbuffered channels always block because they can only have one receiver at a time.
  • Correct — a send on an unbuffered channel blocks until a receive is happening at that exact moment; a send on a buffered channel with room left completes immediately, independent of whether anyone is receiving yet.
  • Incorrect — buffered channels are asynchronous and unbuffered channels are synchronous, full stop, with no further nuance.
  • Incorrect — fmt.Println behaves differently depending on channel buffering.

6. Lesson 6 added a case <-deadline inside duTop's select, using a deadline := time.After(duTimeout) created once before the loop. Why not call time.After(duTimeout) fresh inside the loop, once per iteration?

  • Incorrect — select can only have exactly two cases, so the channel has to be created outside the loop to satisfy that limit.
  • Incorrect — calling time.After inside a loop doesn't compile in Go.
  • Correct — creating a fresh time.After on every iteration would reset the countdown every time a result arrives, so the timeout would only ever fire if one single receive took too long, not if the whole loop ran long overall.
  • Incorrect — it would leak memory too quickly to run even once.

7. Lesson 7's worker pool started exactly maxWorkers goroutines instead of len(dirs). What problem does that solve that Lessons 2–6's "one goroutine per entry" approach doesn't?

  • Correct — one-goroutine-per-entry has no ceiling on how much concurrent work runs at once, so a directory with a huge number of entries launches a huge number of simultaneous goroutines all contending for the same disk; a worker pool caps that at a fixed, chosen number.
  • Incorrect — worker-pool goroutines execute faster than goroutines started directly with go.
  • Incorrect — it fixes the data race from Lesson 4, which one-goroutine-per-entry could never avoid.
  • Incorrect — it's required to make Lesson 6's select/timeout pattern work at all.

8. Lesson 8 replaced the hand-rolled worker pool with errgroup.Group. Which statement about errgroup is accurate?

  • Incorrect — a Group must be created with a special constructor function before use, unlike sync.WaitGroup.
  • Incorrect — g.Wait() returns a combined slice of every error returned by every function passed to Go.
  • Incorrect — SetLimit sets the minimum number of goroutines that must run before Wait can return.
  • Correct — g.Go launches a tracked goroutine without any manual Add/Done bookkeeping, and g.Wait() blocks until they all finish while returning the first non-nil error any of them produced.
