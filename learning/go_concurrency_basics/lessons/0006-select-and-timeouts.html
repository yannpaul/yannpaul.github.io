select and Timeouts

Rebuild Lesson 5's buffered duTop from memory first. Then give it something none of the last five lessons have: a way to give up.

Every version of duTop so far trusts every goroutine to eventually send a result. If one subdirectory sits on a slow network mount, or a disk is failing, or anything else makes one sizeOf call take forever, duTop just waits forever too — it has no way to notice. select lets you wait on more than one channel at once, and time.After turns "waited too long" into a channel you can wait on right alongside your real results.

Warm-up — repeat from Lessons 1–5
  • Checkpoint

    go run -race . du top --path scratch --n 10 prints your known-good sorted lines, no warnings — your baseline before adding a timeout.

New: waiting on two channels at once

select looks like a switch, but each case is a channel operation, not a value. It blocks until one of its cases is ready, then runs that case's body — and if two are ready at the same instant, it picks one at random. time.After(d) returns a channel that receives exactly one value, once, after duration d has passed. Putting the two together — a case for your real channel, a case for time.After's channel — gives you "whichever happens first."

  • Stuck? Show the code 
    package main

import (
	"fmt"
	"time"
)

func main() {
	ch := make(chan string)

	go func() {
		time.Sleep(2 * time.Second)
		ch <- "done"
	}()

	select {
	case msg := <-ch:
		fmt.Println("received:", msg)
	case <-time.After(500 * time.Millisecond):
		fmt.Println("timed out waiting")
	}
}

    The goroutine keeps running and eventually sends "done" — but nothing is left to receive it, since main already moved on after the timeout case fired. That's fine for this scratch demo; duTop's real version below avoids leaving a send stranded by making sure every goroutine's target channel is buffered.

    Checkpoint

    Prints timed out waiting after about 500ms — not received: done, and not a 2-second wait. select took whichever case was ready first, and time.After's 500ms channel won.

  • Checkpoint

    Now it prints received: done after about 100ms. Same select, same two cases — which one fires depends purely on which channel actually has something ready first.

New: a timeout for duTop

Applying this to duTop means putting the select inside the collection loop, so each individual receive can time out — not just the whole function once at the end. The deadline channel from time.After needs to be created once, outside the loop; call time.After fresh on every iteration and you'd reset the clock every time you receive a result, which defeats the point.

  • Stuck? Show the constant 
    const duTimeout = 500 * time.Millisecond

    A constant, not a flag — this lesson is about the mechanism, not about wiring up another command-line option. Nothing stops you from making it configurable later.

  • Stuck? Show the function 
    const duTimeout = 500 * time.Millisecond

func duTop(root string, n int) error {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return err
	}

	results := make(chan sizeResult, len(dirs))
	for _, d := range dirs {
		go func(name string) {
			p := filepath.Join(root, name)
			s, err := sizeOf(p)
			results <- sizeResult{Name: p, Size: s, Err: err}
		}(d.Name())
	}

	deadline := time.After(duTimeout)
	var dSizes []dirSize
	var firstErr error
	for i := 0; i < len(dirs); i++ {
		select {
		case r := <-results:
			if r.Err != nil {
				if firstErr == nil {
					firstErr = r.Err
				}
				continue
			}
			dSizes = append(dSizes, dirSize{r.Name, r.Size})
		case <-deadline:
			return fmt.Errorf("du top: timed out after %s waiting for %d of %d entries", duTimeout, len(dirs)-i, len(dirs))
		}
	}
	if firstErr != nil {
		return firstErr
	}

	sort.Slice(dSizes, func(i, j int) bool { return dSizes[i].Size > dSizes[j].Size })
	n = min(len(dSizes), n)
	for _, d := range dSizes[:n] {
		fmt.Printf("%10d %q\n", d.Size, d.Name)
	}
	return nil
}

    The loop still runs len(dirs) times at most — but now every single iteration races the deadline, not just the function as a whole. The results channel stays buffered from Lesson 5, at capacity len(dirs): if the timeout fires, any goroutines that hadn't sent yet can still send later without blocking forever, even though nothing will ever receive it — a buffered channel with no receiver just holds the value until it's garbage collected, it doesn't panic or leak a blocked goroutine the way an unbuffered one would.

To actually see the timeout fire, you need something slow to wait on. Rather than fighting with real slow disks, fake it directly in code — a one-line, clearly-temporary change you'll delete afterward.

Idiom

time.After is convenient for a one-shot demo like this, but it has a real cost worth knowing about: it starts a timer that isn't cleaned up until it fires, even if your select already returned via the other case. Called once per duTop call, as here, that's negligible. Called inside a hot loop that runs thousands of times, those uncollected timers add up — context.WithTimeout (a good next thing to learn after this course) is the standard fix, since its timer can be cancelled explicitly. For a single timeout guarding one function call, time.After in a select is exactly the right, idiomatic tool.

A timeout doesn't make the slow work finish faster — it just stops duTop from waiting on it forever. Lesson 7 tackles a different problem with the same shape: what happens when there isn't one slow entry, but thousands of entries, and starting a goroutine per one stops being a good idea at all.

Something unclear — why the deadline channel has to be created once outside the loop instead of fresh on every iteration, what happens to a goroutine whose send never gets received, why time.After has a real cost inside a hot loop, anything else? Ask your teacher (me) before moving on.
