Buffered vs. Unbuffered Channels

Rebuild Lesson 3's channel-based duTop from memory first. Then see, provably, exactly when a send blocks and when it doesn't.

Every channel you've made so far — make(chan sizeResult) — is unbuffered: a send has to wait for a receive to actually happen before it completes. A second number in make changes that. Today: a small demo that proves the difference in print order, not just in words, then one line changed in duTop to apply it.

Warm-up — repeat from Lessons 1–4
  • Checkpoint

    go run -race . du top --path race-test --n 10 reliably prints all your test entries, no warnings.

New: proving a send blocks

make(chan sizeResult) makes an unbuffered channel — capacity zero. A send onto it (ch <- v) doesn't complete until some goroutine is actively receiving at that exact moment; until then, the sending goroutine is stuck at that line. make(chan sizeResult, n) makes a buffered channel with room for n values in flight — a send completes immediately as long as the buffer isn't full, with nobody needing to be receiving yet at all.

  • Stuck? Show the code 
    package main

import (
	"fmt"
	"time"
)

func main() {
	ch := make(chan int) // unbuffered

	go func() {
		fmt.Println("goroutine: about to send")
		ch <- 1
		fmt.Println("goroutine: send completed")
	}()

	time.Sleep(200 * time.Millisecond)
	fmt.Println("main: about to receive")
	fmt.Println("main: received", <-ch)
	time.Sleep(50 * time.Millisecond)
}
    Checkpoint

    The order is: goroutine: about to send, then (after the 200ms sleep) main: about to receive, main: received 1, and only then goroutine: send completed. The send genuinely sat blocked for the whole 200ms — it didn't complete until main was ready to receive.

  • Stuck? Show the change 
    ch := make(chan int, 1) // buffered, capacity 1
    Checkpoint

    The order changes completely: goroutine: about to send and goroutine: send completed both print immediately, before main even wakes up from its sleep. The send didn't wait for anyone — it just dropped its value into the buffer and moved on.

New: buffering duTop's results channel

Your results channel in duTop is unbuffered right now, and it's worked fine — every send does eventually get received, since the loop reads exactly len(dirs) times. Buffering it doesn't fix a bug here; it changes a tradeoff. With an unbuffered channel, a goroutine that finishes early has to wait for the receive loop to get around to it. With enough buffer for every result, every goroutine can drop its result off and move on immediately, regardless of how fast duTop is consuming them.

  • Stuck? Show the line 
    results := make(chan sizeResult, len(dirs))
    Checkpoint

    Same output, same -race silence, as before — for this program, buffering is invisible from the outside. Confirm it anyway: go run -race . du top --path race-test --n 10.

Idiom

Sizing a buffer to exactly the number of sends you know are coming — len(dirs) here — is a specific, safe pattern: every goroutine is guaranteed room, so no send ever blocks, and nothing is unbounded. That's different from picking an arbitrary buffer size "to be safe," which just delays a blocking send instead of eliminating it, or from a buffer sized by something you don't control (imagine len(dirs) in the millions) — Lesson 7's worker pools exist specifically for that second case, where you can't or shouldn't size a buffer to match the input.

Buffering didn't change what duTop does — only how tightly the goroutines and the receive loop are coupled in time. Lesson 6 uses that same channel to solve a different problem: what happens if one of them takes too long.

Something unclear — why the print order flips so cleanly between the two versions, when a buffered send can still block (once the buffer's full), why len(dirs) is a safe buffer size specifically here, anything else? Ask your teacher (me) before moving on.

Primary source for this lesson: go.dev, "A Tour of Go": Buffered Channels for the exact blocking rule (a send blocks only when the buffer is full; a receive blocks only when it's empty).
