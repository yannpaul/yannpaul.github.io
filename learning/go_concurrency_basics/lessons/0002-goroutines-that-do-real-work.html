Goroutines That Do Real Work

Today duTop stops scanning subdirectories one at a time. Each call to sizeOf is independent — nothing about summing one subdirectory's size depends on any other's — which makes this exactly the shape of problem goroutines exist for, not an invented example.

New: one goroutine per subdirectory

Open your burrow project's main.go. Right now duTop loops over dirs and calls sizeOf once per entry, appending each result as it finishes. Today that loop starts a goroutine per entry instead — but collecting N results from N independent goroutines needs a plan for where each result goes that doesn't let two goroutines collide.

The plan: pre-size the results slice to the exact number of entries (make([]dirSize, len(dirs))) instead of starting it empty and appending, and give each goroutine its own index to write into. Since no two goroutines ever touch the same index, there's no data race — even though many goroutines are all writing into the same slice variable.

  • Stuck? Show the change 
    dSizes := make([]dirSize, len(dirs))
for i, d := range dirs {
	// ...
}

  • Pass i and d.Name() as arguments to the goroutine's function literal, rather than referring to the loop variables directly inside it — that's what makes each goroutine's copy of i and the name stable and its own, regardless of how far the loop has moved on by the time the goroutine actually runs.

    Stuck? Show the loop 
    var wg sync.WaitGroup
for i, d := range dirs {
	wg.Add(1)
	go func(i int, name string) {
		defer wg.Done()
		p := filepath.Join(root, name)
		s, err := sizeOf(p)
		if err != nil {
			// handled next
		}
		dSizes[i] = dirSize{p, s}
	}(i, d.Name())
}
wg.Wait()

New: getting an error out of a goroutine

Lesson 7 of Go CLI Basics was explicit: never discard an error. But a goroutine has no return value anyone is watching — you can't return err out of one the way sizeOf does. What you need is one small piece of state every goroutine can report a failure into: a shared error variable, protected by a sync.Mutex — a lock that only one goroutine can hold at a time, so two goroutines can never write to that variable simultaneously.

  • Stuck? Show the full function 
    func duTop(root string, n int) error {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return err
	}

	dSizes := make([]dirSize, len(dirs))
	var wg sync.WaitGroup
	var mu sync.Mutex
	var firstErr error

	for i, d := range dirs {
		wg.Add(1)
		go func(i int, name string) {
			defer wg.Done()
			p := filepath.Join(root, name)
			s, err := sizeOf(p)
			if err != nil {
				mu.Lock()
				if firstErr == nil {
					firstErr = err
				}
				mu.Unlock()
				return
			}
			dSizes[i] = dirSize{p, s}
		}(i, d.Name())
	}
	wg.Wait()
	if firstErr != nil {
		return firstErr
	}

	sort.Slice(dSizes, func(i, j int) bool { return dSizes[i].Size > dSizes[j].Size })
	n = min(len(dSizes), n)
	for _, d := range dSizes[:n] {
		fmt.Printf("%10d %q\n", d.Size, d.Name)
	}
	return nil
}

    Add "sync" to your import block.

Idiom

Notice dSizes[i] = ... needed no mutex, but firstErr did. The difference isn't "one is a slice and one isn't" — it's whether two goroutines can ever touch the same memory. Every goroutine's index into dSizes is unique by construction, so two goroutines are never writing to the same slot; firstErr, by contrast, is exactly one variable every goroutine could write to. A mutex exists to protect memory multiple goroutines genuinely share — reach for one exactly there, and nowhere else, or you'll pay for locks you don't need.

burrow du top is now actually concurrent — and, per the race detector, actually correct. Lesson 3 replaces the mutex-protected-error trick with a channel instead, and explains why Go's own advice leans that direction.

Something unclear — why the goroutine takes i and the name as parameters instead of reading the loop variables directly, why only the error needed a mutex, what would happen if you used append instead of an indexed write here, anything else? Ask your teacher (me) before moving on.
