Q4: two conditions on the same team-year

Q4 defines an event E: "for a given (team, year), the team has more than 5 distinct players win an award and some manager has won an award in the same year." Neither award table has a team column, so each half of E needs a join that finds the team. As Lesson 3's join paths showed, a player's team comes from appearances and a manager's team from managers.

The HW page suggests breaking the problem into sub-problems. The tools all come from Lesson 2:

  • A CTE (WITH name AS (…)) gives each sub-problem's result a name that the rest of the statement reads like a table. One WITH can declare several CTEs, separated by commas, so the whole answer stays a single statement.
  • GROUP BY with HAVING keeps the groups whose aggregate passes a test. COUNT(DISTINCT playerID) counts each player once, however many awards he won that year.
  • A correlated EXISTS keeps an outer row only when its subquery finds a matching row. It is Lesson 2's NOT EXISTS example without the NOT.

CMU's official answer reads the question as follows, and the checkpoint matches only this reading:

  • "More than 5" means > 5, counting distinct players.
  • A player's award counts for the team he appeared for in the award's year and league.
  • "Some manager" is the team's own manager: a person with a managers row for that team and year who won a manager award that year, in the team's league. The 62 of 228 manager awards filed under ML never count, because no team plays in ML.
  • Both halves of E must hold for the same league, team and year.
  • E is counted per team name, the name column of teams, not per teamID. Cleveland had E in 1995 and 2016 as the Cleveland Indians and in 2022 as the Cleveland Guardians, so the Indians appear with 2 and the Guardians, with 1, drop out.
  • The league column holds the league's full name from leagues, such as "National League".

Q5: one row per player with a lateral join

Q5 asks for one teammate per inducted Hall-of-Famer, picked out of many candidates. Lesson 2 handled the same shape with a lateral subquery ending in ORDER BY … LIMIT 1: the subquery runs once for each outer row, can use that row's columns, and keeps the best candidate. In Q5 the outer rows are the inducted players, and the candidates are the other players who appeared for the same team in the same year.

Finding the candidates takes a self-join, a join of a table with itself under two aliases. One copy of appearances holds the Hall-of-Famer's rows, and the other holds everyone's rows for the same team and year. DuckDB accepts the lateral join written with a comma, as in Lesson 2 (FROM hof, LATERAL (…) AS t), or as FROM hof JOIN LATERAL (…) AS t ON TRUE; the two give the same rows.

The official answer settles three details:

  • The Hall-of-Famer is left out of his own candidates. Without that condition, 8 of the first 10 rows name the player as his own earliest teammate.
  • "Earliest" compares years first. The teammate's constructed name only breaks ties within that year.
  • An inducted player is a halloffame row with inducted = 'Y'. There are 363 such rows for 362 people, because Minnie Minoso was inducted twice, and 70 of the 362 have no rows in appearances. A lateral subquery that returns nothing produces no output row, as 15-799 vanished from Lesson 2's best-GPA query, so those 70 drop out. Without its final LIMIT 10, the official answer returns 293 rows, Minoso's twice.

Inserting or updating in one statement

Q6 needs a statement that Lectures #01 and #02 don't cover. Lesson 1 showed that a primary key rejects a second row with the same key, and Lesson 2 used INSERT INTO … SELECT to add a query's result to an existing table. When a plain INSERT meets a duplicate key, DuckDB rejects the whole statement, and none of its rows are added. An upsert (update or insert) decides row by row instead: a row with a new key is inserted, and a row whose key already exists either updates the existing row or is skipped. DuckDB writes it as an ON CONFLICT clause at the end of the INSERT.

CREATE TABLE stock (item VARCHAR PRIMARY KEY, qty INTEGER);
INSERT INTO stock VALUES ('apple', 5), ('pear', 2);

Starting each time from these two rows, here is what INSERT INTO stock VALUES ('pear', 7), ('plum', 3) does with each ending:

EndingDuckDB reportsstock afterwards
noneConstraint Error: Duplicate key "item: pear" violates primary key constraint.apple 5, pear 2
ON CONFLICT DO NOTHINGa count of 1apple 5, pear 2, plum 3
ON CONFLICT DO UPDATE SET qty = -1a count of 2apple 5, pear -1, plum 3
ON CONFLICT (item) DO UPDATE SET qty = EXCLUDED.qtya count of 2apple 5, pear 7, plum 3
  • DO NOTHING skips each row whose key already exists and inserts the rest. DO UPDATE SET … updates the existing row instead.
  • In the SET clause, a plain column name such as qty is the existing row's value, and EXCLUDED.qty is the value from the row that couldn't be inserted.
  • The parenthesized column list after ON CONFLICT, the conflict target, names the key that must conflict. When the primary key is a table's only key, as in teams, you can leave it out. When a table has several keys, such as a primary key and a UNIQUE column, DuckDB requires the target for DO UPDATE.
  • The count is the number of rows inserted plus the number updated.
  • The rows to insert can come from a SELECT on the same table, which is what Q6 does.
In Go terms

Picture the table as a map keyed by its primary key. For each incoming row r, an upsert checks _, ok := m[r.key]. If the key is absent, it stores r. If it is present, DO NOTHING moves on, and DO UPDATE rewrites m[r.key], where a plain column name reads the stored row and EXCLUDED reads r.

Q6: what the upsert has to produce

Q6 adds, for every 2024 team, a row whose teamID is the team's franchID. The key of teams is (yearID, lgID, teamID), so each new row's key is (2024, the team's league, its franchID). Of the 30 teams in 2024, 17 already use their franchID as their teamID: their new row conflicts with the existing one, and the existing row's attendance becomes -1. The other 13 have a different code (Kansas City's teamID is KCA and its franchID is KCR), so 13 rows are added and 2024 ends with 43 rows.

The official answer fills only part of each new row. yearID, lgID, teamRank and attendance come from the 2024 row, franchID goes into teamID, and every other column stays NULL, franchID included. The grading query shows franchID, so your new rows must leave it NULL to match the checkpoint.

    E joins two facts about the same team-year, and each comes from a different table. Write down the three columns that identify a team-year in teams. For each half of E, which tables lead from an award to those three columns?

    Build two CTEs. Then group by league name and team name, keep the groups with more than one distinct year, and sort.
