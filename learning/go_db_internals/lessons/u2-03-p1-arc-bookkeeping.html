P1.1 ARC Replacer: Bookkeeping

Choose constant-time data structures for the ARC replacer, then implement its bookkeeping: RecordAccess for new and alive frames, SetEvictable, Size and Remove, all safe for concurrent use.

The previous lesson stated Project 1's ARC rules and traced BusTub's SampleTest by hand. Now you write the first half of ArcReplacer: everything the replacer does before it ever evicts a page. It must know which frames hold pages, which of those the buffer pool may evict, and when a page has been used a second time and belongs in the MFU list. Eviction and the ghost lists come in the next lesson. Most of the thinking in this stage goes into the data structures, because one test calls RecordAccess more than 2.6 million times on a replacer with 262,144 frames.

Warm-up: retrieval from earlier lessons

In Project 1 the buffer pool manager keeps each frame's pin count and the replacer's evictable flag in sync. When must it call SetEvictable(frameID, true)?

  • Immediately after RecordAccess, so that the page it just loaded can be evicted later.
  • When a flush clears the page's dirty flag, since a clean page is cheap to evict.
  • When the frame's pin count drops to 0, for example when the last guard on its page is dropped.
  • When the free list becomes empty, so that the replacer has candidates to choose from.

Unit 1, Lesson 2: an UPDATE makes a tuple too large to stay on its slotted page. What happens to the tuple's record ID?

  • It can change, because the new version goes to a different page; applications must not rely on record IDs.
  • It stays the same, because the slot array absorbs every move of the tuple.
  • It stays the same, because each tuple stores its own record ID in its header.
  • The update fails, because a record ID can never change once it has been assigned.

t(x) holds 1, 3 and 6, and u(y) holds 2 and 5. Which rows does SELECT x FROM t WHERE x > ALL (SELECT y FROM u); return?

  • 3 and 6
  • 1, 3 and 6
  • No rows, because ALL needs a subquery that returns a single row
  • 6 only

What stage 1 covers

All of Project 1's replacer lives in bufferpool/arc_replacer.go. The pre-built parts are the AccessType and ArcStatus constants, the FrameStatus record with its constructor newFrameStatus, the fields of ArcReplacer, and NewArcReplacer, which creates four empty lists, two empty maps and p = 0. In this stage you replace four stubs:

  • RecordAccess, for two situations only: the frame is alive in MRU or MFU (case 1, a real cache hit), or the page is in no list at all (case 4).
  • SetEvictable, Size and Remove, in full.

Evict stays a stub until the next lesson. Without it nothing ever becomes a ghost, so the ghost-hit cases 2 and 3 can't happen yet, and neither can the two "kill" steps of case 4, which remove ghosts. For now, a miss simply puts the page at the front of the MRU list. The stage-1 tests never call Evict. The accessType argument matters only for the optional leaderboard, so ignore it.

Choosing the data structures

Slide 31 of Lecture #05 gives two hints for the replacer: the eviction algorithm must check each page's "pinned" status, and you may use the standard library's containers for the internal lists (Lecture #05, slide 31). In Go that container is container/list, a doubly linked list. The starter already declares the four lists as *list.List fields, mru, mfu, mruGhost and mfuGhost, with the front of each list as its most recent end. The right structures follow from what each method has to do quickly:

OperationHow it finds the entryWhat it then changes
RecordAccess on an alive framealiveMap[frameID]unlinks the entry from MRU or MFU and pushes it to the front of MFU
RecordAccess on a ghost (next lesson)ghostMap[pageID]unlinks the ghost and pushes a new alive entry to the front of MFU
RecordAccess on a new pageneither map has itpushes a new entry to the front of MRU
SetEvictablealiveMap[frameID]flips one flag and the evictable count
RemovealiveMap[frameID]unlinks the entry from its list
Evict (next lesson)walks MRU or MFU from its backturns the victim into a ghost

Every row except Evict starts with a map lookup, and every row ends with a list operation in the middle of a list. A linked list removes an element in constant time, but only if you already hold that element: list.Remove takes a *list.Element, not the value stored in it. The starter's maps lead to a *FrameStatus, not to an element. So each entry needs a way back to its own element. You can add an element field to FrameStatus, or change the maps to hold *list.Element and keep the *FrameStatus as the element's Value. The starter's comments allow both. Either way, every operation in the table except Evict does a constant amount of work.

The alternative, walking a list until you find the entry, costs up to 262,144 steps per access in TestArcBookkeepingRecordAccessPerformance. That test, BusTub's performance test, fills a replacer with 262,144 frames, all alive and evictable, then makes 10 rounds of 262,144 hits starting in the middle of the list. It fails if a round takes 3 seconds or more on average. With constant-time operations, a round under -race takes a fraction of a second. With a list walk per access, a round takes billions of steps, and the run sits silent until go test gives up. The writeup's Gradescope notes give the same warning: a timeout may mean that "your ArcReplacer is not efficient enough".

Why alive entries are keyed by frame ID and ghosts by page ID

The writeup states the relationship between the two IDs: a page in the buffer pool maps one-to-one to a frame, that mapping doesn't change until the page is evicted, and an evicted page is associated with no frame at all.

  • An alive entry is an entry in MRU or MFU, for a page that is in the buffer pool right now. Its frame ID and page ID identify it equally well. The starter keys aliveMap by common.FrameID, which BusTub's comment calls slightly more intuitive and which guarantees one record per frame. It is also the ID that SetEvictable and Remove receive.
  • A ghost entry is an entry in one of the ghost lists. Its page has no frame any more: the buffer pool reuses a frame as soon as Evict returns it. In SampleTest, frame 2 holds page 2, page 2 is evicted, and frame 2 then holds page 7 while page 2 is still a ghost. When page 2 is read again, it arrives in frame 3. Only its page ID can find its ghost, so ghostMap is keyed by common.PageID.

That fixes the order of lookups in RecordAccess(frameID, pageID, …): first aliveMap[frameID] (a hit), then ghostMap[pageID] (a ghost hit, next lesson), and otherwise a miss. Here is SampleTest after its first three evictions, the state from step 3 of the previous lesson's trace, with the maps added:

aliveMap   frame 6 → p(6,f6)    frame 5 → (5,f5)    frame 1 → (1,f1)
ghostMap   page 4 → 4           page 3 → 3          page 2 → 2

mruGhost   [4, 3, 2]            mru   [p(6,f6), (5,f5)]
mfuGhost   []                   mfu   [(1,f1)]

Each map value is the entry itself, and the entry knows its own list element, so any of them can be unlinked in constant time.

Idiom

container/list has two traps for this project. First, MoveToFront only reorders elements inside the list you call it on. Moving an entry from MRU to MFU takes r.mru.Remove(e) followed by r.mfu.PushFront(v). Second, Remove and MoveToFront silently do nothing when the element belongs to another list: no panic, no error. That is why each entry records which list holds it (arcStatus). PushFront wraps the value in a new *list.Element, so after every move, store the new element. An element's Value has type any; get your entry back with a type assertion, e.Value.(*FrameStatus).

The rules for stage 1

These come from the writeup and from the doc comments in arc_replacer.go, which the stage-1 tests check one by one.

  1. One latch guards everything. Every exported method locks r.latch at the top and holds it for the whole body. sync.Mutex isn't reentrant, so a method that holds the latch must not call another exported method (SetEvictable calling Size, for example); put shared code in unexported helpers that expect the caller to hold the latch.
  2. A new frame enters non-evictable. The buffer pool calls RecordAccess right after pinning the page, so the page can't be a victim yet. Only SetEvictable changes the flag. RecordAccess never changes Size().
  3. A hit moves the entry to the front of MFU, whether it was in MRU (its second access) or already in MFU (now its most recent entry). The evictable flag stays as it was, and p doesn't change.
  4. A frame ID is valid from 0 to the capacity, inclusive. SetEvictable panics on a negative ID or one larger than replacerSize. An ID equal to the capacity is valid, because BusTub's SampleTest uses frame 7 in a replacer of capacity 7. A valid frame that the replacer doesn't track is a no-op, and it must leave no record behind.
  5. Size() counts alive, evictable entries. SampleTest's comment: "The size of the replacer is the number of frames that can be evicted, not the total number of frames entered." SetEvictable changes the count only when the flag really flips.
  6. Remove forgets the page. An unknown frame is a no-op. A non-evictable frame panics, and the failed call changes nothing. An evictable frame leaves its list and aliveMap, Size() drops by 1, and no ghost entry is created: the writeup says to "remove a frame and its corresponding page from the replacer", and Remove is called only for deleted pages, whose IDs NewPage's ever-increasing counter never hands out again. Remove takes a frame ID, so it can never reach a ghost.

Both panics must be deliberate, a panic with a message. The tests' expectPanic helper rejects a runtime error such as a nil-pointer dereference, and rejects the starter's TODO(P1) panic.

Idiom

Write defer r.latch.Unlock() on the line after r.latch.Lock(). Go runs deferred calls while a panic unwinds the stack, so the latch is released even when SetEvictable or Remove panics. With Unlock as the last statement instead, a panic skips it. TestArcBookkeepingInvalidFrameID recovers the panic and calls the replacer again, and that call waits for the latch forever. Validating the frame ID before locking also works, because replacerSize never changes.

Check your understanding

A replacer of capacity 4 starts empty. These calls run in order (every RecordAccess passes AccessUnknown): RecordAccess(0, 10), RecordAccess(1, 11), RecordAccess(2, 12); SetEvictable(0, true) twice; SetEvictable(1, true), SetEvictable(1, false), SetEvictable(1, true); then RecordAccess(0, 10), RecordAccess(1, 11) and RecordAccess(0, 10). What are the MFU list, front to back, and Size()?

  • MFU = [(11,f1), (10,f0)], and Size() = 2
  • MFU = [(10,f0), (11,f1)], and Size() = 3
  • MFU = [(10,f0), (11,f1)], and Size() = 2
  • MFU = [(10,f0), (11,f1)], and Size() = 0

Frame 1 holds page 13, which is evictable and sits in the MRU list. A test calls Remove(1), then RecordAccess(1, 13, AccessUnknown). What does the second call do?

  • It is a plain miss: page 13 goes to the front of MRU as a new, non-evictable entry.
  • It is a ghost hit: page 13 goes from the MRU ghost list to the front of MFU.
  • It is a hit: Remove only made frame 1 non-evictable, so page 13 moves to MFU.
  • It panics, because a removed frame can't be passed to the replacer again.

To handle a hit on an MRU entry, a first draft calls r.mfu.MoveToFront(st.elem), where st.elem is the entry's element in r.mru, then sets st.arcStatus = ArcMFU. What happens?

  • It panics, because the element belongs to a different list.
  • The entry moves from the MRU list to the front of the MFU list.
  • It doesn't compile, because MoveToFront rejects another list's element.
  • Nothing moves, and no error is reported: the entry stays in the MRU list.

Your SetEvictable calls r.latch.Lock() first and r.latch.Unlock() as its last statement, with no defer. TestArcBookkeepingInvalidFrameID calls SetEvictable(-1, true), which panics as required, and the test recovers the panic. What happens on its next call to the replacer?

  • It runs normally, because unwinding a panic releases the goroutine's mutexes.
  • It blocks forever on the latch, and the run hangs until go test's timeout.
  • The race detector reports a data race and fails the test at once.
  • The mutex notices that its holder panicked and unlocks itself on the next Lock.

In SampleTest, frame 2 first holds page 2. Page 2 is evicted, frame 2 is reused for page 7, and later page 2 is read again into frame 3. Why does the replacer index ghost entries by page ID rather than by frame ID?

  • Page IDs take less memory than frame IDs, so the ghost map stays smaller.
  • An evicted page has no frame: its old frame may hold another page, and it returns in whatever frame is free.
  • The buffer pool passes no frame ID to RecordAccess when a page comes back from disk.
  • A ghost entry keeps its old frame reserved, so two ghosts could share one frame ID.

Build it: ARC bookkeeping (stage P1.1)

Every edit in this stage is in bufferpool/arc_replacer.go; leave the Evict stub alone. Run commands from go_db_internals/intro_to_db. You can run the stage's test command after any task: the tests of methods you haven't written yet fail with panic: TODO(P1): ArcReplacer.Remove not implemented or similar, and the rest show your progress. Add -v after the regex to see each test's name and result.

  • Decide what the list elements hold and how a map lookup reaches the element. The FrameStatus struct and the two maps are yours to change.

    What to think about

    list.Remove and PushFront run in constant time only when you already hold the *list.Element. After aliveMap[frameID] hands you an entry, how do you get to its element without walking the list?

    The approach

    Store a *FrameStatus as each element's Value, and add a field to FrameStatus that holds the entry's own element. Every time you push the entry onto a list, save the element that PushFront returns. (Changing the maps to hold *list.Element works as well.) A small helper such as listOf(status ArcStatus) *list.List saves you a switch in every method.

    One key fragment 
    type FrameStatus struct {
	pageID    common.PageID
	frameID   common.FrameID
	evictable bool
	arcStatus ArcStatus     // which of the four lists holds the entry
	elem      *list.Element // the entry's element in that list; elem.Value is the entry
}

  • Lock the latch for the whole method. Check aliveMap[frameID] first (the next task handles a hit there). Otherwise the page is new: it goes to the front of mru, not evictable, indexed by its frame ID. Size() and p don't change. In the next lesson you'll insert the ghost lookup and the case-4 kills before this step.

    What to think about

    Which fields of the replacer must change when a page enters, and which must stay exactly as they are? Think about currSize and mruTargetSize.

    The approach

    Lock, and defer the unlock. Look the frame up in aliveMap; if it's there, handle the hit and return. Otherwise build an entry with the page ID, the frame ID, evictable false and status ArcMRU, push it to the front of mru, save the element in the entry and add the entry to aliveMap.

    One key fragment 
    st := newFrameStatus(pageID, frameID, false, ArcMRU)
st.elem = r.mru.PushFront(st)
r.aliveMap[frameID] = st

  • This is case 1, a real cache hit. The entry may be in MRU or already in MFU; it ends at the front of MFU either way. Its evictable flag, Size() and p stay unchanged.

    What to think about

    A page found in MRU has now been accessed twice, so it belongs in MFU. A page already in MFU just becomes MFU's most recent entry. Which container/list calls work across two lists, and which work only inside one?

    The approach

    Unlink the entry from the list its status names, set its status to ArcMFU, push it to the front of mfu and save the new element. Don't touch evictable: SampleTest's first hit is on an evictable frame, and its Size() must stay 5 afterwards. Return without looking at the ghost map.

    One key fragment 
    r.listOf(st.arcStatus).Remove(st.elem) // whichever list holds it now
st.elem = r.mfu.PushFront(st)          // PushFront returns a new element

  • Valid IDs run from 0 to replacerSize inclusive. A false-to-true flip adds 1 to currSize, a true-to-false flip subtracts 1, and anything else changes nothing.

    What to think about

    Two valid inputs must change nothing at all: a frame the replacer doesn't track, and a flag that already has the requested value. What would happen to Size() if either of them slipped through?

    The approach

    Validate first: frameID < 0 || int(frameID) > r.replacerSize panics with a message. Then, under the latch, look the frame up in aliveMap. If it's missing, or its flag already equals evictable, return. Otherwise set the flag and adjust currSize. Don't create an entry for an untracked frame: TestArcBookkeepingSetEvictableUntrackedFrame checks that the frame later enters non-evictable.

    One key fragment 
    st, ok := r.aliveMap[frameID]
if !ok || st.evictable == evictable {
	return // untracked frame, or nothing to change
}
  • What to think about

    The tests call Size() after almost every step. Should it count anything, or report a number that the other methods keep up to date?

    The approach

    Return currSize while holding the latch. Reading it without the latch is a data race with SetEvictable; -race reports it as WARNING: DATA RACE in TestArcBookkeepingConcurrentAccess. Returning the length of aliveMap instead counts pinned frames too.

    One key fragment 
    // currSize changes in exactly these places:
//   SetEvictable   false to true: +1    true to false: -1
//   Remove         an evictable entry leaves: -1
//   Evict (P1.2)   the victim leaves: -1

  • A pinned frame panics before anything changes, so Size() and the lists look exactly as they did before the call. An evictable frame leaves its list and aliveMap, and currSize drops by 1. The ghost lists and p stay untouched.

    What to think about

    Remove is for deleted pages. Should the replacer keep remembering a page whose ID will never be used again? And what may a failed Remove leave behind?

    The approach

    Under the latch, look the frame up in aliveMap. Missing: return. Not evictable: panic with a message. Otherwise unlink the element from its list, delete the map entry and decrement currSize. For a readable message, use fmt.Sprintf and add "fmt" to the imports.

    One key fragment 
    if !st.evictable {
	panic(fmt.Sprintf("bufferpool: Remove on non-evictable frame %d", frameID))
}
