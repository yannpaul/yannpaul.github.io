P4.5 Undo Logs: Update and Delete

Generate and extend undo logs so that each transaction keeps exactly one per tuple, rewrite delete and update to change tuples in place behind a version chain, and detect write-write conflicts, which taint the transaction and fail the statement with an execution exception.

An insert needs no undo log, because nobody saw the tuple before. A delete or an update replaces a version that other transactions may still be reading, so before it touches the base tuple it has to put the old values into an undo log and link that log in front of the chain. You write the two helpers that build those logs, then the MVCC delete and update executors that use them, and you add the first-writer-wins rule from Lecture #20: a transaction may not change a tuple that someone else changed after its snapshot.

Warm-up: retrieval from earlier lessons

Unit 7, Lesson 6: in delta storage, the main table holds the newest version of each tuple and older versions are kept as deltas, newest first. How does a reader get an older version?

  • It starts from the current version in the main table and applies the deltas in reverse order, newest first.
  • It reads a full copy of the old version from the version chain.
  • It starts from the tuple's first version and applies every delta forward, oldest first.
  • It looks the version up by timestamp in a separate time-travel table.

Unit 6, Lesson 3: what keeps Project 3's UPDATE t SET v = v + 1 from finding and updating its own new versions?

  • The update executor remembers every RID it has written and skips them.
  • The new versions carry a flag that the scan ignores.
  • The scan's iterator is created in Init and stops at the last tuple that existed then.
  • The update reads every child tuple into a buffer before it writes anything.

Unit 7, Lesson 1: which anomaly does the lecture call a lost update?

  • A transaction reads data that another, uncommitted transaction has written.
  • A transaction reads the same object twice and gets two different values.
  • A committed write disappears after a crash.
  • A transaction overwrites uncommitted data of another uncommitted transaction.

One undo log per tuple per transaction

An undo log (Go's concurrency.UndoLog, which P4.2's ReconstructTuple already applies) holds what a change replaced: ModifiedFields marks the columns it holds, Tuple holds their old values laid out by the partial schema of those columns, IsDeleted says the tuple did not exist before the change, Ts is the timestamp of the replaced version, and PrevVersion links to the next older log. The writeup's rule for how many there are:

"Suppose a transaction updates a tuple several times. We expect only one UndoLog for every update within a specific transaction. GenerateNewUndoLog is used for every first modification of each tuple. After that, GenerateUpdatedUndoLog is used to consolidate modifications into one UndoLog."

One log per transaction is enough because other transactions never see the intermediate versions. They are uncommitted, and the transaction replaces them before it commits. What readers need is the version from before the transaction started, so that is what the single log must rebuild.

GenerateNewUndoLog(schema, baseTuple, targetTuple, ts, prevVersion) builds the log for a transaction's first change to a tuple. baseTuple is the tuple before the change (nil if it is a deletion marker), targetTuple the tuple after it (nil for a delete), ts the base tuple's timestamp, and prevVersion the tuple's current first undo link, so the new log goes in front of the existing chain. Three cases:

  • Update: the log holds only the columns whose value changes, with their old values. types.Value.CompareExactlyEquals decides whether a value changes. It treats two NULLs as equal, which a SQL comparison does not.
  • Delete: the log holds every column of the base tuple, so that a reader can rebuild the whole row.
  • Insert into a deleted slot (base nil): the log has IsDeleted set and no columns. In P4.4 an insert always creates a new tuple, so this case first matters in P4.7, but TestTxnUndoLogGenerate checks it now.

GenerateUpdatedUndoLog(schema, baseTuple, targetTuple, log) extends a log the transaction already owns for this tuple. Here baseTuple is the transaction's own current version, before this change. The writeup's advice:

"we recommend simply adding modifications to the existing UndoLog (so that it has the full change (A, 5)), which will make it easier to handle concurrency issues. In other words, make sure you only add / update data in the undo log, and do not remove data."

So a column the log already holds keeps its value, because that value is from before the transaction. A column the log doesn't hold yet joins it if this change alters it (or if this change is a delete), with its value from baseTuple: the transaction hasn't changed that column before, so its value in the current version is still the one from before the transaction. A log with IsDeleted set stays as it is, since "the tuple did not exist" is already the full answer.

A tuple the transaction inserted itself needs no log at all, however often the transaction changes it. Write-write conflicts

Before a delete or an update changes a tuple, it checks for a write-write conflict. The writeup names two cases. "If a tuple is being modified by an uncommitted transaction, no other transactions are allowed to modify it." And a transaction may not change a tuple that another transaction changed and committed after its read timestamp: in the writeup's example, A deletes a tuple and commits, and B, which started before A committed, then tries to delete it too. Both cases show in the base tuple's timestamp, the only thing you need to look at in these single-threaded tests ("The only condition for detecting write-write conflict is to check the timestamp of the base tuple metadata"):

  • The base carries another transaction's temporary timestamp: conflict.
  • The base carries a commit timestamp above the transaction's read timestamp: conflict.
  • The base carries this transaction's own temporary timestamp: no conflict. That is self-modification, the writeup's fourth case.
  • The base carries a commit timestamp at or below the read timestamp: no conflict. The transaction is changing the version it sees.

Since a temporary timestamp is larger than any read timestamp, the first two collapse into one comparison: a conflict is a base timestamp that is not your own temporary timestamp and is above your read timestamp.

On a conflict, two things happen, and the tests check both. The transaction becomes tainted: txn.SetTainted() moves it from RUNNING to TAINTED, which means it has to abort but hasn't cleaned up yet. Then the executor returns common.NewExecutionException(msg) as its error. The execution engine (execution/execution_engine.go) turns an error for which common.IsExecutionException holds into (false, nil), so ExecuteSQLTxn reports that the statement failed without reporting an internal error. Tainting without the exception, or returning the exception without tainting, fails executeTxnTainted:

    txn_executor_test.go:516: sql "UPDATE table1 SET b = 2 WHERE a = 0" in txn3 should not execute successfully: there should be a write-write conflict
        hint: if you want to taint a txn, you should both SetTainted and return common.NewExecutionException.

That message is from a conflict check that only looks for temporary timestamps, so it misses a commit newer than the read timestamp. It fails TestTxnUndoLogUpdateConflict/version_chain, whose dump on a finished stage shows both kinds of conflict at once. Transactions 2 to 5 all began with read timestamp 2. Transaction 2 updated the row with a = 0 and committed at 3; transaction 3 updated the row with a = 1 and hasn't committed:

RID=0/0 ts=3 tuple=(0, 233, 0)
  txn2@0 (_, 0, _) ts=2
RID=0/1 ts=txn3 tuple=(1, 2333, 1)
  txn3@0 (_, 1, _) ts=2

Transaction 4's update of RID 0/0 meets timestamp 3, above its read timestamp 2. Transaction 5's update of RID 0/1 meets another transaction's temporary timestamp. Both are tainted, and neither changes anything. A reader with read timestamp 2 still sees (0, 0, 0) and (1, 1, 1) through the two logs.

Its temporary timestamp also stays on every tuple it changed before the conflict, so those tuples are blocked for everyone else until P4.6's Abort puts them back.

Delete and update with version chains

The writeup's summary for both executors:

  1. Get the RID from the child executor.
  2. Generate the updated tuple.
  3. "For self-modification, update the table heap tuple, and optionally the undo log in the current transaction if there is one."
  4. "Otherwise, generate the undo log, and link them together."

In Go, for each child RID:

  1. Read the base meta, tuple and first undo link with concurrency.GetTupleAndUndoLink(txnMgr, heap, rid).
  2. Check for a write-write conflict on meta.Ts; on one, taint and return the execution exception.
  3. For self-modification, find the transaction's own log for this RID. If it changed the tuple before, its log is at the head of the chain, so the first link points into its own transaction (link.PrevTxn == txn.TransactionID()). Then replace that log with GenerateUpdatedUndoLog through txn.ModifyUndoLog(link.PrevLogIdx, ...), and the link stays. If the first link points elsewhere, or nowhere, the transaction inserted this tuple itself, and there is no log to keep.
  4. Otherwise, build the log with GenerateNewUndoLog(schema, &base, target, meta.Ts, link) and add it with txn.AppendUndoLog, which returns the link to it. That link becomes the tuple's new first link.
  5. Write the new base: meta {Ts: txn.TransactionTempTs(), IsDeleted: target == nil}, the new tuple (for a delete, the old bytes unchanged), and the new link. concurrency.UpdateTupleAndUndoLink(txnMgr, rid, linkPtr, heap, txn, meta, tuple, nil) writes tuple and link together under the page latch; pass a nil link pointer when the tuple has no chain, since a nil pointer means no link.
  6. Add the RID to the write set, so that Commit stamps it.

The writeup says the tests of this task are single-threaded, so the check function can be nil, and writing the tuple (UpdateTupleInPlace) and the link (UpdateUndoLink) separately also passes. P4.7's concurrent tests are where the check function becomes necessary. The delete and the update share every step except the target, so one helper for both saves you writing it twice. The course's reference solution keeps it in delete_executor.go, and the update executor, in the same package, calls it.

The key you remove from an index comes from the base tuple, not the child's tuple. The child's tuple is the version the transaction sees, which in Project 4 is reconstructed. Whenever there is no conflict, the two are the same row: the base is either visible at the read timestamp or the transaction's own version.

The delete keeps the tuple's bytes and changes only the meta: the deleted tuple stays in the heap as a deletion marker with the transaction's temporary timestamp, and its log holds every column.

The update changes three things from Project 3:

  • It is a pipeline breaker. The writeup: "it should first store all tuples from the child executor to a local buffer before writing any updates." Pull every child batch, keep the tuples and RIDs, then compute the targets and write them.
  • It updates in place. The RID stays, the new values overwrite the old ones, and the old ones move into the undo log. Delete plus insert would add a heap entry for every update, and the tests count entries: tableHeapEntryNoMoreThan fails with "you might have implemented your update as delete + insert, so that a new tuple is created every time a tuple gets updated."
  • The target values come from TargetExpressions evaluated on the child's tuple, as before. A statement that sets a column to its current value still counts the row.

Indexes: the primary-key index follows MVCC rules, so its entries are never removed and each keeps its RID. That is P4.7's work, and in this stage a delete or update leaves a primary-key index alone. Every other index keeps Project 3's upkeep: a delete removes the key, and an update that changes a key removes the old entry and inserts the new one, now with the same RID, since the update works in place. Project 3's index tests (TestDeleteRemovesIndexEntries, TestUpdateIndexes, TestUpdateUnchangedIndexKey) and p3.05-index-scan-btree.slt keep checking that. Such secondary indexes are not snapshot-safe in this design; BusTub's Project 4 tests never create one.

VARCHAR updates that change length

An in-place update needs the new tuple to have exactly the old one's size. UpdateTupleInPlace overwrites the bytes in the slot, and the table page panics with "Tuple size mismatch" otherwise. BusTub has the same limit, and the writeup states it: "Starting from this task, your implementation will not be compatible with Project #3, as we only support schemas of fixed-sized data types." In Go the panic is recovered and comes back as the statement's error:

bustub> CREATE TABLE p(id int, name varchar(20));
Table created with id = 32
bustub> INSERT INTO p VALUES (1, 'ab');
bustub> UPDATE p SET name = 'cd';
bustub> UPDATE p SET name = 'abcdef';
Tuple size mismatch
bustub> SELECT * FROM p;
+------+--------+
| p.id | p.name |
+------+--------+
| 1    | cd     |
+------+--------+
bustub> \dbgmvcc p
debug_hook: \dbgmvcc
RID=9/0 ts=5 tuple=(1, cd)
  txn4@0 (_, ab) ts=4

(Count tables left out.) 'ab' to 'cd' keeps the length and works; 'abcdef' doesn't. All of Project 4's tests use fixed-size types, and none of Project 3's .slt files changes a VARCHAR's length (p3.03-update.slt updates an INTEGER column of rows that also hold a VARCHAR), so Project 3 keeps passing. If you want such updates to work, you can fall back to a delete plus an insert for exactly that case; no test asks for it.

Check your understanding

Row (1, 1, 1) of table2(a, b, c) was committed at timestamp 2 and has no undo log. A transaction with read timestamp 2 runs UPDATE table2 SET b = 2. What undo log does it create?

  • ModifiedFields [true, true, true], Tuple (1, 1, 1), Ts 2.
  • ModifiedFields [false, true, false], Tuple (1), Ts 2.
  • ModifiedFields [false, true, false], Tuple (2), Ts 2.
  • ModifiedFields [false, true, false], Tuple (1), Ts equal to the transaction's temporary timestamp.

The same transaction continues with SET b = 3, SET a = 1, SET a = 2 and SET b = 1. The base is now (2, 1, 1). What does its one undo log hold?

  • (1, _, _): only a, because b is back at its original value.
  • (2, 3, _): the values before the last change of each column.
  • (_, 1, _): only b, the first column the transaction changed.
  • (1, 1, _): a and b, each with its value from before the transaction.

Rows (0, 0, 0) and (1, 1, 1) were committed at timestamp 2. Transactions T1 to T4 then begin, all with read timestamp 2. T1 updates the row with a = 0 and commits at 3. T2 updates the row with a = 1 and doesn't commit. Then T3 runs UPDATE table1 SET b = 2 WHERE a = 0 and T4 runs UPDATE table1 SET b = 2 WHERE a = 1. Which of the two statements fail?

  • Only T4's, because T2 hasn't committed.
  • Only T3's, because a committed change is newer than its snapshot.
  • Both, because each meets a change it may not overwrite.
  • Neither, because each updates the version in its own snapshot.

One transaction inserts (1, 1) into an empty table, updates it three times, and then deletes it, all before committing. How many undo logs does it hold, and how many tuples are in the heap?

  • 0 undo logs and 1 tuple.
  • 1 undo log and 1 tuple.
  • 4 undo logs and 1 tuple.
  • 0 undo logs and 4 tuples.

Table p(id int, name varchar(20)) holds (1, 'cd'). With this stage's in-place update, what does UPDATE p SET name = 'abcdef' do?

  • It updates the row, which moves to a new RID with room for the longer value.
  • It fails with "Tuple size mismatch", and the row keeps 'cd'.
  • It stores 'ab', the new value cut to the old length.

Build it: undo logs, delete and update (stage 5)

You edit concurrency/execution_common.go (GenerateNewUndoLog, GenerateUpdatedUndoLog), execution/delete_executor.go and execution/update_executor.go. Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • A transaction keeps at most one undo log per tuple. The first change creates it in front of the chain; later changes only add columns to it. A tuple the transaction inserted itself gets none.
  • A log's Ts is the timestamp of the version it rebuilds, the base's timestamp before the change. Its PrevVersion is the link the tuple had.
  • A write-write conflict is a base timestamp that is not the transaction's own temporary timestamp and is above its read timestamp. On a conflict, call SetTainted and return common.NewExecutionException; change nothing.
  • Delete keeps the bytes and sets {temporary timestamp, deleted}; update overwrites in place with {temporary timestamp, live}. Both add the RID to the write set.
  • What to think about

    Which tuple supplies the values the log stores, the base or the target? Which pointer being nil tells you which case you are in? How is the log's Tuple laid out when it holds two of three columns, and which helper from P4.2 builds that schema?

    The approach

    Make a ModifiedFields slice with one entry per column. Base nil: return a log with IsDeleted set, no columns and an empty tuple. Target nil: mark every column. Otherwise mark the columns where the base and target values are not CompareExactlyEquals. Collect the base's values of the marked columns, build the tuple with the partial schema (types.CopySchema on the marked indices), and fill in Ts and PrevVersion from the arguments.

    One key fragment 
    for i := range modified {
	modified[i] = !baseTuple.Value(schema, i).CompareExactlyEquals(targetTuple.Value(schema, i))
}
  • What to think about

    For a column the log already holds, which value is the one from before the transaction: the log's or the base's? For a column it doesn't hold yet, why is the base's value the right one to add? When should the function return the log unchanged?

    The approach

    If the log has IsDeleted set, or the base is nil, return it as it is. Otherwise walk the columns: where the log already holds one, keep its value (read it with the log's partial schema, counting held columns to know its position); where it doesn't, add the base's value if the target is nil (a delete) or differs from the base. Rebuild ModifiedFields and the partial tuple; keep Ts and PrevVersion.

    One key fragment 
    // a column the log holds keeps the log's value; another column joins
// only if this change alters it (v is the base's value of column i)
joins := !log.ModifiedFields[i] && (targetTuple == nil || !v.CompareExactlyEquals(targetTuple.Value(schema, i)))
  • What to think about

    Why read the base again instead of trusting the child's tuple? Which base timestamps are conflicts, and which one means "I changed this before"? How do you know whether you already own a log for this RID, and where is it? What must you return so that the statement fails cleanly?

    The approach

    For each RID from the child: GetTupleAndUndoLink; on a conflict, SetTainted and return common.NewExecutionException. If meta.Ts is your own temporary timestamp, extend your log with GenerateUpdatedUndoLog(schema, &base, nil, log) and ModifyUndoLog when the first link points into your transaction, and do nothing to the chain otherwise. If not, AppendUndoLog(GenerateNewUndoLog(schema, &base, nil, meta.Ts, link)). Then write meta {temp ts, true} with the old bytes and the new link, add the RID to the write set, and remove the key from every index that isn't the primary key. Writing this as a helper that takes the target (nil here) lets the update reuse it.

    One key fragment 
    if meta.Ts == txn.TransactionTempTs() {
	// self-modification: extend your own log if link.PrevTxn == txn.TransactionID()
} else {
	newLink = txn.AppendUndoLog(concurrency.GenerateNewUndoLog(schema, &base, target, meta.Ts, link))
}
  • What to think about

    What must be in your buffer before the first write? Which RID does the new version have now? For a secondary index, what changes when the key changes, and what when it doesn't? What does the count row count?

    The approach

    Drain the child into two slices (tuples and RIDs) before writing anything. Then compute each target from TargetExpressions on the buffered tuple, and run the delete's steps with that target: conflict check, one log per tuple (GenerateNewUndoLog or GenerateUpdatedUndoLog with &target), meta {temp ts, false} with the target's bytes, the write set. For each index that isn't the primary key, if the key changed, delete the old key and insert the new one with the same RID. The count is the number of buffered rows.

    One key fragment 
    olds = append(olds, e.childTuples...) // inside the drain loop: copy, don't keep the batch slice
oldRIDs = append(oldRIDs, e.childRIDs...)

Idiom

BusTub's const Tuple *base_tuple, with nullptr for "no tuple", is a *table.Tuple in Go, with nil for the same thing. Pass &base of a local copy you read with GetTupleAndUndoLink; a table.Tuple is a small value whose bytes are never modified, so a pointer to your copy is safe. The link argument of UpdateTupleAndUndoLink is a pointer for the same reason as C++'s std::optional<UndoLink>: nil means "no link", and a pointer to concurrency.InvalidUndoLink would store an explicit invalid one. Don't write UndoLink{} for "none": its zero value points at transaction 0, not nowhere.
