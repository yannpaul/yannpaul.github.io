Database Internals in Go · Unit 4 · Lesson 2

P2.2 Point Search

Implement IsEmpty, RootPageID and GetValue: find the root through the header page, binary-search every page on the way down, and hold at most two read guards at a time by dropping each parent only once its child is guarded.

The pages from the last lesson can now be put together into a tree. Stage 2 walks one from the root to a leaf. Insert doesn't exist yet, so the tests build their trees page by page with your stage-1 setters and then search them. The descent you write here is the backbone of everything after it: insertion and deletion start with the same walk, and stage 9 makes it concurrent without changing its shape.

Warm-up: retrieval from earlier lessons

Unit 3, Lesson 5: a is the sorted slice [10, 20, 30, 40]. What does sort.Search(len(a), func(i int) bool { return a[i] >= 25 }) return?

  • 1, the index of the largest element below 25.
  • 2, the index of the first element that is at least 25.
  • 3, the index of the last element.
  • 4, because 25 is not in the slice.

Unit 3, Lesson 7: goroutine A holds a read latch on a page's sync.RWMutex. Goroutine B calls Lock on it and blocks. Then A calls RLock on the same latch again, before releasing its first one. What happens?

  • A gets its second read latch at once, because readers share.
  • The runtime detects the cycle and makes B give up.
  • The second RLock is recognized as recursive and returns without taking anything.
  • A and B are deadlocked: A waits behind B, and B waits for A's first latch.

Unit 2, Lesson 7: a buffer pool with 2 frames has both frames pinned by guards. Code calls bpm.CheckedReadPage(pid, bufferpool.AccessUnknown) for a page that isn't in memory. What happens?

  • It returns (nil, false) and leaves the buffer pool unchanged.
  • It blocks until one of the guards is dropped, then returns the page.
  • It evicts the least recently used frame, even though it is pinned.
  • It returns (nil, false) but leaves the page in the page table with pin count 0.

What stage 2 covers

All three methods are in btree/b_plus_tree.go, plus whatever search helpers you add to the two page files:

  • RootPageID returns the root's page ID from the header page, or common.InvalidPageID for an empty tree.
  • IsEmpty reports whether the root is common.InvalidPageID. That is this course's definition of "empty"; it matters in stage 7, where a root leaf whose entries are all tombstoned still exists.
  • GetValue(key) returns (rid, true) if the key is in the tree and (common.RID{}, false) otherwise. BusTub appends to an output vector and returns a bool; keys are unique, so the vector never holds more than one value, and the Go version returns it directly.

The tests build trees with a helper, buildTree, that writes every page through your stage-1 methods (Init, SetSize, SetKeyAt, SetValueAt, SetNextPageID) and records the root in the header page. Stage 1 must pass first. The main test tree has three levels and deliberately mixes separators that are keys of the tree (10, 20, 30, 50, 60, 70) with one that isn't (40):

                         (30,60)
         (10,20)          (40,50)          (70)
(1,5) (10,12,15) (20,25)  (30,35) (41,45) (50,55)  (60,65) (70,80,90)

The header page holds the root

The root's page ID is not a field of BPlusTree. It lives in the tree's header page, a page whose only content is the root page ID (4 bytes at offset 0). Its ID, headerPageID, is fixed for the tree's lifetime and given to NewBPlusTree, which writes common.InvalidPageID into it. The root itself changes: the first insertion creates it, a root split replaces it, and the last deletion removes it. Keeping it on a page means the root ID is protected by a latch like every other piece of the tree, which is the Lecture #10 hint to protect the root page ID. The pre-built AsBPlusTreeHeaderPage(data) view has RootPageID and SetRootPageID.

Every operation therefore starts at the header page, never at a remembered root. For a lookup: take a read guard on the header page, read the root ID, and, if it is valid, take a read guard on the root before letting go of the header.

Searching inside one page

The writeup asks for binary search inside both page types: "Use binary search to find the place to insert a value when iterating an internal or leaf node. Otherwise, your implementation will probably timeout on Gradescope." The Go tests don't time you, but a full 8-byte-key leaf holds up to 509 entries, and TestBPlusTreeGrowBasicScale in stage 4 makes thousands of descents under the race detector. Two searches are needed:

  • In a leaf, find the first index whose key is greater than or equal to the search key (a lower bound). The key is present if that index is below Size() and the key there compares equal. Write it as a helper that returns both the index and whether it matched: stage 3 uses the same index as the insertion position.
  • In an internal page, find the child whose range contains the key: the largest index i ≥ 1 with KeyAt(i) ≤ key, or 0 if every valid key is greater. A key equal to a separator goes right, the lecture's "≥ goes right" rule.

Traced on the test tree above:

  • Find 30. At the root (30, 60), the largest key ≤ 30 is 30, at index 1, so the search goes to the middle subtree. At (40, 50), no key is ≤ 30, so it takes child 0 and finds 30 in the leaf (30, 35).
  • Find 40. Root: child 1. At (40, 50): 40 ≤ 40, so child 1, the leaf (41, 45). The lower bound in that leaf is index 0, which holds 41, so 40 is absent. A separator doesn't have to be a key of the tree, as Unit 3 put it.
  • Find 29. Root: no key ≤ 29, child 0. At (10, 20): 20 ≤ 29, child 2, the leaf (20, 25), where 29 is absent.

Compare keys only through t.comparator, which returns a negative number, zero or a positive number like bytes.Compare. The tree never interprets key bytes itself; the tests use IntegerComparator over 8- and 16-byte keys, and a byte-wise comparison would sort little-endian integers wrongly.

Crabbing down with read guards

The descent follows Lecture #10's rule for a search: take the read latch on the child, then release the parent, and repeat to the leaf. In this project a latch is a page guard, so "take the latch" means t.bpm.ReadPage(childID, bufferpool.AccessUnknown) and "release" means Drop:

  1. Read-guard the header page and read the root ID. If it is common.InvalidPageID, drop the header guard and return false.
  2. Read-guard the root, then drop the header guard.
  3. While the current page is not a leaf: find the child, read-guard it, drop the current guard, and continue from the child.
  4. At the leaf: run the lower-bound search, read the RID if the key matched, drop the leaf's guard, and return.

Unit 3's race shows why the parent stays guarded until the child's guard is in hand: T2 released node D before it held H, and T1 rebalanced both in the gap. The same order protects the root as well: if you read the root ID, dropped the header guard and only then guarded the root, a concurrent insertion could split the root in between. The old root page would then be just the left child, and a search for a key that moved to the right half would wrongly report it missing. Nothing in stage 2 modifies the tree concurrently, but stage 9 does, and its tests also require the opposite discipline: a lookup must not keep the header guard for the whole descent, or a writer that needs the header page waits for no reason.

Two more rules come from earlier units. Never take the same latch twice in one goroutine: calling t.RootPageID() while you hold the header's read guard takes a second read latch on it, and a writer that arrives in between deadlocks you, as in the warm-up. And drop every guard on every path, including the early return for an empty tree. Go has no destructor to do it for you. The tests check both: pin counts must be 0 after the lookups, and a write guard on every page must be obtainable.

#10 Latching in Data Structures, "Crabbing examples" (45:31), slides 24–26: Find 38 holds at most two read latches on its way from A to H; the delete example after it shows how writers differ.

Idiom

defer guard.Drop() is the right habit for a guard that lives until the function returns, such as the leaf's. Inside the descent loop it is wrong: deferred calls run when the function returns, so every page on the path would stay latched and pinned until the lookup ends, which is not crabbing at all. The tests would mostly still pass, because the pins are gone by the time they check. Write the hand-over explicitly instead: get the child's guard, drop the parent's, and assign the child to the loop variable. Because guards are pointers, reassigning the variable moves ownership without copying anything.

Check your understanding

An internal page has Size() = 4, keys 30, 60 and 90 at indexes 1 to 3, and children P0 to P3. Which child does a search for 60 follow, and which one does a search for 59 follow?

  • P1 for 60, and P1 for 59.
  • P2 for 60, and P2 for 59.
  • P2 for 60, and P1 for 59.
  • P3 for 60, and P2 for 59.

In the stage-2 test tree, GetValue is called for 40, which is a separator in the internal page (40, 50) but not a key of the tree. What does the search do?

  • It reaches the leaf (41, 45) and returns false.
  • It finds 40 in the internal page and returns that entry's value.
  • It reaches the leaf (30, 35) and returns false.
  • It panics, because a separator must be a key of some leaf.

A GetValue reads the root ID under the header's read guard, drops that guard, and only then takes a read guard on the root page. In stage 9, with concurrent insertions, what can go wrong?

  • The header page stays pinned forever.
  • The lookup deadlocks with every writer that needs the header page.
  • Two concurrent lookups block each other on the root page.
  • A root split in the gap makes the lookup start below the new root and miss keys that moved right.

TestBPlusTreeSearchSmallBufferPool searches a 4-level tree through a buffer pool of only 6 frames. With crabbing as described above, what is the largest number of pages a single lookup has pinned at any moment?

  • 1, because each guard is dropped before the next one is taken.
  • 2: a parent and its child, during each hand-over.
  • 5: the header page and all four levels.
  • 27, one per leaf.

Build it: point search (stage P2.2)

You edit btree/b_plus_tree.go and add helpers to btree/b_plus_tree_leaf_page.go and btree/b_plus_tree_internal_page.go. Run commands from go_db_internals/intro_to_db. The rules:

  • Start every operation at the header page (t.headerPageID), never at a root ID saved in the tree or from an earlier call.
  • Use read guards only (t.bpm.ReadPage); a lookup changes nothing. Go through t.bpm, the tracing wrapper, never around it.
  • Hold a parent's guard until the child's guard is held, then drop the parent. Drop every guard on every return path.
  • Binary-search both page types, comparing only with t.comparator. Call the pre-built t.checkKey("GetValue", key) first, so a key of the wrong length fails loudly.
  • Ignore tombstones for now; stage 7 adds "a tombstoned key does not exist" to GetValue.
  • What to think about

    Which page holds the root ID, and which kind of guard does reading it need? When may that guard be dropped: before or after you return the value? Can IsEmpty be written in terms of RootPageID?

    The approach

    RootPageID takes a read guard on t.headerPageID, defers its Drop, and returns AsBPlusTreeHeaderPage(guard.Data()).RootPageID(). A deferred drop is fine here: the function only holds this one guard. IsEmpty compares t.RootPageID() with common.InvalidPageID. Neither method may be called by code that already holds the header page's guard.

    One key fragment 
    guard := t.bpm.ReadPage(t.headerPageID, bufferpool.AccessUnknown)
defer guard.Drop()
  • What to think about

    What should the index be when every key is smaller than the search key? When is the key "found"? The helper needs a comparator, which the page view doesn't have: how does it get one? And does each probe really need a fresh copy of the key?

    The approach

    Give the helper the key and a KeyComparator as parameters. Search the indexes 0 to Size() for the first one whose key compares ≥ 0 with the search key; sort.Search does exactly that, or write the loop by hand. The result is Size() when every key is smaller. Report "found" when the index is below Size() and the comparison there is 0. To avoid allocating on every probe, compare against the private slice-of-the-page helper from stage 1 rather than KeyAt; that slice never leaves the method.

    One key fragment 
    // the first index in a sorted slice whose element is >= x (len(a) if none):
i := sort.Search(len(a), func(i int) bool { return a[i] >= x })
  • What to think about

    Which indexes hold valid keys? If you count how many valid keys are ≤ the search key, how does that count relate to the child index? Check your answer on the page (30, 60, 90) with keys 5, 30, 59, 60 and 100.

    The approach

    Only indexes 1 to Size() − 1 hold keys, and they are sorted. Find the first of them whose key is greater than the search key (an upper bound); the child just before it covers the key. Equivalently, the number of valid keys that are ≤ the search key is the child index: 0 keys means child 0, all of them means the last child. For the page (30, 60, 90): 5 gives 0, 30 gives 1, 59 gives 1, 60 gives 2, 100 gives 3.

    One key fragment 
    // how many elements of a sorted slice are <= x:
n := sort.Search(len(a), func(i int) bool { return a[i] > x })
// in the page, "a" starts at index 1, not 0
  • What to think about

    Which guard must you drop before returning false for an empty tree? Why must the root's guard be taken before the header's is dropped? Once you hold a page, how do you know whether to build a leaf view or an internal view?

    The approach

    Take a read guard on the header page and read the root ID through the header view (not through t.RootPageID(), which would latch the header a second time). If it is invalid, drop the header guard and return common.RID{}, false. Otherwise read-guard the root and only then drop the header guard. Ask AsBPlusTreePage(guard.Data()).IsLeafPage(); for a leaf, build t.leafPage(guard.Data()), run your lower-bound helper, and return ValueAt(index), true on a match, dropping the leaf's guard on the way out. The pre-built t.leafPage and t.internalPage build views with the tree's key size and tombstone count.

    One key fragment 
    guard := t.bpm.ReadPage(rootID, bufferpool.AccessUnknown)
header.Drop() // only now: the root can't change under us
    Checkpoint: empty tree and root leaf

    Run go test -race -run '^TestBPlusTreeSearch(EmptyTree|RootLeaf)$' ./btree/. It runs TestBPlusTreeSearchEmptyTree and TestBPlusTreeSearchRootLeaf, which need no descent: a new tree, and a tree whose root is a leaf holding 3, 7, 11 and 19. Success prints ok intro_to_db/btree. A stub still in place fails with panic: TODO(P2): BPlusTree.IsEmpty not implemented; a RootPageID that doesn't read the header page fails with RootPageID() = ..., want ... (the header page's root).

  • What to think about

    How many guards does the loop hold at the top of each iteration, and how many in the middle of one? What happens to the pins of the pages you passed if a defer inside the loop drops them? Stage 3 needs the same walk with write guards: is it worth writing the descent as its own helper that returns the leaf's guard?

    The approach

    Loop while !AsBPlusTreePage(guard.Data()).IsLeafPage(). Build the internal view, find the child index with your helper, and read the child's page ID with ValueAt. Read-guard the child, drop the current guard, and make the child current. After the loop, the current guard is the leaf's: search it as in the previous task. A helper such as "descend with read guards and return the leaf's guard, or nil for an empty tree" keeps GetValue short, and stage 8's iterator needs the same walk.

    One key fragment 
    child := t.bpm.ReadPage(childID, bufferpool.AccessUnknown)
guard.Drop() // the parent, now that the child is held
guard = child
Checkpoint: stage P2.2

From go_db_internals/intro_to_db, run:

go test -race -run '^TestBPlusTreeSearch' ./btree/

It runs the seven stage-2 tests, all extra tests standing in for CMU's hidden ones: TestBPlusTreeSearchEmptyTree, TestBPlusTreeSearchRootLeaf, TestBPlusTreeSearchMultiLevel (the 3-level tree, with present and absent keys), TestBPlusTreeSearchReleasesLatches (pin counts 0 and every page write-guardable after the lookups), TestBPlusTreeSearchSmallBufferPool (a 4-level tree of 27 leaves through 6 frames), TestBPlusTreeSearchConcurrentReaders (8 goroutines searching while the test itself holds read guards on the header and the root) and TestBPlusTreeSearchKeySize16. Success prints ok intro_to_db/btree and the time, about a second.

Typical failures:

  • An internal search that sends a key equal to a separator left: GetValue(10) = (_, false), want (page_id: 0 slot_num: 10, true), for 10, 20, 30, 50, 60 and 70, the separators that are keys.
  • A parent guard that is never dropped: page 12 has pin count 37 after the operations returned, want 0: a page guard was not dropped, then taking a write guard on a page after the lookups did not return within 10s. With only 6 frames, leaked pins also run the buffer pool dry: panic: bufferpool: CheckedReadPage failed to bring in page 17.
  • A write guard where a read guard belongs, or a second latch on the header: 8 goroutines doing lookups while the test holds read guards on the header and root pages did not finish within 10s.

If the command sits silent for more than a minute, stop it and rerun with a time limit after the regex: go test -race -run '^TestBPlusTreeSearch' -timeout 120s ./btree/. When the limit fires, go test names the running test and prints every goroutine's stack, which shows where each one waits.

Something unclear? For example, why the child for a key equal to a separator is the one to its right, why the root's guard must be taken before the header's is dropped, or why a defer inside the descent loop passes the tests but isn't crabbing. Ask your teacher (me) before moving on.
