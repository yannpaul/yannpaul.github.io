P1.3 Disk Scheduler: a Worker Goroutine and Callback Channels

Build the disk scheduler that carries every page read and write in Project 1, and explain why each request's callback is a capacity-1 channel and how the worker stops without dropping queued work.

The ARC replacer from the last two lessons decides which frame to give up, but it never touches the disk. The disk scheduler does. Every page the buffer pool reads into a frame, and every dirty page it writes back, reaches the disk manager through it as a DiskRequest. Buffer Pools sketched its shape. Here you write its two missing functions, Schedule and the worker loop, and learn the concurrency rules that decide what goes in them.

Warm-up: retrieval from earlier lessons

Unit 1, Lesson 1: starting from an empty database file, the pre-built disk.FileManager writes pages 0, 1 and 2, deletes page 0 and then page 2, and then writes page 5 and page 6. Pages are 8,192 bytes. At which byte offsets do pages 5 and 6 land?

  • Page 5 at 0 and page 6 at 16,384, because freed slots are reused in the order they were freed.
  • Page 5 at 40,960 and page 6 at 49,152, from Offset = Page# × PageSize.
  • Page 5 at 16,384 and page 6 at 0, because the slot freed last is reused first.
  • Page 5 at 24,576 and page 6 at 32,768, because new pages always go at the end of the file.

Unit 2, Lesson 2: the buffer pool needs page 2, which is in no frame. The BPM frees frame 3 for it, and RecordAccess(3, 2, AccessUnknown) finds page 2 in the MRU ghost list. Which statement is right?

  • Page 2's bytes are still stored with its ghost entry, so the BPM can fill frame 3 without reading the disk.
  • ARC counts a pseudo-hit and adapts p, but the BPM must still read page 2 from disk into frame 3.
  • RecordAccess evicts a resident page to make room for page 2, so the BPM never calls Evict for this request.
  • Page 2 goes to the front of the MRU list, because to the buffer pool the access is a miss.

Why all page I/O goes through one scheduler

Lecture #04 ended its I/O discussion with a design rule: the DBMS keeps its own queues of page read and write requests, because only the DBMS knows which requests matter most (slides 34–35, in Buffer Pools). The Project 1 writeup turns that rule into Task #2. The disk scheduler "is responsible for scheduling read and write operations on the DiskManager". Other components queue requests with it (in Project 1 that is only the buffer pool manager), and a background worker processes them. A shared queue sits between the two: one thread adds a request, and the worker takes it off.

With every request going through one interface, the buffer pool only says what it needs: read page P into these bytes, or write these bytes out as page P. How and when the disk does it is the scheduler's business. The slide leaves batching, reordering and issuing requests to you, and the writeup's leaderboard ideas (queueing several requests to prefetch pages, issuing I/O in parallel) all change the scheduler's insides while Schedule and the callbacks stay the same. The caller also decides when to wait. Schedule returns at once and each request carries its own completion signal, so a caller can schedule several reads and wait for each one only when it needs the bytes.

Project 1's scheduler is the smallest one that works: one first-in, first-out queue and one worker goroutine. Its only policy is order: requests run one at a time in the order they were queued, so a read scheduled after a write to the same page sees the write. The writeup holds even a parallel scheduler to that guarantee: several requests to one page must end up as if they were processed in order, and a single thread must get read-after-write consistency, meaning a read always sees that thread's earlier writes. The stage-3 tests check it.

The two pre-built pieces around your code are short enough to read whole:

// in NewDiskScheduler: spawn the background worker
go func() {
	defer close(ds.workerDone)
	ds.startWorker()
}()

func (ds *DiskScheduler) Shutdown() {
	// Put a nil in the queue to signal to exit the loop.
	ds.requestQueue.Put(nil)
	<-ds.workerDone
}

So startWorker is the worker goroutine's entire life. When it returns, the deferred close releases Shutdown, which stands in for BusTub's destructor joining the background thread. The writeup's rule for StartWorkerThread carries over: it "should not return until the DiskScheduler's destructor is called". In Go, that means it keeps working until it takes Shutdown's nil off the queue, and then it returns.

Why the worker stub doesn't panic

Every other TODO(P1) stub panics, but startWorker's stub returns at once. A panic on a goroutine the test didn't start can't be recovered by the test's failOnPanic, so it would stop the whole test binary, and every other test with it. On the starter, Schedule panics in the test's own goroutine, which fails only that test, and Shutdown still returns: Put never blocks, and the stub's return closes workerDone. For the same reason, your worker must never panic.

Requests travel by value and the queue holds pointers

Schedule takes []DiskRequest, a slice of values, but the queue holds *DiskRequest. The pointer makes room for the stop signal. BusTub's queue holds std::optional<DiskRequest> and its destructor puts std::nullopt; in Go, nil plays nullopt. That reserved value is a sentinel: it carries no request, only the message "stop". So Schedule must never queue a nil, and every real request goes in as a non-nil pointer.

Copying a DiskRequest is cheap and safe, because its fields are a bool, a slice header, an int32 page ID and a channel. A copy still points at the caller's buffer and the caller's channel. The Data doc comment calls this aliasing, and the design depends on it: the worker reads a page straight into a frame's bytes, and the issuer receives on the same channel the worker sends on. The queue never needs the caller's slice itself, so queue a pointer to a copy of each request, not a pointer into a slice the caller may reuse.

The issuer has one duty in return: it leaves Data alone until the callback arrives. During a write the worker is reading those bytes, and during a read it is filling them. In the buffer pool, latches and pins give that guarantee; in the tests, each buffer belongs to a single goroutine.

The queue is a common.Channel rather than a Go channel because a buffered chan has a fixed capacity: once it is full, every send blocks, and Schedule would stall behind a slow disk. Lesson 5 of the concurrency course warned that a buffer of arbitrary size only delays a blocking send. common.Channel is BusTub's Channel<T>: a slice guarded by a sync.Mutex and a sync.Cond. Put appends and wakes any waiter. Get waits on the condition variable while the queue is empty, so an idle worker sleeps instead of spinning.

The shutdown signal differs from the worker pool in Lesson 7 of that course, where the producer filled the jobs channel, closed it, and the workers ranged over it. The scheduler's producers are all the goroutines that use the buffer pool, for the scheduler's whole life, so no single one of them can close the queue safely (a send on a closed channel panics). A sentinel in the queue ends the loop instead.

Callbacks: std::promise<bool> becomes a capacity-1 chan bool

In BusTub each DiskRequest carries a std::promise<bool>. The issuer keeps the matching std::future<bool> and blocks in its get() until the worker calls set_value. A promise is one-shot: it delivers exactly one value. The writeup describes it as "a callback mechanism for a thread to know when their scheduled request is completed". The header comment of disk_scheduler_test.go lines the two versions up:

BusTub (C++)Go port
auto promise1 = disk_scheduler->CreatePromise();callback1 := diskScheduler.NewCallback()
auto future1 = promise1.get_future();the same channel
worker: promise.set_value(true);worker: request.Callback <- true, exactly once
ASSERT_TRUE(future1.get());awaitCallback(t, "write request", callback1), which gives up after 10 s

The worker sends exactly one value per request, so a capacity of 1 lets every send complete at once. Lesson 5 of the concurrency course named that pattern: size the buffer to the number of sends you know are coming, and no send ever blocks. With an unbuffered channel, the worker's send would wait until the issuer receives. An issuer that receives late, or never, would then hold up the worker, every request queued behind it, and Shutdown's nil. TestDiskSchedulerShutdownDrainsQueue receives late on purpose: it schedules 100 writes, calls Shutdown, and only then looks at the callbacks. If NewCallback made an unbuffered channel, the worker would block on its first send and the test would report DiskScheduler.Shutdown did not return within 10s.

The channel also makes the worker's writes visible. The worker writes the page into Data before it sends, and the issuer reads Data after it receives. The Go memory model says that a send on a channel is synchronized before the corresponding receive completes, so the issuer sees every byte the worker wrote and go test -race stays quiet. Reading Data without waiting for the callback is a data race, even if the bytes happen to be there already.

Idiom

One capacity-1 channel replaces both halves of a promise/future pair. NewCallback plays CreatePromise and get_future, the worker's single send plays set_value, and the issuer's receive plays future.get(). The capacity matches the one value a promise can deliver. To wait with a deadline, receive in a select with a time.After case, as the tests' awaitCallback does (concurrency course, Lesson 6).

A send on a nil channel blocks forever. A request built without a callback would freeze the worker at its send, so every request needs a channel from NewCallback.

The worker loop and a clean shutdown

The writeup gives the worker two jobs: receive queued requests and dispatch them to the disk manager, and "set the value correctly on the DiskRequest's callback". Each pass of its loop ends one of three ways:

  • Get blocks while the queue is empty.
  • A nil means Shutdown was called, so the worker returns.
  • Anything else is a request. The worker runs it on ds.diskManager with WritePage or ReadPage, two of the three methods of the disk.Manager interface, and then sends the result on the request's callback.

Shutdown's nil joins the back of the queue, behind every request scheduled before it, and a single FIFO worker reaches it last. Shutdown therefore returns only after those requests are done, which is what BusTub's test means by "Call the DiskScheduler destructor to finish all scheduled jobs". TestDiskSchedulerShutdownDrainsQueue checks it: when Shutdown returns, each of its 100 callbacks must already hold a value.

The doc comment adds a rule for the other side: the scheduler must not be used after Shutdown. Put would still accept a request, but no worker is left to take it, so whoever waits on its callback waits forever. In Project 1, BufferPoolManager.Close calls Shutdown, and neither the pool nor its guards may be used afterwards.

Keep the worker on one goroutine. Starting a goroutine per request would overlap the I/O, but it breaks both guarantees: requests to the same page could run in any order, and Shutdown could return while some of them are still running. With that change, four of the five stage-3 tests fail, and TestDiskSchedulerBatchPreservesOrder reports read "page 3, version 2", want "page 3, version 1". Parallel I/O is one of the writeup's leaderboard optimizations, and per-page ordering is the condition it comes with.

When the disk fails

BusTub's disk manager can't fail as far as the scheduler is concerned: it logs I/O errors and carries on, so BusTub's worker only ever sets true. The Go disk managers return an error instead (FileManager does on an I/O error; MemoryManager never does), so the Go port has to say what the worker does with it. The Callback doc comment does: "The worker sends true once the request has been processed and false if the disk manager returned an error."

The rule has a second half, which TestDiskSchedulerReportsDiskErrors checks: after a failure, the worker keeps serving. The test's disk manager fails every operation on page 13. One batch holds a failing write and a failing read of page 13, then a good write and a good read of page 1. Every other reaction to the error fails the test:

  • Skipping the callback leaves the issuer blocked, and the test reports failing write: callback not signalled within 10s.
  • Returning from the loop strands every later request, with the same message.
  • Panicking stops the whole test binary, because the worker runs on a goroutine the test didn't start.

Stages 5 and 6 decide what the buffer pool, as the issuer, does with a false.

Check your understanding

Suppose NewCallback returned make(chan bool), an unbuffered channel. A goroutine schedules a write of page 4 with callback cb, then decides it doesn't need the result and never receives from cb. Other goroutines keep scheduling requests. What happens?

  • The worker's send completes and the value is discarded, since nobody is receiving.
  • The Go runtime detects the deadlock at once and stops the program with a fatal error.
  • The worker blocks on that send forever, so no later request runs and Shutdown never returns.
  • The worker gives up on that callback after a timeout and moves on to the next request.

The disk manager returns an error while the worker is writing page 13. Which behaviour does the stage-3 suite require?

  • Send false on that request's callback, then go on to the next request.
  • Send nothing, so that the issuer can tell from the missing value that the write failed.
  • Panic with the error, so that the failure can't go unnoticed.
  • Return from startWorker, since the disk is probably broken for later requests too.

To overlap disk I/O, a worker starts a new goroutine for each request it takes off the queue, and still returns when it takes the nil. Which statement about this version is true?

  • Schedule now blocks until the goroutine for each of its requests has started.
  • Callbacks stop working, because only the goroutine that made a channel may send on it.
  • Shutdown still returns only after every earlier request has finished, because the nil is queued last.
  • A read scheduled after a write to the same page can run first and miss the write.

An issuer schedules a read of page 9 into buf, receives true from the callback, then reads buf. go test -race reports nothing. Why is there no data race on buf, which the worker goroutine wrote?

  • MemoryManager copies the page under its own latch, and that latch protects buf as well.
  • The worker wrote buf before sending, and a send is synchronized before its receive completes.
  • Slices are passed by value, so the worker wrote into its own copy of buf.
  • The race detector doesn't track writes into byte slices, only into variables.

A goroutine calls Schedule after the scheduler's Shutdown has returned, then waits on the request's callback. What happens?

  • Schedule returns, but no value ever arrives on the callback, so the goroutine waits forever.
  • Schedule panics, because Shutdown closed the queue and the request is sent on a closed channel.
  • The request runs normally, because Put starts a new worker when the old one has returned.
  • The callback receives false, because the scheduler rejects requests that arrive after Shutdown.

Build it: P1.3 the disk scheduler

You edit one file, bufferpool/disk_scheduler.go, and two functions in it: Schedule and startWorker. You may add fields to DiskScheduler (its TODO(P1) comment allows it) and initialize them in NewDiskScheduler, but this stage needs none. Leave the goroutine in NewDiskScheduler, Shutdown and NewCallback as they are: the tests rely on them. The rules, in plain words:

  • Schedule queues every request in the order given and returns without waiting for any I/O. Callers wait on the callbacks.
  • The worker takes requests off requestQueue one at a time, in queue order, and runs each one on the disk manager: WritePage when IsWrite is true, ReadPage otherwise, with the request's PageID and Data unchanged.
  • For each request the worker sends exactly one value on Callback: true if the disk manager returned nil, false if it returned an error. After an error it carries on.
  • The worker returns when it takes Shutdown's nil off the queue, and not before. It never panics.

This stage doesn't use the ARC replacer. Its tests run on disk.MemoryManager, plus a wrapper that fails every operation on page 13.

  • What to think about

    Schedule is the producer side. What type does the queue hold, which value of that type belongs to Shutdown, and what may the caller do with its slice once Schedule has returned? Nothing in Schedule should wait for the disk.

    The approach

    Walk the slice in order and Put one non-nil *DiskRequest per element on ds.requestQueue. Point at a copy of each request rather than into the caller's slice; the copy still shares the caller's Data buffer and Callback channel. Since Go 1.22, the variable of a for … range loop is a new variable on every iteration (go.mod says 1.24), so its address is a different pointer each time. Don't call the disk manager here, and don't receive from any callback.

    One key fragment 
    ds.requestQueue.Put(&request) // request: this iteration's own copy

    With Schedule written and the worker still the stub, the stage-3 tests stop panicking and start waiting. After 10 s each one reports callback not signalled within 10s: does the worker take requests off the queue and send the result on DiskRequest.Callback?, and TestDiskSchedulerShutdownDrainsQueue fails at once with request 0 was not processed before Shutdown returned. That is the expected state until the next two tasks are done.

  • What to think about

    The loop has to sleep while there is nothing to do, wake for each request, and end exactly once, at shutdown. Which call blocks while the queue is empty? What has to happen before Shutdown's <-ds.workerDone can return?

    The approach

    Loop forever. Each pass calls ds.requestQueue.Get(), which blocks until something is queued. If the value is nil, return; NewDiskScheduler's deferred close(ds.workerDone) then lets Shutdown return. Otherwise run the request (next task) before you take the next one. Read from requestQueue and not from a channel of your own, because that is where Shutdown puts its nil, and run each request on this goroutine.

    One key fragment 
    request := ds.requestQueue.Get() // blocks while the queue is empty
if request == nil {
	return // Shutdown's stop signal
}
  • What to think about

    The issuer is blocked on its callback. What must it receive when the disk manager fails, and what should happen to the requests queued behind a failed one?

    The approach

    Call ds.diskManager.WritePage(request.PageID, request.Data) when request.IsWrite is true, and ReadPage with the same arguments otherwise. Keep the returned error, then send err == nil on request.Callback. That send can't block, because NewCallback made the channel with room for one value. Then go round the loop again, error or not.

    One key fragment 
    request.Callback <- err == nil // set_value: true on success, false on a disk error
    Checkpoint

    From go_db_internals/intro_to_db, run go test -race -run '^TestDiskScheduler' ./bufferpool/. It runs the five stage-3 tests: TestDiskSchedulerScheduleWriteReadPage (BusTub's ScheduleWriteReadPageTest), TestDiskSchedulerBatchPreservesOrder, TestDiskSchedulerConcurrentCallers, TestDiskSchedulerShutdownDrainsQueue and TestDiskSchedulerReportsDiskErrors. Success prints ok intro_to_db/bufferpool followed by the run time. To see each test pass, add -v after the regex.

    A typical failure names its cause. panic: TODO(P1): DiskScheduler.Schedule not implemented means Schedule is still the stub. callback not signalled within 10s means a request never got its value: the worker is still the stub, or it skips the send or returns after an error. DiskScheduler.Shutdown did not return within 10s means the worker never returns, or it is stuck on a send. read "page 3, version 2", want "page 3, version 1" means requests to one page ran out of order.

Something unclear? For example, why the queue holds pointers while Schedule takes values, why the callback needs room for exactly one value, or what Shutdown waits for. Ask your teacher (me) before moving on.
