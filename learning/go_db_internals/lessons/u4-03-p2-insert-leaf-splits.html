P2.3 Insertion and Leaf Splits

Implement Insert up to the first internal split: the first insertion, sorted insertion into a leaf, duplicate rejection, and the leaf split that copies a separator into the parent or into a new root, using the split timing and split point the tests expect; then debug trees with cmd/btree_printer.

Until now the tests built every tree by hand. From this stage on, the tree builds itself. Unit 3 traced inserts on paper with the lecture's rules; the Project 2 writeup and this course's tests fix a few details the lecture leaves open, above all when a leaf splits and how many entries each half keeps. This lesson states those conventions, then has you write every part of an insertion except one: an internal page that is already full. That case is the next lesson's.

Warm-up: retrieval from earlier lessons

Lesson 1: a tree has LeafMaxSize = 6 and InternalMaxSize = 4. What do its leaf and internal pages return from MinSize?

  • 2 for leaves and 2 for internal pages.
  • 3 for leaves and 3 for internal pages.
  • 3 for leaves and 2 for internal pages.
  • 2 for leaves and 3 for internal pages.

Unit 3, Lesson 8: under latch crabbing, when is a node safe for an insert, so that the latches on its ancestors can be released?

  • When it isn't full: one more entry, even one pushed up from below, fits.
  • When it is more than half full.
  • Always, if it is a leaf, because inserts only change leaves.
  • Only when it is the root.

Unit 2, Lesson 7: every frame of a buffer pool is pinned, and code calls bpm.NewPage(). What happens?

  • It panics, because no frame can hold the new page.
  • It blocks until a guard is dropped.
  • It evicts a pinned frame to make room.
  • It succeeds: it only hands out the next page ID.

What stage 3 covers

All of stage 3 is BPlusTree.Insert in btree/b_plus_tree.go, plus helpers in the two page files. Insert(key, value) returns true when it adds the key and false when the key is already in the tree; keys are unique, and a duplicate insertion changes nothing. The stage-3 tests exercise:

  • the first insertion into an empty tree, which creates a root leaf and records it in the header page;
  • insertion into a leaf that has room, keeping its entries sorted;
  • duplicates, in the root leaf and in leaves further down;
  • leaf splits, including the very first one, where the root leaf splits and a new internal root appears.

They keep every internal page below its max size, so the separator from a leaf split always fits in the parent. Splitting a full internal page is stage 4.

When a leaf splits, and where

The writeup recommends, without requiring it, a split rule: "split a leaf node when the number of values reaches max_size after insertion, and split an internal node when number of values reaches max_size before insertion." It gives the reason: with this rule an insertion "will never cause a page data overflow". It also says CMU's tests don't check which rule you follow. This course's tests do, because about twenty of them compare the exact shape of a tree. The doc comment on BPlusTree.Insert states the rules, and Unit 3 promised them here:

  • Split timing. Insert the entry first. If the leaf now holds LeafMaxSize entries, split it. A leaf at rest therefore holds at most LeafMaxSize − 1 entries: a tree with LeafMaxSize = 4 has leaves of at most 3 keys, the lecture's "nodes hold at most 3 keys".
  • Split point. With n = LeafMaxSize entries, the left page keeps the first n/2, rounded down. A new right page takes the rest and follows the left page in the leaf chain.
  • Separator. The right page's first key is copied up into the parent; it stays in the leaf too, as in the lecture.
  • New root. When the leaf that splits is the root, a new internal root with two children is created, and the header page records it.

The split point differs from the one Unit 3 used for HW3. There, a leaf of 5 keys kept 3 on the left; here the left page keeps 2. Inserting 1 to 5 into a tree with LeafMaxSize = 5 gives (3) / (|1,2) (|3,4,5), not a split at 4. (Trees are written as the tests write them: level by level, separated by " / ", internal pages as their keys, leaves as (tombstones|keys).) Odd max sizes make the rule visible:

LeafMaxSizeKeys insertedTree after the last insertion
31, 2, 3(2) / (|1) (|2,3)
41, 2, 3(|1,2,3), no split yet
41, 2, 3, 4(3) / (|1,2) (|3,4)
51, 2, 3, 4, 5(3) / (|1,2) (|3,4,5)

The rule also keeps every insertion inside the page. A tree created with Options{} gets the largest leaves a page allows: LeafMaxSize equals the slot count, 510 for 8-byte keys. The 510th entry goes into the last slot, and the leaf splits at once. A lazy rule that waits for a 511th entry would write it past the end of the key array, into the RID array. TestBPlusTreeInsertDefaultLeafSize inserts 2000 keys into such a tree to catch exactly that.

One insertion, step by step

An insertion may change the root, so it takes the header page's write guard first. In this stage, keep it simple: hold the header's write guard and a write guard on every page of the path for the whole insertion. That is correct but serializes all writers, much like the global latch the writeup forbids. The doc comment on BPlusTree allows a simpler correct scheme for stages 2 to 8; stage 9 replaces it with latch crabbing (releasing safe ancestors early) and an optimistic first pass.

  1. Header. Write-guard the header page and read the root ID. If the tree is empty, allocate a page with t.bpm.NewPage(), write-guard it, Init it as a leaf with t.leafMaxSize, put the entry at index 0, record its ID with SetRootPageID, and return true.
  2. Descend. From the root, write-guard each page and push its guard onto the path; in internal pages, pick the child with your stage-2 helper. Stop at the leaf.
  3. Duplicate check. Run the leaf's lower-bound search. If the key is there, return false having changed nothing.
  4. Insert. Shift the entries from the lower-bound index one slot to the right and write the new key and RID there. If the leaf now holds fewer than LeafMaxSize entries, you are done.
  5. Split. Allocate and Init a new leaf, move the entries from index Size()/2 on into it, and link it into the chain after the left leaf.
  6. Separator. Insert the right leaf's first key and page ID into the parent, right after the left leaf's pointer. If the left leaf was the root, create a new internal root instead.

The pre-built Context struct holds this state, and the writeup's tips are in its doc comment. ctx.HeaderPage is the header's write guard (a *bufferpool.WritePageGuard, nil when not held), ctx.RootPageID records the root, and ctx.WriteSet is the path of write guards from the root down. The writeup's tip: a node's parent is at the back of the write set, so when the leaf is WriteSet[len−1], its parent is WriteSet[len−2]. If a page splits and nothing is above it in the write set, it must be the root, and ctx.HeaderPage must still be held. ctx.Release() drops everything the context still holds, header first, then the path from the top down, which is the release order the writeup asks for. Call it with defer right after NewContext(), the Go stand-in for BusTub's destructor.

Pages created during a split get guards of their own: NewPage returns an ID, and t.bpm.WritePage(id, bufferpool.AccessUnknown) guards it. Drop those guards when the split is done (a defer in the helper that creates the page works well). A new page is invisible to other goroutines until its parent points to it, and the parent is write-guarded.

Idiom

Making room for an entry means moving the tail of both arrays one slot to the right, inside the same page. Go's built-in copy handles overlapping source and destination correctly, like C's memmove, so one copy per array moves a whole run of keys or RIDs at once, with no loop and no temporary buffer. The same call moves the upper half of a page into a new page during a split. Compute every range with keyOffset and valueOffset, so that it stays right for any key size and tombstone buffer.

Debugging with cmd/btree_printer

The writeup's "Tree Visualization" tool is ported as cmd/btree_printer. It runs on your buffer pool and your tree, so it works as soon as Insert does. It asks for the leaf and internal max sizes, then reads commands: i k inserts key k, f file inserts every integer in a file, p prints the tree, g tree.dot writes it in Graphviz format, q quits, and ? lists the rest. Its -tombs flag sets the tombstone buffer, 2 by default as in BusTub; use -tombs 0 until stage 7, to match the tests. From go_db_internals/intro_to_db:

$ go run ./cmd/btree_printer -tombs 0
...
> 4 4
> i 1
> i 2
> i 3
> i 4
> p
        (3)
  (|1,2)    (|3,4)

Internal Page: 3
Contents: 1, 3: 2

Leaf Page: 1	Next: 2
Contents: 1, 2
Tombstoned keys:

Leaf Page: 2	Next: -1
Contents: 3, 4
Tombstoned keys:

The p command prints two views. The first is DrawBPlusTree, the same picture a failing shape test prints. The second is Print, a depth-first dump with page IDs: Contents: 1, 3: 2 means child page 1, then key 3 with child page 2, and each leaf shows its next page, so a broken chain is easy to spot. The page IDs show the order of events: the header is page 0, the root leaf page 1, the right half of its split page 2, and the new root page 3. For a picture, g tree.dot followed by dot -Tpng -O tree.dot, or the online viewer the writeup links, draws internal pages in pink and leaves in green. Lecture #10's hint to start with tiny pages applies here as small max sizes: 3 or 4 makes a split happen every few keys.

Inside a test you are debugging, the same helpers are available: t.Log(tree.DrawBPlusTree()), or tree.Print(os.Stderr). They take read guards top-down and keep a parent's guard while visiting its children, so call them only when no other goroutine is changing the tree.

Check your understanding

A tree has LeafMaxSize = 5. A leaf holds 13, 14, 15 and 17, and its parent has room. Key 16 is inserted. What happens?

  • The leaf splits into (13, 14, 15) and (16, 17), and 16 is copied up.
  • The leaf splits into (13, 14) and (15, 16, 17), and 15 is copied up.
  • The leaf takes 16 as its fifth entry and splits on the next insertion.
  • The leaf splits into (13, 14) and (16, 17), and 15 moves up into the parent.

Keys 10, 20, 30, 40 and 50 are inserted in that order into an empty tree with LeafMaxSize = 4. What is the tree afterwards?

  • (|10,20,30,40) with 50 waiting in a second leaf, under the root (50).
  • (40) / (|10,20,30) (|40,50)
  • (30,50) / (|10,20) (|30,40) (|50)
  • (30) / (|10,20) (|30,40,50)

A tree uses Options{}, so LeafMaxSize is 510, the leaf's slot count. Why does the "split when the leaf reaches the max after an insertion" rule matter here?

  • A leaf never needs a 511th slot, which the page's arrays don't have.
  • It keeps the leaf's MinSize at 255 instead of 256.
  • It makes the tree one level shorter.
  • It avoids one write guard per insertion.

An Insert splits the root leaf and creates a new internal root correctly, but never calls SetRootPageID. What do later operations see?

  • Nothing wrong: NewPage updates the header page automatically.
  • An empty tree, because the header page holds common.InvalidPageID.
  • The old root leaf, now only the left half, so keys in the right half are invisible.
  • A deadlock on the header page.

Leaf L points to M as its next page. L splits, and its upper half moves into a new leaf R. What must the next-page pointers be afterwards?

  • L points to R, and R points to M.
  • L still points to M, and R points to M.
  • R points to L, and L still points to M.
  • L points to R, and R's next page is common.InvalidPageID.

Build it: insertion and leaf splits (stage P2.3)

You edit btree/b_plus_tree.go (Insert and any helpers) and add helpers to btree/b_plus_tree_leaf_page.go and btree/b_plus_tree_internal_page.go. Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • Call t.checkKey("Insert", key) first. Return false for a key that is already in the tree, without changing anything; otherwise insert it and return true.
  • Take the header page's write guard before reading the root, and keep it while the root can still change. Use write guards on the path, and drop every guard you take, including those of new pages.
  • New leaves are initialized with t.leafMaxSize, new internal pages with t.internalMaxSize.
  • Split a leaf when it reaches LeafMaxSize entries after the insertion. The left page keeps Size()/2 entries, rounded down; the right page follows it in the leaf chain, and its first key goes into the parent.
  • When the root splits, create a new internal root with two children and record it in the header page.
  • What to think about

    Which byte ranges move, in which array, and by how many bytes? Does the order of moving and writing matter? Which header field changes? And in stage 7, a tombstone records an entry's index: what happens to it when its entry shifts right?

    The approach

    Let n be Size(). Move the keys at indexes index to n − 1 to index + 1 to n with one copy on the key array's byte range, and do the same on the RID array. Then write the new key with your key setter and the RID with SetValueAt, and ChangeSizeBy(1). The caller guarantees a free slot. Leave a note for stage 7: tombstone indexes at or after index will have to grow by one.

    One key fragment 
    // keys [index, n) move one slot right; copy is a memmove, so the overlap is fine
copy(p.data[p.keyOffset(index+1):p.keyOffset(n+1)], p.data[p.keyOffset(index):p.keyOffset(n)])
  • What to think about

    Why a write guard on the header, even when the tree turns out not to be empty? Two goroutines insert into an empty tree at the same time: what keeps them from creating two roots? What must happen to the new page's guard and to the header guard before Insert returns?

    The approach

    Create a Context with NewContext() and defer its Release. Store the header's write guard in ctx.HeaderPage and the root ID from AsBPlusTreeHeaderPage(ctx.HeaderPage.DataMut()) in ctx.RootPageID. If the root is common.InvalidPageID: get an ID from t.bpm.NewPage(), write-guard it, Init(t.leafMaxSize) it through t.leafPage(guard.DataMut()), insert the entry at index 0 with your helper, drop the guard, set the header's root ID, and return true. The deferred Release drops the header guard.

    One key fragment 
    ctx := NewContext()
defer ctx.Release()
ctx.HeaderPage = t.bpm.WritePage(t.headerPageID, bufferpool.AccessUnknown)
  • What to think about

    The descent is the stage-2 walk with two changes. Which guard type, and what happens to each parent's guard now? Which index does the lower-bound search give you when the key is absent, and why is it exactly the insertion position?

    The approach

    Starting at ctx.RootPageID, write-guard each page and append the guard to ctx.WriteSet, keeping all of them. In an internal page, choose the child with your stage-2 helper. At the leaf, which is the last guard in the write set, run the lower-bound search on t.leafPage(guard.DataMut()). If the key matched, return false; the deferred Release drops the whole path. Otherwise insert at the returned index and return true when the leaf still holds fewer than t.leafMaxSize entries. Leave a placeholder for the split.

    One key fragment 
    guard := t.bpm.WritePage(pageID, bufferpool.AccessUnknown)
ctx.WriteSet = append(ctx.WriteSet, guard) // Release drops it later
    Checkpoint: insertion without splits

    Run go test -race -run '^TestBPlusTreeInsert(IntoEmptyTree|Basic|KeepsLeafSorted)$' ./btree/. It runs TestBPlusTreeInsertIntoEmptyTree, BusTub's BasicInsertTest (TestBPlusTreeInsertBasic) and TestBPlusTreeInsertKeepsLeafSorted (12 shuffled keys in one leaf of max size 16), none of which needs a split. Success prints ok intro_to_db/btree. A header page that isn't updated fails with RootPageID() = -1, header page root = -1: the header page must record the new root.

  • What to think about

    Which entries stay: the first Size()/2, or the last? What does the new page need before entries go into it? Which two next-page pointers change, and in which order must you read and write them so that nothing is lost? What does the parent need from the split?

    The approach

    Allocate a page, write-guard it, defer its Drop, and Init(t.leafMaxSize) it. Let mid = Size()/2. Copy the keys and the RIDs at indexes mid to Size() − 1 into the new page starting at index 0 (one copy per array), then set the new page's size to Size() − mid and the old page's to mid. A leaf-page helper that moves a range of entries into another leaf is worth writing now; stages 5 and 6 move entries between leaves too. Then give the right page the left page's old next pointer and point the left page at the right page. Hand the right page's KeyAt(0) and page ID to the parent step.

    One key fragment 
    mid := left.Size() / 2 // left keeps [0, mid); the new right leaf gets [mid, Size())
right.SetNextPageID(left.NextPageID())
left.SetNextPageID(rightID)
  • What to think about

    How do you tell that the leaf that split was the root? Where in the write set is the parent, and at which index does the new pointer go? For a new root: which child goes in slot 0, which key and child in slot 1, and what is its size? In stage 4 the same step runs one level higher with an internal page on the left, so which inputs does it really need?

    The approach

    Write a helper that takes the context, the position in the write set of the page that split, the separator key and the new right page's ID. If that position is 0, the page that split was the root: check that ctx.HeaderPage is held, allocate an internal page, Init(t.internalMaxSize), point child 0 at the old root and child 1 at the right page with the separator as key 1, set the size to 2, and record the new root in the header page. Otherwise the parent is the guard just before it in the write set: find the left page's index with ValueIndex and insert (separator, right page ID) at that index + 1, with an internal-page insert-at helper that shifts both arrays as the leaf one does. In this stage the parent always has room.

    One key fragment 
    root.SetValueAt(0, leftID)
root.SetKeyAt(1, separator)
root.SetValueAt(1, rightID)
root.SetSize(2)

Shape failures print the tree you built next to the one expected, then your tree drawn by DrawBPlusTree:

--- FAIL: TestBPlusTreeInsertRootLeafSplit (0.00s)
    b_plus_tree_insert_extra_test.go:102: tree shape:
         got: (3) / (|1,2) (|3)
        want: (2) / (|1) (|2,3)

That one keeps the larger half on the left. Other typical failures:

  • A lazy split, waiting for an entry beyond the max: got: (|1,2,3,4), want: (3) / (|1,2) (|3,4), and in DefaultLeafSize wrong RIDs such as GetValue(1050) = (page_id: 2000 slot_num: 0, true), from the 511th entry overwriting the RID array.
  • A broken chain: invalid tree: the leaf chain (next page ids from the leftmost leaf) visits [1], but the leaves in key order are [1 2].
  • A new root not recorded: after the root split: RootPageID() = 1 (old root 1), header page root = 1: the header page must record the new root.
  • A guard never dropped: page 5 has pin count 1 after the operations returned, want 0: a page guard was not dropped, or a test that runs into its 10-second bound.

Run with a time limit after the regex while you iterate, go test -race -run '^TestBPlusTreeInsert' -timeout 120s ./btree/, so that a loop that never ends is stopped and every goroutine's stack is printed.
