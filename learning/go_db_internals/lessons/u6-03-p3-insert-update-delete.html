P3.2 Insert, Update, and Delete

Write the three modification executors: drain the child, change the table heap, keep every index of the table in step, and return one count row; then see why an update is a delete plus an insert, and how the scan's stop point keeps BusTub clear of the Halloween problem.

With a working scan you can read tables; these three stages let you change them. Lecture #13 says modification operators "are responsible for modifying the target table and its indexes", and that second half is where most bugs hide: an index that still holds a deleted row's key, or a key that points at an old version, gives wrong answers only later, when an index scan uses it. The stages come in the order Insert, Delete, Update, because an update is a delete followed by an insert. Each has its own checkpoint.

Warm-up: retrieval from earlier lessons

Unit 4, Lesson 3: your B+tree already holds key 7. What does Insert(7, rid) do?

  • It replaces the RID stored under 7 and returns true.
  • It stores a second entry for 7 next to the first and returns true.
  • It returns false and leaves the tree unchanged.
  • It panics, because duplicate keys are a programming error.

Unit 6, Lesson 1: an optimized plan reads Update { table_oid=32, target_exprs=["#0.0", "#0.1", "(#0.2+#0.0)"] } over a SeqScan of t1(v1, v2, v3). What does the first target expression, #0.0, do?

  • It sets the new v1 to the old v1, column 0 of the child's tuple.
  • It sets the new v1 to the constant 0.0.
  • It marks column 0 for deletion from the tuple.
  • It reads column 0 of the left input of a join below the update.

Unit 5, Lesson 5: Lecture #13 describes the Halloween problem with an UPDATE over an index scan on salary. What exactly goes wrong?

  • Two concurrent updates overwrite each other's change to the same row.
  • The update deletes the old index entry, and the scan never sees the row at all.
  • The update writes the new salary to the wrong row.
  • The updated row moves ahead of the scan, which finds it again and updates it a second time.

Three executors with one shape

Here are the optimized plans for the three statements, from EXPLAIN (o,s) on a table t1(v1 INT, v2 VARCHAR(100), v3 INT):

Insert { table_oid=32 } | (__bustub_internal.insert_rows:INTEGER)
  Values { rows=2 } | (__values#0.0:INTEGER, __values#0.1:VARCHAR(2), __values#0.2:INTEGER)

Delete { table_oid=32 } | (__bustub_internal.delete_rows:INTEGER)
  SeqScan { table=t1, filter=(#0.0>=3) } | (t1.v1:INTEGER, t1.v2:VARCHAR(100), t1.v3:INTEGER)

Update { table_oid=32, target_exprs=["#0.0", "#0.1", "(#0.2+#0.0)"] } | (__bustub_internal.update_rows:INTEGER)
  SeqScan { table=t1, filter=(#0.0>=3) } | (t1.v1:INTEGER, t1.v2:VARCHAR(100), t1.v3:INTEGER)

Each node has one child that produces the rows to work on, a TableOID naming the table to change, and an output schema of a single INTEGER column. The three executors share a shape:

  • Init looks up the table and its indexes in the catalog, resets the executor's state, and calls the child's Init.
  • The first Next pulls batches from the child until the child returns false, and changes the table and indexes for every tuple. Then it returns true with one tuple, the count row: how many rows it inserted, deleted or updated.
  • Every later Next returns false with an empty batch.

The count row comes back even when the count is 0: CMU's p3.02-insert.slt expects insert into t2 select * from t1 where v1 != v1 to print 0. Build it with table.NewTuple, a one-element slice holding types.NewIntegerValue(int32(count)), and the executor's output schema; its RID is common.RID{}. The writeup adds that a Delete executor is always the root of its plan, and the same holds for Insert and Update in every test, so nothing above them reads the count except the engine.

Draining the child means a loop: the child returns at most batchSize tuples per call, so one call is not enough. TestInsertManyBatches inserts 107 rows, which a Values child returns in 6 batches. Keep two slices in the struct for the child's batches, so that each call reuses them.

The catalog gives you what you need. Catalog().GetTableByOID(plan.TableOID) returns the *catalog.TableInfo (its Table heap, Schema and Name), and Catalog().GetTableIndexes(info.Name) returns a []*catalog.IndexInfo, empty when the table has no index. Look both up in Init.

Keeping the indexes in step

An index stores key tuples, not table tuples. Each IndexInfo has a KeySchema (the key's columns) and an Index whose KeyAttrs() lists, for each key column, which table column it comes from. An index on t(c, b) has KeyAttrs() = [2, 1]. Tuple.KeyFromTuple builds the key from a table tuple:

key := t.KeyFromTuple(info.Schema, idx.KeySchema, idx.Index.KeyAttrs())

The index.Index interface then offers three operations, each a thin adapter over your Project 2 tree (Lesson 4 looks at the adapter in detail):

  • InsertEntry(key, rid) bool adds key → RID, and returns false if the key is already there (your tree's Insert).
  • DeleteEntry(key, rid) removes the key; the RID is ignored, since keys are unique (your tree's Remove).
  • ScanKey(key) []common.RID returns the RID stored under the key, if any (your tree's GetValue).

The writeup promises that the tests "will never insert duplicate rows into tables with indexes", so in Project 3 InsertEntry doesn't return false. Project 4's primary keys use that return value.

Insert

The insert's child produces tuples in the table's schema already: the writeup says "the planner will ensure that the values have the same schema as the table". That is Lecture #13's second choice for INSERT, an operator that inserts whatever tuples its child passes in. For each child tuple:

  1. Append it to the heap with info.Table.InsertTuple(table.TupleMeta{Ts: 0, IsDeleted: false}, t), which returns its new RID. In Project 3 every new tuple has this meta; TestInsertTupleMeta checks it.
  2. For every index of the table, build the tuple's key and InsertEntry it with the new RID.
  3. Count it.

TestInsertUpdatesIndexes creates a one-column index on a and a two-column index on (c, b), inserts three rows, and looks each key up with ScanKey, expecting exactly the RID the row has in the heap.

Delete

A delete's child is a scan, which produces the tuples to delete together with their RIDs. The writeup's hint: "get a RID from the child executor and update the is_deleted_ field of the corresponding TupleMeta". For each child tuple and its RID:

  1. Mark it deleted with info.Table.UpdateTupleMeta(table.TupleMeta{Ts: 0, IsDeleted: true}, rid). The tuple's bytes stay in the page (Unit 1, Lesson 2), which is why your scan checks the meta.
  2. For every index, build the key from the child's tuple and DeleteEntry it.
  3. Count it.

The child's tuple is the old row exactly as stored, so the key you build from it is the key that is in the index. TestDeleteMarksMetaKeepsData reads the deleted tuple back with GetTuple and expects the deleted flag and the original bytes; TestDeleteRemovesIndexEntries expects every deleted row's keys to be gone from both of its indexes, and every live row's keys to still point at their RIDs.

Update is a delete plus an insert

The writeup's hint for UPDATE: "first delete the affected tuple and then insert a new tuple". The plan's TargetExpressions hold one expression per table column, and evaluating them on the child's tuple, with the child's output schema, gives the new row's values. For each child tuple and its RID:

  1. Evaluate every target expression on the old tuple, and build the new tuple from the values with the table's schema.
  2. Mark the old tuple deleted, as Delete does.
  3. Insert the new tuple, as Insert does. It gets a new RID, at the end of the heap.
  4. For every index: DeleteEntry the old tuple's key, then InsertEntry the new tuple's key with the new RID.
  5. Count it.

Step 4 applies to every index, including those whose columns the statement didn't touch. UPDATE t SET a = a + 100 leaves an index on b with the same key, but the row now lives at a new RID, and the old RID is a deleted tuple. An index entry left alone points at the dead version, and an index scan, which skips deleted tuples, then loses the row.

The order inside step 4 matters for the same case. If the key didn't change, inserting first fails, because the key is still there, and the delete that follows removes it: the index loses the key altogether. Here is that bug in the shell, with an index on b and an update of a only:

bustub> CREATE TABLE t(a INT, b INT);
Table created with id = 32
bustub> CREATE INDEX t_b ON t(b);
Index created with id = 0 with type = BPlusTree
bustub> INSERT INTO t VALUES (1, 10), (2, 20);
+-------------------------------+
| __bustub_internal.insert_rows |
+-------------------------------+
| 2                             |
+-------------------------------+
bustub> UPDATE t SET a = a + 100 WHERE a = 1;
+-------------------------------+
| __bustub_internal.update_rows |
+-------------------------------+
| 1                             |
+-------------------------------+
bustub> SELECT * FROM t WHERE b = 10;
+-----+-----+
| t.a | t.b |
+-----+-----+
bustub> SELECT * FROM t;
+-----+-----+
| t.a | t.b |
+-----+-----+
| 2   | 20  |
| 101 | 10  |
+-----+-----+

The full scan finds the row (101, 10); the lookup on b = 10, which the optimizer turns into an index scan once stage 5 is done, doesn't. With the delete first, the same lookup returns the row. TestUpdateUnchangedIndexKey checks exactly this case, and CMU's .slt files don't, so keep the order right from the start.

The Halloween problem in your executors

Unit 5, Lesson 5 described the Halloween problem: an update moves a tuple to where the scan below it will see it again, and the tuple is updated twice. Your update has exactly that setup. Its child scans t1, and every new version goes into t1 too, at the end of the heap, ahead of the scan.

The lecture's fix is to track the record IDs the query has modified. BusTub uses a simpler guard that works because the heap only ever appends: MakeIterator records the last tuple that exists when it is called, and the iterator stops there. Your scan makes its iterator in Init, before the update has inserted anything, so no new version is ever visited. The same guard protects INSERT INTO t1 SELECT * FROM t1, which on a 100-row table inserts exactly 100 rows.

The protection lives in the scan, so your update needs no extra bookkeeping. But it explains what you'll see if the scan is wrong. With an iterator that runs to the current end of the heap (MakeEagerIterator), TestUpdateHalloween, which runs v = v + 1 over 600 rows in an 8-frame pool, never finishes:

--- FAIL: TestUpdateHalloween (30.01s)
    update_executor_test.go:108: updating every row: first Next did not return within 30s: a page latch (or an index iterator) is probably never released, or the executor loops forever

CMU's p3.03-update.slt passes with the same bug. Its tables hold 5 or 10 rows, so the update's first batch from the scan takes every row before anything is inserted, and the scan is at its end before the first new version exists. It takes more rows than one batch, and new versions on pages the scan hasn't reached yet, to show the problem; that is why the unit test uses 600.

Check your understanding

On a table t1 with five rows, INSERT INTO t2 SELECT * FROM t1 WHERE v1 != v1 runs. What does the insert executor's first Next call return?

  • False with an empty batch, since nothing was inserted.
  • True, with one tuple holding the INTEGER 0.
  • True, with one tuple holding 5, the number of rows scanned.
  • True, with an empty batch.

A table t(a, b) has an index on b. Your update handles UPDATE t SET a = 7 WHERE a = 1 by skipping every index whose key didn't change. What does a later index lookup on that row's b return?

  • The old version of the row, with a = 1.
  • The new version of the row, since the key is the same.
  • It panics, because the index entry is stale.
  • No row: the index points at the deleted old version, which the index scan skips.

For the same update, your code updates every index, but with InsertEntry(new key, new RID) first and DeleteEntry(old key) second. The key in the index on b didn't change. What is in that index afterwards?

  • Nothing for that key: the insert was rejected as a duplicate, and the delete then removed it.
  • The key with the new RID, because InsertEntry overwrote the old one.
  • The key twice, once with each RID.
  • The key with the old RID, unchanged.

A table holds 600 rows over many pages. Its scan uses an iterator that runs to the current end of the heap instead of stopping where the table ended at Init. What does UPDATE t SET v = v + 1 do?

  • It updates each row once, because new versions are inserted behind the scan.
  • It stops with an error the first time it meets a row it already updated.
  • It keeps finding the versions it inserted and never finishes.
  • It updates the first batch of 20 rows only.

After DELETE FROM t WHERE a = 1 removes one row, a test reads that row's RID with info.Table.GetTuple(rid). What does it get?

  • A zero-filled tuple, because the delete erased the bytes.
  • The original tuple, with IsDeleted set in its meta.
  • A panic: "Tuple ID out of range".
  • The next tuple in the page, which moved into the freed slot.

Build it: insert (stage P3.2a)

You edit execution/insert_executor.go. Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • Init looks up the table and its indexes, resets the executor, and initializes the child.
  • The first Next drains the child, inserts every tuple with TupleMeta{Ts: 0, IsDeleted: false}, adds its key to every index with the new RID, and returns true with one INTEGER count row, 0 included. Every later Next returns false with an empty batch.
  • Clear the output slices on every call, and return the child's errors.
  • What to think about

    What does Next need to remember between its first call and the next one? What must a second Init reset so that the executor reports a new count? Where does the list of indexes come from, and what key does it use?

    The approach

    Keep the *catalog.TableInfo, the []*catalog.IndexInfo, a done flag and two slices for the child's batches in the struct. In Init, get the table with GetTableByOID (an error if it is nil), its indexes with GetTableIndexes(info.Name), set done to false, and return the child's Init().

    One key fragment 
    e.indexes = e.ExecutorContext().Catalog().GetTableIndexes(info.Name)
e.done = false
return e.child.Init()
  • What to think about

    How many times do you call the child's Next, and what tells you to stop? What do you return the second time your Next is called? Which schema does the count tuple use?

    The approach

    Clear the output slices. If done, return false. Otherwise loop: call the child's Next into your two slices; on an error return it; on false leave the loop. For each tuple in the batch, call InsertTuple with the Project 3 meta and keep the RID for the next task; count it. After the loop set done, append the count tuple and a zero RID, and return true.

    One key fragment 
    count := table.NewTuple([]types.Value{types.NewIntegerValue(int32(n))}, e.OutputSchema())
*tuples = append(*tuples, count)
*rids = append(*rids, common.RID{})
  • What to think about

    An index on (c, b) stores a key tuple with two columns in that order. What tells you which table columns go into the key, and in which order? Which RID belongs in the index: the child's, or the heap's?

    The approach

    For each IndexInfo, build the key with KeyFromTuple from the table's schema, the index's KeySchema and Index.KeyAttrs(), then call Index.InsertEntry with the RID that InsertTuple returned. The child's RID means nothing here: Values tuples carry the zero RID.

    One key fragment 
    key := t.KeyFromTuple(e.tableInfo.Schema, idx.KeySchema, idx.Index.KeyAttrs())
idx.Index.InsertEntry(key, rid)

Build it: delete (stage P3.2b)

You edit execution/delete_executor.go. The rules are the insert's, with a different change per tuple: mark the tuple at the child's RID deleted with TupleMeta{Ts: 0, IsDeleted: true}, and remove its key from every index. The count row counts deleted rows.

  • What to think about

    Which slice tells you where each tuple to delete lives? What happens to the tuple's bytes? How is Init different from the insert's?

    The approach

    Init is the insert's Init. In Next, drain the child the same way; for tuple i of a batch, its RID is element i of the child's RID slice. Call UpdateTupleMeta on the heap with the deleted meta and that RID, and count. The bytes stay where they are.

    One key fragment 
    rid := e.childRIDs[i]
e.tableInfo.Table.UpdateTupleMeta(table.TupleMeta{Ts: 0, IsDeleted: true}, rid)
  • What to think about

    Where do you get the column values to build the key from, now that the tuple is marked deleted? Is it the same key that the insert put in the index?

    The approach

    The child's tuple is the row as stored, so build each index's key from it exactly as the insert did, and call DeleteEntry with the key and the RID (the adapter ignores the RID; keys are unique).

    One key fragment 
    idx.Index.DeleteEntry(t.KeyFromTuple(schema, idx.KeySchema, idx.Index.KeyAttrs()), rid)

Build it: update (stage P3.2c)

You edit execution/update_executor.go; the struct already has a tableInfo field. Per child tuple: compute the new tuple from TargetExpressions, mark the old tuple deleted, insert the new one, and in every index delete the old key and then insert the new key with the new RID. The count row counts updated rows.

  • What to think about

    How many target expressions are there, and which column of the new tuple does each one give? Which schema describes the tuple the expressions read, and which one lays out the tuple you build?

    The approach

    Init is the insert's. In Next, drain the child as before. For each old tuple, evaluate every expression of e.plan.TargetExpressions with Evaluate(&old, e.child.OutputSchema()), collect the values in order, and build the new tuple with table.NewTuple(values, e.tableInfo.Schema).

    One key fragment 
    for _, expr := range e.plan.TargetExpressions {
	values = append(values, expr.Evaluate(&old, e.child.OutputSchema()))
}
  • What to think about

    Why not overwrite the tuple in place? (A new value can have a different size, and the writeup asks for delete-then-insert.) Which two RIDs do you have afterwards, and which steps need each?

    The approach

    Mark the old RID deleted with UpdateTupleMeta, as the delete does, then InsertTuple the new tuple with the Project 3 meta and keep the RID it returns. Count the row. The scan below won't revisit the new version, because its iterator stopped growing at Init.

    One key fragment 
    heap.UpdateTupleMeta(table.TupleMeta{Ts: 0, IsDeleted: true}, oldRID)
newRID, _ := heap.InsertTuple(table.TupleMeta{Ts: 0, IsDeleted: false}, updated)
  • What to think about

    If the statement didn't touch an index's columns, what still changed for that index? What happens if you insert before you delete and the key is the same?

    The approach

    For each index, build the old key from the old tuple and the new key from the new tuple, both with the table's schema. Call DeleteEntry on the old key first, then InsertEntry on the new key with the new RID. Do it for every index, without comparing the keys.

    One key fragment 
    idx.Index.DeleteEntry(old.KeyFromTuple(schema, idx.KeySchema, attrs), oldRID)     // first
idx.Index.InsertEntry(updated.KeyFromTuple(schema, idx.KeySchema, attrs), newRID) // then

Idiom

All three executors keep the child's batches in two slices stored in the struct and pass pointers to them on every call: e.child.Next(&e.childTuples, &e.childRIDs, batchSize). The child clears them with [:0] and appends, so after the first few calls no batch allocates, as with BusTub's reused std::vector. Don't keep a pointer into a child batch, such as &e.childTuples[i], past the next call: that call overwrites the slice's elements. A table.Tuple value copied out of the slice stays valid, because a tuple's bytes are never modified.
