P2.7 Tombstones

Implement Fall 2025's leaf tombstone buffer: delay deletions, apply the oldest when the buffer is full, revive a tombstoned key on insertion, and keep every tombstone attached to its entry, in the right order, through splits, borrows and merges.

So far a deletion removes the entry from its leaf at once. Fall 2025's Project 2 adds a twist that Unit 3 previewed: a leaf can postpone its deletions, keeping the entry in place and recording its index in a small buffer of pending deletes. This stage builds it, and most of the work is bookkeeping. The buffer stores positions in the leaf, every insertion, removal, split, borrow and merge moves entries around, and each pending delete has to follow its entry while the leaf remembers which one came first.

Warm-up: retrieval from earlier lessons

Unit 3, Lesson 1: a linear-probe hash table deletes keys with tombstones. What does a lookup do when it reaches a tombstone?

  • It stops, because the key it looks for can't be further along.
  • It treats the slot as occupied and keeps scanning.
  • It removes the tombstone and stops, since the slot is now free.
  • It returns the deleted entry's value, marked as deleted.

Unit 3, Lesson 5: in a write-optimized B+tree (a Bε-tree), an inner node's mod log holds "Delete 10", while the leaf below still holds 10. What must a search for 10 do?

  • Go straight to the leaf and return 10, because leaves hold the data.
  • Apply every pending change on its path first, then search the leaf.
  • Fail, because the tree is inconsistent until the mod log is flushed.
  • Check the mod logs on its way down, find the pending delete, and report 10 as absent.

A small buffer of pending deletes

The writeup describes the buffer in one paragraph: it "stores the last k indexes of entries in key/value arrays that have been deleted. Thus, when a key is deleted from the index (if k > 0) its entry in its corresponding leaf page is not actually deleted but the index is appended to the tombstone buffer. Only when the buffer of said leaf page has k entries in it is the oldest buffered deletion actually applied to the key/value arrays. This is a simplified version of the Bε-tree discussed in the lectures." A tombstone, here, is one of those buffered indexes: a delete that has been recorded but not yet applied. Unit 3's Bε-tree buffered changes in the inner nodes and pushed them down later; Project 2 buffers only deletions, only in the leaf that holds the key, and applies them in the order they arrived.

The buffer's size k comes from Options.NumTombs, through the pre-built LeafPageTombCount: 0 means no tombstones, so deletions are applied at once as in stages 5 and 6, and a negative value means LeafPageDefaultTombCount, which is 0 in the starter. In the page, the buffer is num_tombstones_ (8 bytes at offset 16) followed by k slots of 8 bytes, each holding an index into the key and RID arrays; Lesson 1 laid them out. How you order the indexes in those slots is up to you. What is tested is Tombstones(), which must return the tombstoned keys "in order of recency (oldest at front)", and KeyAt, which must keep returning the physical entry "regardless of whether a tombstone exists for that entry".

#08 B+Trees, "B+ tree optimizations" (1:07:57), slides 56–57: the write-optimized B+tree, whose mod logs delay inserts and deletes, the idea the tombstone buffer simplifies.

The rules

The doc comments of BPlusTreeLeafPage, Insert and Remove fix the behaviour the tests check:

  • Deleting a live key appends its index to the buffer as the newest tombstone. If the buffer already holds k, the oldest tombstone is applied first: its entry is physically removed, which shifts the entries after it, so the new tombstone's index may drop by one.
  • Removing a key that is already tombstoned does nothing, as does removing an absent key.
  • GetValue treats a tombstoned key as absent. So will the iterator in stage 8.
  • Inserting a tombstoned key revives it: the tombstone goes away, the RID is replaced by the new one, and Insert returns true. Inserting a live key still returns false.
  • Size counts physical entries, tombstoned or not, and underflow is decided on physical sizes. A deletion that only adds a tombstone can't make a leaf underflow; applying the oldest tombstone can.
  • A root leaf whose entries are all tombstoned stays, and the tree is not empty. IsEmpty reads the header page, which still names that root.

A trace with NumTombs = 2 on the root leaf (|1,2,3,4,5,6), in the test's notation, where tombstoned keys are listed before the |, oldest first:

OperationLeaf afterwardsWhy
Remove 5(5|1,2,3,4,5,6)the buffer has room: 5 stays, tombstoned
Remove 1(5,1|1,2,3,4,5,6)the buffer is now full
Remove 3(1,3|1,2,3,4,6)the oldest, 5, is applied first; then 3 is tombstoned
Remove 3, Remove 9(1,3|1,2,3,4,6)already tombstoned, and absent: no change

Indexes that follow their entries

The buffer stores positions, and positions change. Inserting an entry at index i moves every entry from i on one slot to the right, so every tombstone index ≥ i must grow by one. Removing the entry at i moves the later ones left, so tombstone indexes above i drop by one, and the removed entry's own tombstone, if it has one, disappears. If these two helpers keep the buffer right, every operation built on them does too. The random-mix test, TestBPlusTreeTombstoneRandomMix, catches a helper that forgets: within a few hundred operations, a tombstone ends up on the wrong key, and the check reports tombstone on key ..., which is not an entry of the leaf or has two tombstones or a live key the model says is gone.

Moving entries between leaves needs one more rule. A split moves the upper half of a leaf into a new, empty leaf, and the tombstones of the moved entries go with them, renumbered, in the same relative order. TestBPlusTreeTombstoneSplit deletes 3, 2 and 0 from a leaf holding 0 to 3 (buffer 3), then inserts 4, which splits it into (0|0,1) and (3,2|2,3,4): each half keeps its own tombstones, oldest first. Borrows and merges move entries into a leaf that may already have tombstones, and the writeup says whose come first: "When a leaf is coalesced or redistributed into another leaf we consider all of its pending deletions to be more recent than any pending deletion in the recipient leaf (in other words: the node with entries being inserted into it should have its tombstones processed first)." Arriving tombstones go to the back of the receiving buffer. If the buffer then holds more than k, the oldest are applied until it fits, and those are the receiving leaf's own.

A merge with buffers of 1, leaf max size 4, starting from (3,5) / (|1,2) (|3,4) (|5,6):

  1. Remove 3, then 1: two tombstones, one per leaf, (3,5) / (1|1,2) (3|3,4) (|5,6).
  2. Remove 2: the first leaf's buffer is full, so the tombstone on 1 is applied, leaving [2], and 2 is tombstoned: (2|2). One entry is below the min size of 2.
  3. The right sibling (3|3,4) is at its minimum, so it merges into (2|2). Its tombstone on 3 arrives as the newest, the buffer holds two in a slot of one, and the oldest, 2, the receiving leaf's own, is applied.

The result is (5) / (3|3,4) (|5,6).

A borrow can leave the receiving leaf still underflowing. If the borrowed entry is tombstoned and the receiver's buffer is full, the arriving tombstone pushes out one of the receiver's own, whose entry is then removed. The doc comment of Remove says what to do: "If a page still underflows after a borrow (a tombstoned entry arrived and pushed out one of the page's own), apply the rules again." TestBPlusTreeTombstoneBorrowRepeats builds exactly this: the leaf borrows the tombstoned 4, loses 2 to the push-out, and borrows again, ending at (6) / (3,4|3,4,5) (|6,7,8).

Idiom

The buffer lives in the page bytes, but the logic is easier on a Go slice. Two small helpers make the rest of the stage short: one that reads the buffer into a []int of entry indexes, oldest first, and one that writes such a slice back and sets the count. Inside them, the slice is ordinary Go: append to add the newest, recs[1:] to drop the oldest, a loop to shift indexes. The page view still keeps no state of its own, as Lesson 1 required: the slice exists only for the length of one method call, and the page bytes stay the only copy. The tests evict pages through a 12-frame pool in TestBPlusTreeTombstoneRandomMix to make sure tombstones survive the trip to disk.

  • Insert returns true and adds a second entry for 1, next to the tombstoned one.
  • Insert returns false, because the key is still in the leaf.
  • Insert returns true and removes the tombstone, but GetValue(1) still returns the old RID.

Buffers of 1, leaf max size 4. The tree is (3,5) / (1|1,2) (3|3,4) (|5,6), and 2 is removed. What is the tree afterwards?

  • (5) / (2|2,4) (|5,6)
  • (3,5) / (1,2|1,2) (3|3,4) (|5,6)
  • (3,5) / (2|2) (3|3,4) (|5,6)
  • (5) / (3|3,4) (|5,6)

Buffers of 2, leaf max size 4 (min size 2). A non-root leaf (3|3,4) holds two entries, one of them tombstoned. Removing the live key 4 does what?

  • It applies the tombstone on 3, removes 4, and the leaf underflows.
  • It adds a tombstone on 4; the leaf, (3,4|3,4), keeps its size of 2 and doesn't underflow.
  • It adds a tombstone on 4, and the leaf underflows because it has no live entries left.
  • It deletes the leaf, since all its keys are deleted.

Build it: the tombstone buffer (stage P2.7)

You edit btree/b_plus_tree_leaf_page.go (the buffer and the entry helpers) and btree/b_plus_tree.go (GetValue, Insert, Remove). Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • The buffer holds at most LeafPageTombCount(NumTombs) entry indexes. With 0, deletions are applied at once, as before.
  • Deleting a live key appends a tombstone; if the buffer is full, the oldest is applied first. A tombstoned or absent key: no change.
  • A tombstoned key is absent for GetValue, and Insert revives it with the new RID and returns true.
  • Tombstone indexes follow their entries through every insertion, removal and move. Moved tombstones keep their order; tombstones arriving in a leaf by a borrow or merge are newer than its own, and overflow applies the oldest.
  • Sizes are physical. If a leaf still underflows after a borrow, repair it again.
  • What to think about

    How many bytes is the count, and how many is each slot? What should the writing helper do if it is handed more indexes than the buffer can hold? Which operations does the rest of the stage need: check whether an index is tombstoned, add the newest, remove one, take the oldest?

    The approach

    The reading helper reads the count with binary.LittleEndian.Uint64 at numTombstonesOffset, then that many 8-byte values at tombstoneOffset(i), into a []int. The writing helper stores each value and then the count, and panics if the slice is longer than the view's buffer size. Build the small operations on top of the two. Tombstones() from stage 1 may already do the reading; it must return KeyAt of each index, in buffer order.

    One key fragment 
    binary.LittleEndian.PutUint64(p.data[p.tombstoneOffset(i):], uint64(recs[i])) // slot i, oldest first
binary.LittleEndian.PutUint64(p.data[numTombstonesOffset:], uint64(len(recs)))
  • What to think about

    After an insertion at i, which tombstone indexes point at a different entry than before? After a removal at i, which ones do, and what happens to a tombstone that pointed at i itself? Does either helper change the order of the buffer?

    The approach

    In insert-at: after shifting the entries, add 1 to every buffered index ≥ i. In remove-at: drop a buffered index equal to i, and subtract 1 from every index > i, keeping the others in their order. Skip the work when the count is 0, so trees without tombstones pay nothing.

    One key fragment 
    for j, r := range recs {
	if r >= index { // the entry moved one slot right
		recs[j] = r + 1
	}
}
  • What to think about

    When the oldest tombstone is applied, its entry leaves the page. Where was it relative to the key you are deleting now, and what happens to that key's index? Which of the two can make the leaf underflow, and does the stage-6 repair still run afterwards?

    The approach

    In GetValue, after a match, return false if the index is tombstoned. In Remove, return early if the key is absent or tombstoned. With a buffer size of 0, remove the entry as before. Otherwise, if the buffer is full, take the oldest index off the buffer, remove that entry with remove-at, and if it was before the key's index, lower the key's index by one; then append the key's index. Run the stage-6 underflow repair on the leaf afterwards in every case: it does nothing when the size didn't drop.

    One key fragment 
    leaf.removeAt(oldest)
if oldest < index { // everything after oldest moved left
	index--
}

    Run go test -race -run '^TestBPlusTreeTombstone(DeleteMarksEntry|BufferOverflow|Disabled)$' ./btree/. They check that a deletion keeps the entry, that repeated and absent removals change nothing, that an all-tombstoned root leaf stays, the overflow order, and that NumTombs 0 and −1 delete at once.   • What to think about

    Your duplicate check finds the key in the leaf. What distinguishes a duplicate from a revive? Does a revive change the leaf's size, and can it cause a split?

    The approach

    Where Insert finds the key already in the leaf, check whether its index is tombstoned. If it is, remove that index from the buffer (keeping the others in order), overwrite the RID with SetValueAt, and return true. The size doesn't change, so no split follows. Otherwise it is a real duplicate: return false.

    One key fragment 
    if found && leaf.isTombstoned(index) {
	// drop its tombstone, SetValueAt(index, value), return true
}
    Checkpoint: reinsertion

    Run go test -race -run '^TestBPlusTreeTombstoneReinsert$' ./btree/. It removes 2, inserts it again with a new RID, and expects true, no tombstone, three entries and the new value; inserting the live 3 must return false. Success prints ok intro_to_db/btree.

  • What to think about

    Which of the source's tombstones belong to the moved range, and what are their indexes in the destination? What happens to the source's other tombstones, and to the destination's tombstones whose entries shift to make room? When the destination's buffer overflows, whose tombstones go first, and what does applying one do to the destination's size?

    The approach

    Before copying, split the source's buffer into the moved range's indexes (renumbered as r − from + at, in order) and the rest (renumbered for the gap the move leaves). Shift the destination's indexes ≥ at by the number of moved entries, then append the moved ones at the back. Copy the entries and fix both sizes. While the destination's list is longer than its buffer, remove the entry of the oldest index and renumber. Write both buffers back. Splits, borrows and merges all use this helper, so they all follow the rules. In the leaf repair, turn "borrow once" into "borrow while the leaf is below MinSize and the sibling is above it", then merge if it still underflows.

    One key fragment 
    for len(dstRecs) > dst.tombCount { // arrivals are newest: dst's own go first
	// remove entry dstRecs[0] from dst, drop it, renumber the rest
}
