HW1 Hands-On, Part 1: DuckDB, the Lahman Database, and Q1–Q3

Set up DuckDB and CMU's baseball dataset on a Mac, find your way around its eleven tables, and answer the first three questions of Homework #1 with DISTINCT, aggregation, CTEs and a correlated subquery.

CMU's Homework #1 asks six questions about the Lahman baseball database, and each answer must be a single SQL statement. The data is real, about 180,000 rows in eleven tables. Some first names are NULL, and several tables hold many rows per player, so a careless join repeats people. Lesson 4 covers the last three questions.

Install DuckDB and get the data

Homework #1 runs on DuckDB, the engine you installed in Lesson 2. If you skipped that step, install it now. Then download the dataset, check it, and unpack it into a folder of its own:

brew install duckdb
mkdir -p ~/cmu-db/hw1 && cd ~/cmu-db/hw1
curl -LO https://15445.courses.cs.cmu.edu/fall2025/files/lahman-cmudb2025.db.gz
md5 lahman-cmudb2025.db.gz        # MD5 (lahman-cmudb2025.db.gz) = a4fb302c11f80030f26bb6bb59d68cac
tar -xzf lahman-cmudb2025.db.gz   # unpacks lahman-cmudb2025.db, about 40 MB
mv lahman-cmudb2025.db lahman.db
cp lahman.db lahman-pristine.db   # a clean copy, because Q6 changes the database
  • curl -LO downloads the same file as the HW page's wget, which macOS doesn't ship. The page checks the file with md5sum; md5 on macOS computes the same hash, and it must be a4fb302c11f80030f26bb6bb59d68cac.
  • Despite its name, lahman-cmudb2025.db.gz is a gzipped tar archive, not a gzipped database. gunzip alone would leave a tar file that DuckDB can't open; tar -xzf decompresses and unpacks it in one step, as the HW page's tar zxf does. If a small ._lahman-cmudb2025.db file appears as well, it is macOS metadata from whoever built the archive. Ignore it.
  • The HW page also says "You can start with using SQLite." That line is outdated: the file is a DuckDB database, and SQLite rejects it as "not a database". Use DuckDB throughout.

Open the database

duckdb lahman.db

DuckDB prints a banner with its version and waits for input. CMU's transcript shows version 1.3.2; Homebrew will give you a newer one, which is fine, since the official answers produce the same output on DuckDB 1.5.6:

DuckDB v1.3.2 (Ossivalis) 0b83e5d2f6
Enter ".help" for usage hints.

Commands that start with a dot are commands of the shell itself, not SQL, and they take no semicolon. The HW page uses .tables to list the eleven tables:

.tables
appearances     collegeplaying  leagues         schools
awardsmanagers  divisions       managers        teams
awardsplayers   halloffame      people

The SQL statement SHOW TABLES; lists the same names. To see a table's columns, types, nullability and key columns, use DESCRIBE:

DESCRIBE appearances;

│ column_name │ column_type │  null   │   key   │ default │  extra  │
│   varchar   │   varchar   │ varchar │ varchar │ varchar │ varchar │
├─────────────┼─────────────┼─────────┼─────────┼─────────┼─────────┤
│ yearID      │ SMALLINT    │ NO      │ PRI     │ NULL    │ NULL    │
│ teamID      │ VARCHAR     │ NO      │ PRI     │ NULL    │ NULL    │
│ lgID        │ VARCHAR     │ YES     │ NULL    │ NULL    │ NULL    │
│ playerID    │ VARCHAR     │ NO      │ PRI     │ NULL    │ NULL    │
│ G_all       │ SMALLINT    │ YES     │ NULL    │ NULL    │ NULL    │
│ G_batting   │ SMALLINT    │ YES     │ NULL    │ NULL    │ NULL    │
│ HR          │ SMALLINT    │ YES     │ NULL    │ NULL    │ NULL    │
└─────────────┴─────────────┴─────────┴─────────┴─────────┴─────────┘

The three PRI columns form the primary key: one row per player, per team, per year. G_all is the number of games played, G_batting the games batted, and HR the home runs hit. As a sanity check, SELECT count(*) FROM appearances; should print 115355.

A tour of the schema

The database declares its primary and foreign keys, so you can read the join paths straight from the schema. DESCRIBE marks the primary key; to list a table's foreign keys, run SELECT constraint_type, constraint_column_names, referenced_table FROM duckdb_constraints() WHERE table_name = 'appearances';. These are the eleven tables, with the columns the homework uses:

TableRowsPrimary keyHolds
people21,271playerIDone row per person: nameFirst, nameLast, nameGiven, birth and death details
appearances115,355(yearID, teamID, playerID)a player's season with one team: lgID, G_all, G_batting, HR
teams3,075(yearID, lgID, teamID)a team's season: franchID, divID, teamRank, name, attendance
leagues8lgIDthe league's full name in league, and active: 'Y' for AL, NL and ML, 'N' for the five inactive ones
divisions11(divID, lgID)division (such as "AL East") and active
awardsplayers12,632none declaredone row per award won: awardID, yearID, lgID, playerID
awardsmanagers228(playerID, awardID, yearID, lgID)awards won by managers
managers3,786(yearID, teamID, inseason)who managed each team in each season
halloffame6,283(playerID, yearid, inducted)Hall of Fame candidates by year; inducted is 'Y' or 'N'
collegeplaying17,340noneone row per player, per school, per year
schools1,207schoolIDname_full, city, state, country

The join paths follow the declared foreign keys:

  • Every table about a person joins people on playerID: appearances, collegeplaying, both award tables, managers and halloffame.
  • collegeplaying joins schools on schoolID.
  • appearances and managers join teams on (yearID, lgID, teamID), and teams joins divisions on (divID, lgID).
  • The two award tables and divisions declare lgID as a foreign key to leagues. teams, appearances and managers declare no such key, but every lgID they hold exists in leagues, so they join it on lgID too.
  • An award row has no team. A player's team in an award year comes from appearances (same player and year), and a manager's team from managers.

Pitfall: repeating rows

collegeplaying has one row per player per school-year, so a player who spent four seasons at one school appears four times. Bobby Higginson, Q2's first row, played four seasons at Temple. Any join through this table repeats his other columns four times, exactly as Lesson 2's joins repeated RZA and Taylor.

The HW page's DESCRIBE awardsplayers marks all four columns as the primary key, with lgID not null. In the database you download, awardsplayers has no primary key and lgID allows NULL. The HW page also has a diagram of these tables.

How you'll run and check each answer

Write each answer in its own file in ~/cmu-db/hw1: q1.sql, q2.sql and so on. The homework allows exactly one SQL statement per answer. Run a file from the terminal, or from inside the shell:

duckdb lahman.db < q1.sql     # from the terminal
.read q1.sql                  # inside the duckdb shell

In the interactive shell, results print as a box-drawn table, like the DESCRIBE output above. The HW page writes rows pipe-separated instead (Ichiro|SEA|10); inside the shell, .mode list switches to that form, and .quit leaves the shell.

If .read, .mode list or .quit behaves differently in your DuckDB version, .help lists the dot commands it supports. Ctrl-D also leaves the shell.

DuckDB locks the database file. While a shell has lahman.db open, running duckdb lahman.db < q2.sql in a second terminal fails with "Could not set lock on file". Use .read in the open shell, or quit the shell first.

CMU grades by comparing your output with the official answer's using a diff-like function. Column order matters but column names don't, and each question spells out its sort order and tie-breakers, which decide the rows that survive a LIMIT. Names in Q2 (and later Q5) are built as {FIRST} ({GIVEN}) {LAST} from nameFirst, nameGiven and nameLast. CMU's own students submit the files under longer names, such as q1_sample.duckdb.sql, to Gradescope; this course doesn't need a submission.

    Details: List all active divisions ordered alphabetically.

  • Find ten people with the highest home-runs (HR) in any single appearance, irrespective of year or team. Only consider people who have played at some point for a school in PA. Order the results from most to least home runs, and then by first name alphabetically.

    Hints: The || might be useful for constructing the name field. The name should be assembled as {FIRST} ({GIVEN}) {LAST}. A player's highest home-runs in any appearance can be found by aggregating over all years and teams of a given player's appearances.

    Your output should look like this: name|max_hr_appearance

    Your first row should look like this: Bobby (Robert Leigh) Higginson|30

    What to think about

    You need three facts per person, and each lives at a different grain. Whether they played for a school in PA comes from collegeplaying (one row per school-year), their best single appearance from appearances (one row per team-year), and their name from people (one row per person). Which of these joins can repeat a person, and what does a repeat do to a top-ten list?

    The approach

    Build three pieces, ideally as CTEs: the distinct playerIDs linked through collegeplaying to a school whose state is 'PA'; each player's maximum HR over all of their appearances; and the names from people. Join the pieces on playerID, build the name with ||, sort by the maximum descending and then by nameFirst, and keep ten rows.

    One key fragment 
    SELECT DISTINCT … playerID …   -- each PA player once
MAX(HR) … GROUP BY playerID    -- best single appearance
nameFirst || ' (' || nameGiven || ') ' || nameLast
    Checkpoint

    Run duckdb lahman.db < q2.sql (or .read q2.sql). Expect 10 rows; the first five are:

    name|max_hr_appearance
Bobby (Robert Leigh) Higginson|30
Harry (Harry Walter) Anderson|23
Dick (Richard Edward) Gernert|21
Mark (Mark Thomas) DeRosa|21
Matt (Matthew James) Adams|20

    The tie at 21 tests the tie-breaker: Dick sorts before Mark. If Higginson fills several of the first rows, a join through collegeplaying is repeating him. If his number is 187, you summed his home runs instead of taking the maximum.

  • Find ten (player, team) pairs where the player won the Gold Glove award in an active league after 1999 and batted in more games than the player's team's average since 1999. Order by the number of distinct award-winning years from most to least, and then by given name alphabetically.

    Hints: Only consider awardID that matches Gold Glove. The team average can be computed by taking the average over the batted games by each team player's appearances since 1999. You might find Correlated Subqueries in DuckDB useful.

    Your output should look like this: nameGiven|teamID|distinct_years

    Your first row should look like this: Ichiro|SEA|10

    What to think about

    Each award row raises three questions. Was it a Gold Glove after 1999, in an active league? Which team did the player appear for that year, and in how many games did he bat? (awardsplayers has no team column.) And what is that team's average G_batting since 1999? The last number depends on the team of the row being tested, so it can't be a single fixed value.

    The approach

    Join awardsplayers (Gold Glove, yearID after 1999) to leagues (active = 'Y') and to the player's appearances in the same year and league. Keep the rows whose G_batting beats a correlated subquery that averages G_batting over every appearance of the same team since 1999. Group by given name and team, count the distinct award years, sort by that count descending and then by nameGiven, and keep ten rows.

    One key fragment 
    G_batting > (SELECT AVG(G_batting) FROM appearances AS a2
             WHERE a2.teamID = <outer appearances>.teamID AND <since 1999>)
    Checkpoint

    Run duckdb lahman.db < q3.sql (or .read q3.sql). Expect 10 rows; the first five are:

    nameGiven|teamID|distinct_years
Ichiro|SEA|10
Yadier Benjamin|SLN|9
Alex Jonathan|KCA|8
Andruw Rudolf|ATL|8
Nolan James|COL|8

    The three 8s test the tie-breaker on given name. If Andruw Rudolf shows 9, you included the 1999 awards: "after 1999" means yearID > 1999. For the team average, the official answer also uses yearID > 1999, though >= 1999 gives the same ten rows. Comparisons are case-sensitive, so 'gold glove' matches nothing.

    The top ten can't confirm your batting filter, because the pairs it removes all fall below the first ten. To check it, run the query without its LIMIT: the official answer then returns 223 rows.

Check your understanding

In DuckDB, what does SELECT 'Bobby' || ' (' || NULL || ') ' || 'Higginson'; return?

  • 'Bobby () Higginson'
  • NULL
  • 'Bobby (NULL) Higginson'
  • An error, because || can't take a NULL operand

apps(team, player, g) holds (SEA, a, 150), (SEA, b, 50), (SEA, c, 100), (NYA, d, 30) and (NYA, e, 50). Which players does SELECT player FROM apps AS o WHERE g > (SELECT AVG(g) FROM apps AS i WHERE i.team = o.team); return?

  • a and c
  • a only
  • None: the query fails, because the inner query references the outer alias o
  • a and e

college(playerID, schoolID, yearID) has three rows for player p1, all at the same school, and one row for p2. stats(playerID, max_hr) has one row per player. What does SELECT c.playerID, s.max_hr FROM college AS c JOIN stats AS s ON c.playerID = s.playerID; return?

  • 4 rows, 3 of them for p1
  • 2 rows, one per player
  • 8 rows, one per pairing of the two tables
  • An error, because playerID repeats in college
