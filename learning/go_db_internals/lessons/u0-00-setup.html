Database Internals in Go · Unit 0 · Lesson 0

Setup: Sparse Checkout, Go, and a Tour of the Code

Get only this course's Go code onto your Mac, confirm the toolchain works, and learn where each of CMU's four projects lives in the codebase.

CMU's 15-445/645 projects are built on BusTub, a small disk-oriented relational database written in C++ for teaching. This course ports BusTub to Go as one module, intro_to_db, which lives inside the same repository as these lessons. The repository also holds every other course, so you'll download only the code directory. After that, a quick tour shows which packages are already built and which ones you'll write yourself.

What you'll build

A disk-oriented database keeps its data in fixed-size pages on disk and brings them into memory only as needed. BusTub layers its components so that each layer talks only to the one below it. The four CMU projects are four of those layers, built from the bottom up:

Everything else comes pre-built, so your time goes into the four projects. That includes the shared types in common/, the disk manager in storage/disk/, and, from Unit 6, the SQL front end. The front end runs the real Postgres parser through pg_query_go, then a binder, planner and optimizer, so later units can run actual SQL against your executors. Today the module holds only what Project 1 needs. Each later unit's packages arrive with a git pull (see Getting later units' code).

Idiom

The Go code keeps BusTub's names and structure and uses Go idioms where C++ ones don't carry over. Four mappings come up throughout the course:

  • An RAII guard, whose destructor releases a pin or latch when the object goes out of scope, becomes an explicit Drop() method that you call with defer guard.Drop().
  • std::promise<bool> and std::future, a one-shot "this I/O finished" signal, become a capacity-1 chan bool.
  • std::optional<T> becomes Go's (T, bool) return pair.
  • Latches (std::mutex, std::shared_mutex) become sync.Mutex and sync.RWMutex.

Tools on your Mac

You need three things, installed once:

  • The Xcode Command Line Tools, which provide git and the C compiler. Go's cgo needs that compiler for the Postgres parser in Unit 6. Check with xcode-select -p; if it prints an error, run xcode-select --install.
  • Go 1.24 or newer. Check with go version, and install or upgrade with brew install go or the macOS package from go.dev/dl. If your Go is at least 1.21 but older than 1.24, the go command downloads the right toolchain the first time you build, because go.mod asks for 1.24.
  • Git access to the private repository. If you already clone GitHub repositories over SSH, you're set. Otherwise run brew install gh, then gh auth login, and answer "yes" to Authenticate Git with your GitHub credentials. HTTPS clones then work without a password prompt.

Get the code: a shallow, sparse checkout

Pick a parent folder; this lesson uses ~/code. Run these four commands exactly:

mkdir -p ~/code && cd ~/code
git clone --depth 1 --filter=blob:none --sparse git@github.com:yannpaul/learning_with_teach.git
cd learning_with_teach
git sparse-checkout set go_db_internals/intro_to_db

If you use HTTPS instead of SSH, swap the URL in the second command for https://github.com/yannpaul/learning_with_teach.git. Everything else is identical.

Each flag does one job:

  • --depth 1 downloads only the latest commit, not the repository's history.
  • --filter=blob:none skips file contents ("blobs") until Git needs them. Files outside your checkout are never downloaded.
  • --sparse starts the working tree with only the files at the repository root.
  • git sparse-checkout set go_db_internals/intro_to_db adds the code directory to the working tree. Git now fetches just those blobs.

Now look at what you have:

ls -a                      # .git  .gitignore  README.md  go_db_internals
ls go_db_internals         # GLOSSARY.md  MISSION.md  NOTES.md  RESOURCES.md  index.html  intro_to_db
cd go_db_internals/intro_to_db
ls                         # README.md  bufferpool  common  go.mod  storage

The extra top-level files (README.md, the course's own .md files and index.html) come from Git's default cone mode, which always includes the files sitting directly in each parent folder of the directory you asked for. They add up to a few kilobytes and you can ignore them. No other course's files are on your disk.

Already have a full clone?

If learning_with_teach is already on your Mac, you don't need a second copy. Run git pull in it, then cd go_db_internals/intro_to_db.

First run

From go_db_internals/intro_to_db:

go version          # go1.24 or newer
go build ./...      # compiles every package, including the stubs you'll fill in
go vet ./...
go test ./...

The last command should print ok for the pre-built packages and FAIL for intro_to_db/bufferpool, which is expected. Every method you'll implement starts as a stub that panics with TODO(P1): … not implemented, and the tests report that panic as a failure, so they fail at once instead of hanging. Each project lesson gives you a go test -run '…' command that targets the tests for its stage. You're done with a stage when that command prints ok.

From Project 1 on, several goroutines share the buffer pool, so run the tests with Go's race detector as well: go test -race ./bufferpool/. You used -race in the concurrency course, and on macOS it needs no extra setup.

Your workflow

Keep your work on a local branch of its own, and commit whenever a stage passes:

git switch -c my-work
# …implement a stage, run its checkpoint…
git add -A && git commit -m "P1: ARC bookkeeping passes"

Don't push this branch, and don't share your solutions publicly. CMU asks everyone who works through its projects to keep their implementations private; BusTub's README makes that the condition for using CMU's public autograder. The repository is private, so local commits are fine.

Getting later units' code

New packages (the B+tree, the SQL front end, and so on) are added to main as the course grows. To pull them into your branch:

git pull --no-rebase origin main

The merge is clean because the course never changes a starter file after it ships. New units only add files, so nothing collides with your edits.

When you're truly stuck

Each task in a project lesson has three hints, from gentlest to strongest:

  1. what to think about
  2. the approach, in words or short pseudocode
  3. one key fragment of a few lines

None of them shows a whole method. A complete reference implementation lives on a separate branch, go-db-internals-solutions, for comparing after you pass or as a last resort. To read one file from it without leaving your branch:

git fetch --depth 1 origin go-db-internals-solutions
git show FETCH_HEAD:./bufferpool/arc_replacer.go     # run from go_db_internals/intro_to_db

How each lesson works

  • Warm-up. Two or three quick questions on earlier lessons. Retrieving something you learned a few days ago is what makes it stick, so expect older material to keep coming back.
  • Subject matter. The database concept, with figures from the CMU slides and links to the part of the lecture video where Andy Pavlo covers it.
  • Check your understanding. Questions adapted from CMU's homeworks wherever possible, with answers checked against CMU's official solutions.
  • Build it. In project lessons, a staged task list with hidden hints and a go test checkpoint for each stage. Optional stretch lessons cover CMU's performance leaderboards.

Check your understanding

After the four checkout commands, which statement describes your disk?

  • Every course in the repository is present, at its latest commit.
  • The intro_to_db code plus a few small files from its parent folders.
  • Only the files under go_db_internals/intro_to_db and nothing else.
  • The repository's full commit history, with only intro_to_db checked out.

Your B+tree (Project 2) needs to read a node that's stored on page 42. Following BusTub's layering, how does it get that page?

  • It reads the page straight from the database file with the disk manager.
  • It asks the query executor, which fetches the page on its behalf.
  • It asks the buffer pool manager, which returns a guard on the page's frame.
  • It asks the transaction manager, which loads the page for it.

Why does the course promise never to change a starter file after it ships?

  • Your edits and the course's edits to the same file would conflict on git pull.
  • A sparse checkout can't receive changes to files it already has.
  • Go refuses to build packages whose files changed after the first build.
  • A --depth 1 clone can never pull new commits.

Something unclear? For example, the clone fails with "Repository not found" (an authentication problem), go test ./... shows something other than the expected FAIL in bufferpool, or you're not sure where your work should live. Ask your teacher (me) before moving on.
