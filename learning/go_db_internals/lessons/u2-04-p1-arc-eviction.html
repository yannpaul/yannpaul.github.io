P1.2 ARC Replacer: Eviction and Ghost Lists

Implement ArcReplacer.Evict and the ghost-list cases of RecordAccess, and predict by hand which frame each eviction returns and where the target size p moves.

After the last lesson the replacer tracks pages, but it can't give one up. This lesson adds the adaptive half of ARC. Evict hands the buffer pool a victim frame and remembers the victim's page in a ghost list. A later access to that page is a ghost hit, which moves the target size p toward the list that would have kept the page. On a complete miss, the replacer forgets its oldest ghosts so that the four lists never hold more than twice the capacity. When the stage passes, ArcReplacer is finished.

Warm-up: retrieval from earlier lessons

Lecture #04's LRU-K keeps a ghost cache. What does it hold, and why?

  • Copies of recently evicted pages' data, so that a page read again soon needs no disk read.
  • The access history of recently evicted pages, so that a page that returns soon isn't always evicted again.
  • Dirty pages that were evicted but not yet written back, so that no update is lost.
  • Pinned pages that the policy skipped, so that it can evict them as soon as they are unpinned.

In the Go module, DiskScheduler.NewCallback returns a chan bool with capacity 1. Why capacity 1?

  • So that the issuer can receive the result twice, once on success and once on completion.
  • Because Go forbids sending on an unbuffered channel from a background goroutine.
  • So that Schedule can block until the worker has finished the request.
  • So that the worker's single send never blocks, even if the issuer receives late or not at all.

An OLTP query fetches one user's entire tuple by its ID. Why does Unit 1's Lesson 4 call NSM ideal for this, compared with DSM?

  • The tuple's attributes sit together, so the lookup reads one page; DSM stitches the tuple from many.
  • NSM compresses better, so the tuple's page is more likely to be cached in the buffer pool.
  • DSM can't answer point queries at all, because it stores no tuple IDs with its values.
  • NSM keeps tuples sorted by ID, so the DBMS finds the tuple without any index.

What stage 2 adds

You keep working in bufferpool/arc_replacer.go. Evict gets its first implementation, and RecordAccess gets the two branches it skipped in P1.1. In the paper, the replacement step runs inside the access routine. BusTub splits it out: in the words of the RecordAccess doc comment, it "performs all changes to the four lists as preparation for Evict to simply find and evict a victim into the ghost lists". The split gives each method a short list of things it never does:

  • RecordAccess never evicts an alive page and never changes Size(). It checks aliveMap[frameID] first (case 1, done), then ghostMap[pageID] (cases 2 and 3, new), and otherwise treats the access as a miss (case 4, which now trims the ghost lists before inserting).
  • Evict never changes p and never removes a ghost. It turns one alive entry into one ghost entry, so the total size of the four lists stays the same.

How Evict picks a victim

The buffer pool calls Evict when it needs a frame and its free list is empty. The writeup's rule has two levels: first choose a side, then choose an entry on that side.

  1. Compare |MRU|, the length of the MRU list, with p. If |MRU| < p, try MFU first. Otherwise, including when |MRU| = p, try MRU first. The doc comment lists the tie as BusTub's first deliberate change from the paper, which checks the last access at that point; the comment calls the paper's own choice there arbitrary.
  2. Walk the chosen list from its back, the least recently used end, toward its front. Skip every entry that isn't evictable, and take the first one that is.
  3. If the chosen list has no evictable entry, try the other list the same way. This fallback is BusTub's second change, and its victim goes to its own list's ghost list: a victim taken from MFU becomes an MFU ghost, whichever side was preferred.
  4. If neither list has an evictable entry, return (common.InvalidFrameID, false).

A victim leaves its alive list and aliveMap. Its page ID goes to the front of the matching ghost list and into ghostMap, Size() drops by 1, and Evict returns the victim's frame ID and true. Writing the old page back if it is dirty, removing it from the page table and reusing the frame are the buffer pool's job.

|MRU| means r.mru.Len(), every entry, pinned ones included; the writeup defines the MRU list's actual size as mru_.size(). Counting only the evictable MRU entries changes the side choice whenever MRU holds a pinned page. SampleTest catches it when MRU is [(7,f2), p(6,f6), (5,f5)] with p = 3: three entries, 3 ≥ 3, so the answer is frame 5 from MRU. Counting two evictable entries gives 2 < 3 and frame 1 from MFU, and so does sending the tie to MFU. Both bugs fail with the same line, Evict() = 1, want frame 5.

Idiom

BusTub's Evict returns std::optional<frame_id_t>, and std::nullopt when nothing is evictable. Go has no optional type, so the port returns (common.FrameID, bool), the same comma-ok shape as v, ok := m[k]. The caller writes fid, ok := r.Evict() and checks ok before using fid. On failure fid is common.InvalidFrameID, which is −1; a buffer pool that skipped the check and indexed its frame slice with it would panic with an index out of range.

How the target size p adapts

p is mruTargetSize: the size the MRU list should have. It starts at 0 and stays between 0 and the capacity c. A ghost hit is an access to a page found in a ghost list. The writeup calls it a pseudo-hit: for the buffer pool it is still a miss, and the page has to be read from disk, but it tells the policy that it evicted the page too early. The writeup gives the reasoning for each direction. After an MRU-ghost hit, "if the MRU list is a little larger, then the DBMS could have had a cache hit", so p goes up. After an MFU-ghost hit, the same holds for the MFU list, so p goes down.

The size of the step depends on the two ghost lists' lengths. Write |B1| for the MRU ghost list and |B2| for the MFU ghost list, the lecture's names.

Page found inConditionStepNew p
MRU ghost list|B1| ≥ |B2|1min(p+1, c)
MRU ghost list|B1| < |B2|⌊|B2| / |B1|⌋min(p+step, c)
MFU ghost list|B2| ≥ |B1|1max(p-1, 0)
MFU ghost list|B2| < |B1|⌊|B1| / |B2|⌋max(p-step, 0)

The step grows when the other ghost list is much longer. One of the extra tests, TestArcEvictionGhostHitFloorDivision, has an MFU-ghost hit with |B2| = 1 and |B1| = 3, so p drops by ⌊3/1⌋ = 3, from 4 to 1. After adapting p, remove the ghost from its list and from ghostMap, and add a new alive entry for the page, in the frame passed to this call, at the front of MFU, non-evictable. The page has now been accessed twice, which is why it goes to MFU and not MRU. Its frame is almost never its old one: in SampleTest, page 1 leaves frame 1 and comes back in frame 5.

The divisor is always the length of the list that was hit, and that list contains the page, so it is at least 1 when you measure it. That holds only if you measure both lengths before removing the page, which is also the writeup's order: adapt the target size, "then move the page to the front of MFU".

Pitfall: integer arithmetic
  • Measure |B1| and |B2| before unlinking the hit page. Afterwards the ghost list that held the page can be empty, and Go stops the program with panic: runtime error: integer divide by zero. SampleTest, SampleTest2 and TestArcEvictionTargetSizeBounds all reach that point.
  • Go's / on integers truncates toward zero. For non-negative operands that is the writeup's "rounded down": 3/2 is 1. Don't convert to float64 and round, because math.Round(1.5) is 2.
  • Clamp with the built-in min and max (Go 1.21 and later): min(p+step, c) and max(p-step, 0). Neither public sample test notices a missing clamp; TestArcEvictionTargetSizeBounds does.
  • Keep p and the sizes as int, as the starter declares them. BusTub stores p in an unsigned size_t, where p − step wraps around instead of going below 0. A Go uint wraps the same way, before max ever sees the value.

Trimming the ghost lists on a miss

Case 4, a page found in no list, now does one of three things before it adds the page to the front of MRU as in P1.1:

  • (a) If |MRU| + |B1| = c, kill the last (oldest) entry of the MRU ghost list.
  • (b) Otherwise, if the four lists together hold 2c entries, kill the last entry of the MFU ghost list.
  • (c) Otherwise, kill nothing.

To kill a ghost is to forget it: remove it from its list and from ghostMap. If that page is accessed later, it is a plain miss. The order matters, because both conditions can hold at once, and then only (a) applies. The writeup adds that |MRU| + |B1| "should never be larger" than c "if you do things correctly". As in Evict, the counts include pinned entries.

The previous lesson compared this rule with slide 29's simplified miss case, which evicts from T1 or T2. For the project, follow the writeup: a miss only ever trims ghost lists, and alive pages leave only through Evict.

Check your understanding

An ArcReplacer has capacity 4 and p = 2. MRU, front to back, is [(4,f3), p(3,f2)]: page 4 in frame 3 is evictable, and page 3 in frame 2 is pinned. MFU is [(2,f1), (1,f0)], both evictable, and both ghost lists are empty. What does Evict() return?

  • Frame 0, and page 1 goes to the MFU ghost list.
  • Frame 2, and page 3 goes to the MRU ghost list.
  • Frame 3, and page 4 goes to the MRU ghost list.
  • Frame 1, and page 2 goes to the MFU ghost list.

An ArcReplacer has capacity 6 and p = 1. MRU is empty, MFU is [p(2,f3)], the MRU ghost list is [6, 5] and the MFU ghost list is [1, 4, 3]. RecordAccess(0, 5, AccessUnknown) is called. What is p afterwards?

  • 0
  • 2
  • 3
  • 4

An ArcReplacer has capacity 3 and p = 3. MRU is [(2,f3), (7,f2)], the MRU ghost list is [6], MFU is empty, and the MFU ghost list is [5, 4, 1], front to back. Page 3 is in none of the lists, and RecordAccess(1, 3, AccessUnknown) is called. Which ghost does the replacer forget?

  • Page 1, because the four lists hold 2c = 6 entries.
  • Page 5, because it is the newest entry of the MFU ghost list.
  • None, because the access is a ghost hit that moves page 3 to MFU.
  • Page 6, because |MRU| + |MRU ghost| = 3 = c.

Why does the Go Evict return (common.FrameID, bool) instead of a bare common.FrameID?

  • The bool says whether a victim exists; it is the Go form of BusTub's std::optional<frame_id_t>.
  • The bool says whether the victim's page is dirty and must be written back first.
  • The bool says whether the victim came from the MRU list rather than the MFU list.
  • The bool reports an internal error, such as a corrupted list, for the caller to log.

A learner changes mruTargetSize to a uint and writes r.mruTargetSize = max(r.mruTargetSize-step, 0) for MFU-ghost hits, with step also a uint. On a 64-bit machine p is 1 and the step is 2. What is p afterwards?

  • 0, because max replaces the negative result with 0.
  • It doesn't compile, because 0 is an int and p is a uint.
  • 18446744073709551615, because 1 − 2 wraps around before max compares.
  • The program panics with an integer overflow error at run time.

Build it: eviction and ghost lists (stage P1.2)

All edits are in bufferpool/arc_replacer.go: the Evict stub, plus new branches in RecordAccess. Run commands from go_db_internals/intro_to_db. Start with the hand trace; it exercises every rule you are about to write, and the tests' failure messages are easier to read once you have done it.

  • A replacer has capacity c = 6. Two pages are in MFU and one is in MRU, all evictable, and nothing has been evicted yet. Lists are written front to back, and p(…) marks a pinned entry:

    MRU ghost  []
MRU        [(3,f2)]
MFU        [(2,f1), (1,f0)]
MFU ghost  []
p = 0      Size() = 3

    These calls run in order (every RecordAccess passes AccessUnknown):

    1  Evict()
2  Evict()
3  Evict()
4  RecordAccess(0, 3)
5  RecordAccess(1, 4)
6  SetEvictable(1, true)
7  Evict()
8  RecordAccess(1, 4)
9  RecordAccess(2, 1)

    Write down the four lists after each call. Then compare with the hints.

    What to think about

    Several rules meet here: a tie at |MRU| = p = 0, a preferred list that is empty or fully pinned, the ratio rule when the other ghost list is longer, and the frame a re-admitted page lands in. Which ghost list does a fallback victim join?

    The approach

    For Evict: compare |MRU| with p, walk the preferred list from the back, skip pinned entries, fall back to the other list, and send the victim's page to its own list's ghost list. For RecordAccess: alive frame, then ghost page, then miss; for a ghost hit, measure both ghost lists before removing the page. Halfway check: after call 3, both alive lists are empty, the MRU ghost list is [3] and the MFU ghost list is [2, 1].

    The answer 
    call                    returns  p  why
1 Evict()               2        0  |MRU| = 1 ≥ 0: MRU; page 3 → MRU ghost [3]
2 Evict()               0        0  0 ≥ 0: MRU first, but it is empty; MFU's back (1,f0); page 1 → MFU ghost [1]
3 Evict()               1        0  same again; page 2 → MFU ghost [2, 1]
4 RecordAccess(0, 3)             2  MRU-ghost hit, |B1| = 1 < |B2| = 2: +⌊2/1⌋; page 3 → MFU front, frame 0, pinned
5 RecordAccess(1, 4)             2  miss: 0 + 0 < 6 and 3 entries < 12, nothing killed; page 4 → MRU front, pinned
6 SetEvictable(1, true)          2  Size() = 1
7 Evict()               1        2  |MRU| = 1 < 2: MFU first, but p(3,f0) is pinned; fall back to MRU: (4,f1); page 4 → MRU ghost [4]
8 RecordAccess(1, 4)             4  MRU-ghost hit, 1 < 2 again: +2; page 4 → MFU front, frame 1
9 RecordAccess(2, 1)             3  MFU-ghost hit, |B2| = 2 ≥ |B1| = 0: -1; page 1 → MFU front, frame 2

end:  MRU ghost []   MRU []   MFU [p(1,f2), p(4,f1), p(3,f0)]   MFU ghost [2]   p = 3   Size() = 0

    Call 4 is where measuring after the removal goes wrong: the MRU ghost list would be empty, and the division by its length would panic.

  • The helper takes mru or mfu, expects the caller to hold the latch, and reports the frame it freed, or that the list had no evictable entry. Evict calls it once or twice.

    What to think about

    Which end of a list holds the entry that has gone longest without use? And once you find the victim, which of your structures still mention it as alive, and which must now know it as a ghost?

    The approach

    Walk from Back() with Prev() and skip non-evictable entries. For the first evictable one: remember its frame ID, remove its element from the list and its frame from aliveMap, decrement currSize, set its status to ArcMRUGhost or ArcMFUGhost to match the list it came from, push it to the front of that ghost list, save the new element, and index it in ghostMap by page ID. Return right away; Prev() of a removed element is nil, so the loop can't continue past a removal anyway. Clearing the entry's evictable flag and frame ID keeps the ghost from looking alive.

    One key fragment 
    for e := l.Back(); e != nil; e = e.Prev() {
	st := e.Value.(*FrameStatus)
	if !st.evictable {
		continue
	}
	// st is the victim: alive bookkeeping out, ghost bookkeeping in
}

  • Lock the latch for the whole call. |MRU| < p prefers MFU; anything else, the tie included, prefers MRU. |MRU| counts pinned entries. When neither list gives a victim, return (common.InvalidFrameID, false). Leave p alone, and don't trim any ghost list.

    What to think about

    p is a target for the MRU list. If MRU is already smaller than its target, which list should shrink? And what should happen when the list you want to shrink has only pinned pages?

    The approach

    Set a first and second list from the comparison, call the helper on the first, and if it found nothing, call it on the second. Because the helper always uses the ghost list that matches the list it evicted from, a fallback victim lands in its own ghost list without any extra code.

    One key fragment 
    first, second := r.mru, r.mfu
if r.mru.Len() < r.mruTargetSize { // strict: a tie keeps MRU first
	first, second = r.mfu, r.mru
}

  • This branch goes after the alive-frame check and before the miss code, and it looks the page up by pageID. Use the table above for the step; cap p at replacerSize and floor it at 0. The re-admitted entry uses the frame passed to the call and starts non-evictable.

    What to think about

    A hit in the MRU ghost list says a slightly larger MRU list would have kept the page. How should the target react, and by how much when the MFU ghost list is much longer? Which list length is the divisor, and why can't it be 0?

    The approach

    Read both ghost lengths first. Use the ghost entry's status to tell the two cases apart, compute the step, and clamp p. Then remove the ghost's element from its list and its page from ghostMap, and add a new alive entry for (pageID, frameID) at the front of mfu, as you add new entries to mru in P1.1. The MFU-ghost case is the mirror image of the MRU-ghost case.

    One key fragment 
    b1, b2 := r.mruGhost.Len(), r.mfuGhost.Len() // before removing the page
step := 1
if b1 < b2 {
	step = b2 / b1 // rounds down; b1 >= 1 because the page is in the MRU ghost list
}
r.mruTargetSize = min(r.mruTargetSize+step, r.replacerSize)

  • Check 4(a) first: |MRU| + |B1| = c kills the MRU ghost list's back entry. Only otherwise check 4(b): all four lists holding 2c entries kills the MFU ghost list's back entry. Then run your P1.1 code that pushes the new page onto MRU.

    What to think about

    The writeup asks you to consider why, in cases 4(a) and 4(b), there must be items in the ghost lists. Hint: the frame passed for a miss isn't alive.

    The approach

    The frame came from the free list, from Evict or after Remove, so at most c − 1 frames are alive and |MRU| ≤ c − 1. In 4(a) that leaves |B1| ≥ 1. In 4(b), |MFU| + |B2| = 2c − (|MRU| + |B1|) > c with |MFU| ≤ c − 1, so |B2| ≥ 2. (This is our reasoning from the rules, not a CMU statement.) A kill is Back(), then remove that element from its list and its page from ghostMap. A small helper serves both cases.

    One key fragment 
    if r.mru.Len()+r.mruGhost.Len() == r.replacerSize {
	// 4(a): forget the oldest MRU ghost
} else if total == 2*r.replacerSize {
	// 4(b): forget the oldest MFU ghost
}
