P1.6 Buffer Pool Manager: Delete, Flush, and Concurrency

Implement DeletePage and the four flush methods, explain when a delete must fail and how the safe and Unsafe flushes differ, and run the concurrency tests that check the whole buffer pool under the race detector.

After P1.5 the buffer pool can bring pages in and push them out, but it can't forget a page for good, and it writes a dirty page only when it evicts one. This stage adds both: DeletePage removes a page from memory and disk, and the flush methods write pages out while they stay in memory. Both have to work while other goroutines fetch, write and drop guards, so the stage ends with the concurrency tests and the full test suite under -race.

Warm-up: retrieval from earlier lessons

The pre-built disk.FileManager stores every page in one database file. What does its DeletePage do with the deleted page's slot in the file?

  • It truncates the file so that the slot's bytes are given back to the operating system.
  • It puts the slot on a free list, and a page accessed for the first time later can reuse it.
  • It writes a tombstone into the slot, so that a later read of the page returns an error.
  • It keeps the slot reserved for the same page ID, in case that page is created again.

Lecture #04 describes background writing, which Project 1 doesn't have. What does a background writer do?

  • It writes each change to disk as soon as a thread modifies the page.
  • It picks the next victim ahead of time, so that eviction doesn't have to call the replacer.
  • It re-reads clean pages from disk so that their copies in memory stay current.
  • It periodically writes dirty pages out early, then evicts them or just clears their dirty flags.

In Project 1's ArcReplacer, what does Remove(frameID) do?

  • It drops an evictable frame without leaving a ghost entry, and panics if the frame isn't evictable.
  • It moves the frame's page ID to the front of its list's ghost list, as an eviction does.
  • It removes the frame whether or not it is evictable, because a deleted page is never used again.
  • It removes the frame and lowers the target size p, since the cache now holds one page fewer.

Deleting a page

The doc comment of DeletePage gives the rule and the hint. The rule: "If the page is pinned in the buffer pool, this function does nothing and returns false. Otherwise, this function removes the page from both disk and memory (if it is still in the buffer pool), returning true." The hint: "Think about all of the places that a page or a page's metadata could be." After P1.5 you can list them:

  • the page table, and your reverse map from frames to pages;
  • the frame itself: its bytes, its pin count and its dirty flag;
  • the replacer, which tracks the frame as an alive entry;
  • the free list, where the frame belongs once it holds nothing;
  • the disk, where DiskScheduler.DeallocatePage frees the page's space.

A delete must fail on a pinned page because a pin means some goroutine holds a guard on it. Its owner can read or write the frame's bytes at any moment, and the guard's Drop will later unpin that frame. Freeing the frame would hand those bytes to the next fetch while the old guard still uses them. The replacer enforces this too: your Remove panics on a frame that isn't evictable, so a delete that skips the pin check shows up as that panic. Do the whole delete under bpmLatch, so that no fetch can pin the page between your check and your cleanup.

Two more rules come from the doc comment and this course's tests:

  • A page that isn't in memory is still deleted on disk, and the call returns true: the doc comment returns "true if the page didn't exist or deletion succeeded". TestBufferPoolManagerDeleteNonResidentPage expects exactly one DeallocatePage for a page that lives only on disk, and true for a page ID that never existed.
  • A deleted page's data is discarded, even if it is dirty. Writing it back would be wasted work at best. With the file manager it is worse: the deleted page's slot goes on the free list, and a late write-back would claim a slot for a page that no longer exists. TestBufferPoolManagerDeleteFreesFrame checks that a deleted dirty page is never written, not even by a later FlushAllPages.

Deleting never makes a page ID available again. NewPage counts upwards only, so a stale reference to a deleted page can't silently land on a newer page with the same ID.

Flushing: writing a page without evicting it

A flush writes a page's bytes to disk if the page is dirty, clears its dirty flag, and leaves everything else alone: the page stays in its frame with the same pin count. A clean page needs no write. All four methods report false for a page that isn't in the page table, because there is nothing in memory to write. The flush tests check every part of that: the bytes on disk, the dirty flag, the pin count, and that the page is still in memory afterwards.

The methods come in two pairs, and the pairs differ in one thing: whether they take the frame's latch.

FlushPageUnsafe, FlushAllPagesUnsafeFlushPage, FlushAllPages
Frame latchnone ("You should not take a lock on the page")shared, for each page while it is written
A writer active on the pageits half-done changes can be written; in Go that is a data race, which -race reportsthe flush waits until the writer drops its guard

The safe flush brings back the lock-order rule from P1.5. Waiting for the frame latch while holding bpmLatch deadlocks the whole pool behind one slow writer. But releasing bpmLatch leaves a different hole: while the flush waits for the latch, the page could be evicted and its frame reused for another page, and the flush would then write that page's bytes under the wrong page ID. The answer is the same pin-then-release move a fetch makes:

  1. Under bpmLatch, look the page up (absent: return false), add a pin and call SetEvictable(frameID, false). Skip RecordAccess: a flush doesn't use the page, and counting it as an access would make ARC treat a flushed page as popular.
  2. Release bpmLatch.
  3. Take the frame's latch in shared mode, which waits for any writer. Write the page if it is dirty, wait for the callback, and release the latch.
  4. Give the pin back exactly as a guard's Drop does: under bpmLatch, decrement the pin count, and if it reached 0, call SetEvictable(frameID, true).

TestBufferPoolManagerFlushWaitsForWriter checks both halves. It holds a write guard while another goroutine calls FlushPage, expects the flush to wait, fetches a different page meanwhile (which hangs if the flush holds bpmLatch), then finishes writing and expects the final bytes on disk.

FlushAllPages applies the same protocol to every page. Copy the page IDs out of the page table under bpmLatch, release it, and flush each page with FlushPage. A page evicted in between was written back by its eviction if it was dirty, so FlushPage returning false for it is fine. FlushAllPagesUnsafe takes no frame latches, so it can simply walk the page table while holding bpmLatch.

When to clear the dirty flag

The doc comment of FlushPageUnsafe warns that without the page latch "you should carefully consider when to toggle the isDirty bit." Picture a writer still changing the page while an Unsafe flush runs. If the flush clears the flag after writing, a change made during the write is in memory, missing from disk, and the page looks clean, so the next eviction drops it. If the flush clears the flag before writing, any later change can set it again, and the page is written once more when it is evicted. That only works if writers also mark the page dirty when they finish. Your write guard already marks the page when it is created (the P1.4 tests require it). Marking it again in Drop, before the frame latch is released, also covers a change made after the guard's own Flush. In Go, a flush racing a writer is a data race anyway, so the tests never do it; the same ordering is what keeps a guard's Flush followed by more writes correct.

Idiom

FrameHeader.isDirty is an atomic.Bool. Its Swap(false) clears the flag and returns the old value in one atomic step, which is "test and clear before writing" without a gap in between. Eviction, the guards' Flush and all four flush methods do the same thing (write the frame if it is dirty, then wait for the callback), so one small helper serves them all. Likewise, factor the unpin step of Drop into a helper and call it from FlushPage, so both release a pin the same way.

The concurrency tests

The stage-6 regex also runs seven TestBufferPoolManagerConcurrency tests. Four are BusTub's own, and they need nothing from this stage: PageAccessTest, ContentionTest, DeadlockTest and EvictableTest pass as soon as P1.5 is correct, which is why the previous lesson already ran DeadlockTest. They stay here as regression and stress tests: any change you make in this stage, or later for performance, runs them again under -race.

EvictableTest is the one that checks the writeup's warning that the pin count and SetEvictable must stay in sync. Two places can break the sync. A fetch that hits a page with pin count 0 must call SetEvictable(false) (P1.5). And the last unpin must happen under bpmLatch, together with its SetEvictable(true). If a guard's Drop decrements the count outside the latch, three goroutines can interleave like this:

reader A: Drop: pin 1 → 0                     (no bpmLatch)
reader B: fetch hit under bpmLatch: pin 0 → 1, RecordAccess, SetEvictable(false)
reader A: SetEvictable(true)                  ← the frame is pinned, yet evictable
reader C: fetch of another page evicts the frame out from under B's guard

The P1.5 tests run one goroutine at a time and never produce this interleaving. EvictableTest repeats the race 1000 times with 8 readers, and it reports round N: CheckedReadPage(1) succeeded although the only frame is pinned.

Check your understanding

Page 4 is in memory, and a goroutine holds a read guard on it, so its pin count is 1. Another goroutine calls DeletePage(4). What should happen?

  • The call returns false, but the page's space on disk is deallocated so the delete finishes later.
  • The call waits until the read guard is dropped, then deletes the page and returns true.
  • The call returns false and changes nothing; the page stays in memory with pin count 1.
  • The page leaves the page table and the replacer, and the frame is freed once the guard is dropped.

Page 9 is in memory, unpinned and dirty. DeletePage(9) is called. Which list describes everything it should do?

  • Remove the frame from the replacer, delete the page-table entry, reset the frame, put it on the free list, call DeallocatePage and return true.
  • Write the page back because it is dirty, then remove it from the page table and the replacer and return true.
  • Delete the page-table entry and call DeallocatePage, leaving the frame in the replacer to be evicted later.
  • Return false, because a dirty page must be flushed before it can be deleted.

FlushPage pins the page under bpmLatch before it releases the latch and waits for the frame latch. What would go wrong without that pin?

  • Read guards on the page would be unable to share the frame latch with the flush.
  • The disk scheduler could run the flush's write before an earlier read of the same page.
  • GetPinCount could return a torn value while the flush is running.
  • The page could be evicted while the flush waits, and the flush would write another page's bytes under its ID.

A buffer pool's Drop releases the frame latch, then decrements the pin count with an atomic Add(-1), and only then takes bpmLatch to call SetEvictable(true) when the count reached 0. Why does EvictableTest fail on it?

  • The frame latch is released twice, so the second reader's guard panics.
  • Another reader can pin the frame between the decrement and SetEvictable(true), which then leaves a pinned frame evictable.
  • The atomic decrement can be lost when two readers drop at the same moment.
  • Taking bpmLatch after the frame latch makes Drop deadlock against a fetch.

Build it: delete, flush, and harden

Everything is in bufferpool/buffer_pool_manager.go, except the last task, which reviews bufferpool/page_guard.go. Read the doc comments of DeletePage and the four flush methods in full; each says when its method should be written, and in which order relative to the others. Each task ends with a check that runs only that method's tests.

  • What to think about

    List every place the page or its metadata can be. Which checks must come before you change anything, and what must DeletePage still do for a page that isn't in memory at all?

    The approach

    Lock bpmLatch for the whole call. If the page is in the page table: if its pin count is above 0, return false; otherwise call replacer.Remove on its frame, delete the page-table entry and the reverse-map entry, reset the frame (dropping the bytes, dirty or not), and append the frame to freeFrames. Then, whether or not the page was in memory, call diskScheduler.DeallocatePage and return true.

    One key fragment 
    if frame.pinCount.Load() > 0 {
	return false // a guard still uses this frame
}
bpm.replacer.Remove(frameID) // legal now: the frame is evictable
    Checkpoint

    go test -race -run '^TestBufferPoolManagerDelete(VeryBasic|PinnedPage|NonResidentPage)$' ./bufferpool/ runs BusTub's full VeryBasicTest and the pinned and non-resident delete tests, and prints ok intro_to_db/bufferpool. The fourth delete test, ...DeleteFreesFrame, also calls FlushAllPages, so it fails with panic: TODO(P1): BufferPoolManager.FlushAllPages not implemented until the last flush task. A delete that ignores pins ends in your replacer's panic from Remove.

  • What to think about

    What does the method return for a page that isn't in memory, and for a clean page that is? When do you clear the dirty flag relative to the write, and why does the order matter only when a writer could be active?

    The approach

    Lock bpmLatch. Look the page up; if it is absent, return false. Clear the dirty flag, and if it was set, schedule a write of the frame's bytes under this page ID and wait on the callback. If the callback reports false, set the flag again, since the page still differs from disk. Return true otherwise. This "write if dirty" step is the same one your eviction does; make it a shared helper.

    One key fragment 
    if frame.isDirty.Swap(false) { // clear first, then write
	// schedule IsWrite: true for this page and wait on the callback
}
    Checkpoint

    go test -race -run '^TestBufferPoolManagerFlushPageUnsafe$' ./bufferpool/ prints ok intro_to_db/bufferpool. The test checks false for a page that isn't in memory, the bytes on disk after the flush, a cleared dirty flag, and a page that is still in memory with pin count 0.

  • What to think about

    You will wait for the frame latch. What must you not be holding while you wait, and what stops the page from being evicted once you let go of it? Is a flush an access that ARC should hear about?

    The approach

    Lock bpmLatch and look the page up; if it is absent, unlock and return false. Add a pin and call SetEvictable(frameID, false), but not RecordAccess. Unlock. Take the frame's latch with RLock, run your "write if dirty" helper, and RUnlock. Finally unpin under bpmLatch: decrement, and call SetEvictable(frameID, true) if the count reached 0. Return what the write reported.

    One key fragment 
    bpm.bpmLatch.Unlock() // the pin keeps the frame from being evicted
frame.rwlatch.RLock() // waits for a writer, holding no pool latch
    Checkpoint

    go test -race -run '^TestBufferPoolManagerFlush(Page|WaitsForWriter)$' ./bufferpool/ prints ok intro_to_db/bufferpool. If FlushPage waits for the frame latch while holding bpmLatch, TestBufferPoolManagerFlushWaitsForWriter fails after 10 seconds with ReadPage of another page while FlushPage waits for a page latch did not return within 10s. If it takes no frame latch, the test reports FlushPage returned while another goroutine held a WritePageGuard on the page.

  • What to think about

    Which pages count as "in memory"? Can anything in this method wait for another goroutine, and so is it safe to keep bpmLatch for the whole loop?

    The approach

    Lock bpmLatch with a deferred unlock, range over the page table, and run your "write if dirty" helper on each page's frame. Waiting on disk callbacks under the pool latch is fine, because the disk worker never takes it.

    One key fragment 
    for pageID, frameID := range bpm.pageTable {
	// write bpm.frames[frameID] as pageID if it is dirty
}
    Checkpoint

    go test -race -run '^TestBufferPoolManagerFlushAllPagesUnsafe$' ./bufferpool/ prints ok intro_to_db/bufferpool. The test writes six pages through four frames, so two were written back by eviction and four are flushed by your method; it then checks all six on disk.

  • What to think about

    Each safe flush may wait for a writer. Can you range over pageTable while doing that? What happens to a page that is evicted between the moment you list it and the moment you flush it?

    The approach

    Under bpmLatch, copy the page table's keys into a slice. Unlock. Call FlushPage for each ID and ignore its result: a page evicted in the meantime was written back by the eviction if it was dirty, and a deleted page should not be written at all.

    One key fragment 
    ids := make([]common.PageID, 0, len(bpm.pageTable))
for pageID := range bpm.pageTable {
	ids = append(ids, pageID)
}
    Checkpoint

    go test -race -run '^TestBufferPoolManagerFlushAllPages$' ./bufferpool/ prints ok intro_to_db/bufferpool. Rerun the delete tests now: ...DeleteFreesFrame can pass at last.

  • What to think about

    Find every place your code waits: on a frame latch, on bpmLatch, on a disk callback. For each one, which latches does the goroutine hold at that moment? And find every place a pin count can reach 0: is bpmLatch held there?

    The approach

    Check four rules. No goroutine waits for a frame latch while holding bpmLatch (fetches, FlushPage, FlushAllPages). Every fetch that succeeds calls SetEvictable(false), hits included. Every unpin (guards' Drop and FlushPage) decrements the count and calls SetEvictable(true) at 0, both under bpmLatch, after the frame latch has been released. And a write guard marks the page dirty in Drop before releasing its latch, as well as when it is created. Then run the concurrency tests; when one fails or hangs, add -v and -timeout 120s after the regex to see which test and which goroutines are stuck.

    One key fragment 
    g.frame.isDirty.Store(true) // in WritePageGuard.Drop: still holding the latch
g.frame.rwlatch.Unlock()    // latch first...
// ...then unpin under bpmLatch
    Checkpoint

    go test -race -run '^TestBufferPoolManagerConcurrency' ./bufferpool/ runs the seven concurrency tests in a few seconds and prints ok intro_to_db/bufferpool. A goroutine that never finishes makes its test fail when the bounded wait expires, for example the readers did not finish within 10s: a latch is never released, or there is a deadlock.

Checkpoint: stage P1.6

From go_db_internals/intro_to_db, run:

go test -race -run '^TestBufferPoolManager(Delete|Flush|Concurrency)' ./bufferpool/

It runs the 16 stage-6 tests: four delete tests (including BusTub's full VeryBasicTest), five flush tests and the seven concurrency tests. It takes several seconds, mostly in ContentionTest and the stress test. Success prints:

ok  	intro_to_db/bufferpool	6.808s

Typical failures: a stub still in place (panic: TODO(P1): BufferPoolManager.FlushPage not implemented); a pinned frame left evictable (round 0: CheckedReadPage(1) succeeded although the only frame is pinned); and deadlocks, which fail when a bounded wait expires, after 10 seconds with ... did not return within 10s: a page latch is probably never released (or the buffer pool latch is held while waiting for a page latch). A hang outside those bounds runs until go test's own 10-minute timeout, which prints panic: test timed out after 10m0s and every goroutine's stack; add -timeout 120s after the regex to see it sooner.

Then run the whole project once, every package and every stage:

go test -race -count=1 ./...

-count=1 makes Go run the tests again instead of printing cached results, which matters for concurrency tests: a lucky pass shouldn't be replayed from the cache. It prints three ok lines, for intro_to_db/bufferpool, intro_to_db/common and intro_to_db/storage/disk, and takes around ten seconds or more with the race detector. Run it a few times; a concurrency bug can pass once and fail the next run. When it passes repeatedly, Project 1 is done. Commit your branch.

Something unclear? For example, why DeletePage returns true for a page that never existed, why FlushPage pins the page but doesn't call RecordAccess, or how the unpin race in EvictableTest can happen with an atomic pin count. Ask your teacher (me) before moving on.
