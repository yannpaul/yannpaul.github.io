Testing What You Built

Rebuild Lessons 1–11 from memory first. Then write real, automated tests for two functions that have been correct only because you kept manually re-checking them.

Every checkpoint in this course has been you, by hand, running a command and reading its output. That's been the right call for a CLI's end-to-end behavior — but perms and sizeOf are pure enough underneath that they don't need a CLI invocation at all to check. Today: go test, a table-driven test for perms, and an I/O-touching test for sizeOf that cleans up after itself.

New: a table-driven test for perms

A Go test lives in a file ending _test.go, in the same package as the code it tests. A test function's name starts with Test and takes one argument, *testing.T. perms is a good first target: no I/O, no dependencies, the same inputs always give the same output — exactly the shape go test is built for.

  • Stuck? Show the skeleton 
    package main

import "testing"

  • Cover at least: every bit set, exactly one bit set, and no bits set — the three shapes perms's own if statements branch on.

    Stuck? Show the test 
    func TestPerms(t *testing.T) {
	cases := []struct {
		name string
		mode os.FileMode
		want string
	}{
		{"all three", 0700, "read, write, execute"},
		{"read only", 0400, "read"},
		{"none", 0000, "(none)"},
		{"write and execute", 0300, "write, execute"},
	}
	for _, c := range cases {
		t.Run(c.name, func(t *testing.T) {
			got := perms(c.mode, 0400, 0200, 0100)
			if got != c.want {
				t.Errorf("perms(%v, ...) = %q, want %q", c.mode, got, c.want)
			}
		})
	}
}

    Add "os" to main_test.go's import block.

  • Stuck? Show the command 
    go test -v ./...
    Checkpoint

    Four === RUN lines, one per case (named after your case names with spaces turned into underscores), all reporting --- PASS, then an overall PASS and ok line.

New: testing something that touches disk

sizeOf isn't pure — it reads real files. Testing it without leaving junk behind (or depending on files that happen to already exist) means giving it a directory built just for the test and thrown away afterward. t.TempDir() does exactly that: it returns a fresh, empty directory that go test deletes automatically when the test finishes, pass or fail.

  • os.WriteFile(path, make([]byte, n), 0644) is a quick way to create a file of an exact size without caring what's in it. Fail fast with t.Fatal on any setup error — if creating the test's own files fails, there's no point continuing to the actual assertion.

    Stuck? Show the test 
    func TestSizeOf(t *testing.T) {
	dir := t.TempDir()
	if err := os.WriteFile(filepath.Join(dir, "a.txt"), make([]byte, 100), 0644); err != nil {
		t.Fatal(err)
	}
	sub := filepath.Join(dir, "sub")
	if err := os.Mkdir(sub, 0755); err != nil {
		t.Fatal(err)
	}
	if err := os.WriteFile(filepath.Join(sub, "b.txt"), make([]byte, 50), 0644); err != nil {
		t.Fatal(err)
	}

	got, err := sizeOf(dir)
	if err != nil {
		t.Fatal(err)
	}
	if got != 150 {
		t.Errorf("sizeOf(dir) = %d, want 150", got)
	}
}

    Add "path/filepath" to main_test.go's import block.

  • Checkpoint

    TestSizeOf now runs and passes alongside all of TestPerms's subtests. Check your burrow directory afterward — no leftover temp directory anywhere; t.TempDir() cleaned it up itself.

Idiom

Notice which functions got tests today and which didn't: perms and sizeOf, not findName, duTop, checkPerm, or whoOwns. Those four all either print directly to stdout or call one of the two functions you just tested — testing them meaningfully would mean capturing stdout or mocking the filesystem, real techniques with real cost, not a natural next step for a basics course. The functions worth testing first are usually the ones already shaped like this: take arguments, return a value, no side effects (or, like sizeOf, side effects limited to reads you can point at a throwaway directory). That shape isn't an accident here — it's the same "pull the pure logic out of the function that also does I/O or printing" instinct that's been this course's structure since getConfig/run in Lesson 1.

burrow now has working tests for its two purest pieces. Lesson 13 is the capstone: real --help polish, go install, and one last pass through everything this course built.

Something unclear — why t.Run subtests instead of one big loop with plain if checks, why t.TempDir() beats a hand-rolled temp directory, which of the untested functions you'd test first if you kept going, anything else? Ask your teacher (me) before moving on.
