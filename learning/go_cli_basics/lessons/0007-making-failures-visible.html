Making Failures Visible

Rebuild Lessons 1–6 from memory first. Then learn why "it just does nothing" is almost never true — and what to reach for once errors can't hide anymore.

This lesson exists because of a bug you can very plausibly have right now: a subcommand case in run that calls a function returning error, without returning that error itself. It compiles clean. go vet says nothing. It just quietly does less than it should, some of the time, with no message at all. Today's job is learning to (1) stop that class of bug from hiding in the first place, and (2) actually watch a program's insides when something still goes wrong anyway.

Warm-up — repeat from Lessons 1–6
  • Forgot the overall shape? Show the skeleton (bodies omitted) 
    type Config struct {
	Command string
	Path    string
	Pattern string
	N       int
}

func getConfig() (Config, error) { /* dispatches on os.Args[1] to getFindConfig / getDuConfig / a perm flag set */ }
func getFindConfig() (Config, error) { /* dispatches on os.Args[2]: "name" */ }
func getDuConfig() (Config, error) { /* dispatches on os.Args[2]: "top" */ }

func run(cfg Config) error {
	switch cfg.Command {
	case "find name":
		return findName(cfg.Path, cfg.Pattern)
	case "du top":
		return duTop(cfg.Path, cfg.N)
	case "perm":
		fmt.Println("burrow perm: not implemented yet")
		return nil
	}
	return nil
}

func main() {
	cfg, err := getConfig()
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	if err := run(cfg); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}
    Checkpoint

    All three commands print what you'd expect from Lessons 5–6, with no crashes, before you touch anything below. Pay close attention to run's "du top" (or however you named that case) — you'll be looking hard at it in a moment.

New: find the error you're already throwing away

Look at every case inside your run function. Each one calls a function that returns error — findName, duTop, and eventually perm's real implementation. A case that calls one of those functions but doesn't return its result has thrown the error away. If that function fails partway — a permission error, a path that doesn't exist, anything — your program will look like it succeeded: exit code 0, no message, and whatever partial work got done before the failure, silently incomplete.

  • Stuck? Show the shape of the fix 
    case "du top":
	return duTop(cfg.Path, cfg.N)

    Not duTop(cfg.Path, cfg.N) on its own — that line runs the function and then throws away the only thing it told you about whether it worked.

  • Stuck? Show the command 
    go vet ./...
    Checkpoint

    Exits with status 0 and prints nothing — even with the bug still in place. go vet catches real classes of mistakes (a Printf verb that doesn't match its argument, unreachable code, a few dozen others), but a discarded error return isn't one of them. Clean vet output is not the same thing as "no bugs."

  • Stuck? Show the commands 
    go install github.com/kisielk/errcheck@latest
errcheck ./...
    Checkpoint

    One line of output per discarded error, formatted file:line:col:\t<the expression whose error was ignored>. If you already applied the fix above, your run case won't be in the list anymore; if you haven't yet, it will be — that line is errcheck pointing at the exact bug this lesson opened with.

Idiom

This isn't an oversight in go vet — it's a deliberate consequence of how Go models errors. An error is just an ordinary value, returned like any other; there's no "must-use" marker forcing you to look at it, the way some languages warn on an unused Result. That's exactly why the if err != nil { return err } pattern this course has used since Lesson 1 is a habit you enforce yourself, not something the compiler enforces for you — and why a tool like errcheck exists to catch the moments discipline alone missed. Many teams wire it into golangci-lint and run it in CI for exactly this reason.

  • Checkpoint

    A real error message prints to stderr (something naming the missing path — the exact wording comes from os.ReadDir) and the process exits with a nonzero status. Before your fix, this same command would have printed nothing at all.

Print debugging: fast, and completely legitimate

Once errors can't hide, some bugs will still need real investigation — the logic ran, nothing failed, but the result is wrong. The fastest tool for that in Go is the same one you've probably already reached for without thinking of it as a technique: a fmt.Println or fmt.Printf dropped at a decision point to see what's actually happening. There's no special setup, no tooling to learn, and the edit-run loop (go run .) is fast enough that it's often the right first move, not a lesser one.

  • That's not a trick question — it's genuinely easy to leave a debug print in once it's done its job. Decide now: delete it, or leave it deliberately (some tools keep a --verbose flag around for exactly this kind of output — a real feature this course hasn't built yet, but worth remembering as the "grown-up" version of a debug print you didn't want to lose).

    Checkpoint

    You've made a conscious decision either way — not left it in by accident.

Idiom

Print debugging's real cost isn't that it's unsophisticated — it's that it's manual on both ends. You have to remember to add it, and remember to remove it (or it ships, the way that sizeOf print quietly did). It also only shows you what you thought to print, at the moment you thought to print it. For "is this branch running, and roughly what does this value look like," it's usually the fastest honest answer. For "let me pause here and look around," it isn't the right tool at all.

delve: pausing the program instead of printing at it

Delve (dlv) is Go's standard debugger — it runs your program under its control and lets you stop it at a specific line, inspect variables as they actually are in memory, and step forward one line at a time, without editing any code to do it.

  • Stuck? Show the command 
    go install github.com/go-delve/delve/cmd/dlv@latest
  • Stuck? Show the commands 
    dlv debug . -- du top --path . --n 5

    Once you're at the (dlv) prompt:

    break sizeOf
continue
    Checkpoint

    Execution stops right at the top of sizeOf, before totalSize has even been declared — printing it right now would fail, since it doesn't exist in scope yet. That's expected, not a mistake.

  • Stuck? Show the commands 
    next
next
print totalSize
    Checkpoint

    next steps over the filepath.WalkDir(...) call as a single line — it runs the entire walk (every file under that root) in one step, since that's all one statement, rather than pausing inside the callback for each file. When you print totalSize afterward, you'll see the finished total for that one entry, not a running count. If you wanted to pause inside the walk instead, on each visited file, that's what step is for — it steps into a call instead of over it. Try setting a second breakpoint inside the callback itself (on the totalSize += i.Size() line, or whatever's on it) and continue to it if you want to see that instead.

  • Checkpoint

    You're back at your normal shell prompt, and the program's usual output (the sorted size report) printed in between your breakpoint hits, exactly like a normal run — delve doesn't change what the program does, only your ability to watch it happen.

Idiom

The dividing line worth internalizing: reach for a print statement when you just need a quick fact ("is this branch running," "roughly what's in this variable") and the edit-run loop is fast. Reach for delve when you need to pause at a specific moment and look around — inspect a whole struct, walk a call stack, or step through a loop iteration by iteration without editing code each time you want to check something new. Neither replaces the other; this lesson's first half (never discard an error) prevents the largest category of bug that would otherwise send you to either one for nothing.

One more thing: the bug that isn't a bug

Not every "my program gives the wrong answer" is a bug in the program. A remarkably common alternative: the test data doesn't match what you think it matches. You build a scratch directory to check du top, run it, and the numbers look wrong — but the actual cause is that a file you meant to create inside a subdirectory landed one level up instead, sitting at the top level alongside it. Nothing in duTop, sizeOf, or the sort is broken; the input simply isn't the input you meant to build. Every tool this lesson covered — errcheck, a print statement, delve — would have told you your code was doing exactly what it was told to do, because it was.

  • Stuck? Show the command 
    ls -la /path/you/tested
    Checkpoint

    The number of entries ls -la shows (minus . and ..) matches the number of lines your program reports. If it doesn't, you've found a real bug worth taking to errcheck, a print statement, or delve. If it does, and every value is explainable once you actually look at what's there, there was never a bug — only a test that quietly stopped matching what you thought you'd built.

Idiom

This is debugging step zero, before any tool: verify your assumptions about the input are still true, not just your memory of what the input was supposed to be. It costs one ls, and it's astonishing how often it's the entire fix.

Put together, in order: check your own inputs first — the cheapest bug to fix is the one that was never a bug. Stop swallowing errors next — most of what's left that looks like a mystery turns out to be exactly that. Reach for a print statement for a fast fact. Reach for delve when you need to actually watch the program think.

Something unclear — why go vet doesn't catch discarded errors, the difference between next and step in delve, when a print statement should become a real --verbose flag instead of getting deleted, anything else? Ask your teacher (me) before moving on.
