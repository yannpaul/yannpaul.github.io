Cleaning Up the Dispatch

Rebuild Lessons 1–9 from memory first. No new subcommand today — a short lesson in noticing repetition and naming it.

burrow now has five working commands: find name, du top, perm check, perm who. Every single one of their getXConfig cases starts the exact same way — build a flag.NewFlagSet, register a -path flag, done. Today that repetition gets a name and a single definition. New: naming the repetition

Open getFindConfig, getDuConfig, and getPermConfig side by side. Every single case in all three starts with the same two lines: create a named flag.NewFlagSet, and register a -path string flag defaulting to ".". What follows differs (an extra -pattern here, an extra -n there, nothing extra in perm's two cases) — but that opening pair never does.

Idiom

This is close to where hand-rolled deduplication of CLI dispatch should stop. You could keep going — a table mapping subcommand names to handler functions, reflection-based flag binding, a generic three-level tree walker — but at that point you're slowly rebuilding a worse version of a library that already exists and is already trusted by thousands of projects. Recognizing that point — "I'm about to reinvent a dependency" — is as much a part of writing idiomatic Go as any single syntax rule. Lesson 11 makes the swap.

newSubFlagSet is a small change, but it's the right size for what it fixed: five repeated lines became one shared function, nothing about behavior moved, and every command is still exactly as easy to read as before. That's the bar for any refactor — smaller, not just different.

Something unclear — why this refactor stops here instead of going further, what a subcommand "registry" would even look like, anything else? Ask your teacher (me) before moving on.
