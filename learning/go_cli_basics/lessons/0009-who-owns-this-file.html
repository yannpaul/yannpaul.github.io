New: looking up an owner's name

An fs.FileInfo's .Sys() method returns any — an escape hatch to operating-system-specific data fs.FileInfo doesn't standardize, because not every OS represents file ownership the same way. On Unix-like systems (Linux, macOS), the concrete type behind that any is *syscall.Stat_t, which has numeric Uid and Gid fields — a user ID and group ID, not names. Turning those into names is a second step, via os/user: user.LookupId and user.LookupGroupId, both of which take the ID as a string, not an int.

  • user.LookupId takes a string, and Uid/Gid are numeric — strconv.Itoa(int(stat.Uid)) converts it. Handle the type assertion's second return value: if it's false, you're not on a platform where this works (see the idiom callout below) — return a clear error rather than letting a failed assertion panic.

    Stuck? Show the function 
    func whoOwns(path string) error {
	info, err := os.Stat(path)
	if err != nil {
		return err
	}
	stat, ok := info.Sys().(*syscall.Stat_t)
	if !ok {
		return fmt.Errorf("can't read owner info for %s on this platform", path)
	}

	owner, err := user.LookupId(strconv.Itoa(int(stat.Uid)))
	if err != nil {
		return err
	}
	group, err := user.LookupGroupId(strconv.Itoa(int(stat.Gid)))
	if err != nil {
		return err
	}

	fmt.Println(path)
	fmt.Println("  owner:", owner.Username)
	fmt.Println("  group:", group.Name)
	return nil
}

    Add "os/user", "strconv", and "syscall" to your import block.

Idiom

This is the mission's promised platform caveat, and it's a real one, not a hedge: syscall.Stat_t only exists on Unix-like systems. Cross-compiling this exact code for Windows (GOOS=windows go build) fails outright at compile time — undefined: syscall.Stat_t — because Windows represents file ownership completely differently (via security descriptors, not a numeric UID/GID pair), and Go's syscall package only defines Stat_t for the platforms where it makes sense. macOS and Linux both cross-compile clean, since both are POSIX-like here. If burrow ever needed to run on Windows, perm who specifically would need a build-tag-gated Windows implementation calling a completely different API — a real, separate piece of work this course intentionally leaves out.

Every subcommand this course set out to build — find name, du top, perm check, perm who — now does real work. Lesson 10 steps back and cleans up the dispatch code itself, before Lesson 11 replaces it with a real library.

Something unclear — why .Sys() returns any instead of something more specific, the two-value type assertion form, why Windows needs a totally different approach, anything else? Ask your teacher (me) before moving on.
