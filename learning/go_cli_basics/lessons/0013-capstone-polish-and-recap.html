New: real --help text

Right now burrow --help lists find, du, and perm with no description next to any of them — Cobra shows whatever you gave it, and you never gave it anything. A Short field on any *cobra.Command is a one-line description shown in exactly that listing.

  • Stuck? Show two examples 
    rootCmd := &cobra.Command{
	Use:           "burrow",
	Short:         "burrow finds files, reports disk usage, and inspects permissions",
	SilenceErrors: true,
	SilenceUsage:  true,
}

findCmd := &cobra.Command{Use: "find", Short: "Find files by name pattern"}

    A command's Short shows up wherever that command is listed — the root's appears as the one-line summary at the top of burrow --help; find's appears next to its name in that same output's "Available Commands" table; name's would appear next to its name in burrow find --help's table. Each command only ever displays its own Short, never a parent's or a child's. Write your own wording for the remaining six commands (du, perm, and all four leaves) — a short, accurate sentence for each, the same as you'd want to read if you'd never seen this tool before.

    Checkpoint

    burrow --help now shows a one-line description next to every command. burrow find --help shows one next to name.

  • Stuck? Show the field 
    rootCmd := &cobra.Command{
	Use:     "burrow",
	Short:   "burrow finds files, reports disk usage, and inspects permissions",
	Version: "0.1.0",
	// ...
}

    Any string works, but the convention — major.minor.patch, semantic versioning — is worth following even for a tool only you will ever run, since it's what --version output looks like almost everywhere else. The important mechanical detail: Cobra only adds the --version/-v flag at all when Version is non-empty. Leave it blank (the default, since you never set it before today) and the flag simply doesn't exist — that's why burrow --version hasn't worked until now.

    Checkpoint

    burrow --version (and its shorthand, burrow -v) now prints it — a flag you never registered yourself. Cobra adds it automatically the moment Version is non-empty.

New: installing it for real

  • Stuck? Show the command 
    go install .

    go install does what go build does — compiles your module's main package into a binary — but instead of leaving that binary in your current directory, it copies it to $(go env GOPATH)/bin (or $GOBIN, if you've set that environment variable). That's a single, fixed location every Go installation already has, which is exactly why putting that one directory on your shell's PATH once makes every tool you ever go install — this one included, and any future one — runnable by name from anywhere, permanently, with no further per-project setup.

    Checkpoint

    A burrow binary now exists at $(go env GOPATH)/bin/burrow — check with ls $(go env GOPATH)/bin. If that directory is on your shell's PATH (a one-time setup step this lesson can't do for you — it's specific to your shell and OS), you can now run burrow find name --pattern "*.go" from any directory, with no go run, no ./, no rebuilding.

The recap

Twelve questions, one per lesson, in order. Each tests the one thing that lesson was actually teaching — not "did this happen" but "do you understand why." Pick an answer; you'll get immediate feedback either way, including why the right answer is right. One attempt per question — this is retrieval practice, not a form to resubmit until it's correct.

1. Why does main stay almost empty from Lesson 1 onward, wiring only getConfig() then run()?

  • It's required by the Go compiler for any command-line program.
  • It keeps the real logic callable and testable without going through os.Exit, and separates configuration from execution.
  • It produces a smaller compiled binary.
  • Go's flag.Parse() only works when called directly inside main.

2. Which statement about single-dash flags is correct?

  • The standard library's flag package and Cobra's pflag both treat -name and --name identically.
  • The stdlib flag package accepts both -name and --name for a long flag; pflag reserves a single dash for one-letter shorthands only.
  • Cobra's pflag is more forgiving about dashes than the standard library's flag package.
  • Neither library accepts a single dash for anything.

3. What does returning filepath.SkipDir from a filepath.WalkDir callback actually do?

  • Stops the entire walk immediately, the same as any other non-nil error would.
  • Skips the rest of the current directory's contents, without stopping the walk over everything else.
  • Skips only the current file and moves on to the next sibling.
  • Retries the current entry after a short delay.

4. Why couldn't a single global flag.Parse() handle burrow find name --pattern x on its own?

  • Because os.Args[0] is the subcommand name, and flag.Parse() tries to read it as a flag.
  • Because flag.Parse() stops parsing at the first non-flag argument, and a verb-first CLI needs the verb to come before its flags.
  • Because the standard library's flag package doesn't support a flag named pattern.
  • Because Go doesn't allow calling flag.Parse() outside of main.

5. What does filepath.Match(pattern, name) actually compare the pattern against?

  • The file's full path, including every directory separator along the way.
  • A single path element, like a base filename — it never matches across a path separator.
  • The file's contents.
  • Every ancestor directory name, concatenated together.

6. In sort.Slice(dSizes, func(i, j int) bool {...}), which comparison sorts descending by size?

  • dSizes[i].Size < dSizes[j].Size
  • dSizes[i].Size == dSizes[j].Size
  • dSizes[i].Size > dSizes[j].Size
  • It doesn't matter which — sort.Slice always sorts descending by default.

7. Which of these does go vet actually catch on its own, with no extra tooling installed?

  • A discarded error return value from a function call.
  • A Printf-style format string whose verbs don't match its arguments.
  • A goroutine that's started but never waited on.
  • A data race between two goroutines.

8. Which octal constant checks the "group write" permission bit?

  • 0200
  • 0020
  • 0002
  • 0700

9. Why does perm who's code fail to even compile with GOOS=windows?

  • Because os.Stat doesn't exist on Windows.
  • Because .Sys()'s concrete type is platform-dependent, and syscall.Stat_t isn't defined for Windows at all.
  • Because Windows file paths use backslashes, which os/user can't parse.
  • Because user.LookupId is Unix-only and doesn't exist on Windows.

10. Why did Lesson 10 stop the DRY refactor at one small helper (newSubFlagSet) instead of building a bigger generic subcommand registry by hand?

  • Go doesn't support the map-of-functions pattern a registry would need.
  • Because building a bigger registry by hand would mean reinventing a worse version of what Cobra (Lesson 11) already provides.
  • Because newSubFlagSet already eliminated all the duplication, leaving nothing left to extract.
  • Because a registry pattern only works with global variables, which this codebase avoids.

11. Why did Lesson 11 use RunE instead of Run for every Cobra command?

  • Because RunE is required for any command that registers flags.
  • Because Run has no return value, so an error from a function it calls (like findName) would have no way to reach main — the exact discarded-error problem from Lesson 7.
  • Because RunE runs faster since it skips flag validation.
  • Because Run is deprecated in current versions of Cobra.

12. Why did perms and sizeOf get tests in Lesson 12, but findName, duTop, checkPerm, and whoOwns didn't?

  • Because perms and sizeOf are the only two functions in the codebase without bugs.
  • Because perms has no side effects, and sizeOf's only side effect (reading files) can be pointed at a disposable t.TempDir() — the other four either print directly or just call one of these two.
  • Because go test can't test any function that returns an error.
  • Because table-driven tests only work on functions with exactly one input parameter.
