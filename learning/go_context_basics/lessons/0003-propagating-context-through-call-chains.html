Propagating Context Through Call Chains

Rebuild Lesson 2's context.WithTimeout-guarded duTop from memory first. Then see what happens once more than one context exists at once, and give burrow's whole command tree a real one.

Every context so far has been a single one, created and used within one function. Real programs derive context after context — a per-request context wrapping a program-lifetime one, a per-attempt context wrapping a per-request one — and none of that would be useful if canceling the outer one didn't reliably reach every context derived from it. Today: prove that it does, then wire a real context tree into burrow itself, from main down into an individual command.

Warm-up — repeat from Lessons 1–2
  • Checkpoint

    A normal fixture completes well under your configured timeout; a fixture with a deliberately slow entry still fails with an error containing context deadline exceeded.

New: canceling a parent cancels every child

Every WithCancel/WithTimeout/WithDeadline call takes an existing context as its first argument — the parent — and returns a new one derived from it, a child. That parent/child relationship isn't just naming: canceling a parent automatically cancels every context ever derived from it, with no extra code, no matter how many layers deep. Canceling a child, on the other hand, affects only that child (and anything derived from it) — the parent is untouched.

  • Stuck? Show the code 
    package main

import (
	"context"
	"fmt"
	"time"
)

func watch(name string, ctx context.Context) {
	<-ctx.Done()
	fmt.Printf("%s: done, err=%v\n", name, ctx.Err())
}

func main() {
	parent, cancelParent := context.WithCancel(context.Background())
	child, cancelChild := context.WithCancel(parent)
	defer cancelChild()

	go watch("parent", parent)
	go watch("child", child)

	time.Sleep(100 * time.Millisecond)
	fmt.Println("main: canceling parent")
	cancelParent()

	time.Sleep(100 * time.Millisecond)
}
    Checkpoint

    Both child: done, err=context canceled and parent: done, err=context canceled print, even though only cancelParent was ever called — canceling the parent reached the child automatically.

  • Stuck? Show the code 
    parent, cancelParent := context.WithCancel(context.Background())
defer cancelParent()
child, cancelChild := context.WithCancel(parent)

cancelChild()
time.Sleep(50 * time.Millisecond)

fmt.Println("parent err:", parent.Err()) // nil — still active
fmt.Println("child err:", child.Err())   // context canceled
    Checkpoint

    parent.Err() prints <nil> — it's still fully active — while child.Err() prints context canceled. Cancellation only ever flows downward, parent to child, never back up.

Idiom

This also means a child's own timeout doesn't protect it from its parent. A context.WithTimeout(parent, 10*time.Second) child still ends the instant its parent is canceled, however much of its own 10 seconds was left. A context's actual lifetime is always the shorter of its own deadline and whatever happens to its ancestors — never longer. Design with that in mind: a child's timeout is a ceiling on how long it personally is willing to wait, not a guarantee of how long it gets to run.

New: a real context tree in burrow

burrow's Cobra commands already run inside a context tree, whether you've used it or not — cobra.Command has a Context() method, and rootCmd.ExecuteContext(ctx) is how you supply the root of that tree from main. Every command's RunE can retrieve it with cmd.Context() and derive its own child from there, instead of starting fresh from context.Background().

  • Stuck? Show the change 
    ctx, cancel := context.WithCancel(context.Background())
defer cancel()

if err := rootCmd.ExecuteContext(ctx); err != nil {
	fmt.Fprintln(os.Stderr, err)
	os.Exit(1)
}
  • Stuck? Show the change 
    RunE: func(cmd *cobra.Command, args []string) error {
	ctx, cancel := context.WithTimeout(cmd.Context(), 500*time.Millisecond)
	defer cancel()
	return duTop(ctx, path, n)
},

    Nothing about duTop itself changes — it still just takes whatever ctx it's handed. Only where that ctx ultimately traces back to changed.

    Checkpoint

    burrow du top --path scratch --n 10 behaves identically to before — same output, same timeout behavior. This step doesn't change anything observable yet; it's setting up the tree Lesson 4 actually uses.

  • Stuck? Show the temporary code 
    ctx, cancel := context.WithCancel(context.Background())

go func() {
	time.Sleep(300 * time.Millisecond)
	cancel() // simulates something external canceling the whole program
}()

if err := rootCmd.ExecuteContext(ctx); err != nil {
	fmt.Fprintln(os.Stderr, err)
	os.Exit(1)
}
    Checkpoint

    The command fails at around 300ms, with an error containing context canceled — not context deadline exceeded, and nowhere near its own 10-second timeout. The root's cancellation reached all the way down into duTop's ctx.Done(), through cmd.Context(), exactly as the scratch demo predicted. Remove the temporary goroutine and restore a real timeout afterward.

Idiom

That temporary goroutine was a stand-in for something real: a process-level signal telling the whole program to stop. Lesson 4 replaces it with exactly that — a real Ctrl+C, wired to the same root cancel() through os/signal.NotifyContext, so pressing it during a long du top stops the command cleanly instead of the whole process being killed out from under it.

burrow now has a genuine context tree: a root tied to the whole program's run, with each command deriving its own timeout from it rather than from a disconnected context.Background(). Lesson 4 gives that root a real reason to cancel early.
