Cancellation on Interrupt

Rebuild Lesson 3's context tree in burrow from memory first. Then replace the simulated external cancellation with a real one: your own Ctrl+C.

Lesson 3 proved burrow's context tree really works by simulating an external cancellation — a goroutine that slept 300ms and called the root's cancel(), standing in for "something outside this program decided to stop it." Today that simulation becomes real. os/signal.NotifyContext turns an actual OS signal — Ctrl+C in your terminal — into exactly the same kind of cancellation, reaching the same root context, propagating through the same tree.

New: turning a real signal into a real context

signal.NotifyContext(parent, signals...) returns a context derived from parent, plus a stop function. The moment your process receives any of the listed signals (os.Interrupt is Ctrl+C; syscall.SIGTERM is the polite "please stop" most process managers send), that context is canceled — same Done(), same Err(), same everything you've already been using.

  • Stuck? Show the code 
    package main

import (
	"context"
	"fmt"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func longRunningWork(ctx context.Context) error {
	select {
	case <-time.After(10 * time.Second):
		fmt.Println("work: finished normally")
		return nil
	case <-ctx.Done():
		return fmt.Errorf("work: interrupted: %w", ctx.Err())
	}
}

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	fmt.Println("pid:", os.Getpid())
	if err := longRunningWork(ctx); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}
    Checkpoint

    Run it, then press Ctrl+C in that same terminal within 10 seconds. It prints work: interrupted: context canceled and exits with status 1 — no stack trace, no "killed," just an ordinary error your own code produced and handled.

    Start a du top against a fixture with a deliberately slow entry and a generous timeout (10+ seconds), so it's still running. Press Ctrl+C. The command stops within a fraction of a second, printing an error containing context canceled — nowhere near its own long timeout. This is Lesson 3's simulated cancellation, now genuinely triggered by you, reaching all the way down through cmd.Context() into duTop's own ctx.Done().

Idiom

Watch what happens if some later code between the cancellation and your program's actual exit ever hangs — a goroutine that doesn't check ctx, say. With stop() only deferred to run at the very end, a second Ctrl+C during that hang does nothing at all: NotifyContext is still intercepting the signal, silently, and your process just sits there. Calling stop() immediately once you've already reacted to the first cancellation — not waiting for the deferred call — hands signal handling back to the normal OS default, so a second Ctrl+C actually terminates the process instead of being swallowed. For a command as fast-exiting as burrow's, the deferred-only version is fine; for anything with a real cleanup phase after cancellation, call stop() as soon as you've received the first signal, not only at the end.

burrow can now be stopped from outside, cleanly, the moment you ask it to — not just when its own timeout happens to elapse. Lesson 5 turns to a different, unrelated thing a context can carry: request-scoped values, and exactly how narrow that use case is meant to be.

Something unclear — why a second Ctrl+C can get silently swallowed if stop() is only deferred, why SIGTERM is worth listening for alongside os.Interrupt, what happens to goroutines that never check ctx.Done() at all when cancellation happens, anything else? Ask your teacher (me) before moving on.
