WithCancel and WithTimeout on duTop

Rebuild Lesson 1's watch/cancel demo from memory first. Then replace duTop's hand-rolled timeout with the real thing.

Go Concurrency Basics' Lesson 6 left duTop with a package-level const duTimeout and a select racing a real channel against time.After(duTimeout). It works, but the deadline lives entirely inside duTop — nothing about it can be handed to a caller, shortened by an outer function, or shared with anything else that also needs to know "has this operation run out of time." context.WithTimeout fixes all of that with one change: the deadline becomes a real context, created by whoever calls duTop, not a constant baked into the function itself.

New: duTop takes a context

context.WithTimeout(parent, d) is context.WithCancel plus a built-in timer: the returned context cancels itself automatically once d elapses, with the exact same Done()/Err() mechanics from Lesson 1 — you just get context.DeadlineExceeded back instead of context.Canceled when it fires on its own.

		return fmt.Errorf("du top: %w waiting for %d of %d entries", ctx.Err(), len(dirs)-i, len(dirs))

    %w wraps ctx.Err() inside the returned error rather than just interpolating its text — this preserves it as a real wrapped error, so a caller could later check it with errors.Is(err, context.DeadlineExceeded) if it ever needed to distinguish "timed out" from any other failure programmatically, not just read it in a message.

    ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
defer cancel()

    defer cancel() here matters even though the timeout will often fire (or the function will simply return) before the full duration elapses — it releases the timer immediately on every exit path, rather than leaving it running uselessly until its own deadline arrives.

Idiom

Notice what moved: the timeout's actual duration used to be a constant baked directly inside duTop; now it's a choice made by whoever calls duTop, at the moment they call it. This is the real payoff of taking a context.Context as a parameter instead of managing a deadline internally — the function that does the work no longer decides how long it's allowed to take. A caller in a hurry can pass a short timeout; a caller running as a background batch job could pass context.Background() with no timeout at all; a caller already inside its own deadline (once Lesson 3 covers context trees) can pass that same context straight through. duTop itself doesn't need to change for any of those cases — it just respects whatever context it's handed.

duTop now takes its deadline from the outside, using the real cancellation mechanism the standard library gives every function that might need to stop early. Lesson 3 goes one level further: what happens once a context is passed through more than one layer of function calls, and why canceling the top of that chain reliably cancels everything underneath it.

Something unclear — why the error wraps ctx.Err() with %w instead of just including its text, what changes if you pass context.Background() with no timeout at all, why the timeout is created in the caller instead of inside duTop itself, anything else? Ask your teacher (me) before moving on.
