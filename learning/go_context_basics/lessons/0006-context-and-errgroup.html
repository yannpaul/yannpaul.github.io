Context and errgroup

Rebuild Lesson 5's WithValue collision demo from memory first. Then watch duTop waste five real seconds — and fix it with one function you already know.

go_concurrency_basics Lesson 8 replaced duTop's hand-rolled worker pool with a plain errgroup.Group: g.Go, g.SetLimit, g.Wait() returning the first error. That version has a real gap you haven't seen yet: when one goroutine fails, the others have no idea. They keep running — potentially for a long time — computing results nobody's going to use, because the whole call is about to fail anyway. errgroup.WithContext closes that gap using exactly the cancellation mechanism this course has spent five lessons on.

  • Checkpoint

    duTop takes the full ~5 seconds to return, even though the broken entry failed almost instantly. g.Wait() still has to wait for every goroutine to actually finish — including the one whose result nobody will ever see, since the whole call is already doomed to return that first error.

New: errgroup.WithContext

errgroup.WithContext(parent) returns a group exactly like before, plus a derived context. The moment any goroutine started with g.Go returns a non-nil error, that context is canceled — automatically, no extra code. Any other goroutine that's watching ctx.Done() can notice and stop early instead of running to completion pointlessly.

  • Stuck? Show the code 
    package main

import (
	"context"
	"errors"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

func slowTask(ctx context.Context, name string, d time.Duration) error {
	select {
	case <-time.After(d):
		fmt.Println(name, "finished normally")
		return nil
	case <-ctx.Done():
		fmt.Println(name, "stopped early:", ctx.Err())
		return ctx.Err()
	}
}

func main() {
	g, ctx := errgroup.WithContext(context.Background())

	g.Go(func() error {
		return slowTask(ctx, "task-fails-fast", 100*time.Millisecond)
	})
	g.Go(func() error {
		return errors.New("deliberate failure")
	})
	g.Go(func() error {
		return slowTask(ctx, "task-would-run-5s", 5*time.Second)
	})

	start := time.Now()
	err := g.Wait()
	fmt.Println("g.Wait() returned after", time.Since(start), "with err:", err)
}
    Checkpoint

    g.Wait() returns in well under a second — not 5 — with err: deliberate failure. Both other goroutines print stopped early: context canceled. The one deliberate failure canceled ctx, and everything watching it noticed almost immediately.

    func duTop(ctx context.Context, root string, n int) error {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return err
	}

	dSizes := make([]dirSize, len(dirs))
	g, ctx := errgroup.WithContext(ctx) // shadows the parameter on purpose
	g.SetLimit(maxWorkers)

	for i, d := range dirs {
		g.Go(func() error {
			p := filepath.Join(root, d.Name())
			s, err := sizeOf(ctx, p)
			if err != nil {
				return err
			}
			dSizes[i] = dirSize{p, s}
			return nil
		})
	}

	if err := g.Wait(); err != nil {
		return err
	}

	sort.Slice(dSizes, func(i, j int) bool { return dSizes[i].Size > dSizes[j].Size })
	n = min(len(dSizes), n)
	for _, d := range dSizes[:n] {
		fmt.Printf("%10d %q\n", d.Size, d.Name)
	}
	return nil
}

    Shadowing ctx with the errgroup's own derived one is deliberate, not an accident to fix — every goroutine started after that line should watch the errgroup's context (which also carries duTop's own timeout as its parent, from Lesson 2, plus the root's cancellation from Lesson 4), not a stale reference to the one duTop was originally called with.

    Checkpoint

    Re-run the same broken-plus-slow fixture. duTop now returns in well under a second — not 5 — with the broken entry's error. The slow entry's sizeOf call noticed the canceled context and gave up almost immediately, instead of finishing a computation nobody needed. go run -race . stays clean.

Idiom

This only works because sizeOf actually checks ctx.Done() somewhere in its slow path. A canceled context doesn't reach into running code and stop it by force — nothing in Go does that safely. Every function on the hot path of something that might need to give up early has to cooperate, by checking its context at the points where waiting could actually be long: before a slow operation, inside a loop over many items, around a blocking read. errgroup.WithContext gives you the cancellation signal for free; propagating it into every place that could actually benefit from checking it is still your job.

You've now used context cancellation to stop duTop on a timeout (Lesson 2), from a real Ctrl+C (Lesson 4), and now from a sibling goroutine's own failure — three different sources, the same Done()/Err() mechanism underneath all of them.
