Recap — from memory, no hints

Answer each question before checking — this is retrieval practice, not a reading exercise. Every option gets an explanation once you answer, right or wrong.

1. In Lesson 1, calling a context's cancel function a second time printed no error and didn't panic. What does this actually guarantee?

  • A second call to cancel is a documented no-op — safe to call defensively (e.g. via defer cancel()) even if the context was already canceled some other way.
  • Calling cancel twice cancels the context's parent as well as the context itself.
  • Calling cancel twice resets the context back to its original, uncanceled state.
  • Calling cancel twice is undefined behavior that happens not to crash in simple programs.

2. You replaced duTop's select-against-time.After timeout with context.WithTimeout. What actually changed about its behavior, not just its code?

  • None — they produce identical behavior, context.WithTimeout is just a cleaner way to write the same select/time.After pattern.
  • The timeout now originates from whoever calls duTop, not from a constant baked into duTop itself — different callers can choose different timeouts, or none at all, without duTop's own code changing.
  • It makes duTop's goroutines run faster.
  • It removes the need for a select statement inside duTop entirely.

3. A context.WithTimeout(parent, 10*time.Second) child's own 10 seconds hasn't elapsed, but its parent is canceled after 2 seconds. What happens to the child?

  • Nothing — a context's own deadline always takes priority over anything that happens to its parent.
  • The child ends at the 2-second mark too, reporting context canceled (not context deadline exceeded) — its real lifetime is always the shorter of its own deadline and whatever happens to its ancestors.
  • The child keeps running until its own 10-second deadline, then reports context canceled.
  • The parent's cancellation is queued and only takes effect once the child's own timeout would have fired anyway.

4. Your program's stop() (from signal.NotifyContext) is only deferred to run at the very end, and code between the first Ctrl+C and program exit hangs. What happens if the user presses Ctrl+C a second time?

  • Nothing visible — NotifyContext is still intercepting the signal, so the second Ctrl+C is silently absorbed and the program keeps hanging.
  • The second Ctrl+C is ignored by the operating system entirely, regardless of your program.
  • The second Ctrl+C immediately force-kills the process, the same as if NotifyContext were never used.
  • The second Ctrl+C cancels the context a second time, running any cleanup code twice.

5. Two unrelated pieces of code both used the bare string "requestID" as a context.WithValue key, and one silently clobbered the other's value. What specifically would have prevented this?

  • Using a longer, more specific string, like "myPackageRequestID", instead of a generic one.
  • Each defining its own unexported key type — two distinct types are never equal to each other via ==, even if both happen to have the same underlying value.
  • Calling context.WithValue with a sync.Mutex held.
  • Storing the value in a package-level variable instead of the context.

6. You made sizeOf check ctx.Done() during its slow path, then switched duTop to errgroup.WithContext. Why was that check inside sizeOf itself still necessary — why doesn't errgroup.WithContext stop a slow goroutine on its own?

  • Canceling a context never forcibly stops running code — it only closes a channel that already-running code has to actively check to notice anything happened at all.
  • It wasn't necessary — errgroup.WithContext always stops every goroutine's execution immediately once one of them fails.
  • SetLimit requires every goroutine to check ctx.Done(), or it refuses to enforce the concurrency limit.
  • It only needed ctx to log a message, not for any functional reason.
