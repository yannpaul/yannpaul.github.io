TLS and Certificates

The mechanism behind the padlock, and why where it terminates matters as much as whether it's there.

Every hop so far has been waved at as "encrypted" without saying how. This lesson opens that box just enough to make one fact land precisely: encryption between the browser and Cloudflare says nothing at all about what happens between Cloudflare and your origin — that's a separate, configurable decision, and getting it wrong quietly undoes most of the point.

The handshake, in one pass

Before a browser and a server exchange any real data, TLS runs a handshake that ends with both sides holding the same secret key, without ever sending that key across the network in the clear:

StepWhat happens
ClientHelloThe client proposes: which TLS versions and cipher suites it supports, plus a random value.
ServerHello + certificateThe server picks a cipher suite from the client's list and sends its digital certificate — its claimed identity.
Key exchangeBoth sides derive a shared secret using asymmetric cryptography, without ever transmitting the secret itself.
Session keyThat shared secret becomes a symmetric key, used to encrypt every byte of the actual conversation from here on.
Why two kinds of cryptography

Asymmetric cryptography (a public/private key pair) is what makes it possible for two strangers to agree on a secret over an open connection without ever sending the secret itself — but it's computationally expensive. Symmetric cryptography (one shared key both sides already have) is fast enough for the actual data. TLS uses the slow, safe method for a few milliseconds just to bootstrap the fast one.

The certificate chain

The certificate a server presents isn't self-certifying — trusting it means trusting whoever signed it. Browsers and operating systems ship with a built-in list of root certificate authorities (CAs) they trust unconditionally. A server's certificate (the leaf, issued for one specific domain) is typically signed by an intermediate CA, which is itself signed by one of those trusted roots — a chain of signatures the client can walk and verify without ever needing to trust the leaf directly.

Where termination happens — and why it's a choice, not a given

Lesson 1 said Cloudflare "terminates TLS" without saying what that costs or configures. Terminating TLS means Cloudflare is the one actually running the handshake above with the browser, decrypting the request, and deciding what to do next — which means the browser-to-Cloudflare leg and the Cloudflare-to-origin leg are two separate encrypted (or not!) connections, not one continuous encrypted tunnel. Cloudflare gives you four choices for that second leg:

ModeCloudflare → originOrigin cert validated?
FlexiblePlain HTTP — unencryptedn/a
FullHTTPS — encryptedNo — any certificate is accepted, even an expired or self-signed one
Full (Strict)HTTPS — encryptedYes — must be valid, unexpired, and from a trusted CA (public or Cloudflare's own Origin CA)
The trap in "Flexible"

A visitor sees the padlock and a valid https:// URL — because their connection to Cloudflare really is encrypted. But under Flexible mode, the Cloudflare-to-origin leg (Lesson 2's load balancer, sitting in a public subnet, potentially crossing the open internet to reach it) is plain HTTP. Anything sensitive in that request — a session cookie, a password on login — travels that second leg in the clear. The padlock is telling the truth about one hop and saying nothing about the other.

Think first: Full mode encrypts the Cloudflare-to-origin leg but doesn't validate the origin's certificate. Is that actually safe against an attacker sitting on the network path between Cloudflare and your origin?

No — encryption without validation only stops a passive eavesdropper from reading the traffic. It doesn't stop an active attacker from presenting their own certificate and impersonating your origin, since Cloudflare in Full mode will accept any certificate at all, expired or self-signed included. Full (Strict) closes exactly this gap by requiring the certificate to be valid and from a trusted CA — which is why it's the mode worth actually running, not just "Full."

A site runs Cloudflare in Flexible mode. A visitor's browser shows a secure padlock. Is the request encrypted all the way to the application code running in the origin's Kubernetes Pod?

  • Yes — the padlock means the whole path is encrypted end to end.
  • No — encryption stops at Kong, since that's where the request enters the private subnet.
  • No — Flexible mode only encrypts the browser-to-Cloudflare leg; everything past Cloudflare is unencrypted.
  • Yes, but only if the origin's Kubernetes cluster has its own separate certificate installed.

A preview: what if both sides need to prove who they are?

Everything above is one-way authentication — the client verifies the server's identity via its certificate, but the server has no cryptographic proof of who the client is (that's what login credentials are for, separately, at the application layer). Mutual TLS (mTLS) is the same handshake with both sides presenting a certificate, so each end cryptographically proves its identity to the other. This isn't hypothetical or exotic — it's already running inside this exact stack: Kong's own control-plane and data-plane nodes authenticate to each other via mTLS, and Lesson 10 will show it as the mechanism Istio's Citadel uses to give every Pod a verifiable identity. Same handshake as above; the difference is nobody skips the certificate check in either direction.
