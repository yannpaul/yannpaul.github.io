AuthN vs. AuthZ, End to End

The same two questions, asked by four different layers — and why a static asset barely asks them at all.

Every lesson since 4 has quietly reused the same two words. Time to collect them: authentication ("who are you, proven") and authorization ("given who you are, what are you allowed to do"). This lesson lines up every layer that asks one or both of those questions, then answers the other thing this course promised early on — why a static asset and a restricted one take genuinely different paths.

Four layers, two questions, four different answers

LayerAuthenticates?Authorizes?
Cloudflare edge (Lesson 4)No — the WAF/DDoS checks filter traffic, not identityNo
Kong gateway (Lesson 6)Yes — validates the end user's API key/JWTCoarse only — "may this Consumer call this Route at all"
Service mesh / Citadel (Lesson 10)Yes — mTLS proves service identity, not end-user identityYes — AuthorizationPolicy decides which service may call which
Application codeRarely — usually trusts the identity Kong already establishedYes — the fine-grained "can user 42 edit resource 99" business rule

Notice what's missing: nobody before the application layer checks whether this specific user can touch this specific record. Kong knows the caller is a valid, authenticated user; the mesh knows the calling service is who it claims to be; only the application actually holds the business rule ("orders belong to the account that created them") needed to answer the fine-grained question. Every layer before it narrows down who could possibly be asking, but the last mile of authorization always lands in the code that knows the data.

A request carries a perfectly valid JWT — Kong's jwt plugin passes it through without complaint. The application then rejects the request anyway, because the authenticated user doesn't own the order they're trying to view. What just happened?

  • This is a bug — Kong should have caught this and never let the request through.
  • Kong re-checks authorization internally using its own copy of the ownership data.
  • Kong authenticated the caller successfully; the application then authorized (or in this case, denied) the specific action, which is a separate, later check.
  • The service mesh's AuthorizationPolicy is what actually rejected this request.

Static vs. restricted: why they take different paths

Lesson 4 planted this and deferred it — now it's time to answer directly. A static resource (a JS bundle, a logo, a CSS file) is the same bytes for every visitor, with no notion of "who's asking" baked into the response at all. A restricted resource (an authenticated dashboard, an API response scoped to one account) is different for every caller, and serving the wrong one to the wrong person is a security incident, not a caching optimization.

The one-sentence version

A static resource can skip most of this course's hops entirely, because nobody needs to be authenticated to receive it. A restricted resource can't skip any of them, because every hop from Kong onward exists specifically to answer "who is this, and are they allowed" — questions a static asset never needed asked in the first place.

Think first: a marketing page at /pricing is fully static and cacheable — but it embeds a "Log in" button that calls an authenticated API. Does caching the pricing page at Cloudflare's edge create any risk for the authenticated API call?

No — the two are entirely separate requests on separate paths. Caching /pricing's static HTML at the edge only affects that one response; the authenticated API call the login button triggers is its own request, carrying its own credentials, evaluated fresh by Kong and everything downstream every time. Caching is scoped per-response, not per-page — a cached static shell embedding a link to a dynamic endpoint creates no shortcut into that endpoint at all.
