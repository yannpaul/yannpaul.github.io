Kubernetes Services and kube-proxy

Pods come and go constantly. Something has to give them a stable address anyway.

Lesson 1 called hop 5 "Kubernetes Service: picks one healthy Pod out of possibly many" and moved on. Time to open that box — starting with the problem it exists to solve, since Kubernetes' whole approach to networking only makes sense once you see what it's working around.

The problem: Pods are not stable

A Pod is disposable by design. It gets rescheduled to a different node, restarted after a crash, or replaced entirely during a rolling deploy — and every time, it's assigned a brand-new IP address (Lesson 8 covers exactly how). If Kong, or any other caller, had to track individual Pod IPs directly, every one of those routine events would break every connection pointed at it.

A Service is Kubernetes' fix: a stable virtual IP address and DNS name that sits in front of a set of Pods, so nothing outside that set ever needs to know which specific Pods currently exist behind it.

How a Service knows which Pods are behind it

A Service doesn't point at Pods by name — it points at a label selector (e.g. "every Pod labeled app: orders"). Kubernetes continuously tracks which Pods currently match that selector and are passing their readiness checks, recording the current, healthy set as an EndpointSlice. Add a Pod, remove a Pod, fail a health check — the EndpointSlice updates automatically, with no one editing the Service itself.

Three ways to expose a Service

ClusterIPA stable virtual IP, valid only inside the cluster's own network. The default.Other Pods in the cluster

In this course's map, the Kong data plane Pods typically sit behind a LoadBalancer Service (or the origin load balancer from Lesson 1 points at one) — that's how traffic crosses from "outside the cluster" to "inside it" at all. Everything Kong then forwards onward to your application, though, almost always targets a plain ClusterIP Service — internal traffic never needs a cloud load balancer of its own.

kube-proxy: a configurer, not a proxy in the traffic path

Despite the name, kube-proxy — a process running on every node — doesn't sit in the middle of each connection relaying bytes. In its default mode, it watches Services and EndpointSlices, and translates them into packet-forwarding rules installed directly in the node's kernel (via iptables, or the faster IPVS/eBPF-based alternatives on newer setups). When a packet arrives addressed to a Service's ClusterIP, the kernel itself — not a running kube-proxy process — rewrites the destination to one specific, currently-healthy Pod IP and forwards it on. kube-proxy's job is keeping those kernel rules in sync with reality as Pods and Services change, not sitting in the data path.

The DNS half of the story

Every Service also gets a stable cluster-internal DNS name — my-service.my-namespace.svc.cluster.local — resolved by the cluster's own DNS server (CoreDNS) to the Service's ClusterIP. This is how your application code finds another internal service at all: by name, never by chasing a Pod IP directly.

A Pod backing an orders Service crashes and Kubernetes reschedules it, giving it a new IP. What has to change for other services still calling orders.default.svc.cluster.local to keep working?

  • Every caller must update its configuration with the new Pod IP.
  • A person needs to manually update kube-proxy's rules to point at the new Pod IP.
  • Nothing, from a caller's point of view — the Service's IP and DNS name stay the same; only the EndpointSlice behind it updates.
  • DNS must re-resolve the service name to the new Pod's IP directly.

Think first: why does Kong typically reach your application via a ClusterIP Service rather than a LoadBalancer Service, even though LoadBalancer "does more"?

A LoadBalancer Service provisions a real, often-billed cloud load balancer — useful for the one deliberately-public entry point into the cluster, but wasteful and unnecessary for traffic that's already inside the cluster. Kong is already inside the same network the application Pods are in (or one hop from it); a ClusterIP gives it a stable internal address with none of the external-facing machinery a LoadBalancer adds for traffic that was never going to arrive from outside anyway.
