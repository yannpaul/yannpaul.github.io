API Gateways and Kong

What a plain load balancer doesn't do — and where end-user authentication actually gets checked.

Lesson 1 described Kong as the hop that "checks the request, decides which internal service should handle it," which is also a fair description of a load balancer. This lesson makes the difference precise: a load balancer answers which healthy server; an API gateway answers should this request even proceed, and if so, on what terms — and it answers that question the same way for every route, instead of every service reimplementing it separately.

The problem a gateway solves

Imagine ten internal services, each needing to check an API key, enforce a rate limit, and log every request the same way. Without a gateway, that's the same logic written (and maintained, and inevitably drifted) ten times. An API gateway puts these cross-cutting concerns — the things nearly every route needs, that aren't specific to any one service's business logic — in exactly one place, enforced before a request ever reaches application code.

Kong's model: Services, Routes, Plugins, Consumers

ConceptWhat it is
ServiceOne upstream target — the internal API a group of routes should ultimately reach (e.g. the orders service).
RouteA match rule (host, path, method) that says which incoming requests belong to which Service.
PluginA behavior attached at a chosen scope — global, one Service, one Route, or one Consumer — that runs during the request lifecycle: auth checks, rate limiting, transformation, logging.
ConsumerAn identity Kong tracks credentials for — an API key, a JWT signing secret, an OAuth client — used by auth plugins to know who is calling.

A request arrives, Kong matches it to a Route, resolves the Route's Service, and runs every Plugin that applies to that request — in scope order — before ever proxying the request onward.

Where end-user authentication actually happens

This is the detail worth being precise about: when a plugin like key-auth or jwt is attached to a Route, an invalid or missing credential means Kong itself returns 401 Unauthorized — your upstream service, and the Kubernetes cluster behind it, never see the request at all. Kong checks the JWT's signature and claims (issuer, expiry) against the Consumer it identifies from the token; a bad signature or an expired token fails right there, at the gateway, before hop 5 of Lesson 1's map even begins.

AuthN, not AuthZ — a distinction Lesson 11 makes precise

Kong answering "is this a valid, recognized caller?" is authentication. Whether that caller is allowed to, say, delete this specific order is a different question — authorization — and it's usually left to the application (or, as Lesson 10 will show, partly to the service mesh) rather than the gateway. Kong's plugins can do coarse authorization (this Consumer may call this Route at all), but fine-grained "can user 42 edit resource 99" logic almost always belongs downstream, where the business rules actually live.

A client sends a request with an expired JWT to a Kong Route protected by the jwt plugin. What actually returns the 401, and does the request reach the Kubernetes cluster?

  • The upstream application service returns the 401, after Kong forwards the request and lets the app validate the token.
  • Kong itself returns the 401, and the request never reaches the Kubernetes Service or any Pod.
  • Cloudflare returns the 401 at the edge, before the request ever reaches Kong.
  • It's inconsistent — sometimes Kong catches it, sometimes it slips through to the application.

Control plane and data plane

Kong's own architecture splits into two roles: control plane nodes hold the configuration (Routes, Services, Plugins) and the database connection; data plane nodes proxy the actual live traffic, using a copy of that configuration pushed down to them. Data plane nodes initiate the connection to the control plane and authenticate to it via mTLS — the exact mechanism Lesson 5 previewed, already in production use one layer below the traffic you've been tracing. If the control plane goes offline, data planes keep serving traffic on their last known configuration; they just can't receive updates until it's back.

Think first: why split configuration (control plane) from live traffic handling (data plane) at all, instead of one Kong process doing both?

It's the same motivation as most of this course's other splits: an operator changing configuration shouldn't be able to destabilize the path every live request is currently flowing through, and a data plane node handling thousands of requests per second shouldn't also be managing a database connection for config writes. Separating them means the thing under the most load (traffic proxying) stays lean and focused, while the thing doing occasional, heavier work (config management) doesn't sit in the hot path at all.

Kong as a Kubernetes Ingress Controller

So far this lesson has treated Kong as a standalone proxy. In front of a Kubernetes cluster specifically, Kong usually runs as the Ingress Controller: it watches the cluster's Ingress/Gateway API resources and translates them into its own Routes, Services, and Plugins automatically, in real time, as those Kubernetes resources change. That's the bridge into Lesson 9, which is dedicated entirely to unpacking what an Ingress resource is and exactly how Kong plays this role — Kong's data plane is, in that deployment, one more thing running inside (or just in front of) the very cluster it's routing into.
