Capstone: Trace a Real Request

Fourteen lessons, one map. Time to walk it end to end — twice — then see if it transfers.

Three parts: a quick interleaved recall across all fourteen lessons, two full request traces walked side by side, and a new scenario this course never touched, to test whether the mental model actually generalizes or just memorized well.

Part 1: Rapid recall

One question per lesson, deliberately out of order — interleaving is harder than reviewing in sequence, which is the point.

(Lesson 9) An Ingress resource exists in the cluster, but no Ingress Controller is watching for its IngressClass. What happens to matching traffic?

  • Kubernetes provisions a default controller automatically.
  • The nearest Service handles the routing directly.
  • Nothing — the resource is inert config until a matching controller exists.
  • Kong claims it by default regardless of IngressClass.

(Lesson 2) A subnet's route table has no route to an internet gateway, but an instance in it has a public IP attached. Is it reachable from the internet?

  • No — routing, not the address itself, decides reachability.
  • Yes — any public IP is reachable regardless of routing.
  • Only if a NAT gateway is also present.
  • Only during the TCP handshake, not afterward.

(Lesson 5) Cloudflare is set to Flexible mode. Is the Cloudflare-to-origin leg encrypted?

  • Yes, always.
  • Yes, but only the certificate isn't validated.
  • Only if the origin requests it.
  • No — Flexible mode leaves that leg as plain HTTP.

(Lesson 7) kube-proxy, in its default mode, relays traffic through a running process sitting between client and Pod. True or false?

  • True — kube-proxy proxies every packet itself.
  • False — it programs kernel rules (iptables/IPVS/eBPF) that the kernel itself uses to forward packets.
  • True, but only for LoadBalancer-type Services.
  • False — CoreDNS handles all the forwarding instead.

(Lesson 4) A request for a static image gets a Cloudflare cache HIT. Did it reach the origin load balancer?

  • Yes, to log the request.
  • Yes, but only to revalidate the cached copy.
  • No — a HIT is served entirely from Cloudflare's edge.
  • Only if the WAF flagged it first.

(Lesson 10) PeerAuthentication and AuthorizationPolicy answer the same question. True or false?

  • False — one governs mTLS strictness (AuthN), the other governs access rules (AuthZ).
  • True — both configure certificate rotation.
  • True — both are enforced by Kong, not Istio.
  • False — AuthorizationPolicy is deprecated in favor of PeerAuthentication.

(Lesson 3) A route table has both a /16 and a more specific /24 entry that could match a packet's destination. Which wins?

  • The /16, since broader routes take priority.
  • The /24, since it's the more specific (longest prefix) match.
  • Whichever route was added first.
  • Neither — the packet is dropped as ambiguous.

(Lesson 8) Two Pods on different nodes communicate via a VXLAN overlay. What is actually happening to their packets?

  • They travel unwrapped, routed by BGP.
  • They pass through Kong as an intermediate hop.
  • They're translated via NAT at each node.
  • They're encapsulated inside a packet addressed node-to-node, tunneling across the physical network.

(Lesson 13) A 404 comes back with Kong's generic error body, no custom branding. Most likely cause?

  • No Kong Route matched this host/path — a routing-config issue, not an application one.
  • The application's database query returned zero rows.
  • Cloudflare's cache expired.
  • The service mesh rejected the request for a mismatched identity.

(Lesson 6) An expired JWT reaches a Kong Route with the jwt plugin attached. Does the request reach the Kubernetes Service?

  • Yes, and the Service itself rejects it.
  • Yes, and the application rejects it.
  • No — Kong returns 401 itself, before the Service is ever involved.
  • It depends on which Pod would have handled it.

(Lesson 1) On the six-hop map, which two hops does a Cloudflare cache HIT skip entirely?

  • DNS and the Cloudflare edge.
  • The origin load balancer and everything inside Kubernetes.
  • Only Kong, while Kubernetes still runs a health check.
  • The TLS certificate chain validation step.

(Lesson 12) A valid JWT passes Kong's auth check, but the application still returns 403. What's the correct read?

  • This shouldn't happen — Kong's approval should be final.
  • The token must actually be invalid despite Kong's check.
  • The service mesh silently overrode Kong's decision.
  • Authentication succeeded; authorization — a separate, later question — failed instead.

(Lesson 14) A Kubernetes Service matches traffic by ClusterIP and port, with no idea what HTTP host or path was requested. Which OSI layer does that put it at?

  • Layer 2 — it's just switching frames.
  • Layer 3 — it only knows the IP address.
  • Layer 4 — IP address and port, no content awareness.
  • Layer 7 — it reads the full HTTP request.

(Lesson 11) An external API is called from inside the mesh, but with `outboundTrafficPolicy` set to REGISTRY_ONLY and no ServiceEntry registered for it. What happens?

  • The call passes through unobserved, same as the default ALLOW_ANY behavior.
  • The sidecar blocks the call — an unregistered destination isn't in Istio's service registry at all.
  • Kubernetes' own NetworkPolicy decides instead, ignoring Istio's setting entirely.
  • An AuthorizationPolicy on the destination decides instead.

Part 3: Transfer — a new scenario

This course never covered video conferencing. If the mental model actually transferred, it shouldn't matter.

A SaaS video-conferencing product runs the same stack this course built: Cloudflare in front, Kong as the API gateway and Kubernetes Ingress Controller, a Kubernetes cluster with an Istio mesh inside. A user joins a meeting: the browser first calls POST /api/meetings/42/join (authenticated, returns a short-lived signaling token), then opens a long-lived WebSocket connection to a signaling-service Pod using that token, which in turn calls an internal media-relay-service to actually route audio/video packets between participants.

Think first: which layer(s) authenticate the WebSocket connection to signaling-service, and which authenticate the internal signaling-service → media-relay-service call? Are they the same mechanism?

No — they're different layers doing different jobs, exactly as Lesson 12's table laid out. The WebSocket connection carries the short-lived signaling token from the join call; Kong (or the app itself, since Kong's plugin support for long-lived WebSocket upgrades varies) validates that end-user-facing credential once at connection time. The internal signaling-service → media-relay-service call is a service-to-service hop entirely inside the mesh — it's authenticated via mTLS and each side's SPIFFE identity (Lesson 10), with an AuthorizationPolicy deciding whether signaling-service's identity is even allowed to call media-relay-service at all — enforced, per Lesson 10, on media-relay-service's own inbound side, not as a rule attached to signaling-service's outbound calls. The end user's identity and the calling service's identity are two separate proofs, checked by two separate mechanisms.

Think first: would Cloudflare ever return a cache HIT for the join call's response? Why or why not?

No. The join response contains a signaling token scoped to one specific user and one specific meeting — serving a cached copy to the next caller would hand them someone else's session token entirely, a severe security failure, not a performance win. This is Lesson 12's static-vs-restricted distinction in its sharpest form: this response is about as restricted as a response gets, and Cloudflare (correctly configured) would mark it DYNAMIC and never cache it regardless of any Cache-Control header claiming otherwise on a response like this.

Think first: a user reports "meeting join works, but no video ever appears." Using Lesson 13's diagnostic habits, what's your first move — and what would distinguish a Kong-layer problem from a mesh-layer problem here?

Since the join call itself succeeds (Kong's auth check and Kubernetes routing to signaling-service are both working), the failure is most likely one hop further in: the internal signaling-service → media-relay-service call. Check that hop specifically — a mesh-layer problem (an AuthorizationPolicy blocking the call, or strict mTLS rejecting an unexpected identity) would show up as a connection failure or 403-equivalent between those two specific Pods, visible in the mesh's own logs/metrics, not as anything Kong or Cloudflare would ever see or report — those two layers already did their job successfully and have no visibility into a purely internal, Kong-bypassing service-to-service call.

Think first: media-relay-service also needs to reach a third-party STUN/TURN service out on the open internet to help participants behind restrictive NATs connect. What does that call need that a purely internal call to signaling-service doesn't?

A ServiceEntry (Lesson 11) registering that external STUN/TURN host into Istio's service registry — without it, and if the mesh runs with outboundTrafficPolicy: REGISTRY_ONLY, the sidecar has no way to know the destination is allowed and blocks the call outright. A purely internal call to signaling-service needs no such registration, since Kubernetes' own Service object already makes it a known, in-mesh destination. This is the same "is this destination even known" gate Lesson 11 walked through with external APIs generally — a third-party real-time service is just another instance of it.
