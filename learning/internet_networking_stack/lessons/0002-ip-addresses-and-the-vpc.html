IP Addresses and the VPC

Why Kong and your Pods aren't directly reachable from the internet — and Cloudflare is.

Lesson 1 ended on a claim worth justifying properly: only some of the six hops have an address the public internet can reach at all. This lesson gives you the vocabulary — public vs. private IP addresses, and the VPC that groups them — to see exactly where that line falls, and why it falls there on purpose.

What an IP address actually is

An IP address is a number that identifies one network interface — 203.0.113.10 in the common (IPv4) format, four bytes written as dotted decimal. Every hop in Lesson 1's chain has one. The question this lesson answers is: which of those addresses can a stranger on the internet actually send a packet to?

Public vs. private address space

Not every IP address is globally reachable. A set of address ranges was set aside specifically to never be routed on the public internet — routers everywhere are configured to drop or ignore them. Anyone can reuse these ranges internally, which is exactly why your home router, your company's office network, and a stranger's office network can all have a device at 192.168.1.5 without conflict: none of those addresses ever needs to be globally unique, because none of them is ever routed past your own network's edge.

The private ranges (RFC 1918)
RangeTypical use
10.0.0.0/8Large networks — this is what most cloud VPCs use
172.16.0.0/12Medium networks; also Docker's default bridge range
192.168.0.0/16Small networks — most home routers

Everything outside those ranges is, in principle, a public address — globally unique, and routable by the internet's backbone. Cloudflare's anycast addresses from Lesson 1 are public. Your company's actual servers, more often than not, are not — and that's a choice, not an accident.

The VPC: your own private network, carved up

A VPC (Virtual Private Cloud) is an isolated slice of a cloud provider's network that a company controls — its own private address space, its own routing rules, walled off from every other customer's VPC. Inside it, the company divides addresses into subnets, and — this is the part people get wrong first — a subnet isn't "public" or "private" because of a label someone picked. It's public or private because of what its route table says:

  • A subnet is public if its route table sends internet-bound traffic (0.0.0.0/0) to an internet gateway — a direct door to the public internet.
  • A subnet is private if it has no such route. Traffic destined for the internet instead goes to a NAT gateway, which sits in a public subnet and translates outbound traffic on the private instance's behalf — letting it call out to the internet (say, to pull a container image) without ever being reachable from it.
The gotcha worth knowing cold

An instance in a private subnet can technically still have a public IP address assigned to it — and still be unreachable from the internet, because the subnet's route table has no path to an internet gateway for inbound traffic to travel back on. "Private subnet" is a statement about routing, not about which addresses happen to be attached to a machine.

Placing Lesson 1's hops on the map

Here's a typical shape for a SaaS company's own infrastructure — everything after Cloudflare, which isn't in this VPC at all; it's part of Cloudflare's own network, sitting in front of it.

Company VPC — 10.0.0.0/16
Public subnet — route to Internet Gateway
Origin load balancer public IP
NAT gateway public IP
Private subnet — route to NAT Gateway
Kong gateway 10.0.2.11
Kubernetes worker nodes 10.0.2.x
Pods (CNI-assigned) 10.0.3.x

Only the load balancer has an address the internet can dial directly — and in practice, even that's usually locked down to accept traffic only from Cloudflare's published IP ranges, not the whole internet. Kong, the Kubernetes nodes, and every Pod live on private addresses one or two layers further in. A Pod's IP, assigned by the cluster's CNI plugin, is typically private even relative to the node it runs on — reachable from other things inside the cluster's network, and from nowhere else. (You'll meet the CNI properly in Lesson 8.)

A Kubernetes worker node in a private subnet has a public IP address attached to it by mistake, but its subnet's route table still only routes internet-bound traffic to a NAT gateway. Can a stranger on the internet reach it directly?

  • Yes — any machine with a public IP address is reachable from the internet.
  • No — the subnet's route table has no path from the internet gateway, so the address being public doesn't matter.
  • Yes, but only through the NAT gateway, which forwards inbound connections to it.
  • It depends on whether Kong is configured to allow it.

Think first: why put the load balancer in a public subnet at all, instead of hiding everything behind Cloudflare and a NAT gateway?

Something has to be the one thing with a real, stable, internet-reachable address for Cloudflare to forward traffic to — a NAT gateway only handles outbound traffic initiated from inside the VPC, it doesn't accept inbound connections from the internet at all. The load balancer is that one deliberately-exposed door; everything behind it — Kong, the cluster, your Pods — stays on private addresses precisely because nothing past that door needs to be reachable any other way.

Answering Lesson 1's open thread

This is why Lesson 1's quiz ruled out "Kong" and "the Kubernetes Service" as the address DNS could hand back: neither has a public, internet-routable address at all. Only Cloudflare's edge (outside the VPC entirely) and, one hop further in, the load balancer (the one deliberately public resource inside it) do.
