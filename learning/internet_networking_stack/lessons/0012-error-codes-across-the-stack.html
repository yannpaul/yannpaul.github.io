Error Codes Across the Stack

Every hop in this course can fail. Each one fails with a different, readable signature.

Every lesson so far has mentioned an error code in passing — 522 in Lesson 4, 401 in Lesson 6. This lesson collects them into one diagnostic map: given a code, which hop produced it, and what does that tell you about where to actually look?

The full map, hop by hop

HopCodeWhat it means
Cloudflare edge (Lesson 4)521The origin refused the connection outright — nothing is listening.
522Cloudflare couldn't complete a TCP connection to the origin within its timeout (Lesson 4).
523The origin's IP is unreachable — often a DNS or routing problem.
524The origin accepted the connection but didn't finish responding before Cloudflare's read timeout (Lesson 4).
Cloudflare edge (TLS)526Full (Strict) mode (Lesson 5) rejected the origin's certificate — invalid, expired, or untrusted.
Kong gateway (Lesson 6)401Missing or invalid credential — an auth plugin rejected the request before it reached your Route's Service.
429A rate-limiting plugin tripped — too many requests from this Consumer/IP in the configured window.
502 / 504Kong reached the Service but got a broken (502) or too-slow (504) response from it — the problem is one hop further in, at Kubernetes.
Kubernetes (Lessons 7–9)503 (from Kong)No healthy Pod was available in the Service's EndpointSlice at all — Kong has nowhere to send the request.
Application code400The request itself is malformed — bad JSON, a missing required field.
403Authenticated, but not authorized for this specific action (Lesson 11) — a business-rule rejection, not a credentials problem.
404 / 500The resource genuinely doesn't exist, or the application code itself threw an unhandled error.
The trap: the same code means different things at different hops

A 404 from Kong means no Route matched the request's host/path at all — a routing-configuration problem, nothing to do with your application. A 404 from your application means the route matched fine, the request reached your code, and your code decided the specific resource doesn't exist. Same three digits, completely different fix. The same is true of 429: it can come from Cloudflare's own rate limiting (Lesson 4) or from a Kong rate-limiting plugin (Lesson 6) — both block the request before your application ever runs, but at different hops, often with different configured thresholds.

Telling them apart without guessing

Two habits resolve most of this ambiguity fast:

  • Check the response headers, not just the code. Cloudflare-originated responses typically carry a cf-ray header; Kong-originated responses typically carry Kong-specific headers (e.g. rate-limit counters) your application never sets. A 404 or 429 with neither is more likely to have come from your own application code.
  • Check the response body. Kong's own error responses have a distinct, generic JSON shape; Cloudflare's error pages are Cloudflare's own branded HTML; your application's 404 page is whatever you built. If the body doesn't look like something your team wrote, it probably didn't come from your application.

A client reports a 429 Too Many Requests. The response body is generic JSON with no branding, and there's no cf-ray header. Which hop most likely produced it?

  • Cloudflare's edge, since 429 is a classic rate-limiting response.
  • Kong's gateway layer, since its rate-limiting plugin returns a generic response by default and the missing cf-ray header rules out the edge.
  • The application itself, since only application code can decide how many requests are "too many."
  • The service mesh, since Citadel enforces rate limits between Pods.

Think first: your team sees an intermittent 503 on one specific Route, correlated with deploys. Using Lessons 7–9's model, what's the most likely mechanism, and where would you look first?

During a rolling deploy, old Pods terminate and new ones start, and there's a brief window where the EndpointSlice behind the Service (Lesson 7) has zero ready Pods — new ones haven't passed their readiness check yet, old ones already have. Kong, unable to reach any healthy Pod for that Service, returns 503. The fix isn't in application code at all: it's tuning the deployment's rollout strategy (e.g. ensuring new Pods are ready before old ones terminate) so the EndpointSlice never goes empty during a rollout.
