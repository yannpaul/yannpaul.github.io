Pod Networking and the CNI

kube-proxy picked a Pod IP. This lesson is how a packet actually gets there.

Lesson 7 ended with kube-proxy rewriting a packet's destination to one specific Pod's IP address. That's a decision, not a delivery — something still has to physically carry the packet from wherever it is to that exact Pod, possibly on a completely different machine. That's the job of the CNI (Container Network Interface).

The one rule every CNI has to satisfy

Kubernetes' networking model rests on a single, deliberately simple guarantee: every Pod gets its own real IP address, and every Pod can reach every other Pod's IP directly — no NAT between Pods, ever. Compare that to Docker's default networking, where containers on one host share an address space translated through the host's own IP — a model that makes "which container is this" ambiguous across machines. Kubernetes' flat, NAT-free model is what lets a Service's EndpointSlice hand kube-proxy a bare Pod IP and trust that it's reachable from anywhere in the cluster, full stop. The CNI plugin is whatever piece of software actually makes that guarantee true on the wire.

Same node: a virtual cable and a virtual switch

When a Pod is created, the CNI plugin creates a veth pair — think of it as a virtual ethernet cable with two ends: one end is placed inside the Pod's own network namespace (where the container sees it as its network interface), the other end stays on the host. That host-side end gets plugged into a bridge (commonly named cni0) — a device, virtual here rather than physical, that joins multiple links into one by forwarding each frame to the port its destination MAC address lives on, with no IP awareness at all ("bridge" and "switch" mean the same thing today; cni0 is a software one, connecting every Pod on that node).

Two Pods on the same node reach each other purely through this bridge — a Layer 2 switching decision, no routing involved at all. "Layer 2" and "routing" aren't the same thing: Layer 2 forwards by MAC address within one shared segment (switching); routing, strictly speaking, is a Layer 3 concept — forwarding by IP address, across networks, which is what Lesson 3's route tables do.

Different nodes: overlay or underlay

Once the destination Pod is on a different node, the packet has to cross the real network connecting the nodes — and that network typically has no idea what a "Pod IP" is. CNIs solve this one of two ways:

ApproachHow it worksTrade-off
Overlay (e.g. VXLAN)Uses tunneling: wraps the Pod-to-Pod packet entirely inside another packet addressed node-to-node — an envelope inside an envelope — so the underlying network only ever reads the outer, node-to-node address and just sees ordinary traffic between two nodes it already knows how to reach.Works on almost any network; costs ~50 bytes of overhead per packet for the extra wrapping.
Underlay / BGPThe physical network itself is taught the Pod IP routes directly (via BGP), so packets travel unwrapped.Zero encapsulation overhead; requires a network fabric that supports BGP peering with the cluster's nodes.
At cluster scale: what overlay actually buys you (and what it costs)

It's tempting to think overlay networking is what separates Pod IPs from node IPs — it isn't; that separation is universal to every CNI, overlay or not. What overlay actually buys you is address-space independence: the Pod-IP range can be a large, private CIDR (a /16, say — 65,536 addresses) with no relationship to your real VPC's address space at all, since it only ever exists inside the tunnel. Cloud-native alternatives that skip the overlay — AWS's VPC CNI, GKE's VPC-native mode — hand Pods real, routable IPs straight from the VPC subnet instead: better performance and native compatibility with VPC-level tooling (security groups, flow logs), but now genuinely bounded by real VPC subnet size, and by a sharper limit most people don't expect first — each node's network interface can only hold so many secondary IPs (an AWS ENI limit tied to instance type), which is a common wall for clusters running many small Pods per node.

Overlay's encapsulation overhead (Lesson 8's table above) also stops being trivial at high east-west throughput — the CPU cost of wrapping/unwrapping every packet, and the reduced effective MTU, is why some large, performance-sensitive clusters choose BGP underlay (or an eBPF dataplane like Cilium in native-routing mode) specifically to eliminate it. And Pod networking isn't the only thing that stops scaling gracefully: Lesson 7's default iptables kube-proxy mode evaluates a roughly linear rule chain that gets slow with thousands of Services, which is why large clusters often move to IPVS or an eBPF dataplane there too.

Think first: a company runs Kubernetes on a restrictive cloud network that only allows standard TCP/UDP traffic between nodes — no custom IP protocols. Which approach, overlay or underlay/BGP, is more likely to work without special network configuration?

Overlay (VXLAN) — it encapsulates Pod traffic inside ordinary UDP packets between node IPs, which passes through almost any network that allows normal traffic at all. BGP-based underlay routing needs the physical/cloud network fabric itself to speak BGP with the cluster's nodes, which isn't something every environment permits or supports — it trades that flexibility for zero per-packet overhead where it's available.

Two Pods on the same Kubernetes node need to communicate. What actually happens?

  • Their veth pairs both connect to the same node-local bridge, which switches the traffic between them directly — no routing needed.
  • The traffic is wrapped in a VXLAN tunnel just like cross-node traffic, for consistency.
  • kube-proxy intercepts the packet and manually forwards it between the two Pods.
  • The traffic leaves the node, goes out to the internet, and comes back in — since every Pod has its own routable IP.

Closing the loop from Lesson 3: who actually enforces a NetworkPolicy?

Lesson 3 previewed Kubernetes' NetworkPolicy resource — ingress/egress allow-rules scoped to a Pod — and promised the mechanism would come once Pods and their networking were covered properly. Here it is: NetworkPolicy is just another declarative Kubernetes resource, and like the Ingress resource Lesson 9 covers next, it does nothing by itself. The CNI plugin is what actually has to read those rules and enforce them, by programming the packet filtering that allows or drops traffic accordingly. Not every CNI plugin implements this — the basic bridge plugin described above doesn't enforce NetworkPolicy at all, which is why production clusters typically run a CNI (Calico, Cilium, and others) chosen specifically for that capability, not just for basic connectivity.
