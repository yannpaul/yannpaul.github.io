Ingress and Kong as Ingress Controller

What "Ingress" actually is, and the precise sense in which Kong is one.

This is the lesson the rest of Kubernetes networking has been building toward. Lessons 7 and 8 gave every Pod and every Service a stable, reachable address — but that's all Layer 4: a forwarding decision made from IP address and port alone (Lesson 3's route tables handle the IP part at Layer 3; a Service adds port-awareness on top), never by reading the connection's actual content. None of it understands hostnames or URL paths. That gap is exactly what Ingress fills, and Kong's specific role in filling it is what this lesson makes precise.

The problem: Services don't speak HTTP

Say you run three separate apps behind three hostnames — app.example.com, admin.example.com, docs.example.com — all in one cluster. Each has its own Service. But a Service, on its own, has no idea what a Host header is; it just forwards whatever arrives at its IP and port. Give each app its own LoadBalancer Service (Lesson 7) and you've provisioned three separate, separately-billed cloud load balancers, with no shared place to apply routing logic, TLS, or the auth/rate-limiting Lesson 6 covered. You want one entry point that reads the request's host and path and routes accordingly — HTTP-aware routing, which is a job a plain L4 Service structurally cannot do.

What an Ingress resource actually is

An Ingress is a Kubernetes API resource — a declarative record, like any other Kubernetes object — that describes HTTP(S) routing rules: which host and path should go to which Service. A minimal one reads roughly like this:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-routes
spec:
  ingressClassName: kong
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app-service
                port:
                  number: 80

That's it — a mapping from app.example.com/* to the app-service Service. Kubernetes matches more specific paths first when a request could match more than one rule (an Exact path wins over a Prefix one) — the same "most specific wins" instinct Lesson 3's longest prefix match already taught you, one layer up the stack.

The single most important fact in this lesson

An Ingress resource, by itself, does nothing. It's a config record sitting in the cluster's API — like a route table with no router plugged in to read it. Creating one with no software watching for it changes nothing about how traffic actually flows. Something has to actively watch for Ingress resources and program a real, running proxy to actually enforce them. That something is an Ingress Controller — and it's the single detail most explanations of Ingress skip past.

IngressClass: which controller claims which Ingress

A cluster can run more than one Ingress Controller at once (or, before one is installed, none at all). The ingressClassName field in the example above — kong — says which controller should pick up this particular Ingress resource. Without a matching controller watching for that class, the resource just sits there, valid YAML, doing nothing, exactly as the callout above warned.

Kong's specific role, made precise

This is where Lesson 6 and Kubernetes finally connect directly. The Kong Ingress Controller (KIC) is Kong's own controller: it watches the cluster for Ingress resources (plus Kong-specific CRDs and, on newer setups, Gateway API HTTPRoute resources), and for every rule it sees, it automatically creates the matching Kong Route and Kong Service — the exact entities from Lesson 6 — and pushes that configuration to the running Kong Gateway data plane Pods, which are the thing actually proxying live traffic. This reconciliation happens continuously and in real time: edit the Ingress resource, and KIC updates Kong's configuration to match within moments, with no one touching Kong's admin API by hand.

Ingress resource Declarative YAML — inert on its own
→
Kong Ingress Controller Watches the cluster, translates continuously
→
Kong Route + Service Lesson 6's exact entities, auto-generated
→
Kong data plane Actually proxies the live traffic

So when Lesson 1 drew "Kong" as hop 4 and Kubernetes docs talk about "the Ingress," they're not two separate systems that happen to sit near each other — in this deployment shape, Kong is the Ingress Controller. The Ingress resources you write are simply a Kubernetes-native way of configuring the same Kong Routes, Services, and Plugins Lesson 6 already taught you, instead of calling Kong's admin API directly.

A teammate applies a new Ingress resource routing billing.example.com to a billing-service, but no Kong Ingress Controller (or any other) is installed in the cluster yet. What happens when a request for billing.example.com arrives?

  • Kubernetes rejects the Ingress resource at creation time, since no controller exists to enforce it.
  • The billing-service's own ClusterIP handles the routing directly, since Ingress is just a hint layered on top of it.
  • Kubernetes automatically provisions a default load balancer to satisfy the new rule.
  • Nothing changes for real traffic — the Ingress resource just sits there unenforced until an Ingress Controller exists to act on it.

Think first: Lesson 6 covered Kong Plugins scoped to a Route or Service via Kong's own admin API. If your team writes Ingress resources instead of touching Kong's admin API directly, how do you attach a plugin (say, rate limiting) to one specific Ingress rule?

Kong Ingress Controller supports Kong-specific Kubernetes annotations and CRDs (e.g. a KongPlugin resource, referenced from the Ingress via an annotation) that map directly onto Lesson 6's Plugin-scoping model — global, Service-level, Route-level, or Consumer-level. The mechanism underneath is identical to Lesson 6; only the interface changed, from Kong's admin API to Kubernetes-native YAML that KIC translates on your behalf.
