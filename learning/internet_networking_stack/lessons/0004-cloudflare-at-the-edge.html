Cloudflare at the Edge

What actually happens inside the second hop of Lesson 1's map, before your infrastructure ever hears about the request.

Lesson 1 called this hop "nearest point of presence: security checks, maybe a cached answer" and moved on. This lesson opens that box: what a Cloudflare PoP actually does to a request, in order, and why a healthy fraction of all traffic to a well-configured site never reaches the origin at all.

Getting to the nearest PoP

Lesson 1 already named the mechanism: Cloudflare's anycast addresses are announced from hundreds of physical data centers (points of presence, or PoPs) at once, and BGP — the internet's own routing protocol — naturally delivers each request to whichever announcement is cheapest to reach from where it started. No central dispatcher decides this per-request; it falls out of how the internet already routes everything.

What happens inside the PoP, in order

1. DDoS / rate checks Always on, absorbed across the whole anycast network's capacity
→
2. WAF Rule-based filtering for known attack signatures
→
3. Cache lookup Is there already a valid, cached copy of this exact response?
→
4a. HIT: serve it Origin never contacted at all

On a cache miss, step 4 becomes "forward to the origin load balancer" instead — the request continues down Lesson 1's map as originally drawn.

The security checks run before the cache lookup and apply to every request, cached response or not — a malicious request aimed at a cached URL still gets inspected on the way in. Only after clearing both checks does Cloudflare ask "do I already have this?"

DDoS mitigation: a capacity property, not a filter

Because the same address is announced from every PoP, a flood of attack traffic aimed at one site gets naturally spread across Cloudflare's entire global network rather than concentrating on one machine — the same anycast property that gets a legitimate user to their nearest PoP also disperses an attack across all of them. Cloudflare layers rate-based and behavioral detection on top of that structural resilience.

The WAF: pattern-matching against known attacks

The Web Application Firewall inspects each request against rulesets for known attack patterns — SQL injection attempts, cross-site scripting payloads, and similar — and can block, challenge, or log a match before the request goes anywhere near your origin. This is the layer that answers a question Lesson 1 didn't: your application code never has to defend itself against the internet's background noise of scanning and exploit attempts, because most of it is filtered out one hop before your infrastructure exists from the internet's point of view.

Caching: the hop that can end here entirely

By default, Cloudflare caches by file extension — images, CSS, JS, fonts, and similar static file types — and leaves HTML pages and API responses uncached unless told otherwise. The origin's own response headers steer this precisely: Cache-Control: max-age=86400 tells both the browser and the edge how long to keep a copy; s-maxage sets a separate, edge-only duration (useful for caching aggressively at the edge while still having browsers revalidate).

Cache statusWhat happened
HITServed straight from the edge. The origin was not contacted for this request at all.
MISSCacheable, but no valid copy was on hand — fetched from the origin this time, and (usually) cached for next time.
DYNAMICCloudflare decided this response shouldn't be cached at all, typically because the origin's own headers said not to.
Where this is going

This HIT/DYNAMIC split is the seed of Lesson 11's static-vs-restricted-resources question: a static asset (a JS bundle, a logo) is exactly the kind of response that can be a HIT and skip your entire infrastructure, while a personalized, authenticated API response is exactly the kind that has to stay DYNAMIC — caching someone else's dashboard data for the next visitor would be a serious bug, not an optimization.

A request for /logo.png gets a Cloudflare cache HIT. Which parts of the six-hop map from Lesson 1 did this request actually reach?

  • Just DNS and the Cloudflare edge — nothing past the edge was contacted.
  • DNS, the Cloudflare edge, and the origin load balancer, but not Kong or Kubernetes.
  • All six hops, since every request has to be authenticated and routed the same way regardless of caching.
  • Only the WAF — even DNS and the rest of Cloudflare's edge logic gets bypassed on a cache hit.

When the edge can't reach the origin at all

On a cache miss, Cloudflare has to open a connection to your origin load balancer — and that hop can fail in ways specific to this one leg of the journey, surfaced as Cloudflare-specific error codes (the full diagnostic map comes in Lesson 12, but these two are worth knowing now since they're squarely about this lesson's hop):

CodeWhat it means
522Cloudflare couldn't even establish a TCP connection to the origin within its timeout — often a security-group/route-table misconfiguration from Lessons 2–3 blocking Cloudflare's IP ranges.
524The connection succeeded and the origin acknowledged the request, but didn't send a full HTTP response before Cloudflare's read timeout — the origin is reachable but too slow, not unreachable.
Think first: your origin load balancer's security group only allows inbound traffic from Cloudflare's published IP ranges — correctly, per Lesson 3's ingress/egress model. A teammate tightens it further by accident, blocking Cloudflare entirely. Which error code would visitors see, and why not a 524?

522, not 524 — the security group change blocks the TCP connection from ever being established at all, which is exactly what 522 means. 524 requires the connection to have succeeded first (the origin accepted it and started responding); a blocked ingress rule prevents that first step entirely, so the failure happens earlier in the sequence than 524 describes.

Something unclear — the DDoS/WAF/cache ordering, cache-control headers, the 522 vs. 524 distinction, anything else? Ask your teacher (me) before moving on.
