CIDR, Route Tables, and Traffic Direction

Lesson 2 used 10.0.0.0/16 and route tables without fully unpacking them. Here's the mechanism.

Lesson 2 drew a VPC as public and private subnets and said a subnet is public "if its route table sends internet-bound traffic to an internet gateway." This lesson makes that precise: what the /16 in an address actually means, exactly how a route table picks a target when more than one route could match, and why a single request can be allowed one way but silently dropped on the way back if you get its direction wrong.

CIDR notation: reading an address block

Every address range you've seen so far — 10.0.0.0/16, 0.0.0.0/0, 192.168.1.0/24 — is CIDR notation (Classless Inter-Domain Routing): an IP address, a slash, and a number. That number is the prefix length: how many of the address's 32 bits are fixed as the "network" part. Whatever bits are left over can vary, and every value they can take is one address inside the block.

The rule that matters

Fewer bits fixed (a smaller number after the slash) means more bits free to vary, which means a bigger block. /16 is a bigger network than /24, which is bigger than /32 (one single address, no bits free at all).

CIDR blockFree bitsAddresses it coversTypical use
10.0.0.0/161665,536A whole VPC
10.0.2.0/248256One subnet inside that VPC
203.0.113.10/3201One specific host
0.0.0.0/032every address that exists"Anywhere on the internet" — the default route

Working out a block's actual range: 10.0.2.0/24 fixes the first 24 bits (10.0.2) and leaves the last 8 free, so it spans every address from 10.0.2.0 to 10.0.2.255 — 256 addresses, matching Lesson 2's Kubernetes-node example exactly.

Which covers more addresses: 10.0.0.0/16 or 10.0.2.0/24?

  • 10.0.2.0/24 — the higher number after the slash means more addresses.
  • 10.0.0.0/16 — fewer fixed bits means more addresses can vary.
  • They're the same size — the /16 vs /24 is just a labeling convention.
  • Neither — reachability depends on public vs. private, not the slash number.

Route tables: where "public vs. private" actually gets decided

A route table is a list of rules, each one a (destination CIDR block → target) pair. Every subnet is associated with exactly one route table — its own, or the VPC's default one if it wasn't given a specific one. When something in that subnet sends a packet, the VPC's router checks the packet's destination address against every row in the table and picks a target.

Here's what a public subnet's route table and a private subnet's route table typically look like, side by side — same VPC, same first row, one crucial difference in the second:

SubnetDestinationTarget
Public10.0.0.0/16local (stay inside the VPC)
0.0.0.0/0Internet gateway
Private10.0.0.0/16local (stay inside the VPC)
0.0.0.0/0NAT gateway

Both tables have a row for "anywhere" (0.0.0.0/0) — that's the fallback for any address that isn't inside the VPC's own range. Whether that fallback points at an internet gateway or a NAT gateway is the single fact Lesson 2 was describing as "public vs. private."

Longest prefix match: what happens when two rows could both apply

A packet headed to 10.0.5.100 technically matches both rows in the private table above — it's inside 10.0.0.0/16, and it's also inside 0.0.0.0/0 (everything is). The router doesn't pick arbitrarily: it always takes the most specific matching route — the one with the longest prefix, i.e. the largest number after the slash. /16 beats /0, so VPC-internal traffic goes local, and only traffic that doesn't match the more specific row falls through to the 0.0.0.0/0 catch-all. This is also why you can add a narrow, specific route (say, a /24 to a VPC peering connection) that overrides the broader default without editing the default row at all — the more specific route simply wins for the addresses it covers.

Think first: a route table gets a new row, 10.0.5.0/24 → peering connection, added to the private subnet's table above. Does this change where traffic to 10.0.5.100 goes? What about traffic to 10.0.9.50?

10.0.5.100 now matches three rows: /16 (local), /24 (peering), and /0 (NAT gateway). Longest prefix match picks the /24 — the most specific — so this traffic now goes over the peering connection instead of staying local. 10.0.9.50 isn't inside 10.0.5.0/24 at all, so it still only matches the /16 local route: unaffected.

Ingress vs. egress: direction is relative to the thing you're describing

Ingress means traffic coming into something; egress means traffic going out of it. That's the whole definition — but it only means something once you say what the "it" is. A response leaving your Pod is egress from the Pod's point of view and, a moment later, ingress to whatever's receiving it. Every rule you'll meet that mentions ingress or egress is scoped to one specific thing: an instance, a subnet, a Pod.

The reason this needs its own lesson, rather than being a one-line aside, is that not every layer treats a request and its response as linked — and that distinction has broken more than one person's first deployment.

The gotcha this explains

A stateless NACL requires an ingress rule allowing the inbound request and a separate egress rule allowing the reply back out — typically on the high, unpredictable "ephemeral" ports operating systems use for return traffic, not the port the request came in on. Miss the egress rule, and the request arrives at your server just fine (ingress was allowed), the server sends a perfectly good response — and it never leaves the subnet. No error, no log on your server; from the client's side it just looks like a timeout. A security group never has this failure mode, because it's stateful: allowing the inbound request is enough, and the matching reply is let out automatically without needing a rule of its own.

A client's HTTPS request reaches your server — the TCP handshake completes and your app logs the request. But the client never receives a response, with no error on either side. The subnet's NACL allows inbound (ingress) on port 443 but has no matching outbound (egress) rule for the ephemeral return port. What's happening?

  • The security group is blocking the request before it reaches the server, so the app should never have logged it.
  • DNS resolved to the wrong IP address, so the request silently went to a different server.
  • The application crashed while handling the request, before it could send any response.
  • The NACL let the request in but has no egress rule allowing the response back out, so the reply is silently dropped at the subnet boundary.

The same direction split, one layer up

Once a request is inside your Kubernetes cluster, the identical ingress/egress split reappears at the Pod level via a NetworkPolicy: an ingress section lists what's allowed to send to a Pod, an egress section lists what that Pod is allowed to send to. With no NetworkPolicy at all, a Pod allows all traffic both ways by default — the restrictive behavior only turns on once at least one policy selects that Pod. And Pod-to-Pod traffic needs both sides to agree: A can only reach B if A's egress rules allow sending to B and B's ingress rules allow receiving from A — this comes back in Lesson 7, once Services and Pods have been covered properly.
