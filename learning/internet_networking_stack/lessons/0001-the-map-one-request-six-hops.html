The Map: One Request, Six Hops

Before any single piece gets a deep dive, see the whole shape of the thing.

Say you've built a SaaS app and someone types app.example.com into their browser, already logged in, and lands on their dashboard. From your side of the fence — the company running the service — that one request crosses a chain of systems before a single line of your application code runs, and the response retraces the same chain backward. This lesson is just the map. Every hop on it gets its own lesson later; today, learn the shape.

The six hops

Here's the path for GET https://app.example.com/dashboard, at the altitude you'll use for the rest of this course:

1. DNS Browser asks "what's the address for app.example.com?"
→
2. Cloudflare edge Nearest point of presence: security checks, maybe a cached answer
→
3. Origin load balancer Entry point into your company's own infrastructure
→
4. Kong gateway Checks the request, decides which internal service should handle it
→
5. Kubernetes Service Picks one healthy Pod out of possibly many
→
6. Your Pod Your application code finally runs

"Six" is a teaching simplification, not a law — real deployments add or fold together hops (a service mesh sidecar in front of the Pod, a CDN cache that answers before Cloudflare's security logic even runs, multiple internal services chained together). But this shape — edge → gateway → cluster → Pod — is the one that recurs across nearly every SaaS company's architecture, and it's the skeleton the rest of this course hangs off.

Why it's split into pieces at all

A reasonable question: why not just point DNS straight at your server and skip the rest? Because each hop exists to solve one specific problem, and solving all of them in your own application code would be its own multi-year project:

HopProblem it exists to solve
Cloudflare edgeAbsorb attacks and abuse before they ever reach your infrastructure; serve cacheable content from close to the user
Origin load balancerSpread traffic across more than one entry point into your infrastructure; give you one stable address to put behind DNS
Kong gatewayEnforce cross-cutting rules (who's allowed in, how fast they can call) in one place instead of in every service
Kubernetes ServiceGive a moving target — Pods that get created, destroyed, and rescheduled constantly — one stable address
Your PodRun your actual business logic, and nothing else

Notice the pattern: everything before your Pod exists so that your Pod's code can stay simple. That's the throughline for the whole course — each layer takes on one job so the layers behind it don't have to.

The detail that surprises people first

When Cloudflare sits in front of your site, the IP address DNS hands back for app.example.com is not your server's address — it's one of Cloudflare's own anycast addresses, shared by hundreds of Cloudflare data centers worldwide. Your server's real address is hidden behind it. Lesson 3 explains exactly how that routing works and why it doubles as a security feature.

A browser resolves app.example.com and gets back an IP address. When Cloudflare sits in front of the site, whose address is that?

  • The company's Kong API gateway, since that's the first thing that inspects the request.
  • The company's actual origin server, since DNS always points straight at the real backend.
  • One of Cloudflare's own addresses, shared across its edge network — not the company's server at all.
  • The Kubernetes Service IP inside the company's cluster.

The return trip

Every hop above is two-way. Your Pod builds a response, which travels back through the Kubernetes Service, back through Kong, back through the origin load balancer, back through Cloudflare's edge (which may now cache it, if it's cacheable — more in Lesson 3), and finally back to the browser. When something breaks, it breaks at exactly one of these hops, and later — in the lesson on error codes — you'll use the specific error you see to figure out which one.

Where this course is going

Lesson 2 is a detour that's worth taking before going any further: IP addresses, public vs. private, and what a VPC is. Every hop above lives on one side or the other of a public/private boundary, and that boundary is the reason Kong and your Pods aren't directly reachable from the internet at all — only Cloudflare and the load balancer are. After that, Lessons 3–10 each zoom into one hop or one cross-cutting concern (TLS, auth, error codes, static-vs-restricted resources) in depth.
