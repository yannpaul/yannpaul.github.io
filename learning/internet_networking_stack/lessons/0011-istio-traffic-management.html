Istio Traffic Management

Lesson 10 covered who's allowed to call whom. This is what decides where a call actually goes — including calls that leave the mesh entirely.

Lesson 10 was scoped deliberately narrow: Citadel, PeerAuthentication, AuthorizationPolicy — the identity half of Istio. It left out an entire other set of resources: the ones that decide how a request is routed once identity is settled, and whether a call is even allowed to reach something outside the mesh at all. This lesson fills that in, ending with ServiceEntry — the piece that makes an external destination visible to Istio in the first place.

VirtualService: the mesh's own routing rules

A VirtualService does inside the mesh roughly what a Kong Route (Lesson 6) does at the edge, or an Ingress resource (Lesson 9) does at the cluster boundary: it matches a request — by hostname, path, headers — and decides where it goes. The difference is scope: a VirtualService governs traffic between services already inside the mesh, after Kong has already made its own routing decision and handed the request to a Pod's sidecar.

A VirtualService can also do things no earlier lesson's routing layer could: split traffic by percentage across versions (90% to v1, 10% to a v2 canary), inject retries and timeouts, or deliberately inject faults to test resilience — all without touching application code.

DestinationRule: what happens once a destination is picked

A DestinationRule is the companion resource: where a VirtualService decides where traffic goes, a DestinationRule decides how to treat it once it's headed there — load balancing algorithm, connection pool limits, circuit-breaking (outlier detection) settings, and subsets (named groups of Pods, usually by version label) that a VirtualService's routing rules can then target by name.

The pairing, concretely

A DestinationRule defines v1 and v2 as subsets of the orders service (by Pod label). A VirtualService then says: 90% of traffic to v1, 10% to v2. Neither resource does anything useful alone — the DestinationRule has nothing to point traffic at without the VirtualService's routing rule, and the VirtualService can't reference a subset that doesn't exist yet.

ResourceQuestion it answersCourse parallel
VirtualServiceWhich destination should this request go to?Kong's Route (Lesson 6) — but for mesh-internal traffic
DestinationRuleGiven that destination, on what terms — which subset, what load balancing, what circuit breaker?Kong's Plugins (Lesson 6) — applied per-destination instead of per-Route

A team wants to send 10% of traffic to a new v2 of the payments service as a canary, with the rest going to v1. Which resource actually expresses the 90/10 split?

  • DestinationRule — it defines the split directly.
  • VirtualService — its routing rule carries the weighted split across the subsets a DestinationRule defines.
  • AuthorizationPolicy — it decides which version an identity may call.
  • PeerAuthentication — strict mode routes a fixed percentage to each subset.

ServiceEntry: making the outside world visible to Istio

Everything above assumes the destination is already a Kubernetes Service Istio knows about. A ServiceEntry is how something outside the mesh — an external API, a legacy VM, a third-party service — gets added to Istio's own internal service registry, so it can be addressed, routed, and governed exactly like an internal one. A typical use: registering api.stripe.com so a payments service's calls to it get routed through the mesh's own traffic-management and observability, rather than slipping past Istio unnoticed.

Directly answering the question this lesson exists to answer

Without a ServiceEntry, an external destination is invisible to Istio's own configuration — it isn't a "thing" a VirtualService can route to, a DestinationRule can apply policy to, or (as the next section covers) an AuthorizationPolicy on an egress gateway can name. ServiceEntry is the resource that makes an external call a first-class citizen of the mesh's config model at all.

The egress gate: outboundTrafficPolicy and the Sidecar resource

Istio's mesh-wide default, ALLOW_ANY, lets every outbound call leave a Pod's sidecar untouched, whether or not Istio knows anything about the destination — easy to start with, but it means calls to unregistered destinations are neither observed nor governed by the mesh at all. Setting outboundTrafficPolicy.mode to REGISTRY_ONLY flips that: a sidecar will only let a call through to a destination already in Istio's service registry — a Kubernetes Service, or something a ServiceEntry has explicitly registered. Anything else is blocked at the sidecar before it ever leaves the Pod.

This is a genuinely different, coarser gate than either of the two egress mechanisms this course already covered — worth placing in order, since all three can be true or false independently for the same call:

1. NetworkPolicy CNI/kernel level (Lesson 3, 8) — is this IP:port allowed to leave at all?
→
2. REGISTRY_ONLY Sidecar level — is this destination even known to Istio?
→
3. AuthorizationPolicy On an egress gateway (Lesson 10) — is this specific identity allowed to reach it?

A cluster can (and often does) run all three at once, each catching what the others don't: NetworkPolicy is a blunt, IP-level allowlist enforced before Istio ever sees the packet; REGISTRY_ONLY refuses to forward to anything Istio wasn't told about; an AuthorizationPolicy on an egress gateway adds identity-aware, per-caller rules on top of a destination that's already known.

The Sidecar resource is also how this default gets overridden per-namespace — a tooling namespace that genuinely needs unrestricted egress can carry its own Sidecar resource loosening the mesh-wide REGISTRY_ONLY default, without changing it everywhere. The same resource has a second, unrelated job worth knowing: scoping which services and namespaces a given sidecar actually bothers to track configuration for, which keeps a large mesh's per-Pod Envoy config from growing unbounded — the same "don't make every node hold state it doesn't need" instinct Lesson 8's CNI design and Lesson 7's EndpointSlice both share.

Think first: a workload calls an external API with no ServiceEntry registered for it, in a mesh running REGISTRY_ONLY. What actually happens, and which resource would fix it?

The sidecar blocks the call outright — REGISTRY_ONLY means an unregistered destination isn't reachable at all, regardless of NetworkPolicy or AuthorizationPolicy settings, since the block happens before either would even be relevant. The fix is a ServiceEntry registering that external host, which makes it a known destination the sidecar will forward to (and, from there, a VirtualService/DestinationRule pair or an egress-gateway AuthorizationPolicy could optionally govern further).

A naming collision worth resolving: three things called "Gateway"

By this point in the course, "Gateway" has meant three different things, and it's worth disambiguating explicitly rather than letting them blur:

"Gateway"What it actually is
Kubernetes Gateway API (Lesson 9)The newer, more expressive alternative to the Ingress resource — still just declarative config, still inert without a controller.
Kong (this course's actual stack)The thing running as the Ingress Controller (Lesson 9), proxying real traffic at the cluster boundary — hop 4 of Lesson 1's map.
Istio's own Gateway resourceA separate Istio config object that configures a dedicated ingress or egress proxy's L4–L6 listener (port, protocol, TLS) — paired with a VirtualService for the actual L7 routing rules attached to it.

In this course's specific stack, Kong is the thing actually sitting at the boundary — Istio's own Gateway resource would typically only enter the picture if Kong were swapped out, or for a dedicated egress gateway specifically. Worth knowing it exists, so the name doesn't collide with Kong's role when you encounter it in Istio's own docs.
