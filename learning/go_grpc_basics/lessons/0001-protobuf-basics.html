Protobuf Basics

Set up logline — the small service this whole course builds — and write its very first piece: one message, in one schema file, turned into real Go code.

Every message this course's client and server ever exchange starts life as a declaration in a .proto file, not as a Go struct you hand-write. That's the core idea of Protocol Buffers: describe a message's shape once, in a small language-neutral schema, and let a compiler generate the actual Go (or Python, or Java, or anything else) code to read and write it. Today: install that compiler, write logline's first message, generate real code from it, and read what came out.

Before you start: set up the tools and the project

  • Stuck? Show the commands 
    # Debian/Ubuntu
sudo apt-get install -y protobuf-compiler

# macOS
brew install protobuf

# either way, confirm it's installed
protoc --version
    Checkpoint

    protoc --version prints something like libprotoc 3.21.12 — the exact version doesn't matter much, but it needs to run at all before anything else in this course works.

  • Stuck? Show the commands 
    go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

# make sure this directory is on your PATH (add to your shell rc if not)
echo $(go env GOPATH)/bin

    If a later protoc command in this course fails with something like protoc-gen-go: program not found or is not executable, this is almost always the cause — the plugin binary exists, but the shell running protoc can't find it on PATH.

  • Stuck? Show the commands 
    mkdir -p logline/proto/logline/v1 logline/gen
cd logline
go mod init logline

    The v1 directory is a deliberate convention, not decoration — it's how a real protobuf schema leaves room for a future breaking change (a v2 package) to live alongside the original without colliding. This course only ever needs v1, but the layout is worth having from day one.

New: writing your first message

A .proto file's message block declares a data shape: a name, and a list of typed, numbered fields. That's it — no behavior, no methods, just a description of what a piece of data looks like on the wire and in generated code.

  • Stuck? Show the file 
    syntax = "proto3";

package logline.v1;

option go_package = "logline/gen/logline/v1;loglinev1";

message LogEntry {
  string id = 1;
  string message = 2;
  int64 created_at_unix = 3;
}

    The numbers after each field (= 1, = 2, = 3) aren't cosmetic — they're what's actually written to the wire, not the field names. This matters enough to get its own idiom callout below.

Idiom

A protobuf message on the wire is a sequence of (field number, value) pairs — the field name id never leaves your source code. That's what makes protobuf tolerant of schema evolution: a service can add a new field with a new number and old clients that don't know about it just ignore it, while a service reading an old message just doesn't see fields that haven't been sent. What it can't tolerate is reusing a number for a different field, or renumbering an existing one — either one makes old and new code disagree about what a given number means, silently corrupting data instead of failing loudly. Treat field numbers as permanent once anything depends on them.

New: generating real code from it

protoc itself doesn't know how to produce Go — that's what the protoc-gen-go plugin you installed above is for. You tell protoc where to find your .proto files, where to write output, and which plugin(s) to run.

  • Stuck? Show the command 
    protoc --go_out=gen --go_opt=paths=source_relative \
  --proto_path=proto \
  proto/logline/v1/logline.proto
    Checkpoint

    A new file appears at gen/logline/v1/logline.pb.go — real, compilable Go source, not a stub or a template. --proto_path=proto tells protoc where import paths inside your .proto files should resolve from; paths=source_relative tells the Go plugin to mirror your .proto's own directory layout under gen/, rather than flattening everything or using the full go_package path.

  • Checkpoint

    The file's very first lines say Code generated by protoc-gen-go. DO NOT EDIT. — meant literally. LogEntry is a real Go struct with exported fields (Id string, Message string, CreatedAtUnix int64) you could technically set directly, plus a getter per field. Every field also carries a struct tag like protobuf:"bytes,1,opt,name=id,proto3" — that 1 is the same field number from your .proto file, now baked into the Go code that reads and writes it on the wire.

New: using the generated type

The generated struct is a normal Go type once it exists — construct it with a literal, pass it around, read its fields. The one genuinely new piece is proto.Marshal/proto.Unmarshal, from the google.golang.org/protobuf/proto package: turning a message into its binary wire form and back, exactly what a real client and server will do to send messages to each other starting next lesson.

  • Stuck? Show the code 
    package main

import (
	"fmt"
	"time"

	"google.golang.org/protobuf/proto"

	loglinev1 "logline/gen/logline/v1"
)

func main() {
	entry := &loglinev1.LogEntry{
		Id:            "1",
		Message:       "hello, protobuf",
		CreatedAtUnix: time.Now().Unix(),
	}

	fmt.Println("field access:", entry.GetId(), entry.GetMessage())

	data, err := proto.Marshal(entry)
	if err != nil {
		panic(err)
	}
	fmt.Printf("marshaled to %d bytes\n", len(data))

	decoded := &loglinev1.LogEntry{}
	if err := proto.Unmarshal(data, decoded); err != nil {
		panic(err)
	}
	fmt.Println("round-tripped:", decoded.GetId(), decoded.GetMessage(), decoded.GetCreatedAtUnix())
}
    Checkpoint

    go mod tidy pulls in google.golang.org/protobuf, then go run ./cmd/inspect prints your field values, a small byte count (a couple dozen bytes for this message), and then the exact same field values again after the round trip through Marshal/Unmarshal — proof the binary encoding actually preserves your data, not just that the code compiles.

  • Stuck? Show the line 
    var nilEntry *loglinev1.LogEntry
fmt.Println("nil message GetMessage():", nilEntry.GetMessage() == "")
    Checkpoint

    Prints true — no panic, even though nilEntry is a nil pointer. Every generated getter is written to check for a nil receiver and return the field's zero value instead of dereferencing it.

Idiom

Prefer a generated getter (entry.GetMessage()) over direct field access (entry.Message) once a message might have come from somewhere else — deserialized from a network call, say, or a field of another message that itself might be unset. Direct field access is perfectly fine on a value you just constructed yourself, like the literal above, but it panics on a nil pointer where the getter would just hand back an empty string. This becomes more than a style preference once nested messages show up: a field that's itself a message type, unset, reads as nil, and chaining getters (reply.GetEntry().GetMessage()) stays completely safe through any number of unset levels, where chaining direct field access would panic at the first one.

You now have a real message, generated Go code that reads and writes it, and a working program that proves the round trip. Nothing has talked to a network yet — proto.Marshal/Unmarshal just turn a message into bytes and back, entirely locally. Lesson 2 is where those bytes actually travel somewhere: a real client, a real server, and gRPC as the thing connecting them.
