A Library Package and a Second Binary

Rebuild Lesson 1's greet package from memory first. Then pull real logic out of burrow's main.go, and build a second, independent binary that reuses it.

Every function in burrow — findName, sizeOf, duTop, checkPerm, whoOwns — still lives in one main.go, in package main, alongside the Cobra command tree that wires them up. Nothing about the scanning logic itself needs package main or Cobra at all; it's trapped there only because that's where it was first written. Today: move it into its own importable package, confirm the CLI still works exactly as before, then prove the extraction was worth it by building a second, much smaller binary that reuses the same code.

Warm-up — repeat from Lesson 1
  • Checkpoint

    go run . prints its two greeting lines; temporarily adding fmt.Println(greet.defaultName) and running go build . fails with name defaultName not exported by package greet, exactly as before.

New: extracting a library package from burrow

Pick the logic in burrow that's genuinely independent of the CLI: the directory-scanning functions (sizeOf, and whatever computes a sorted top-N — duTop or equivalent, depending on which lesson's shape you're on). None of it needs os.Args, a Cobra command, or anything else CLI-specific to run.

  • Stuck? Show the package 
    // Package scanner holds burrow's directory-scanning logic, independent of
// any CLI framework, so it can be imported by more than one binary.
package scanner

import (
	"io/fs"
	"os"
	"path/filepath"
	"sort"
)

type DirSize struct {
	Name string
	Size int64
}

func SizeOf(root string) (int64, error) {
	var total int64
	err := filepath.WalkDir(root, func(path string, d fs.DirEntry, err error) error {
		if err != nil {
			return err
		}
		if !d.IsDir() {
			info, err := d.Info()
			if err != nil {
				return err
			}
			total += info.Size()
		}
		return nil
	})
	return total, err
}

func Top(root string, n int) ([]DirSize, error) {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return nil, err
	}

	sizes := make([]DirSize, 0, len(dirs))
	for _, d := range dirs {
		p := filepath.Join(root, d.Name())
		s, err := SizeOf(p)
		if err != nil {
			return nil, err
		}
		sizes = append(sizes, DirSize{Name: p, Size: s})
	}

	sort.Slice(sizes, func(i, j int) bool { return sizes[i].Size > sizes[j].Size })
	if n < len(sizes) {
		sizes = sizes[:n]
	}
	return sizes, nil
}

    This is a simplified, single-goroutine version to keep the extraction itself the focus — if your own duTop is already concurrent (from go_concurrency_basics) or context-aware (from go_context_basics), extract that version instead; the package boundary works identically either way. DirSize, SizeOf, and Top are all exported (capitalized) because package main needs to call every one of them.

  • Stuck? Show a minimal example 
    package main

import (
	"fmt"
	"os"

	"burrow/scanner"
)

func main() {
	sizes, err := scanner.Top(os.Args[1], 10)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	for _, s := range sizes {
		fmt.Printf("%10d %q\n", s.Size, s.Name)
	}
}

    This is deliberately stripped down to just the scanning call — your real cmd/burrow/main.go keeps its full Cobra command tree (find, du, perm, all their subcommands and flags); only the internals of whichever handler called the scanning logic directly need to change to call scanner.Top/scanner.SizeOf instead.

    Checkpoint

    go build ./... succeeds, and go run ./cmd/burrow du top --path . --n 5 (or your CLI's equivalent invocation) prints exactly the same output it did before the extraction. The behavior hasn't changed at all — only where the logic physically lives.

Idiom

A useful test for "does this belong in a library package": could you explain what this function does without mentioning the command line at all? SizeOf and Top pass that test — they're about filesystem sizes, full stop. Something like "parse the --path flag and call Top" does not — it's fundamentally about the CLI's interface to a human, and stays in cmd/burrow/main.go. This distinction is what a later lesson in this course comes back to directly when deciding what does and doesn't belong in internal/.

New: a second binary, same package

Now that scanner is a real importable package, nothing says only cmd/burrow can import it. A second package main directory, anywhere else in the same module, is a second, completely independent binary — built separately, run separately, sharing only the library code both of them import.

  • Stuck? Show the code 
    package main

import (
	"fmt"
	"os"

	"burrow/scanner"
)

func main() {
	total, err := scanner.SizeOf(os.Args[1])
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Printf("%d\n", total)
}
  • Stuck? Show the commands 
    go build ./...
go run ./cmd/burrow du top --path . --n 5
go run ./cmd/burrowstat .
    Checkpoint

    go build ./... produces two separate binaries — one per cmd/ subdirectory. burrow prints its usual sorted report; burrowstat prints one number, the same directory's total size, computed by the exact same SizeOf function both binaries import. Neither binary knows the other exists — they only share code, not runtime state.

Idiom

go build ./... walks every package in your module and, for each package main it finds, produces a separate executable named after that directory. This is why the cmd/<name> convention exists at all: it's not a build-system feature with special rules, just a directory layout that happens to make "one subdirectory per binary" fall out naturally from how go build ./... already works. A library package like scanner produces no binary of its own — go build compiles it only insofar as something else imports it.

You now have real logic living outside any single binary, and a second, independent program proving that extraction actually bought you something. Lesson 3 looks at internal/ — the convention (and, unlike exported/unexported, the actual compiler-enforced rule) for a package that should never be imported from outside your own module.
