Your First Unary RPC

Rebuild Lesson 1's LogEntry message and generated code from memory first. Then give logline its first real RPC — a server, a client, and an actual network connection between them.

Lesson 1 got a message from a .proto file into working Go code, but nothing left your own process — proto.Marshal and proto.Unmarshal ran back to back in the same program. Today those bytes actually travel: a separate server process implements Append, a separate client process calls it, and gRPC is what makes calling a function on another process feel like calling an ordinary Go function.

New: adding a service to the schema

A service block in a .proto file declares an RPC: a name, a request message type, and a reply message type. rpc Append(AppendRequest) returns (AppendReply); is the entire contract — the client sends one AppendRequest, the server sends back exactly one AppendReply. This specific shape, one request and one reply, is called a unary RPC — the simplest of gRPC's four RPC shapes, and the only one this course needs until Lesson 4.

  • Stuck? Show the additions 
    message AppendRequest {
  string message = 1;
}

message AppendReply {
  LogEntry entry = 1;
}

service Logline {
  rpc Append(AppendRequest) returns (AppendReply);
}

    Add these below LogEntry in the same file — nothing about the file's syntax, package, or go_package lines needs to change.

New: implementing the server

LoglineServer is an interface with one method, Append. A type that implements it, registered with a *grpc.Server listening on a real TCP port, is your server.

  • Stuck? Show the code 
    package main

import (
	"context"
	"fmt"
	"log"
	"net"
	"strconv"
	"sync"
	"time"

	"google.golang.org/grpc"

	loglinev1 "logline/gen/logline/v1"
)

type server struct {
	loglinev1.UnimplementedLoglineServer

	mu     sync.Mutex
	nextID int
}

func (s *server) Append(ctx context.Context, req *loglinev1.AppendRequest) (*loglinev1.AppendReply, error) {
	s.mu.Lock()
	s.nextID++
	id := strconv.Itoa(s.nextID)
	s.mu.Unlock()

	entry := &loglinev1.LogEntry{
		Id:            id,
		Message:       req.GetMessage(),
		CreatedAtUnix: time.Now().Unix(),
	}
	return &loglinev1.AppendReply{Entry: entry}, nil
}

func main() {
	lis, err := net.Listen("tcp", ":50051")
	if err != nil {
		log.Fatalf("listen: %v", err)
	}

	grpcServer := grpc.NewServer()
	loglinev1.RegisterLoglineServer(grpcServer, &server{})

	fmt.Println("logline server listening on :50051")
	if err := grpcServer.Serve(lis); err != nil {
		log.Fatalf("serve: %v", err)
	}
}
Idiom

Embedding loglinev1.UnimplementedLoglineServer isn't boilerplate to delete — it's what keeps your server compiling after a future lesson adds a new RPC to the service block. Without it, adding a method to LoglineServer's interface would break every existing implementation until they added that method too; with it, your server struct automatically satisfies any new method (by inheriting the embedded type's version, which just returns an "unimplemented" error) until you get around to writing a real one. This is the same forward-compatibility idea as protobuf's field numbers from Lesson 1, applied to services instead of messages.

New: writing the client

LoglineClient is the generated stub — a concrete type whose Append method actually makes the network call. You get one from a connection.

  • Stuck? Show the code 
    package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"

	loglinev1 "logline/gen/logline/v1"
)

func main() {
	conn, err := grpc.NewClient("localhost:50051", grpc.WithTransportCredentials(insecure.NewCredentials()))
	if err != nil {
		log.Fatalf("dial: %v", err)
	}
	defer conn.Close()

	client := loglinev1.NewLoglineClient(conn)

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	reply, err := client.Append(ctx, &loglinev1.AppendRequest{Message: "hello from the client"})
	if err != nil {
		log.Fatalf("append: %v", err)
	}

	entry := reply.GetEntry()
	fmt.Printf("server assigned id=%s message=%q created_at=%d\n", entry.GetId(), entry.GetMessage(), entry.GetCreatedAtUnix())
}

    insecure.NewCredentials() means no TLS — fine for this course, run entirely on your own machine, and explicitly out of scope to fix per this course's MISSION.md. A real production service needs real transport security; that's a deployment concern layered on top of everything this course teaches, not a change to the RPC code itself.

  • Stuck? Show the commands 
    # terminal 1
go run ./cmd/server

# terminal 2
go run ./cmd/client
go run ./cmd/client
    Checkpoint

    The server prints logline server listening on :50051 and keeps running. Each client run prints a line like server assigned id=1 message="hello from the client" created_at=... — and the second run prints id=2, not id=1 again, proving the ID came from the server's own in-memory state (which survived between the two separate client processes), not from anything the client sent.

  • Checkpoint

    The client fails with something like rpc error: code = Unavailable desc = connection error: ... connection refused — not a generic Go network error, a structured gRPC error carrying a real status code, codes.Unavailable. This is your first look at gRPC's error model, ahead of Lesson 3's dedicated treatment of it: even a plain network failure comes back through the same status/codes machinery your own RPC methods will use on purpose.

Idiom

grpc.NewClient doesn't dial eagerly — creating the connection object never fails just because nothing is listening yet. The actual connection attempt happens lazily, on the first RPC call, which is exactly why the checkpoint above fails at client.Append(...), not at grpc.NewClient(...). This matters in practice: a client can be constructed once, early in a program's life, well before the server it talks to is guaranteed to be up.

You now have two real, separate processes exchanging real protobuf messages over a real TCP connection — the whole rest of this course is variations on exactly this shape. Lesson 3 adds a second RPC, Get, and replaces the placeholder error handling above with the real thing: returning a specific status code on purpose, not just seeing one show up from a connection failure.
