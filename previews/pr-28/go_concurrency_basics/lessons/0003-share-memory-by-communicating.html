Share Memory By Communicating

Rebuild Lesson 2's duTop from memory first. Then replace its mutex with a channel — and notice how much else disappears with it.

Lesson 2's duTop works, and the race detector agrees. But it needed two different synchronization mechanisms for two different pieces of shared state: indexed writes for dSizes, a mutex for firstErr. Today, one mechanism handles both — a channel, carrying each goroutine's entire result (size and error) back to a single place that's the only thing touching either.

Warm-up — repeat from Lessons 1–2
  • Forgot the shape? Show Lesson 2's function 
    func duTop(root string, n int) error {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return err
	}

	dSizes := make([]dirSize, len(dirs))
	var wg sync.WaitGroup
	var mu sync.Mutex
	var firstErr error

	for i, d := range dirs {
		wg.Add(1)
		go func(i int, name string) {
			defer wg.Done()
			p := filepath.Join(root, name)
			s, err := sizeOf(p)
			if err != nil {
				mu.Lock()
				if firstErr == nil {
					firstErr = err
				}
				mu.Unlock()
				return
			}
			dSizes[i] = dirSize{p, s}
		}(i, d.Name())
	}
	wg.Wait()
	if firstErr != nil {
		return firstErr
	}

	sort.Slice(dSizes, func(i, j int) bool { return dSizes[i].Size > dSizes[j].Size })
	n = min(len(dSizes), n)
	for _, d := range dSizes[:n] {
		fmt.Printf("%10d %q\n", d.Size, d.Name)
	}
	return nil
}
    Checkpoint

    burrow du top --path scratch --n 10 and go run -race . du top --path scratch --n 10 both behave exactly as they did at the end of Lesson 2.

New: a channel instead of a mutex

A channel is a typed pipe: one goroutine sends a value into it with ch <- value, another receives it with <-ch, and the receive blocks until a value is actually there. That blocking is the whole trick — instead of a shared variable multiple goroutines write to (needing a lock to keep them from colliding), each goroutine sends its own result down a channel, and exactly one goroutine — the one receiving — ever touches what comes out the other end. This is the idea behind Go's own stated preference, quoted in nearly every serious discussion of the language: "Don't communicate by sharing memory; share memory by communicating."

  • Stuck? Show the type 
    type sizeResult struct {
	Name string
	Size int64
	Err  error
}

  • Receive exactly len(dirs) times no matter what — even after seeing an error, keep receiving until every goroutine's send has been read. If you stopped early, any goroutine still trying to send on an unbuffered channel with nobody receiving would block forever: a real goroutine leak, not just a style problem. Lesson 5 comes back to exactly this risk.

    Stuck? Show the function 
    func duTop(root string, n int) error {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return err
	}

	results := make(chan sizeResult)
	for _, d := range dirs {
		go func(name string) {
			p := filepath.Join(root, name)
			s, err := sizeOf(p)
			results <- sizeResult{Name: p, Size: s, Err: err}
		}(d.Name())
	}

	var dSizes []dirSize
	var firstErr error
	for range dirs {
		r := <-results
		if r.Err != nil {
			if firstErr == nil {
				firstErr = r.Err
			}
			continue
		}
		dSizes = append(dSizes, dirSize{r.Name, r.Size})
	}
	if firstErr != nil {
		return firstErr
	}

	sort.Slice(dSizes, func(i, j int) bool { return dSizes[i].Size > dSizes[j].Size })
	n = min(len(dSizes), n)
	for _, d := range dSizes[:n] {
		fmt.Printf("%10d %q\n", d.Size, d.Name)
	}
	return nil
}

    Identical output to before — big at 100, small at 20, empty at 0 — and -race stays silent, with less code and zero explicit locks.

Idiom

Notice what quietly vanished: no sync.WaitGroup, no sync.Mutex, no indexed writes. Receiving from results exactly len(dirs) times is the wait — you can't finish that loop until every goroutine has sent, which is the same guarantee wg.Wait() gave you, produced as a side effect of the channel's own blocking behavior instead of a second, separate primitive. This is the pattern Go's channels are specifically good at: collecting an unknown-in-advance-but-countable set of results from independent work, without anyone needing to share memory to do it.

duTop is shorter, and arguably easier to convince yourself is correct, than Lesson 2's version — one synchronization idea instead of two. Lesson 4 breaks it on purpose, to see exactly what the race detector says when that guarantee is violated for real.

Something unclear — why receiving len(dirs) times replaces wg.Wait(), what would happen if you stopped receiving early after an error, why append is safe here but wasn't safe in the version this lesson is about to break, anything else? Ask your teacher (me) before moving on.
