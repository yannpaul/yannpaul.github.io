P2 Stretch: Leaderboard Benchmark

Explain what CMU's B+tree leaderboard measures, run the Go benchmark that reproduces its workload, read its reads/s and writes/s correctly, and test the speed-up ideas as measured experiments.

This lesson is optional. Your B+tree is complete once the full test suite passes, and the writeup says the same about its leaderboard: "Optimizing for the leaderboard is optional (i.e., you can get a perfect score in the project after finishing all previous tasks)." It adds one condition that applies to everyone: "your solution must finish the leaderboard test with a correct result and without deadlock and segfault." The leaderboard asks how many lookups and updates per second your tree sustains with several goroutines at once. As in the Project 1 stretch, the method is to measure first and change one thing at a time.

Warm-up: retrieval from earlier lessons

Unit 2, Lesson 9: BenchmarkBufferPoolManagerScanGet splits b.N among 16 goroutines and reports 2055 ns/op. What does that number measure?

  • The average latency of one page access.
  • The inverse of the pool's throughput: about 487,000 accesses per second in total.
  • The number of iterations the benchmark ran.
  • The time spent sleeping in simulated disk latency.

Unit 3, Lesson 5: what is pointer swizzling, and what is its catch?

  • Storing page IDs instead of pointers, so that pages can move freely in memory.
  • Storing disk offsets in the nodes; the catch is that the file can't grow.
  • Reordering a node's keys for faster binary search; the catch is slower inserts.
  • Replacing a pinned page's ID with a raw pointer; it must become a page ID again before the page is evicted.

Unit 4, Lesson 7: a tree is created with Options{NumTombs: -1}, and the starter's LeafPageDefaultTombCount is unchanged. What does Remove do with a live key?

  • It removes the entry at once, because the buffer size is LeafPageDefaultTombCount, which is 0.
  • It tombstones the key in a buffer of one slot.
  • It panics, because a negative buffer size is invalid.
  • It tombstones every deletion, without limit.

What CMU's leaderboard measures

CMU runs tools/btree_bench/btree_bench.cpp against each submission. It builds a tree with 8-byte integer keys, BusTub's default page sizes and NumTombs = -1, on a 1024-frame buffer pool over an in-memory disk; the source explains the size: "We should keep the BPM size large enough to hold all pages in memory, to minimize the dependency on P1." It inserts the keys 0 to 99,999, each with the RID (key, key), and then runs six threads for a fixed duration, 30 seconds by default:

  • Four reader threads each own a quarter of the keys. Each round, a reader picks a random key in its quarter and calls GetValue on up to 2048 consecutive keys, stopping at the end of its quarter. It checks that every key the writers never remove (key % 7 != 0) is found, and that a key nobody touches still maps to (key, key).
  • Two writer threads each own half of the keys. Each round, a writer walks up to 2048 keys from a random start. Every multiple of 7 is removed in even rounds and inserted again in odd rounds. Every other multiple of 5 is inserted again with a new RID; the key is already there, so the insertion returns false and changes nothing, which measures the cost of an insertion that finds its key.

The tool prints writes per second and reads per second over the whole run; one read is one GetValue, one write is one Insert or Remove. The leaderboard ranks on them. Lecture #10's slide 45 adds how it is run and rewarded: Gradescope runs the code "with a specialized in-memory version of BusTub", the 20 fastest implementations in the class receive extra credit, and "You must pass all the test cases to qualify!"

#10 Latching in Data Structures, "Summary and conclusion" (1:18:04), slides 41–45: the Project 2 announcement, ending with the leaderboard's extra-credit rules.

The writeup adds two rules for this run. Tombstones are your choice: "We will run your B+Tree with a NumTombs value of -1 which means we will not enforce any specific behavior concerning tombstoning. You can modify the LEAF_PAGE_DEFAULT_TOMB_CNT macro to use your own custom default number of tombstones in this case." And only integer keys are used. Its suggested starting point is "considering more efficient representations of tombstones", with the Bε-tree paper and Goetz Graefe's books as further reading.

The Go benchmark

BenchmarkBPlusTreeReadWriteMix in btree/b_plus_tree_bench_test.go runs the same workload on your buffer pool and your tree: the same constants (4 readers, 2 writers, 1024 frames, 100,000 keys, ranges of 2048), Options{NumTombs: -1}, the same per-round access patterns and the same checks. Two things differ. A Go benchmark repeats a fixed amount of work rather than running for a duration, so each benchmark iteration is 700 rounds per goroutine. And each goroutine's random generator has a fixed seed, so two runs make the same accesses. Run it from go_db_internals/intro_to_db:

go test -bench BPlusTree -run '^$' -benchtime=1x ./btree/

-bench BPlusTree selects the benchmark. -run '^$' matches no test name, so the 82 tests don't run first. -benchtime=1x runs exactly one iteration, which is already about 12 seconds of work. Leave out -race: it slows the tree several times over, and not evenly, so it can change which version looks faster. On the reference solution, on a 4-core machine, one run printed:

goos: linux
goarch: amd64
pkg: intro_to_db/btree
cpu: Intel(R) Xeon(R) Processor @ 2.10GHz
BenchmarkBPlusTreeReadWriteMix-4   	       1	11918747381 ns/op	    461925 reads/s	     74238 writes/s
PASS
ok  	intro_to_db/btree	12.058s

The benchmark also fails like a test when your tree is wrong: a reader that misses a key reports key not found: ..., a changed value invalid data: ..., and goroutines that don't finish within 5 minutes report a deadlock or a guard that is never dropped. A fast result with an error is not a result.

Reading reads/s and writes/s

The two metrics come from b.ReportMetric: the total number of GetValue calls, and of Insert and Remove calls, each divided by the same elapsed time. That time starts after the 100,000 setup insertions (the benchmark resets its timer there) and ends when the last of the six goroutines finishes. ns/op is that same time for one iteration, here about 11.9 seconds, so it adds nothing beyond the two rates.

The ratio between the two rates is mostly fixed by the workload, not by your tree. In a round, a reader makes up to 2048 reads. A writer walks up to 2048 keys but writes only on multiples of 7 and the other multiples of 5: 5 + 6 = 11 keys in every 35, about 644 writes per round. With four readers and two writers, that is about 8192 reads for every 1288 writes, a ratio near 6.4; the run above gave 461,925 / 74,238 ≈ 6.2. So compare a change by both rates against your own baseline; don't read a low writes/s as slow writes.

Two consequences of the shared elapsed time are worth knowing before you optimize. If one kind of goroutine finishes early, the elapsed time still runs until the slowest one is done, so the early finishers' rate is understated: making reads faster shows up only partly while the writers set the end time. And a change that slows one side can slow the other through contention. A writer holding a leaf's write latch makes the readers of that leaf wait, and every guard, read or write, passes through your buffer pool's latch.

Expect noise. Run the benchmark several times, for example with -count=5, before and after a change, and compare the spreads, as in the Project 1 stretch lesson. The profiling flags from that lesson work here too: -cpuprofile cpu.out and -mutexprofile mutex.out, opened with go tool pprof.

Idiom

b.ReportMetric(value, "reads/s") adds a column to the benchmark line, and tools such as benchstat compare custom metrics just like ns/op. A metric whose unit ends in /op is understood as per iteration; reads/s is a plain rate. When you write a benchmark of your own for an experiment, report the quantity you care about directly instead of reconstructing it from ns/op.

Ideas to try

The reference solution has no leaderboard optimizations: one latch per page through the Project 1 buffer pool, whose single pool latch every guard takes and releases, and no tombstones at all with NumTombs = -1. Three directions come from the writeup and from where that design spends its time. Each one below is an experiment: record a baseline, make one change, measure, and keep it only if it is faster and the full test suite still passes.

The first is tombstones, the writeup's suggestion. Half of the writers' removals are undone by an insertion one round later. With a buffer, a removal can become a tombstone and the insertion a revive, without shifting entries; fewer leaves underflow, so fewer operations restart pessimistically. The size of the buffer is LeafPageDefaultTombCount, and how the buffer is represented in the page is open: the tests only observe it through Tombstones(). Raising the default changes what NumTombs −1 means: it now asks for a buffer of that size. TestBPlusTreeTombstoneDisabled checks that −1 deletes at once only while the default is 0, so every test must still pass with your new default.

#08 B+Trees, "B+ tree optimizations" (1:07:57), slides 49–63: node size, merge thresholds, in-node search, pointer swizzling and the write-optimized B+tree, the menu the writeup's further reading draws on.

The second is the optimistic path's guard count. Every optimistic insertion or removal read-guards the leaf, drops it and write-guards it again, because the descent can't know a page is a leaf before latching it. Every guard costs a pin, a latch and a trip through the buffer pool's own latch.

The third is the buffer pool latch. The tree fits in memory, so the buffer pool never evicts during the run, yet every ReadPage, WritePage and Drop still takes the pool's single latch. Six goroutines making millions of guard calls contend on it. The Project 1 stretch lesson's partitioning idea applies here unchanged, and your B+tree benchmark is a second workload to measure it with.

Check your understanding

A run reports 461,925 reads/s and 74,238 writes/s. Why are there about six times as many reads as writes?

  • Because a write takes about six times as long as a read in this tree.
  • Because the writers run fewer rounds than the readers.
  • Because there are twice as many readers, and a writer writes on only 11 of every 35 keys it walks.
  • Because the duplicate insertions return false and aren't counted.

A writer calls Insert for a key that is a multiple of 5 but not of 7. What happens, with the reference design?

  • The key is already there: Insert returns false without changing the leaf, and it counts as one write.
  • Insert replaces the key's RID with the new one and returns true.
  • Insert revives a tombstone for the key and returns true.
  • Insert runs the pessimistic path, because duplicates may split a leaf.

You make every GetValue twice as fast, but the writers are unchanged and still finish last. How does reads/s change?

  • It doubles, because the readers do the same work in half the time.
  • It more than doubles, because faster reads also speed up the writers.
  • It can't change, because reads/s depends only on the workload.
  • It rises by less than double, because the elapsed time is set by the slowest goroutines, here the writers.

You set LeafPageDefaultTombCount to 8 and run go test -race -count=1 ./.... What should you expect?

  • Most page-layout tests fail, because the slot count of every leaf changes.
  • Every test must still pass, so any failure is a bug to fix.
  • TestBPlusTreeTombstoneDisabled fails on its −1 case, and that failure is expected.
  • The concurrent tests fail, because they run with the default buffer.

Experiments

None of these has a test command of its own; the benchmark and the full suite are the measure. The hints describe directions, not code.

  • What to think about

    Later projects build on this tree. How will you get back to a version that passes everything if an experiment goes wrong? And what will each experiment be compared against?

    The approach

    Commit on your branch with a message such as "P2 complete". Run the benchmark command with -count=5 and redirect the output to a file. Note the machine's state, plugged in and otherwise idle, because later runs must be made the same way.

    The crux, in words

    Keep both rates from every run. A baseline is a spread of values, and a change counts only if it moves outside that spread.

  • What to think about

    Is the time spent working (binary searches, copying entries, encoding and decoding integers) or waiting (on the pool latch, on page latches)? Which of your own functions appear near the top?

    The approach

    Run the benchmark once with -cpuprofile and once with -mutexprofile, and open each with go tool pprof, using top and list. In the mutex profile, see whether the waiting is on the buffer pool's latch or on frame latches; in the CPU profile, see how much of your tree's time is spent inside guard calls.

    The crux, in words

    The profile decides which of the next three experiments is worth doing first. A change to a part that takes 5% of the time can't gain more than 5%.

  • What to think about

    What does a removal followed, one round later, by an insertion of the same key cost with no buffer, and what with one? How often does your code ask "is this index tombstoned?" during a lookup, and how much work is each answer? What does a larger buffer cost in leaf capacity?

    The approach

    Try a few values of LeafPageDefaultTombCount and measure each. Then look at the tombstone checks in your hot paths and consider representations that answer them with less work, while Tombstones() still reports the deletions oldest first and all stage-7 tests still pass.

    The crux, in words

    Tombstones trade cheaper writes for more work on every read, which the Bε-tree lecture called the cost of buffered updates. The benchmark has four readers and two writers, so measure both rates.

  • What to think about

    Count the guards one optimistic operation takes from the header page to the leaf. Which of them exist only because the descent learns that a page is a leaf after latching it? Which outcomes, such as a duplicate insertion, never needed a write latch at all?

    The approach

    Look for information the descent could have before it reaches a page, and for outcomes it could decide with weaker latches. Keep the stage-9 rules: exactly one write guard for a safe operation, and never a write latch above the leaf on the optimistic path. Count guards with the wrapper's Reads() and Writes().

    The crux, in words

    Whatever you skip, the leaf you finally write must still be the one that covers the key, which the parent's read latch guaranteed. TestBPlusTreeConcurrentOptimisticInsert, ...OptimisticDelete and ...OptimisticTakesReadLatches tell you if the rules broke.

  • What to think about

    In this benchmark the whole tree is in memory. Which work does a page hit still do under the pool latch, and which of it truly needs that latch? What did the Project 1 stretch lesson suggest for a single contended latch?

    The approach

    Revisit the contention experiment from the Project 1 stretch lesson with this second workload. Measure BenchmarkBPlusTreeReadWriteMix and BenchmarkBufferPoolManagerScanGet before and after, since a change can help one and hurt the other.

    The crux, in words

    The buffer pool's invariants still hold: a page is never in two frames, and a pinned frame is never evictable. Run go test -race -count=1 ./... several times after every change; the Project 1 concurrency tests are the guard here.

After each experiment

From go_db_internals/intro_to_db, first make sure nothing broke, then measure:

go test -race -count=1 ./...
go test -bench BPlusTree -run '^$' -benchtime=1x -count=5 ./btree/

The first command must print ok for intro_to_db/btree, intro_to_db/bufferpool, intro_to_db/common and intro_to_db/storage/disk, every time you run it. The second gives five samples of each rate to compare with your baseline. Keep a change only if both rates are clearly better, or one is better and the other unchanged; otherwise revert to your commit. There is no score to reach here, so the goal is to understand where the time goes.

Something unclear? For example, why writes/s is so much lower than reads/s even for a fast tree, why a faster lookup may barely move reads/s, or why a tombstone buffer can make writes cheaper and reads more expensive. Ask your teacher (me) before moving on.
