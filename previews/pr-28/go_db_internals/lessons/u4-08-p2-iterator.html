P2.8 The Index Iterator

Build IndexIterator with Begin, BeginAt and End: start a scan at the first entry or at a key, walk the leaf chain in key order while skipping tombstoned entries, hold one leaf's read guard at a time, and release it on Close.

A B+tree's leaves are sorted and chained, which is what makes it the index for range queries. Lecture #08's clustered scan starts at the leftmost leaf and reads every leaf in turn; a range predicate starts at the first key in the range instead. Task #3 of the writeup asks for exactly that, as an iterator. It is the smallest stage of the project, but it raises one new question: what a scan should do with its latch when it steps sideways from one leaf to the next.

Warm-up: retrieval from earlier lessons

Unit 3, Lesson 4: how does a DBMS scan a table in key order through a clustered B+tree?

  • It reads the table's pages and sorts the tuples by key for each query.
  • It runs one root-to-leaf search for every key in the table.
  • It goes to the leftmost leaf and reads the tuples from every leaf in turn.
  • It collects the record IDs, sorts them by page ID and fetches each page once.

Unit 3, Lesson 8 (HW3 Q3(d)iv): under the lecture's crabbing, a read-only thread scanning the leaves moves from leaf C to its sibling B. What does the protocol say about C's latch?

  • The reader can release C before asking for B, because readers never change nodes.
  • The reader keeps C latched until it holds the latch on B.
  • The reader takes no latches at all under the optimistic scheme.
  • The reader keeps every latch from the root down until the scan ends.

Unit 4, Lesson 2: why is defer guard.Drop() inside the descent loop of GetValue wrong, even though the tests mostly pass?

  • Each guard is dropped twice, once by the defer and once by the loop.
  • The compiler rejects defer statements inside a loop.
  • The deferred calls never run, so the pins leak forever.
  • Every page on the path stays latched and pinned until the function returns.

The writeup describes isEnd() as "Return whether this iterator is pointing at the last key/value pair". The tests mean "past the last pair": an iterator on the last entry is not at the end, and Entry must still work there. The loop in the doc comment shows the intended use, and every test scans this way or with for ; !it.IsEnd(); it.Next():

it := tree.Begin()
defer it.Close()
end := tree.End()
defer end.Close()
for ; !it.Equal(end); it.Next() {
	key, rid := it.Entry()
	...
}

The struct is yours to define (BusTub: "add your own private member variables here"). One shape that fits every method: the tree, for its buffer pool and page views; the read guard of the current leaf, nil at the end; the current leaf's page ID, common.InvalidPageID at the end; and the index of the current entry, 0 at the end. With those fields, IsEnd is "no guard", and Equal compares the page ID and the index, so all end iterators are equal to each other. Write your own constructor; Begin, BeginAt and End call it.

Starting a scan

Begin descends to the leftmost leaf by following child 0 at every internal page, with the same read crabbing as GetValue. BeginAt descends to the leaf that covers the key and starts at its lower-bound index, the first entry whose key is ≥ the search key. That index can be Size(): a key above everything in its leaf, say 35 in a leaf [10,20,30] followed by [40,50], belongs before the next leaf's first entry, so the iterator has to move on before it is usable. And the entry it lands on may be tombstoned. Both cases are the same job that Next does after advancing the index, so one helper can do it for all three: "move forward until the index points at a live entry, crossing to the next leaf when it runs off the end of this one, or reach the end".

An empty tree gives an end iterator at once, from Begin and from BeginAt. So does a tree whose entries are all tombstoned: BusTub's TombstoneBasicTest removes every key and expects Begin().IsEnd() to be true, although every leaf is still in the tree.

Stepping to the next leaf

To cross to the next leaf, the iterator reads NextPageID() from the current leaf, and if it is common.InvalidPageID, the scan is over. Otherwise it needs a read guard on the next leaf and must give up the current one. The order matters, and the two choices pull in different directions.

Lecture #10's crabbing says to hold the current leaf until the next one is latched, as the warm-up recalled, so that no writer can change the next leaf in between. But a scan moves sideways, and a writer may be latching in the other direction. In stage 6 your Remove repairs a last child with its left sibling: it holds the right leaf's write guard and asks for the left one. A scan that holds the left leaf and waits for the right one would complete the cycle, the deadlock of slide 36. The lecture's answer is a no-wait mode for sibling latches, and the writeup says the same: a correct implementation would throw an exception "when it cannot acquire a latch on its sibling to avoid potential dead-locks". Your Project 1 buffer pool has no such mode: ReadPage waits until it gets the latch.

The simplest safe choice in this course is to drop the current leaf's guard first and then read-guard the next leaf. The iterator never holds two latches, so it can't take part in a deadlock. The price is the gap between the two: if the tree changed in it, the next leaf could have been merged away. The doc comment states the condition that makes this acceptable here: "The tests do not scan while other goroutines modify the tree", which matches the writeup's "We do not test your iterator for thread-safe leaf scans". The stress test of stage 9 scans the tree only after its goroutines have finished. A scan that is safe against concurrent writers needs a no-wait sibling latch and a restart, which is beyond this project.

Holding one leaf at a time also keeps the buffer pool usable. TestBPlusTreeIteratorReleasesGuards scans a 13-page tree through a pool of 4 frames, twice, and then checks that another goroutine can write-guard the last leaf while an iterator sits on the first. An iterator that never drops the leaves it leaves runs the pool dry within a few leaves.

#10 Latching in Data Structures, "Leaf node scans" (59:33), slides 33–37: scans in both directions, the deadlock between a scan and a delete, and the no-wait rule.

Idiom

A C++ iterator releases its page guard in its destructor, when it goes out of scope. Go has no destructors, so Close does it, and the caller writes defer it.Close() right after creating the iterator, as with a file. Make Close safe to call twice and safe on an end iterator, which holds nothing: set the guard to nil after dropping it. An iterator that reaches the end on its own should drop its last guard at that moment, so a loop that runs to completion leaks nothing even if the caller forgets Close.

Check your understanding

A tree holds the keys 1 to 10, and a := tree.Begin(), b := tree.Begin() and c := tree.BeginAt(key(2)) are created. Then a.Next() is called once. Which statement is true?

  • a.Equal(c) is true and a.Equal(b) is false.
  • a.Equal(b) is true, because both came from Begin().
  • No two of them are equal, because each holds its own read guard.
  • a.Equal(c) is false, because c starts at the entry after key 2.

The leaves are (|10,20,30) and (|40,50), in that order. What do BeginAt(key(35)) and BeginAt(key(60)) visit?

  • Nothing for 35 (it is absent), and nothing for 60.
  • 30, 40, 50 for 35, and 50 for 60.
  • 40, 50 for 35, and nothing for 60.
  • 40, 50 for 35, and 10, 20, 30, 40, 50 for 60.

The leaves are (1|1,2,3), (4,5,6|4,5,6) and (|7,8,9): 1, 4, 5 and 6 are tombstoned. Where do Begin() and BeginAt(key(4)) start?

  • On 1 and on 4.
  • On 2 and on 5.
  • On 2, and BeginAt(4) is at the end.
  • On 2 and on 7.

A goroutine stops a scan after the first entry and forgets Close. The same goroutine then calls tree.Remove on a key in that first leaf. What happens?

  • The garbage collector drops the iterator's guard, and Remove proceeds.
  • Remove waits forever for a write latch that the goroutine itself holds in read mode.
  • Remove upgrades the iterator's read latch to a write latch and proceeds.
  • Remove panics with a message that the leaf is already latched.

Build it: the iterator (stage P2.8)

You edit btree/index_iterator.go (the struct, a constructor, IsEnd, Entry, Next, Equal, Close) and btree/b_plus_tree.go (Begin, BeginAt, End). Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • The iterator only ever sits on a live entry, or at the end. Tombstoned entries are skipped, including at the start.
  • Descend with read guards, crabbing as in GetValue. Hold at most one leaf's read guard; to cross to the next leaf, drop the current guard, then read-guard the next.
  • End means past the last entry. Every end iterator equals every other one, and End() holds no guard.
  • Entry returns a copy of the key. Close drops the guard and can be called twice.
  • What to think about

    What does an iterator need to read the next entry later, and what identifies its position? What does the end state look like in those fields, so that any two end iterators compare equal? What must Close leave behind so a second call is harmless?

    The approach

    Keep a pointer to the tree, a *bufferpool.ReadPageGuard for the current leaf, its page ID and an entry index. The end state is a nil guard, common.InvalidPageID and index 0; End() returns an iterator in that state. IsEnd reports a nil guard. Equal compares page IDs and indexes. Close drops the guard if there is one and puts the iterator in the end state.

    One key fragment 
    func (it *IndexIterator) Equal(other *IndexIterator) bool {
	return it.pageID == other.pageID && it.index == other.index
}
  • What to think about

    Your stage-2 descent picks a child by key. What does the leftmost descent pick instead? Who owns the leaf's read guard once the descent returns it?

    The approach

    Give your read-descent helper a "leftmost" mode that follows ValueAt(0) at every internal page, keeping the hand-over order (child guarded before the parent is dropped). If the tree is empty, return End(). Otherwise hand the leaf's guard to the constructor with index 0; the iterator now owns it. The first entry may be tombstoned, which the next task handles.

    One key fragment 
    child := internal.ValueAt(0) // leftmost: no key needed
if !leftmost {
	child = internal.ValueAt(childIndex(internal, key)) // your stage-2 search
}
  • What to think about

    After the index moves, it may point past the leaf's last entry or at a tombstoned one. How many leaves might the helper have to cross before it finds a live entry? What happens to the guard when there is no next leaf?

    The approach

    The helper loops while the iterator holds a guard: skip tombstoned indexes in the current leaf; if the index is now below Size(), stop; otherwise read NextPageID(), drop the guard, enter the end state, and if the next page ID is valid, read-guard it and set the page ID and index 0. Next increments the index and calls the helper; at the end it does nothing. The constructor calls the helper too. Entry returns KeyAt and ValueAt of the current index, and panics at the end.

    One key fragment 
    next := leaf.NextPageID() // read it before the guard is gone
it.guard.Drop()          // never hold two leaves
