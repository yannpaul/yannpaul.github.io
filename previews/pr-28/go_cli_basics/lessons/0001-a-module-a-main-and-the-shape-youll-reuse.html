A Module, a Main, and the Shape You'll Reuse

Get a Go module running at all, then adopt the one structural pattern every remaining lesson in this course will make you rebuild.

Every lesson here is a checklist of things to do, not code to copy. Where you might get stuck, there's a collapsed hint — a <details> box like the one right below this paragraph — with the exact command or snippet. Open it only if you're actually stuck; the point is to write this yourself.

By the end of this lesson you'll have a real, if useless, Go program: a module, a main, and the getConfig/run skeleton that every future lesson in this course — including the finished burrow tool from the mission — builds on top of.

Before you start

  • Stuck? Show the command 
    go version

    If that fails, install Go from go.dev/doc/install first — everything else in this course assumes it works.

Set up the module

A Go module is a project's unit of dependency management, declared by a go.mod file at its root. Nothing about your code needs a module to exist as text files, but the go command needs one to know what it's building.

  • Stuck? Show the commands 
    mkdir burrow
cd burrow

  • You need a module path — a string that names the module. Since you're not publishing this, any short name works.

    Stuck? Show the command 
    go mod init burrow

    If you might ever go get this from another machine under your GitHub account, go mod init github.com/<your-username>/burrow works just as well — the path is just a name until you actually publish something at it.

  • Checkpoint

    You should see two lines: a module line echoing the path you gave go mod init, and a go line naming the Go version go mod init found installed. Nothing else — no dependencies yet, because you haven't imported anything outside the standard library.

The go line isn't decorative: it's the minimum Go version this module requires, and it's how the toolchain decides which language features (generics, newer standard-library functions) are safe to assume. See "How to Write Go Code" for the full picture of what a module is for beyond this course's needs.

Hello, burrow

  • Any message proving it ran is fine — something like "burrow: not implemented yet".

    Stuck? Show a minimal skeleton 
    package main

import "fmt"

func main() {
	fmt.Println("burrow: not implemented yet")
}
  • Stuck? Show the command 
    go run .
    Checkpoint

    Your placeholder message prints to the terminal, and no new file appears in the directory afterward.

  • Stuck? Show the commands 
    go build
./burrow

    On Windows: burrow.exe instead of ./burrow.

    Checkpoint

    A new file named burrow (or burrow.exe) now sits in the directory, and running it prints the exact same message go run . did.

go run . compiles to a temporary location, executes it, and throws the binary away — good for fast iteration. go build compiles a real binary that persists, so you can run it again later without recompiling. Both do the same compilation; they just differ in what happens to the result. package main and func main are a convention the compiler enforces: only a package literally named main, with a function literally named main taking no arguments and returning nothing, can be built into a standalone executable.

Idiom

Nothing forces the file with func main to be named main.go — the compiler only cares about the package and function names inside it. Naming the file main.go anyway is a near-universal convention, purely so anyone opening your project can guess where execution starts without reading every file.

The shape you'll reuse: getConfig() and run()

Right now, all your logic lives directly inside main. That's fine for one fmt.Println, but it stops scaling the moment main needs to do more than one thing — which happens as soon as Lesson 2 adds a command-line flag. This course adopts a standing pattern from here on: main does almost nothing except call getConfig() to gather configuration, call run() to do the actual work, and turn any error either one returns into a message on stderr plus a nonzero exit status. All real logic lives in run (and, later, in whatever run calls) — never in main itself.

  • Stuck? Show the function 
    func run() error {
	fmt.Println("burrow: not implemented yet")
	return nil
}

  • It has nothing to configure yet — that starts in Lesson 2. The point right now is just that the shape exists.

    Stuck? Show the function 
    func getConfig() error {
	return nil
}

  • You'll need os.Exit and fmt.Fprintln(os.Stderr, ...) — both standard library, both worth reading the docs for once: os.Exit.

    Stuck? Show the function 
    func main() {
	if err := getConfig(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}

    Don't forget to add "os" to your import block alongside "fmt".

    Checkpoint

    Run go run . again. The output should be exactly the same message as before — you haven't changed what the program does, only how it's structured. If the message changed or disappeared, something in the rewiring is wrong.

Idiom

If this rewiring changed nothing observable, why do it? Because run() — unlike code embedded straight in main — can be called from a test without going through os.Exit, which would kill the test process. Lesson 11 cashes this in directly. And once getConfig() actually has something to parse (Lesson 2), keeping it separate from run() means the "what are we configured to do" step and the "now go do it" step can be reasoned about, and changed, independently.
