P4 Stretch: T-NET Benchmark

Explain what CMU's T-NET leaderboard ranks, run BusTub's two T-NET benchmarks as a Go benchmark and read its throughput and space metrics, and test garbage collection and verification ideas as measured experiments.

This lesson is optional. Project 4's leaderboard is a workload, not a query: terriers trading tokens on T-NET, "the Terrier NFT Exchange Network", with several transactions running at once. It ranks two things that pull against each other, how many transfers your MVCC commits per second and how many rows it keeps while doing so. Your code from the last eight lessons runs it as it is. As in the earlier stretch lessons, the method is to measure first, change one thing, and measure again, with the whole suite passing after every change.

Warm-up: retrieval from earlier lessons

Unit 7, Lesson 6: in Lecture #20's transaction-level GC example, Txn #1 begins with TS 10, updates A and B, and commits with TS 15. Its updates ended the versions A2 and B6 at 10. When can the vacuum reclaim A2 and B6?

  • As soon as Txn #1 commits at 15.
  • Once no active transaction has a timestamp below 10.
  • Once no active transaction has a timestamp below 15.
  • Only after a background vacuum has scanned the whole table.

Unit 7, Lesson 4: under predicate locking, when do two predicate locks conflict?

  • When the two queries touch the same page.
  • Only when the two predicates are the same expression.
  • Whenever the two queries read the same table.
  • When at least one is exclusive and their predicates can overlap.

Unit 6, Lesson 11: what does BenchmarkLeaderboard/q1-index's ns/op cover?

  • One run of the timed query with its result check; the setup is untimed.
  • The insertion of the million rows and the query together.
  • Building and starting the test binary.
  • Ten runs of the query, as BusTub's timing:x10 option asks.

What CMU's leaderboard measures

The writeup's "Leaderboard Benchmark" section defines two benchmarks on one table of terriers.

Benchmark #1 is token transfer under snapshot isolation: "one terrier can initiate a transfer of a number of NFTs to another terrier":

CREATE TABLE terriers(terrier int primary key, token int);
-- each transaction: transfer A tokens from X to Y
UPDATE terriers SET token = token + A WHERE terrier = X;
UPDATE terriers SET token = token - A WHERE terrier = Y;

Benchmark #2 is the trading network, under SERIALIZABLE. Each terrier has a network ID, and a transfer between two networks costs a fee: the receiver gets 97%. Each transfer first reads both terriers' networks. Other transactions change networks: "X invites Y to join the network" with a sign-on bonus of 1000 tokens, and "X starts a new trading network" for a fee of 1000:

CREATE TABLE terriers(terrier int primary key, token int, network int);
X_network = SELECT network FROM terriers WHERE terrier = X;
Y_network = SELECT network FROM terriers WHERE terrier = Y;
UPDATE terriers SET token = token + A * 0.97 WHERE terrier = X; -- if X_network != Y_network
UPDATE terriers SET token = token + A WHERE terrier = X;        -- if X_network == Y_network
UPDATE terriers SET token = token - A WHERE terrier = Y;

"You will be ranked on speed of transfers and space usage of the database system respectively. The speed of transfers is measured by the throughput of the system, and the space usage is measured by the total number of rows in table tuples and undo logs in the system." A background thread counts the rows periodically, and the space score is the maximum count seen during the run. Each ranking gives bonus points (25 for first place, 15 for 2nd to 10th, 5 for 11th to 20th), capped at the leaderboard maximum.

Two rules from the writeup limit what you can try. "The leaderboard test will not call the stop-the-world garbage collector you have implemented in Task 3." So with the code you have, every undo log ever written stays until the run ends, and the space count only grows. And the leaderboard policy forbids the cheap ways to win: "You are not allowed to stall the system so that your system has a super low throughput while having a low space usage", nor "to use a global lock to serialize all transactions in order to reduce the number of write-write conflicts". TAs dump data at the end and review submissions by hand, and "your performance should be reasonable compared with reference solution in order to get a bonus for the space usage rank."

The writeup's suggestions: "a more fine-grained garbage collection when sequential scan is running or on transaction commit / abort", where "you can clear the undo buffer instead of removing the transaction from the map", because some tests read a transaction's commit timestamp after it commits; and "a more efficient serializable verification (i.e., precision locking)", or "parallel serializable verification".

BenchmarkTerrier

txntest/terrier_bench_test.go ports BusTub's tools/terrier_bench/terrier.cpp as BenchmarkTerrier, with sub-benchmarks bench1 and bench2. It lies outside every stage regex, so go test ./... never runs it. One iteration:

  1. Runs a small precondition in an instance of its own: a transaction that began before another one's committed update must still read the old token. On an unfinished Project 4 this fails at once, instead of racing.
  2. Builds a fresh instance with a buffer pool of 4096 frames (BusTub's size, commented "ensure benchmark does not hit BPM"), creates terriers, and checks with EXPLAIN (o) that every point query is planned as an IndexScan, as BusTub's PrintPlan does.
  3. Loads the terriers with 10000 tokens each (in bench2, terrier i starts in network i).
  4. Runs the workers for the run time, plus one goroutine that samples the space every 100 ms. In bench1 every worker transfers; in bench2 the even-numbered workers run joins (invite, start a network, or two terriers joining each other's networks at once, of which at most one may commit) and the odd-numbered ones run transfers.
  5. Checks that SELECT SUM(token) FROM terriers equals the initial tokens plus every committed fee, bonus and charge, and that more transactions than the commit threshold committed (both kinds, in bench2).

Its flags, passed after -args:

FlagDefaultBusTub's option
-terrier.duration10s--duration, 30000 ms
-terrier.threads2--threads, 2
-terrier.terriers10--terriers, 10
-terrier.commit-threshold100--commit-threshold, 100

The run time is the one default that differs: BusTub runs each benchmark for 30 seconds, the Go port for 10, so that a first try is quick. Use -terrier.duration=30s for BusTub's run. The other differences from terrier.cpp: workers draw from seeded math/rand/v2 sources, and the seed is logged; a committed bench2 transfer is counted once (BusTub counts it before and after Commit); an ExecuteSQLTxn error that is not a conflict stops the run with that error; the space is sampled every 100 ms instead of every 3 seconds, which catches higher peaks; and the precondition is new.

Running it

From go_db_internals/intro_to_db, BusTub's benchmark 1:

go test -bench 'Terrier/bench1' -run '^$' -benchtime=1x ./txntest/ -args -terrier.duration=30s

As in the earlier stretch lessons, -run '^$' keeps the package's tests from running first, and -benchtime=1x runs one iteration, which is one full T-NET run. Leave out -race for measurements. How to read it:

  • transfer/s and join/s are committed transactions per second of the run, BusTub's throughput metrics. Aborted ones don't count, and the log line gives both counts.
  • max_rows is the space metric: the highest number of heap tuples plus undo logs (of every transaction still in TxnMap) seen by the sampler. Lower is better.
  • rows/committed_txn is max_rows divided by the committed transactions, BusTub's "db_size per committed txn". Here 120221 / 54836 = 2.19.
  • ns/op is the length of the run, about -terrier.duration, and says nothing about your code; the timer is stopped during setup and the checks.

For orientation, the course's reference build (the Go reference solution in a Linux container, 3-second runs) measured about 13.5k transfers/s in bench1, and about 1.4k transfers/s and 1.2k joins/s in bench2; the run above gave 17.9k for bench1. These numbers come from this course, not from CMU, and the reference has none of the optimizations below. They tell you where you start, not what a good result is. Compare your own runs with each other, on one machine, with -count=3 or more to see the spread.

The reference's 2.19 rows per committed transfer has a simple cause. Each transfer updates two terriers, so it leaves two undo logs, and nothing ever removes them; an aborted transaction keeps its undo logs too, and the 10 heap rows add almost nothing. The space metric is a count of everything written since the start. This count is what an online garbage collector lowers.

On the Project 4 starter, or before stage 9, the benchmark stops at its precondition:

--- FAIL: BenchmarkTerrier/bench1
    terrier_bench_test.go:454: T-NET needs Project 4 stages 1 to 9 (1 to 11 for bench2): a transaction that began before a committed update reads [[2]], want [[1]] (the old token)

The sum check catches lost updates ("inconsistent total tokens: expected ..., found ..."), and the end of a run with too few commits fails with "too many txn are aborted". To check an experiment for races, run both benchmarks briefly under the race detector with a lower threshold, since -race slows everything down:

go test -race -bench 'Terrier' -run '^$' -benchtime=1x ./txntest/ -args -terrier.duration=2s -terrier.commit-threshold=10

Where the time goes

A transfer in bench1 is two primary-key point updates and a commit. Each update plans an index scan, reads one RID's version chain, generates an undo log and writes tuple and link under the page latch; the commit takes the commit mutex and stamps two tuples. With 10 terriers and 2 workers, the two workers often pick the same terrier, and the second writer is tainted: more than a quarter of the transfers aborted in the run above. bench2 adds two reads per transfer, the serializable scan predicates they record, and verifyTxn at every commit, which walks the write sets of every transaction that committed during this one. Joins that change networks make transfers' network reads stale, and case 2 of the join task aborts one of its two transactions by design.

Check your understanding

In bench1, under snapshot isolation, why does a transfer abort?

  • Serializable verification found a scan predicate that a later commit changed.
  • The sender would end with a negative number of tokens.
  • One of its updates hits a terrier that another transaction changed after this one's snapshot, or is still changing.
  • A join transaction changed the terrier's network.

The space metric of a run is reported as max_rows. What is it?

  • The highest count, over the run's samples, of heap tuples plus undo logs.
  • The number of tuples in the table heap at the end of the run.
  • The number of undo logs left at the end of the run.
  • The rows written per committed transaction.

bench2's join task, case 2: txn1 reads Y's network and moves X into it; txn2 reads X's network and moves Y into it. txn1 commits successfully. What must happen when txn2 commits, and why?

  • It waits until txn1's changes are garbage collected, then commits.
  • It commits, since the two transactions wrote different rows.
  • It was already tainted by a write-write conflict on row X, so its commit panics.
  • It fails serializable verification, because txn1 changed a row txn2 scanned.

Which of these would the leaderboard policy reject even if every test passed?

  • Removing undo logs at commit time once no running transaction can read them.
  • A global mutex held by each transaction from Begin to Commit, so writers never conflict.
  • Letting several serializable transactions verify at the same time.
  • Checking only the attributes a predicate reads when comparing it with a change.

Experiments

None of these has a test of its own: the benchmark and the full suite are the measure. The hints describe directions, not code, and the ideas come from the writeup's suggestions and the lectures. Try them in any order; the profile and the numbers should decide.

  • What to think about

    How will you get back to a version that passes everything if an experiment goes wrong? How far apart are two runs of the same code on your machine, for throughput and for max_rows? Does a 10-second run rank your versions the same way as a 30-second one?

    The approach

    Commit with a message such as "P4 complete". Run both benchmarks with -count=3 and -terrier.duration=30s, with the machine otherwise idle, and redirect the output to a file. Note the committed and aborted counts from the log lines as well as the metrics: an optimization that changes the abort rate changes everything else.

    The crux, in words

    A change counts only if it moves a metric outside the spread of the baseline runs, and only if the full suite still passes.

  • What to think about

    Which undo logs can a running transaction still need, given the watermark? When a transaction commits, which other transactions' logs may have just become unreachable? Stage 6's stop-the-world rule removes whole transactions; why does the writeup suggest clearing a transaction's undo buffer instead of removing the transaction from the map? What happens to a version chain that still links into a buffer you cleared, and who might follow that link?

    The approach

    Start from your stage-6 reasoning, but apply it incrementally: at the end of a commit or abort, decide which finished transactions no reader at the watermark can need, and drop their logs (Transaction has a ClearUndoLog method for this, documented as "online garbage collection"). Make sure no reader can still reach a cleared log: every chain walk must stop before it, or the chain must no longer point at it. Unit 7, Lesson 6's cooperative cleaning, where readers trim chains as they pass, is another place to start. Measure max_rows and throughput: collection that takes too long per commit costs transfers.

    The crux, in words

    A log is garbage only when no running transaction and no future one can reach it: every version it restores is older than a newer version that the lowest running read timestamp can already see. Get that wrong and an old snapshot reads a wrong row, which the stage 3 to 9 tests and the sum check will show.

  • What to think about

    The writeup names two costs: one transaction verifies at a time, and every write set of every conflict transaction is replayed against every predicate. How many conflict transactions does a bench2 commit see, and how many of their RIDs can match a point predicate terrier = X? Which columns does each predicate read, and which columns did each change modify?

    The approach

    Profile one bench2 run first (-cpuprofile cpu.out and -mutexprofile mutex.out before ./txntest/, then go tool pprof) to see how much time verifyTxn and the commit mutex take. Precision locking, from Lecture #19's predicate locking, compares a predicate with the changed values instead of re-evaluating it on whole replayed tuples: a change that touches no column the predicate reads can't make it true or false. Parallel verification has to keep the result the same as verifying in commit order.

    The crux, in words

    Any shortcut may only skip work whose answer is "no conflict"; it must never skip a real one. TestTxnSerializable* checks both directions, and bench2's join case 2 stops the run if both of its transactions commit.

  • What to think about

    In a transfer, how often is the base tuple already visible to the reader, so that no undo log is needed at all? How many times does one point update take the page latch, the version-info latch and TxnMapMu? What does each statement cost before it touches a tuple: parsing, binding, planning?

    The approach

    Profile a bench1 run with -cpuprofile and -mutexprofile and look at the top entries before changing anything. Candidates: returning early when the base version is visible, avoiding repeated lookups of the same undo log or link within one statement, and reducing allocations in tuple reconstruction. Also try -terrier.threads=4 or -terrier.terriers=100 to see whether contention or per-statement work dominates on your machine.

    The crux, in words

    The stage 9 rules still hold: every write that depends on a read goes through the atomic check, and a reader reads tuple and link together. A shortcut that skips either passes single-threaded tests and loses updates under load, which the sum check reports.

After each experiment

From go_db_internals/intro_to_db, first make sure nothing broke, then check for races, then measure:

go test -race -count=1 ./...
go test -race -bench 'Terrier' -run '^$' -benchtime=1x ./txntest/ -args -terrier.duration=2s -terrier.commit-threshold=10
go test -bench 'Terrier' -run '^$' -benchtime=1x -count=3 ./txntest/ -args -terrier.duration=30s

The first command must print ok for every package, as at the end of Project 4. The second runs both benchmarks briefly under the race detector. The third gives three 30-second samples of each benchmark to compare with your baseline. Keep a change only if it clearly improves a metric, the other metric doesn't get worse by more, and the suite passes; otherwise go back to your commit. There is no score to reach here. The goal is to understand where your MVCC spends its time and its rows.

Something unclear? For example, why max_rows grows with every committed transfer, why clearing an undo buffer is safer than removing the transaction, how precision locking differs from evaluating a predicate on a replayed tuple, or why ns/op says nothing here. Ask your teacher (me) before moving on.
