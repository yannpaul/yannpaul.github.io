P4.6 Garbage Collection and Abort

Remove finished transactions whose undo logs no reader at the watermark can reach, undo an aborted transaction's writes so that other writers can proceed, and keep both clear of the transaction map's latch.

Two things are still missing from the transaction manager. Every transaction stays in TxnMap forever, with its undo logs, because some older reader might need them; garbage collection decides which ones nobody can need any more. And a tainted transaction's temporary timestamps stay on the tuples it changed, blocking every other writer; Abort puts the old versions back. Both work on the version chains you built in the last two lessons, and both run into the same latch, TxnMapMu, if you take it at the wrong moment.

Warm-up: retrieval from earlier lessons

Unit 3, Lesson 7: a goroutine holds a sync.RWMutex in read mode and calls RLock on it again, while another goroutine is already waiting in Lock. What can happen?

  • The second RLock succeeds at once, because the goroutine already holds the read lock.
  • The second RLock blocks behind the waiting writer, which waits for the first read lock: a deadlock.
  • The second RLock panics with a recursive-locking error.
  • The read lock is upgraded to a write lock, and the waiting writer is skipped.

Unit 7, Lesson 6, transaction-level garbage collection: Txn #1 begins with timestamp 10 and commits with 15. Its updates made A2 (begin-ts 1) and B6 (begin-ts 8) obsolete, both now ending at 10. When can the vacuum reclaim A2 and B6?

  • As soon as Txn #1 commits at 15.
  • Once no active transaction has a timestamp below 15.
  • Only after a background vacuum scan finds them in the table.
  • Once no active transaction has a timestamp below 10.

Unit 7, Lesson 1: which mechanism for atomicity records the DBMS's actions in an ordered ledger, so that it can undo the actions of aborted transactions?

  • Shadow paging.
  • Two-phase locking.
  • Logging.
  • OCC validation.

What garbage collection may remove

The writeup explains why the transaction map never shrinks: "once we have added the transaction into the transaction map, we never remove it. We do this because transactions with a lower read timestamp might need to read the undo logs stored in the previous committed or aborted transactions." After thousands of transactions most of those logs have been overtaken by newer commits and are dead weight. Task 3.5 asks for stop-the-world garbage collection: a GarbageCollection call that the tests make only while every transaction is paused, so you don't need to worry about concurrent writers while it runs.

The rule: remove every transaction that is committed or aborted and holds no undo log visible to a transaction reading at the watermark. The watermark (P4.1) is the lowest read timestamp of the running transactions, or the last commit timestamp if none is running. The writeup asks you to "make sure that you understand this: an undo log that is invisible to this transaction should be invisible to all transactions." A reader walks a chain newest first and stops at the first version at or below its read timestamp. A reader with a higher read timestamp stops at that version or earlier, never later, so every log the reader at the watermark doesn't reach, no running transaction reaches.

Running and tainted transactions always stay: they haven't finished, and Abort will need a tainted transaction's logs. Only COMMITTED and ABORTED ones can go.

Removing a transaction leaves the links that point into it dangling. The writeup says that is fine: "You DO NOT need to update the previous undo log to modify the dangling pointer and make it an invalid pointer, and it is fine to leave it there for this project. If everything in your implementation is correct, your sequential scan executor should never even attempt to dereference these dangling pointers, as they are below the watermark." Your CollectUndoLogs stops at the first log at or below the reader's read timestamp, before it reaches a removed one. Your TxnMgrDbg, which prints whole chains, does reach them, and that is why P4.4 had it read logs with GetUndoLogOptional.

#20 Multi-Version Concurrency Control, "Transaction-level GC" (1:07:05), slides 23–24: each transaction tracks the versions it made obsolete, and the vacuum frees them once no active transaction can see them. Project 4's undo logs already live in the transaction that wrote them, so removing a transaction from the map frees all of them at once.

Walking the chains

Finding the transactions that must stay is one walk over every table:

  1. Read the watermark with m.Watermark().
  2. For every table of m.Catalog (GetTableNames, then GetTable), and every RID of its heap (MakeEagerIterator), read the base meta. If its timestamp is at most the watermark, a reader at the watermark sees the base tuple and needs no log: go on to the next RID.
  3. Otherwise follow the chain from GetUndoLink. Mark the owner of each log you pass (link.PrevTxn), and stop after the first log whose Ts is at most the watermark: that is the version the reader at the watermark sees, and everything behind it is unreachable. Stop also at an invalid link, or at a log GetUndoLogOptional can't find.
  4. Then, under TxnMapMu, delete from TxnMap every COMMITTED or ABORTED transaction you didn't mark.

Abort

Until now a tainted transaction just stayed as it was, and its temporary timestamp stayed on every tuple it had changed, and each later writer of those tuples conflicted. Task 3.6: "When aborting a transaction, we should revert this change, so that other transactions can write to the tuple." The writeup offers two designs.

Implementation 1 puts the old values back into the base tuple and leaves the undo logs where they are. The writeup: "This is easier to implement and will leave your version chain with two items with timestamp 3. Your sequential scan / index scan executor should correctly handle this situation after the transaction is aborted. With this implementation, aborted transactions will have undo logs in the version chain, and cannot be immediately reclaimed in garbage collection."

Implementation 2 restores the base tuple from the transaction's own undo log and, in the same atomic step, links the tuple to that log's PrevVersion, so the aborted transaction's log leaves the chain. "You will need to use UpdateTupleAndUndoLink / GetTupleAndUndoLink to update / read tuples and undo links atomically. With this implementation, you do not need to wait until the watermark before removing the aborted transaction from the transaction map."

The course's reference solution uses implementation 2. Its abort goes through the write set and, for each RID:

  • Reads meta, tuple and link with GetTupleAndUndoLink. If the base doesn't carry this transaction's temporary timestamp, there is nothing of its own to undo there.
  • If the first link points into the transaction itself, takes that log (txn.GetUndoLog(link.PrevLogIdx); it's the transaction's own, one per tuple), rebuilds the old tuple with ReconstructTuple from the base and that one log, and writes it back with meta {Ts: log.Ts, IsDeleted: log.IsDeleted} and link log.PrevVersion, all through one UpdateTupleAndUndoLink. A deletion comes back as the live row; an update gets its old values and timestamp.
  • Otherwise the transaction inserted the tuple. The writeup: "If the transaction inserts a fresh new tuple without undo logs, the abort process simply sets it to a deletion marker with ts = 0. The commit timestamp in BusTub starts from 1, and therefore setting it to 0 will be safe." Every reader's read timestamp is at least 0, so every reader sees a deleted base and skips it.

Two more rules from the writeup. "You do not need to revert index modifications. Anything added to the index will stay there and will not be removed. You also do not need to actually remove a tuple from the table heap." And "You should allow multiple threads aborting in parallel. That is, do not take the commit_mutex or any other locks throughout the whole function." Each abort touches only tuples that carry its own temporary timestamp, which no other transaction may write, so parallel aborts don't step on each other. A tainted transaction aborts exactly like a running one.

The TxnMapMu deadlock

P4.1's pitfall warned that m.Watermark(), m.GetUndoLog and m.GetUndoLogOptional take TxnMapMu.RLock themselves. It bites in this lesson's two functions. GarbageCollection needs the watermark and the logs, and it deletes from TxnMap, which needs TxnMapMu.Lock. Abort's shipped body already ends in a TxnMapMu.Lock section. A sync.RWMutex is not reentrant: a goroutine that holds Lock and then asks for RLock waits for itself forever. So:

  • In GarbageCollection, read the watermark and walk every chain first, collecting the transactions to keep. Take TxnMapMu.Lock only for the final loop that deletes from the map, and call nothing in it that locks again.
  • In Abort, revert the write set before the shipped TxnMapMu section, and read the transaction's own logs with txn.GetUndoLog, which uses the transaction's mutex, not the map's.

Every test call into your code is bounded, so the deadlock fails the test with a message instead of hanging. A GarbageCollection that locks the map before it calls Watermark():

Build it: garbage collection (stage 6)

You edit GarbageCollection in concurrency/transaction_manager.go. Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • A reader at the watermark needs no log of a tuple whose base timestamp is at most the watermark, and otherwise every log up to and including the first one at or below the watermark.
  • Keep every transaction that owns such a log, and every running or tainted one. Remove the other COMMITTED and ABORTED transactions from TxnMap.
  • Leave dangling links alone. Read the watermark and the logs without holding TxnMapMu; hold it only to delete. With no catalog, there is nothing to walk.
  • What to think about

    For one tuple, where does a reader at the watermark stop walking? Is the log it stops at needed, or only the ones before it? What should the walk do with a link whose transaction was removed by an earlier collection?

    The approach

    Call m.Watermark() before locking anything. If m.Catalog is nil, skip the walk. For each name in m.Catalog.GetTableNames(), iterate the table's heap with MakeEagerIterator; skip a RID whose base timestamp is at most the watermark; otherwise loop on GetUndoLink/GetUndoLogOptional, adding each link.PrevTxn to a set, and break after the first log with Ts at most the watermark, at an invalid link, or when the log can't be found.

    One key fragment 
    wm := m.Watermark() // takes TxnMapMu.RLock itself: call it before you lock the map
// ...
needed[link.PrevTxn] = true
if log.Ts <= wm {
	break // the version a reader at the watermark sees; nothing behind it is reachable
}
  • What to think about

    Which states may never be removed? Is it safe to delete from a Go map while ranging over it? Which calls must you avoid while you hold the map's write lock?

    The approach

    Take m.TxnMapMu.Lock() with a deferred unlock, range over m.TxnMap, and delete each entry whose state is TxnCommitted or TxnAborted and whose id is not in your set. Read the state with txn.TransactionState(), which is an atomic load and takes no latch.

    One key fragment 
    if s := txn.TransactionState(); (s == TxnCommitted || s == TxnAborted) && !needed[id] {
	delete(m.TxnMap, id)
}

Build it: abort (stage 7)

You edit Abort in concurrency/transaction_manager.go, where the starter says TODO(P4): implement the abort logic. The rules, in plain words:

  • For every tuple in the write set that still carries the transaction's temporary timestamp, put back the version from before the transaction. A tuple with the transaction's own log at the head of its chain gets the base rebuilt from that log, the log's timestamp and deleted flag, and the log's PrevVersion as its link, in one UpdateTupleAndUndoLink (implementation 2). A tuple the transaction inserted becomes a deletion marker with timestamp 0.
  • Leave index entries and heap slots alone. Take neither the commit mutex nor TxnMapMu while reverting; the shipped TxnMapMu section that sets ABORTED and updates the watermark comes after.
  • Aborting a tainted transaction works the same way. An empty write set touches neither heap nor catalog.
  • What to think about

    How do you tell, from the meta and the first link, whether this transaction's log is at the head? Which helper from P4.2 turns the base plus one log into the old tuple, and what does it return for a log that says the tuple didn't exist? Which three things must change together, so that no reader sees a half-restored tuple?

    The approach

    Loop over txn.WriteSets(), looking each table up with m.Catalog.GetTableByOID. For each RID, GetTupleAndUndoLink; skip it unless meta.Ts is the transaction's temporary timestamp. If link is valid and link.PrevTxn is the transaction's id, take txn.GetUndoLog(link.PrevLogIdx), rebuild the tuple with ReconstructTuple(schema, base, meta, []UndoLog{log}) (keep the base bytes when it reports false), and write it with UpdateTupleAndUndoLink: the restored tuple, meta {log.Ts, log.IsDeleted}, and a pointer to log.PrevVersion, or nil when that link is invalid.

    One key fragment 
    log := txn.GetUndoLog(link.PrevLogIdx) // the transaction's mutex, not TxnMapMu
newMeta := table.TupleMeta{Ts: log.Ts, IsDeleted: log.IsDeleted}
UpdateTupleAndUndoLink(m, rid, prevOrNil, heap, txn, newMeta, restored, nil)
  • What to think about

    A tuple carries your temporary timestamp but its first link doesn't point into your transaction. What was it before you touched it? Which timestamp makes a deletion marker invisible as a row to every reader, including ones that began before you?

    The approach

    In the same loop, the other branch: write meta {Ts: 0, IsDeleted: true} with the tuple's bytes unchanged, and keep whatever link it had. Commit timestamps start at 1, so every reader sees a deleted base with timestamp 0 and skips the RID. The index entry the insert added stays.

    One key fragment 
    UpdateTupleAndUndoLink(m, rid, linkOrNil, heap, txn, table.TupleMeta{Ts: 0, IsDeleted: true}, base, nil)

Idiom

Deleting from a Go map while ranging over it is allowed: the spec says an entry removed before the loop reaches it is simply not produced, and removing the current one is fine. So the final loop of GarbageCollection can call delete(m.TxnMap, id) inside for id, txn := range m.TxnMap, where a C++ std::unordered_map needs the it = map.erase(it) pattern. The latch rule has no such convenience. C++'s std::shared_mutex and Go's sync.RWMutex are both non-recursive, and neither tells you when you lock one twice: the program just stops.

Something unclear? For example, why a log the reader at the watermark can't reach is unreachable for every reader, why insert-only transactions can be collected while their rows are still visible, how implementation 2 differs from implementation 1 in what garbage collection can remove, or why Watermark() must come before TxnMapMu.Lock.
