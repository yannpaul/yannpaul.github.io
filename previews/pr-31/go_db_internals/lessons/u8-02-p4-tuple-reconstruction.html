P4.2 Tuple Reconstruction

Read BusTub's undo log format (modified fields, a partial tuple under a partial schema, a deleted flag and a link to the previous version) and write ReconstructTuple, which rolls a base tuple back through a list of undo logs to the version it had before them.

The table heap holds only the newest version of each tuple. Every older version exists only as a chain of undo logs, each recording what one transaction changed. A transaction whose snapshot is older than the base tuple has to undo those changes, newest first, until it reaches its own version: the "applying the delta in reverse order" of Lecture #20's delta storage. This stage writes that undo step as a pure function, without timestamps or latches, and the next stage decides which logs to hand it.

  • It starts from A3 in the main table and applies A2's delta, then A1's.
  • It starts from A3 and applies A1's delta, then A2's.
  • It reads A1 from the main table, where every version is kept.

  • Its bytes and its slot, with IsDeleted set in its TupleMeta.

Where the versions live

Task 2 of the writeup says BusTub keeps transaction data in three places:

  • The table heap always holds the latest version of every tuple, with its TupleMeta (timestamp and deleted flag). This is the base tuple.
  • The transaction manager keeps, for every tuple that has older versions, a link to the newest undo log (BusTub's PageVersionInfo; the Go manager's unexported versionInfo map, one entry per page). You read and set it with GetUndoLink(rid) and UpdateUndoLink, both pre-built in transaction_manager_impl.go.
  • Each transaction keeps the undo logs it created, in a slice in its own workspace: one per tuple it modified. AppendUndoLog adds one and returns a link to it, and ModifyUndoLog replaces one.

An undo link is a pointer into that last place: transaction PrevTxn's undo log number PrevLogIdx.

type UndoLink struct {
	PrevTxn    common.TxnID
	PrevLogIdx int
}

var InvalidUndoLink = UndoLink{PrevTxn: common.InvalidTxnID}

The transaction manager turns a link into a log: GetUndoLog(link) panics if the transaction is gone, and GetUndoLogOptional(link) returns (UndoLog, bool). A link whose PrevTxn is InvalidTxnID points nowhere, and IsValid tells you so. The writeup calls the whole structure the version chain: the base tuple, then its first undo log, then that log's previous version, and so on, newest to oldest. There is no physical delta table, so the chain hops between the workspaces of different transactions.

Pitfall

The zero value UndoLink{} is not invalid. It points to undo log 0 of transaction 0, and transaction 0 is not InvalidTxnID (which is -1). In C++, a default-constructed UndoLink{} is invalid, because its prev_txn_ defaults to INVALID_TXN_ID; when you translate BusTub code that writes UndoLink{}, write concurrency.InvalidUndoLink. Watch GetUndoLink(rid) too: for a tuple without a chain it returns the zero link and false, so check the boolean. GetTupleAndUndoLink, which the scan uses in the next lesson, already returns InvalidUndoLink in that case.

The undo log format

An undo log records how to turn one version of a tuple into the version before it. The Go struct is BusTub's UndoLog, field for field:

type UndoLog struct {
	IsDeleted      bool
	ModifiedFields []bool
	Tuple          table.Tuple
	Ts             common.Timestamp // common.InvalidTS when unset
	PrevVersion    UndoLink
}
  • ModifiedFields has one entry per column of the table's schema. Entry i is true if this log holds an old value for column i.
  • Tuple is a partial tuple: it holds only the columns marked true, in schema order, laid out by the partial schema of those columns. You build that schema with types.CopySchema(schema, attrs), where attrs lists the column indexes whose entry is true. For a table (a INTEGER, b DECIMAL, c BOOLEAN), a full tuple is 4 + 8 + 1 = 13 bytes; a log that modified a and c holds a 5-byte tuple under the partial schema (a INTEGER, c BOOLEAN). A log with no modified columns holds an empty tuple under an empty schema. Read a value with log.Tuple.Value(partial, j), where j counts only the modified columns.
  • IsDeleted means that in the previous version the tuple did not exist. A log with IsDeleted set holds no columns.
  • Ts is the commit timestamp of the version this log restores. An undo log never holds a temporary timestamp, the writeup says: it describes a committed version.
  • PrevVersion links to the next older log, or is invalid at the end of the chain.

The base tuple's TupleMeta has its own IsDeleted flag, and the two flags need not agree. The base can be a deletion marker (a tuple whose meta says deleted) while an older version existed, or the base can be live while an older version was a deletion. The writeup's reason for the second case is Task 4.2: inserting a key that was deleted reuses the deleted tuple's slot, so one RID can go through insert, delete and insert again. Read the chain as going backwards in time: each log says what the tuple looked like just before the change.

Here is one chain from BusTub's CollectUndoLogTest, in the style of BusTub's own debug output, where _ marks a column the log doesn't hold:

RID=0/2  ts=3  tuple=(3, 3.000000, <NULL>)
  undo log  (2, 2.000000, _)  ts=2
  undo log  (1, 1.000000, _)  ts=1

A reader at timestamp 3 or later takes the base, (3, 3.0, NULL). A reader at 2 applies the first log: columns a and b become 2 and 2.0, and c keeps the base's NULL. A reader at 1 applies both logs and gets (1, 1.0, NULL). Choosing how many logs to apply is the next lesson's job.

What ReconstructTuple does

Task 2.1 asks for ReconstructTuple in concurrency/execution_common.go:

func ReconstructTuple(schema *types.Schema, baseTuple table.Tuple, baseMeta table.TupleMeta,
	undoLogs []UndoLog) (table.Tuple, bool)

It takes the table schema, the base tuple and its meta from the table heap, and a list of undo logs ordered from the most recent modification to the oldest. It applies every one of them and returns the tuple as it was before all of them, or false if the tuple did not exist then. Its doc comment fixes the rules:

  • It applies every log it is given, without looking at Ts or PrevVersion. The writeup is firm about this: deciding which logs to pass is the caller's job, so don't pass too many.
  • Start from the base tuple's values. If baseMeta.IsDeleted is set, the tuple starts out deleted.
  • A log with IsDeleted set makes the tuple deleted. Any other log makes it exist, and overwrites the columns it holds with their old values; every other column keeps its value.
  • The result is built for schema and carries no RID; the scan sets it.

One detail of this port: a deletion marker keeps the deleted tuple's bytes (your Project 3 delete already does, and Project 4's delete will too), so start from those values even when the base is deleted. The doc comment's "every other column keeps its value" then covers a partial log over a marker. A marker without bytes can start from a row of NULLs, one per column type (types.NewNullValue(col.Type())). In a chain the executors build, the log right after a deletion holds every column anyway, because a delete's undo log copies the whole tuple.

BusTub's TupleReconstructTest runs four cases on the schema (a integer, b double, c boolean):

Case C's first log modifies nothing, so it must leave the tuple alone. Case D is the one that matters for the deleted flag: a delete followed by a full log is a tuple that exists again. Two more tests stand in for what the writeup leaves to hidden cases: TestTxnReconstructNullsAndTypes restores NULL and non-NULL values of all three types and puts a partial log over a deletion marker, and TestTxnReconstructKeepsInputs checks that the call changes neither the base tuple's bytes nor the logs, and gives the same answer twice.

Idiom

BusTub returns std::optional<Tuple>; Go returns (table.Tuple, bool), and the tuple in the false case doesn't matter (table.EmptyTuple() is a fine choice). BusTub takes const Tuple & and const std::vector<UndoLog> &, so the compiler stops you from writing through them. Go passes table.Tuple and []UndoLog by value, but a Tuple is a struct around a byte slice, and a slice header shares its backing array: writing into baseTuple.Data() or log.ModifiedFields would change the caller's tuple or another transaction's log. Collect the values into a new []types.Value and build the result with table.NewTuple, which allocates fresh bytes.

Why the helpers live in package concurrency

BusTub keeps ReconstructTuple and the other MVCC helpers in src/execution/execution_common.cpp, next to the executors. The Go port can't. BusTub's transaction_manager.cpp includes execution/execution_common.h, because Abort and serializable verification replay version chains with the same helpers. In Go, package execution already imports concurrency (the executor context holds a *concurrency.Transaction), and Go forbids import cycles, so concurrency cannot import execution. The helpers therefore live in concurrency/execution_common.go, and the executors call concurrency.ReconstructTuple. They only need catalog, common, storage/table and types, which concurrency already reaches. The file's header comment says the same, and suggests that you add helpers of your own there; BusTub's reference solution has, for example, GenerateNullTupleForSchema and GetUndoLogSchema.

Build it: tuple reconstruction (stage 2)

You edit concurrency/execution_common.go: ReconstructTuple, plus any unexported helpers you want. Leave the other three helpers' panics and TxnMgrDbg for later stages. The rules, in plain words:

  • Apply every log, in the order given (newest first), and ignore Ts and PrevVersion.
  • A delete log makes the tuple not exist. Any other log makes it exist and overwrites exactly the columns its ModifiedFields marks, read from its partial tuple with the partial schema.
  • The result exists, or not, according to the last log applied, or the base meta if there are no logs.
  • Don't modify the base tuple or the logs.
  • What to think about

    Which helpers will the later stages need again? GenerateNewUndoLog (stage 5) builds partial tuples, so it needs the partial schema too. What does types.CopySchema take as its second argument?

    The approach

    For the partial schema, collect the indexes i where ModifiedFields[i] is true and pass them to CopySchema. For the values, loop over schema.ColumnCount() and call t.Value(schema, i). For NULLs, loop over schema.Columns() and call types.NewNullValue(col.Type()). Keep them unexported, in execution_common.go.

    One key fragment 
    // attrs: the indexes i with modified[i] == true, in order
partial := types.CopySchema(schema, attrs)
  • What to think about

    Which two things does each log change: the values, the deleted flag, or both? Which log decides whether the result exists? When you read the i-th column's old value from a log, which index do you pass to Value, and with which schema?

    The approach

    Keep two variables: a []types.Value with one value per column, filled from the base tuple (or with NULLs if the base is a marker without bytes), and a deleted flag set from baseMeta.IsDeleted. For each log: if it is a delete log, set deleted and go to the next log. Otherwise clear deleted, build the log's partial schema, and copy each modified column's value into the slice. At the end, return false if deleted, or else table.NewTuple(values, schema) and true.

    One key fragment 
    j := 0 // position in the partial tuple
for i, m := range log.ModifiedFields {
	if m { values[i] = log.Tuple.Value(partial, j); j++ }
}
