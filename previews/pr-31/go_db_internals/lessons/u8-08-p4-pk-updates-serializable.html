Database Internals in Go · Unit 8 · Lesson 8

P4.8 Primary-Key Updates and Serializable Verification

Turn an update that changes a primary key into deletes followed by inserts, record what each serializable transaction scanned, and reject at commit any transaction whose scans a later commit changed; then run Projects 1 to 4 together under the race detector.

Two pieces are left. An update that changes a primary key can't happen in place, because the key's index entry would then lead to a row with a different key. And snapshot isolation, which everything so far implements, still allows write skew. The writeup closes both: Task 4.3 implements a key change "as a delete on the original key and an insert on the new key", and Task 4.4 adds the SERIALIZABLE level through OCC backward validation of each transaction's scan predicates. This lesson has two checkpoints, stage 10 and stage 11, and ends with the whole suite.

Warm-up: retrieval from earlier lessons

Unit 7, Lesson 5: in the marble example, Txn #1 turns every white marble black and Txn #2 every black marble white, both from the same snapshot. Why doesn't first-writer-wins stop them?

  • Because one of the two transactions is read-only.
  • Their write sets don't overlap, and the rule only compares writes with writes.
  • Each transaction reads the other's uncommitted writes.
  • Both transactions commit with the same commit timestamp.

Unit 7, Lesson 3: under backward validation, a committing transaction T1 is checked against which transactions?

  • Every transaction that is still active.
  • Every transaction that ever committed.
  • The transactions that started after T1 started, committed or not.
  • The transactions that committed while T1 was running.

Unit 7, Lesson 4: what does the "re-execute scans" defence against phantoms keep for each transaction, and what does it do at commit?

  • The WHERE clause of every query it ran; at commit it re-runs the scans and compares the results.
  • A lock on each index key range it read; at commit it releases them.
  • A lock on every page of the table; at commit it releases them.
  • A copy of every tuple it read; at commit it compares the copies with the table.

Moving a primary key

After stage 9, an update rewrites a tuple in place: same RID, new values, the old values in the undo log. That is right as long as the primary key stays the same. If it changes, the RID would hold a different key from the one its index entry names, and the index entry for the new key would point somewhere else. Your stage-9 code shows the result. After UPDATE maintable SET col1 = col1 + 1 on keys 1 to 4, done in place, key 1's RID holds (2, 0), and the index entry for key 2 still leads to its old RID, which now holds (3, 0). The index scan reconstructs (3, 0), checks the filter col1 = 2 on it, and returns nothing:

txn_index_test.go:206: ERROR: expect col1 = 2 to have 1 row, found 0 rows (txn2, read ts 4): <empty table>

So a key change becomes a delete of the old row and an insert of the new one. The writeup's walk-through runs UPDATE table SET col1 = col1 + 1 in order: "we delete all tuples that will be updated", then "we insert the updated tuple back to the table with new primary keys", then commit. The deletes must all come first. With one row at a time, the insert of the new key 2 would find key 2's row still live and report a unique violation, although the same statement is about to move that row to 3. TestTxnPKUpdateSwap runs SET col1 = 5 - col1, which exchanges keys 1 and 4 and keys 2 and 3, and passes only in this order.

The inserts are the insert executor's inserts, with everything stage 9 added: a key whose slot holds a deletion marker reuses that slot, and here most of those markers are the statement's own deletes. The delete half is your delete code: undo logs, the write set, conflicts, and Project 3's upkeep for any secondary index. On the reference, after the statement above:

RID=9/0 ts=5 <del marker> tuple=(1, 0)
  txn4@0 (1, 0) ts=4
RID=9/1 ts=5 tuple=(2, 0)
  txn4@1 (2, 0) ts=4
RID=9/2 ts=5 tuple=(3, 0)
  txn4@2 (3, 0) ts=4
RID=9/3 ts=5 tuple=(4, 0)
  txn4@3 (4, 0) ts=4
RID=9/4 ts=5 tuple=(5, 0)

Keys 2 to 4 went back into their own slots (the transaction deleted them first, so its own deletion markers were reusable), key 1's slot stays a deletion marker, and key 5 is new. Each old slot has one undo log, as stage 5 requires: the delete created it, and the reinsert by the same transaction extended it. A reader that began before the update still finds keys 1 to 4 through the index, which TestTxnPKUpdateReverify checks.

Two smaller rules. The course's design takes the delete-then-insert path for every row of the statement as soon as any row's key changes; a statement that changes no key stays in place. And the count row is the number of rows the child produced, whichever path ran.

What snapshot isolation still allows

Unit 7, Lesson 5 ended with write skew: two transactions read overlapping data, each writes something the other read, and their write sets don't overlap, so first-writer-wins never fires. Lesson 4 added phantoms: rows inserted or deleted by another transaction that would have matched a scan. Under snapshot isolation, Project 4 allows both. The marble example runs as it is in the Go shell, on two rows of colour 0 and two of colour 1:

Verification at commit

The writeup: "We use OCC backward validation for serializable verification. The verification method we talked about in the lecture only applies to a static database. In BusTub, you will need to consider newly-inserted and deleted records." Comparing read sets of RIDs can't catch a phantom, since a row that didn't exist was never read. So a transaction records what it asked for: "you will need to store the scan filter (aka. scan predicate) in the transaction each time the sequential scan executor or the index scan executor are called." That is Lesson 4's re-execute-scans idea, with the predicate tested against the changed rows instead of re-running the scan. A scan with no filter reads every row, so it records a predicate that is always true. Only SERIALIZABLE transactions need to record anything.

Then, when a serializable transaction commits (the shipped Commit already calls verifyTxn under the commit mutex, and aborts on false):

  1. "You do not need to verify a read-only transaction." No writes, nothing to check: a read-only transaction is serializable at its read timestamp.
  2. Collect the conflict transactions: those that committed after this transaction's read timestamp. These are the transactions in backward validation's scope.
  3. Collect every RID in their write sets.
  4. For each such tuple, walk its version chain back to the version at this transaction's read timestamp and replay the changes one by one, newest first. For an insert, test the new tuple against this transaction's scan predicates on that table; for a delete, the deleted tuple; for an update, both the before image and the after image. Any match: verification fails.

The writeup adds four edge cases, and each has a test:

  • An insert followed by a delete in one transaction leaves a deletion marker, and "should be regarded as a no-op instead of a delete" (TestTxnSerializablePhantoms/insert_then_delete).
  • An update that sets a column to its old value still counts: "you should still process it as an identical update instead of ignoring it".
  • Two transactions that change X to Y and then Y back to X still conflict with a third that started before the first and commits after the second, because the replay sees both changes (TestTxnSerializableRevertedUpdate).
  • "If a transaction needs to be aborted in the commit phase, you should directly go through the abort logic to revert the changes, and set the transaction status to ABORTED instead of TAINTED." The shipped Commit calls your Abort, which does that (TestTxnSerializableAbortedState).

A version with a temporary timestamp in a chain is not a committed change: it is another running transaction's write, or this transaction's own. Only versions with commit timestamps above the read timestamp are replayed. Two lock rules from earlier stages apply here too: GetUndoLog and GetUndoLogOptional take TxnMapMu.RLock, so collect the conflict transactions under TxnMapMu, release it, and only then walk chains; and WriteSets() and ScanPredicates() return the live maps, which is fine for a transaction that has committed and for the one being verified, and nobody else. The concurrency and bustub tests commit transactions with empty write sets on a manager with no catalog, so return before touching m.Catalog when there is nothing to check.

The writeup names the cost: "This verification method is inefficient because (1) only one transaction can enter the verification process (2) we loop over all write sets of possible-conflicting transactions and evaluate scan predicates on that." It suggests parallel verification or precision locking for the leaderboard, which the stretch lesson takes up.

A test that must not abort

A verification that aborts every serializable writer whenever anything committed after it began would pass most of these tests: they check that a conflict aborts. TestTxnSerializableDisjoint checks the other direction. Rows (1, 100) and (1, 102) are in the table; b is the primary key. txn1 runs UPDATE maintable SET a = 5 WHERE b = 100 and txn2 UPDATE maintable SET a = 6 WHERE b = 102, both serializable, both begun before either commits. txn1 commits first. txn2 then reads its own row and commits, and must succeed: txn1 is a conflict transaction, but its change to row 100, before image (1, 100) and after image (5, 100), matches neither of txn2's predicates, b = 102. A snapshot-isolation reader that began before both still sees the original two rows.

The test has an unusual property: it already passes after stage 10, because without verification both writers commit anyway. It fails on the starter only because of its snapshot read. Its job is to keep passing once your verification exists: the other tests check that conflicts abort, and this one checks that a transaction without a conflict commits. If it breaks during stage 11, your verification is too coarse: it probably tests predicates against the wrong table or against rows that didn't change, or it aborts on any conflict transaction without testing predicates.

Check your understanding

A table holds keys 1 to 4. One transaction runs UPDATE t SET a = a + 1, where a is the primary key, and commits. How many tuples does the table heap hold?

  • 4, all updated in place.
  • 8: four deletion markers and four new tuples.
  • 5: keys 2 to 4 reuse their slots, key 5 is new, key 1's slot is a deletion marker.
  • 4: key 1's slot is removed and key 5 takes its place.

Why must a primary-key update delete every affected row before inserting any new one?

  • Otherwise inserting a new key can hit a row with that key that the statement hasn't deleted yet.
  • Otherwise each tuple would get two undo logs from the same transaction.
  • Otherwise the child scan would see the new rows again (the Halloween problem).
  • Otherwise other transactions could see the new rows before the old ones are gone.

TestTxnSerializableBasic: rows (1, 100), (1, 101), (0, 102), (0, 103), with b the key. txn2 runs UPDATE ... SET a = 0 WHERE a = 1, txn3 UPDATE ... SET a = 1 WHERE a = 0; txn2 commits first. What makes txn3's verification fail?

  • Both transactions wrote the same rows.
  • The after images of txn2's updates match txn3's predicate a = 0.
  • The before images of txn2's updates match txn3's predicate a = 0.
  • txn3's own updates match its predicate a = 0.

A verifyTxn tests only the after image of each change, never the before image (and a delete, which has no after image, not at all). Which of these conflicts does it still detect?

  • A committed delete of a row that matches the predicate.
  • A committed update that changes a matching row into a non-matching one.
  • An insert followed by a delete of a matching row in one transaction.
  • A committed insert of a row that matches the predicate.

Which verification would make TestTxnSerializableDisjoint fail?

  • One that skips read-only transactions.
  • One that verifies txn1 before txn2.
  • One that aborts a writer whenever a conflict transaction wrote to a table it scanned.
  • One that tests the before and after images of row 100 against txn2's predicates.

Build it: primary-key updates (stage P4.8a)

You edit execution/update_executor.go. Run commands from go_db_internals/intro_to_db. The rules:

  • Compute every target tuple first, as you already do (the update is a pipeline breaker).
  • If any row's primary key differs from its target's, delete every affected row, as the delete executor does, and then insert every target, as the insert executor does, including the unique check and slot reuse. Otherwise update in place as in stage 9.
  • Any conflict or violation along the way taints the transaction and fails the statement. The count row is the number of child rows.
  • What to think about

    You have each row's old tuple and its target. How do you get the primary-key part of each, for a composite key too? Does SET col2 = col2 + 10 on a table keyed by col1 ever need this path?

    The approach

    Find the index with IsPrimaryKey among the table's indexes. For each pair, build both keys with KeyFromTuple and compare them by content. One difference is enough to switch the whole statement to delete-then-insert. A table without a primary key never switches.

    oldKey := olds[i].KeyFromTuple(schema, pk.KeySchema, pk.Index.KeyAttrs())

    Which code already deletes one row with an undo log, a conflict check and an atomic write? Which code already inserts one tuple with the unique check and slot reuse?     Loop over the RIDs and delete each one with the shared write function from stage 9, doing Project 3's upkeep for any non-primary index. Build it: serializable verification (stage P4.8b)

You edit execution/seq_scan_executor.go, execution/index_scan_executor.go and concurrency/transaction_manager.go (verifyTxn). The rules:

  • A scan run by a SERIALIZABLE transaction records its filter as a scan predicate on its table, or a predicate that is always true when it has no filter.
  • At commit, a serializable transaction with writes fails verification if a change committed after its read timestamp touches a row one of its predicates selects: the new tuple of an insert, the old tuple of a delete, either image of an update. An insert and a delete of one tuple by one transaction are no change.
  • Read-only transactions, and transactions with nothing recorded, pass.
  • What to think about

    Where does a scan know its table and its filter, and is that method called once per scan? An UPDATE ... WHERE b = 100 also reads through a scan: does its predicate need recording? What does a scan without a filter read?

    The approach

    In each executor's Init, after finding the table, check the context's transaction: if its IsolationLevel() is concurrency.Serializable, append the plan's FilterPredicate for the table's OID with AppendScanPredicate. A nil filter becomes a constant TRUE expression. Put this in one helper that both executors call.

    One key fragment 
    if pred == nil {
	pred = expressions.NewConstantValueExpression(types.NewBooleanValue(true))
}
txn.AppendScanPredicate(oid, pred)
  • What to think about

    Which transactions can have changed what this one read: those still running, those that committed before it began, or those that committed after its read timestamp? Which lock protects TxnMap, and which later calls in this function take that lock again? Does a write to a table this transaction never scanned matter?

    The approach

    Return true at once if the write set or the predicate map is empty. Under TxnMapMu.RLock, copy out the transactions whose state is committed and whose commit timestamp is above txn.ReadTs(), then release the lock. Their write sets can no longer change, so read them afterwards: build a set of RIDs per table OID, keeping only tables that have predicates. A RID written by several conflict transactions needs to be checked once, because the next step replays its whole chain.

    One key fragment 
    if other.TransactionState() == TxnCommitted && other.CommitTs() > txn.ReadTs() {
	conflicts = append(conflicts, other)
}
  • What to think about

    Each step of the chain is a pair of versions: the newer one and the one before it. Which of the two is the before image and which the after image, and what is each for an insert and for a delete? When do you stop walking? Which versions carry a temporary timestamp, and why aren't they committed history? What if a log's transaction was garbage collected?

    The approach

    Read the base with GetTupleAndUndoLink. While the current version's timestamp is above the read timestamp, build the next older version: with a link, fetch the log (GetUndoLogOptional), add it to the list of logs applied so far, and call ReconstructTuple on the base with that list; without a link, the older version is "did not exist". If the current version's timestamp is a commit timestamp (below common.TxnStartID), test whichever of the two versions exist against every predicate; a deletion has no image to test, so an insert-then-delete tests nothing. Step back and repeat. Evaluate a predicate on a tuple with the table's schema and treat NULL as false.

    One key fragment 
    v := pred.Evaluate(&tuple, info.Schema)
if !v.IsNull() && v.AsBool() {
	return false // a committed change touched a row we scanned
}
