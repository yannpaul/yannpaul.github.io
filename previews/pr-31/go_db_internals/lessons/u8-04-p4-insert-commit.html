P4.4 Insert and Commit

Make inserts write the transaction's temporary timestamp and record the new RID in its write set, make Commit stamp every written tuple with the commit timestamp, and write the TxnMgrDbg dump that every later test prints.

Up to the MVCC scan, the tests built every version chain by hand. From this stage on they are written in SQL, so the executors themselves have to produce what the scan reads. The first of them is the insert: a new tuple goes into the table heap carrying a timestamp that no other transaction can reach, and only Commit makes it visible, by replacing that timestamp with the commit timestamp. Both steps are short, and they rely on everything from P4.1 to P4.3. This lesson also has you write TxnMgrDbg. The writeup says "If you come to us without this function written, we will ask you to implement it first."

Warm-up: retrieval from earlier lessons

Unit 7, Lesson 5: an uncommitted writer stamps the tuple it changed with a temporary timestamp, TXN_START_ID plus its transaction id (common.TxnStartID = 1 << 62 in Go). Why does no other transaction see that version?

  • The version is kept in the writer's private workspace until commit, so readers can't find it.
  • The writer holds a latch on the tuple until it commits, so readers skip it.
  • It is larger than any read timestamp, and a reader sees only versions at or below its own read timestamp.
  • The temporary timestamp is negative, and readers ignore versions with negative timestamps.

Unit 6, Lesson 3: in Project 3, a table holds 3 rows and no deleted tuples. UPDATE t SET a = a + 1 updates all three. How many tuples does the table heap hold afterwards, deleted ones included?

  • 3, because each row was overwritten in its slot.
  • 6: three deleted old versions and three new ones.
  • 3, because the deleted old versions are removed from the page.
  • 9, because the scan meets each new version once more.

Unit 7, Lesson 3: in OCC's write phase, what does the serial-commit design use, and what does it buy?

  • A global latch, so that only one transaction is in the validation or write phase at a time.
  • Fine-grained write latches taken in key order, so that several transactions can write at once.
  • Exclusive locks on every written object, held until the transaction ends.
  • A restart of every active transaction's read phase, so that they read the new values.

Insert with a temporary timestamp

Your Project 3 insert (Unit 6, Lesson 3) appends each child tuple to the heap with TupleMeta{Ts: 0, IsDeleted: false} and adds its key to every index. Task 3.1 changes two things. The meta's timestamp becomes the transaction's temporary timestamp, txn.TransactionTempTs(). And the new RID goes into the transaction's write set, the set of tuples it has changed, through txn.AppendWriteSet(tableOID, rid). The writeup's whole description:

"The timestamp in the table heap should be set to the transaction temporary timestamp, as described in Task 2.2. You should also add the RID to the write set via AppendWriteSet at this point."

An insert needs no undo log. Before the insert the tuple did not exist, and a reader that cannot see the new base tuple finds no version chain behind it, so CollectUndoLogs reports false and the scan skips the RID. That is the right answer for every reader except the inserting transaction, and the owner is the one case your CollectUndoLogs already treats as visible: a base timestamp equal to the reader's own temporary timestamp. (Task 4.2 adds inserts into a deleted slot, which do need an undo log. That comes in P4.7.)

The rest of the insert stays as it was: one count row, the same index upkeep, and the same Halloween guard in the scan below an INSERT ... SELECT. Primary-key checks come in P4.7.

The write set is a map[catalog.TableOID]map[common.RID]struct{} inside the transaction, guarded by the transaction's own mutex in AppendWriteSet. WriteSets() hands you the live map, so only read another transaction's write set after it has finished. Every modification executor has to maintain it: the insert now, the delete and the update in the next lesson. The transaction manager depends on it twice, at commit (this lesson) and at abort (P4.6).

Commit stamps the write set

Task 3.2 completes the Commit you started in P4.1. The writeup's pseudocode:

  1. Take the commit mutex.
  2. Obtain a commit timestamp ("you will likely need to do a .load() + 1 instead of .fetch_add(1) here, think about why in relation to Begin").
  3. "Iterate through every tuple that has been modified by this transaction (via the write set) and set the timestamp of the base tuples to the commit timestamp."
  4. Set the transaction to the COMMITTED state.
  5. Update the commit timestamp of the transaction.
  6. Update last_committed_ts_.

In concurrency/transaction_manager.go the stamping goes where the starter says TODO(P4): implement the commit logic: after the state check and the serializable check, before the TxnMapMu section that publishes the new state and the new last commit timestamp. Stamping replaces only the timestamp. A deletion marker in the write set stays a deletion marker, now at the commit timestamp; next lesson's deletes depend on that.

P4.1 already arranged steps 2 and 6: the commit timestamp is computed with Load() + 1 and published only at the end, under TxnMapMu, the latch Begin reads it under. The stamping loop is the window that arrangement protects. Take the readers by when they began:

  • A reader that began before this commit has a read timestamp below the commit timestamp. A stamped tuple is still too new for it, so it follows the tuple's version chain, which for a fresh insert is empty, and the tuple stays invisible. A tuple not yet stamped carries the temporary timestamp and is invisible too. So even halfway through the stamping loop, such a reader sees nothing of the commit.
  • A reader can't get the new commit timestamp as its read timestamp until step 6, when every tuple is stamped, so it sees the whole commit. With a fetch_add at step 2, a transaction beginning during the loop would get that timestamp early and see the tuples already stamped but not the ones still carrying the temporary timestamp: half a transaction.

Commits don't race each other, because commitMu lets only one through at a time (the serial commits of Unit 7, Lesson 3). Writers don't interfere either: a tuple that carries this transaction's temporary timestamp is one that no other transaction may change (the next lesson's write-write conflict). So you can read the meta, change its timestamp and write it back with heap.UpdateTupleMeta. Doing both under one page write latch (AcquireTablePageWriteLock, GetTupleMetaWithLockAcquired, then the page's UpdateTupleMeta) is a little tidier, and either passes.

Look each table up with m.Catalog.GetTableByOID(oid), inside the loop over the write set. The pre-built tests in concurrency (TestTransactionManagerCommit and Abort) commit and abort transactions with empty write sets on a manager whose Catalog is nil (the manager of the Project 3 executor tests has no catalog either), so a Commit that touches the catalog before it knows there is something to stamp fails them.

The writeup also describes a tuple that one transaction inserts and then deletes: "We have set the commit timestamp to 0 at the end because this tuple is inserted by txn9 and removed by txn9, which means that it never actually existed." It adds "You could also just ignore this case and follow the usual commit logic." The course's reference solution stamps such a tuple like any other.

TxnMgrDbg and \dbgmvcc

TxnMgrDbg in concurrency/execution_common.go prints a table's heap and version chains. The Go version takes an io.Writer first: the tests pass a buffer and log what you wrote after each step, where go test shows it for a failing test (or always, with -v), and the shell's \dbgmvcc <table> command prints it. Until you replace the starter's body, every dump in a failing test reads

        You see this line of text because you have not implemented `TxnMgrDbg`. You should do this once you have finished task 2. Implementing this helper function will save you a lot of time for debugging in later tasks.

The format is yours ("you can print anything you want to examine the version chain"). The writeup's suggested format, which the course's reference solution follows, is one line per heap tuple and one indented line per undo log:

RID=0/1 ts=2 tuple=(2, 2.000000, <NULL>)
  txn1@0 (1, 1.000000, _) ts=1
RID=0/5 ts=4 <del marker> tuple=(2, 2.000000, <NULL>)
  txn4@1 (2, 2.000000, _) ts=2
RID=0/6 ts=4 tuple=(4, 4.000000, <NULL>)
  txn4@2 <del> ts=2
RID=0/7 ts=txn2 tuple=(100, 100.000000, <NULL>)

What each line needs:

  • Every tuple, deleted ones included. Use heap.MakeEagerIterator(), which runs to the current end of the heap, and read each RID's meta, tuple and first undo link together with concurrency.GetTupleAndUndoLink.
  • The timestamp, in a readable form. A temporary timestamp is 262 plus the id, a 19-digit number. Print it as txnN, where N is the timestamp with the TxnStartID bit cleared (ts ^ TxnStartID, the same thing TransactionIDHumanReadable does for ids).
  • The chain. Follow the links: the log's owner and index (txn1@0), its values, with _ for each column it doesn't hold (lay its Tuple out with the partial schema, as in your ReconstructTuple from P4.2), or a marker for a deletion log, and its Ts. Read each log with GetUndoLogOptional, not GetUndoLog: after garbage collection (P4.6) a chain can point into a transaction that no longer exists, and GetUndoLog panics there. Print something like <garbage collected> and stop.

The test's variable names are not the transaction ids: in TestTxnInsertCommit the variable txn3 is transaction 4 (var=txn3 id=4), so your dump writes its inserts as ts=txn4. Also keep the dump from panicking: it runs inside tests that may already have gone wrong, and a panic there hides the dump you wanted to read.

Check your understanding

txn1 and txn2 both begin with read timestamp 1. txn1 runs INSERT INTO maintable VALUES (1), txn2 runs INSERT INTO maintable VALUES (2), then txn1 commits with commit timestamp 2. What does txn2's SELECT a FROM maintable return now?

  • 1 and 2, because txn1 has committed.
  • Nothing, because neither row is visible at read timestamp 1.
  • 1 only, because txn2's own row is not committed yet.
  • 2 only: its own insert, and not txn1's.

Suppose Commit stored the new last commit timestamp first and stamped the write set after. Transaction R calls Begin while the stamping loop is halfway through a 100-row insert. What can R's scan return?

  • Only the rows already stamped, a part of the committing transaction's insert.
  • None of the 100 rows, because R began before the commit finished.
  • All 100 rows, because R's read timestamp covers the whole commit.
  • Nothing yet: R's Begin waits on the commit mutex until the commit ends.

A transaction inserts a row, deletes it again in a later statement, and commits with commit timestamp 7. With the reference solution's commit, what is that tuple's meta afterwards?

  • {Ts: 7, IsDeleted: false}: commit makes every write-set tuple live.
  • {Ts: 0, IsDeleted: true}, because the writeup requires 0 for a tuple that never existed.
  • {Ts: 7, IsDeleted: true}, a deletion marker at the commit timestamp.
  • {Ts: the temporary timestamp, IsDeleted: true}: commit skips deleted tuples.

After this stage, TestInsertTupleMeta inserts two rows through your insert executor in the Project 3 test environment, whose single transaction never commits. Which metas does it accept?

  • Only {Ts: 0, IsDeleted: false}, the meta Project 3 has always written.

Build it: insert, commit and the debug dump (stage 4)

You edit three files: execution/insert_executor.go (your Project 3 insert), concurrency/transaction_manager.go (Commit) and concurrency/execution_common.go (TxnMgrDbg). Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • A new tuple carries the inserting transaction's temporary timestamp and is not deleted. Its RID goes into the transaction's write set. It gets no undo log and no undo link.
  • A reader sees a base tuple if its timestamp is at most the reader's read timestamp, or is the reader's own temporary timestamp. Otherwise the reader walks the chain, and a fresh insert has none.
  • Commit, under the commit mutex, computes last + 1, stamps every tuple in the write set with it (timestamp only, IsDeleted unchanged), and only then publishes the commit timestamp, the state and the new last commit timestamp under TxnMapMu. An empty write set touches neither heap nor catalog.
  • What to think about

    Where does the executor get its transaction? Which table OID does the write set want, and which RID: the child's or the heap's? Does anything else in your insert need to change for this stage?

    The approach

    Get the transaction from e.ExecutorContext().Transaction() once per Next. Change the meta you pass to InsertTuple to carry txn.TransactionTempTs(). Right after a successful insertion, call txn.AppendWriteSet with the table's OID and the RID that InsertTuple returned. Leave the index upkeep and the count row as they are.

    One key fragment 
    rid, ok := e.tableInfo.Table.InsertTuple(table.TupleMeta{Ts: txn.TransactionTempTs(), IsDeleted: false}, t)
// ...

  • What to think about

    Which part of the meta changes, and which must not? At which point may a new transaction first get this commit timestamp as its read timestamp, and must the stamping be over by then? What happens when m.Catalog is nil?

    The approach

Idiom

BusTub's std::atomic<timestamp_t> last_commit_ts_ is an atomic.Int64 in Go, and the writeup's two operations map one to one: .load() + 1 is m.lastCommitTs.Load() + 1, which publishes nothing, and the final update is a Store (or Add(1)) under TxnMapMu. The write set is a Go set, map[common.RID]struct{}, so the loop visits the RIDs in random order. That is harmless here: each tuple is stamped independently, and no reader can begin at the new timestamp until the loop is over.

Something unclear? For example, why a fresh insert needs no undo log, why Commit must not move the last commit timestamp before the stamping is done, why stamping keeps IsDeleted, or why the shell's commit timestamps jump by more than one. Ask your teacher (me) before moving on.
