P4.3 MVCC Sequential Scan

Decide which version of a tuple a transaction can see from its read timestamp, temporary timestamps and its own writes, write CollectUndoLogs to gather exactly the undo logs that version needs, and rewrite your Project 3 sequential scan to return each tuple as the transaction's snapshot saw it.

With timestamps (P4.1) and reconstruction (P4.2) in place, a scan has everything it needs to read the past. For each tuple in the heap it asks one question: is the base version visible to me? If not, it walks the version chain until it finds the version that is, and rolls the base back to it. This is Task 2.2 of the writeup, and the first stage where your Project 3 executors change. It is also the first stage whose tests run SQL: BusTub's ScanTest builds version chains by hand and then runs SELECT through your scan, once for each of six transactions with different read timestamps.

Warm-up: retrieval from earlier lessons

Unit 6, Lesson 2: the scan's FilterPredicate is b > 4, and a row has b NULL. What does the scan do with it?

  • It skips the row, because the predicate evaluates to NULL and NULL counts as false.
  • It returns the row, because the predicate is not false.
  • It returns an error, because the comparison has a NULL operand.
  • It passes the row up to a Filter node, which decides.

Unit 7, Lesson 5: tuple A has versions with commit timestamps 1, 2, 3 and 4; B has 1, 3 and 4; C has 1, 2 and 4; D has one version, at 3. Which versions does a transaction with read timestamp 3 see?

  • A4, B4, C4 and D3
  • A3, B3 and C2, and no D
  • A3, B3, C2 and D3
  • A3, B3, C3 and D3

Unit 2, Lesson 6: while one goroutine holds a ReadPageGuard on a page, what can other goroutines do with that page?

  • Read it or write it; a read guard only pins the page.
  • Take read guards on it too; a write guard waits until the read guard is dropped.
  • Nothing: the page is latched exclusively until Drop.
  • Evict it, since a read guard never dirties the page.

Which version a transaction sees

Every tuple in the heap carries a timestamp in its TupleMeta.Ts. From P4.1 and Unit 7 you know the two kinds: a commit timestamp, below TxnStartID, for a version a committed transaction wrote, and a temporary timestamp, TxnStartID plus the writer's id, for a version an uncommitted transaction wrote. A transaction txn reading a base tuple is in one of the writeup's three cases:

  1. The base tuple's timestamp is at most txn.ReadTs(). The base is the version txn sees, and nothing needs undoing.
  2. The base tuple's timestamp is txn.TransactionTempTs(): txn itself wrote it. A transaction sees its own writes, so this is the same as case 1. The writeup's example: a transaction with human-readable id 3 that scans a base tuple with timestamp TXN_START_ID + 3 knows it was the most recent modifier.
  3. Otherwise the base is newer than the snapshot: either committed after txn began, or written by another transaction that hasn't committed. Then txn walks the version chain and collects undo logs until it reaches the first one whose Ts is at most its read timestamp. If the chain ends first, the tuple did not exist at txn's read timestamp, and the scan skips it.

Case 3 needs no special test for another transaction's temporary timestamp. Every temporary timestamp is at least 262, far above any read timestamp, so ts <= txn.ReadTs() is false for it, and the chain walk starts. That is the point of putting temporary timestamps at the top of the number line. Only the equality check of case 2 has to look at the transaction's own id.

The writeup's example makes the cases concrete. To keep the numbers readable it uses 1000 for TXN_START_ID, so 1009 is txn9's temporary timestamp. txn9 has read timestamp 3 and has modified A, B and D; C was last committed at 4:

  • txn9's own scan returns (A, 9), (B, 9), (C, 2) and (D, 9). A, B and D carry 1009, its own timestamp (case 2). C's timestamp 4 is above 3, so txn9 walks C's chain to the version at 2 (case 3).
  • A scan by another transaction with read timestamp 4 returns (A, 3), (B, 3) and (C, 4). A and B carry txn9's pending writes, so it walks their chains to the last version at or before 4. C at 4 is visible as it is. D carries 1009 and has no chain: txn9 inserted it, so for this reader D does not exist.

#20 Multi-Version Concurrency Control, "MVCC example" (12:03), slides 6–7: a reader keeps reading the old version while a writer creates a new one, and a second writer runs into an uncommitted change. Temporary timestamps are how Project 4 marks that uncommitted change.

CollectUndoLogs

Case 3's walk is CollectUndoLogs, the second helper in concurrency/execution_common.go:

func CollectUndoLogs(rid common.RID, baseMeta table.TupleMeta, baseTuple table.Tuple, undoLink UndoLink,
	txn *Transaction, txnMgr *TransactionManager) ([]UndoLog, bool)

It returns the undo logs that ReconstructTuple needs to rebuild the version txn can see, newest first, or false if txn can see no version. Its doc comment gives the contract:

  • If the base is visible to txn (case 1 or 2), the result is an empty list and true.
  • Otherwise it starts at undoLink, fetches each log with txnMgr.GetUndoLogOptional, appends it, and stops after the first log whose Ts is at most the read timestamp. That log is needed: it is the one that restores the visible version.
  • It returns false if the chain ends first (an invalid link), or reaches a log whose transaction no longer exists.

The last rule anticipates stage 6. Garbage collection removes transactions whose undo logs no reader can need, and the writeup allows it to leave dangling links behind: a link to a removed transaction points below the watermark, and a correct scan never follows one, because it finds its version earlier in the chain. GetUndoLogOptional returns false for a missing transaction instead of panicking, so a mistake there shows up as a missing row rather than a crash.

BusTub's signature takes std::optional<UndoLink> and returns std::optional<std::vector<UndoLog>>. The Go port passes a plain UndoLink, with an invalid link meaning "no chain", because the type already has that sentinel and GetTupleAndUndoLink returns InvalidUndoLink for a tuple without one; the result becomes ([]UndoLog, bool).

The MVCC sequential scan

Your Project 3 SeqScanExecutor.Next read each tuple's meta and bytes from the iterator, skipped deleted tuples, and applied the filter. The MVCC version keeps the shape and replaces the middle. For each RID the iterator gives:

  1. Read the base tuple's meta, its bytes and its first undo link together, with concurrency.GetTupleAndUndoLink(txnMgr, heap, rid).
  2. Call CollectUndoLogs for the executor's transaction. If it returns false, skip the RID.
  3. With no logs, the version is the base itself: skip it if the base meta says deleted. With logs, call ReconstructTuple, and skip the RID if it reports a deleted version.
  4. Evaluate the FilterPredicate, if there is one, on the reconstructed tuple. A filter on the base tuple would select rows by values the transaction can't see.
  5. Set the RID on the tuple (ReconstructTuple leaves it unset), and append the tuple and its RID to the batch.

The transaction and the manager come from the executor context: e.ExecutorContext().Transaction() and e.ExecutorContext().TransactionManager(). Everything else stays as in Project 3: Init still makes the iterator with MakeIterator, so the stop point still protects an UPDATE above the scan from the Halloween problem, and the batch contract is unchanged. The iterator now only supplies positions: take it.RID(), advance, and read the tuple through GetTupleAndUndoLink instead of it.GetTuple().

Why the combined read in step 1? GetTupleAndUndoLink (pre-built, in transaction_manager_impl.go) takes the page's read latch, reads meta and tuple, reads the undo link, and only then releases the latch. Writers change the tuple and its link together under the page's write latch, with UpdateTupleAndUndoLink, and from stage 9 on the tests run them while scans run. A scan that read the tuple with heap.GetTuple and the link with GetUndoLink separately could pair a new tuple with an old link, or the other way round, and then reconstruct a version that never existed. No test before stage 9 runs writers concurrently with a scan, so that scan would pass every test until then. Use the atomic helper from the start.

Idiom

Put the visibility steps 2 and 3 in a small function of their own, taking the schema, the RID, the meta, the tuple, the link, the transaction and the manager, and returning (table.Tuple, bool). Stage 9's MVCC index scan needs exactly the same steps for each RID an index lookup returns, and both executors are in package execution, so an unexported helper in seq_scan_executor.go serves both. The index scan stays Project 3's until then, and so does the nested index join, which BusTub never makes MVCC-aware either.

Check your understanding

In ScanTest, record2's base is (3, NULL, NULL) at timestamp 3, its first undo log is a delete log with Ts 2, and the next is a full log (4, 4.0, true) with Ts 1. What does txn2, with read timestamp 2, see for record2?

  • (3, NULL, NULL), the base
  • (4, 4.0, true)
  • An error, because a delete log has no columns to restore.
  • Nothing: at timestamp 2 the tuple was deleted.

Record4's base is a deletion marker stamped with txn3's temporary timestamp, with undo logs (6, NULL, NULL) at Ts 2 and a = 7 at Ts 1. What do txn3 (read timestamp 3) and txn4 (read timestamp 4) see?

  • txn3 sees 6; txn4 sees nothing.
  • txn3 sees nothing; txn4 sees 6.
  • Both see 7.
  • Both see nothing, because the tuple is deleted.

A base tuple carries another transaction's temporary timestamp and has no undo link: that transaction inserted it and hasn't committed. What does CollectUndoLogs return for a reader?

  • No logs and false: the tuple doesn't exist for this reader.
  • An empty list and true: the base is the newest version.
  • It waits until the inserting transaction commits or aborts.
  • It panics, because a pending write must have an undo log.

Record1's base is (1, NULL, NULL) with txn4's temporary timestamp, and its only undo log sets a = 2 with Ts 1. txn1 (read timestamp 1) runs SELECT a FROM maintable WHERE a = 1. What does it get?

  • One row, 1, from record1's base.
  • One row, 2, from record1's old version.
  • No rows.
  • One row, 7, from record4's oldest version.

From CollectUndoLogTest: a tuple's base has timestamp 4, and its chain is one undo log with Ts 3 and an invalid PrevVersion. What does CollectUndoLogs return for a reader with read timestamp 2?

  • An empty list and true.

Build it: MVCC sequential scan (stage 3)

You edit concurrency/execution_common.go (CollectUndoLogs) and your own execution/seq_scan_executor.go (Next, plus a helper). The rules, in plain words:

  • A version stamped ts is visible to txn as it stands if ts <= txn.ReadTs() or ts == txn.TransactionTempTs(). Another transaction's temporary timestamp is never visible.
  • If the base isn't visible, collect undo logs from its first link, newest first, up to and including the first log with Ts at most the read timestamp. A chain that ends first, or a log whose transaction is gone, means no visible version.
  • The scan reads meta, tuple and link atomically with GetTupleAndUndoLink, reconstructs the visible version, skips deletions and invisible tuples, and evaluates the filter on the reconstructed tuple.
  • Keep everything else from Project 3: the iterator made in Init, the batch contract, NULL filters counting as false.
  • What to think about

    Which two timestamps can a visible base carry? When the walk reaches a log with Ts at most the read timestamp, is that log part of the answer or not? What should happen when GetUndoLogOptional reports a missing transaction? Is the zero UndoLink invalid?

    The approach

    Write an unexported isVisibleTs(ts, txn) for the two visible cases. In CollectUndoLogs, return an empty, non-nil slice and true if the base's Ts is visible. Otherwise loop while the current link IsValid(): fetch the log (return false if it is missing), append it, return the slice and true if its Ts is at most the read timestamp, and otherwise move to its PrevVersion. After the loop, return false. The function never looks at IsDeleted; that is ReconstructTuple's business.

    One key fragment 
    logs = append(logs, log) // append first, then test:
if log.Ts <= txn.ReadTs() {
	return logs, true // this log restores the visible version
}

    Which part of your Project 3 loop stays, and which part does the visibility helper replace? Which tuple does the filter see? What RID does a reconstructed tuple carry?

    The approach

    Get the transaction and manager from the executor context once per call. In the loop, take the RID from the iterator and advance it, then read meta, tuple and link with concurrency.GetTupleAndUndoLink. Pass them to your helper and continue on false. Your Project 3 IsDeleted check goes away, since the helper handles deletions. Then apply the filter exactly as before, but to the tuple the helper returned. Call SetRID on it and append it with the RID.
