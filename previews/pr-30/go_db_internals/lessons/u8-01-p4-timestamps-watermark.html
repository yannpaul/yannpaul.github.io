P4.1 Timestamps and the Watermark

Pull Project 4 onto your own Project 1 to 3 code, then give every transaction a read timestamp at begin and a commit timestamp at commit, and keep a watermark of the lowest running read timestamp that costs amortized O(1) per update.

Unit 7 described multi-version concurrency control on paper: each transaction reads a snapshot fixed by its timestamp, writers create new versions, and old versions are thrown away once no reader can see them. Project 4 builds that into BusTub, on top of your buffer pool, your B+tree and your executors. Everything later in the project compares timestamps, so the first stage is where they come from: the transaction manager hands them out, and the watermark tracks the oldest snapshot still in use.

Warm-up: retrieval from earlier lessons

Unit 7, Lesson 5: an uncommitted writer stamps its tuples with TXN_START_ID plus its transaction id, where TXN_START_ID is 262. Why bit 62 and not bit 63?

  • Timestamps are 63-bit numbers in BusTub, so bit 63 does not exist.
  • Bit 63 is reserved for the human-readable transaction id.
  • With bit 63 set the number would be negative, and temporary timestamps would no longer compare correctly with < and >.
  • Commit timestamps already use bit 63 to mark a committed version.

Unit 6, Lesson 2: in Project 3, what does a tuple's TupleMeta.Ts hold?

  • Always 0; the field is there for Project 4.
  • The wall-clock time at which the tuple was inserted.
  • The id of the transaction that inserted the tuple.
  • The number of times the tuple has been deleted and re-inserted.

Unit 3, Lesson 7: a goroutine holds a sync.RWMutex in read mode, another goroutine is waiting in Lock, and the first goroutine calls RLock on the same mutex again. What happens?

  • The second RLock succeeds at once, because read mode is shared.
  • The runtime notices that the goroutine already holds the lock and panics.
  • The writer goes first, then the second RLock succeeds.
  • All of them wait forever: the new RLock queues behind the writer, which waits for the first read lock.

Two timestamps per transaction

Unit 7, Lesson 5 introduced Project 4's two timestamps. Task 1.1 of the writeup is about where they come from:

  • When a transaction begins, its read timestamp is the commit timestamp of the most recently committed transaction. The writeup's way to think of it: the timestamp of the latest atomic write into the database. It decides the newest version of each tuple the transaction can see.
  • When a transaction commits, it gets a commit timestamp from a monotonically increasing counter: the last commit timestamp plus one. Commit timestamps are unique, so they give the serialization order, and a committed transaction can be named by its commit timestamp.

Transaction ids are a third, separate sequence. The first id is common.TxnStartID (1 << 62) and each Begin takes the next one; the logs print the human-readable id, the id with that bit stripped (TransactionIDHumanReadable). An id is also the transaction's temporary timestamp (TransactionTempTs), which matters from stage 3 on. The writeup warns not to confuse ids with commit timestamps: both increase, but a transaction that aborts has an id and no commit timestamp, and the order of ids is the order of Begin calls, not of commits.

BusTub's TimestampTracking test shows the rule. Begin two transactions and commit one between them:

- txn_begin var=txn0 id=0 status=RUNNING read_ts=0 iso_lvl=SNAPSHOT_ISOLATION
- txn_begin var=txn_store_1 id=1 status=RUNNING read_ts=0 iso_lvl=SNAPSHOT_ISOLATION
- txn_commit var=txn_store_1 id=1 status=COMMITTED read_ts=0 commit_ts=1

Nothing has committed when txn0 and txn_store_1 begin, so both read at 0. txn_store_1 commits with 0 + 1 = 1, and the next transaction to begin, txn1, reads at 1. txn0 keeps its read timestamp 0 for as long as it runs: a snapshot doesn't move. On the starter the last line says commit_ts=-1 (common.InvalidTS), because Commit never sets one, and the test stops there with txn_store_1 commit ts = -1, want 1.

The watermark

Task 1.2 defines the watermark as the lowest read timestamp among all transactions that have not yet committed or aborted, or the latest commit timestamp if there is no such transaction. Unit 7, Lesson 6 explained what it is for: a version that the reader with the lowest read timestamp can't see, no reader can see, so garbage collection (stage 6) may drop it. Stage 1 only has to keep the number right.

The easy way to compute it is to walk every transaction and take the minimum read timestamp of the running ones. The writeup rejects that as too slow and asks for O(log N); BusTub's reference solution is amortized O(1) with a hash map. The test, TestTxnTsWatermarkPerformance, adds a million read timestamps, then removes them all, once in order and once in reverse order, and checks the watermark after every call. Anything that scans all running transactions per call does hundreds of billions of steps there.

The Go type is BusTub's, with exported fields:

type Watermark struct {
	CommitTs     common.Timestamp
	WatermarkTs  common.Timestamp
	CurrentReads map[common.Timestamp]int
}

Watermark() is already written: it returns CommitTs when CurrentReads is empty, and WatermarkTs otherwise. UpdateCommitTs is written too, and its doc comment adds a rule for the caller: update the commit timestamp before removing the transaction, so that the watermark is right when the last running transaction leaves. Your part is AddTxn and RemoveTxn, and the two facts that make them cheap:

  • Several running transactions can share a read timestamp: every transaction that begins between two commits gets the same one. So CurrentReads counts transactions per read timestamp, and a timestamp leaves the map only when its count reaches zero.
  • A new transaction's read timestamp is the last commit timestamp, which is at least every running read timestamp. So the minimum only changes on AddTxn when the map was empty, and it only ever moves forward. When the minimum's count drops to zero, step forward one timestamp at a time until you reach one that is in the map. Over the watermark's whole life those steps add up to at most the last commit timestamp, which is what makes the cost amortized O(1).

A sorted structure is the O(log N) alternative. Go's standard library has no ordered map (the writeup hints at a container in C++'s), but container/heap with a count map works: push each new read timestamp, and when you need the minimum, pop entries whose count has dropped to zero.

The starter's AddTxn only checks one thing, and panics with read ts < commit ts if a read timestamp below the last commit timestamp is added. That check will catch a race in Begin below.

#20 Multi-Version Concurrency Control, "Transaction-level GC" (1:07:05), slides 23–24: the vacuum frees a finished transaction's old versions once no active transaction has a timestamp below a bound. Project 4's watermark is that bound.

The transaction manager's two latches

TransactionManager in transaction_manager.go has two latches that matter here. They are latches in Unit 3, Lesson 7's sense, protecting in-memory structures for a moment, not the transaction locks of Unit 7:

  • TxnMapMu, a sync.RWMutex, protects TxnMap and the watermark in RunningTxns. The Watermark type is not thread-safe on its own; the manager only calls it under TxnMapMu.
  • commitMu, a sync.Mutex, lets one transaction commit at a time. That keeps commit timestamps in order, and from stage 4 on it keeps the stamping of each committing transaction's writes in order too.

The last commit timestamp lives in lastCommitTs, an atomic.Int64. Begin, Commit and Abort already take the latches in the right places; the TODO(P4) comments sit where your lines go. Two orderings inside them decide whether the stage works.

First, Begin reads the last commit timestamp inside its TxnMapMu section, before AddTxn. Commit publishes a new commit timestamp to the watermark (UpdateCommitTs) under the same latch, so a Begin that reads under it sees either the old commit timestamp in both places or the new one in both. Read it before taking the latch, and a commit can finish in between: Begin then adds a read timestamp below the watermark's commit timestamp, and AddTxn panics. With that bug planted, TestTxnTsConcurrentBeginCommit (8 goroutines, 200 transactions each) fails on every run:

--- FAIL: TestTxnTsConcurrentBeginCommit (0.01s)
    txn_extra_test.go:105: worker 0: worker 0 panicked: read ts < commit ts
                at concurrency.(*Watermark).AddTxn (concurrency/watermark.go:23)
                at concurrency.(*TransactionManager).Begin (concurrency/transaction_manager.go:69)
                at txntest.TestTxnTsConcurrentBeginCommit.func1 (txntest/txn_extra_test.go:87)

Second, Commit computes its timestamp with Load and publishes it at the very end. Under commitMu, the commit timestamp is the last one plus one, read with lastCommitTs.Load(), not taken with Add(1). Then, under TxnMapMu: store the transaction's commit timestamp, set its state to COMMITTED, call UpdateCommitTs(txn.CommitTs()) and RemoveTxn(txn.ReadTs()) (both shipped), and only then store the new last commit timestamp. The reason is the snapshot rule. A transaction that begins with read timestamp c must see everything committed at c. From stage 4 on, a commit stamps its tuples with c before it publishes c. If Add(1) published it early, a Begin could read c while the commit is still stamping, see some of its writes as uncommitted, and see them appear later in the same snapshot.

Abort needs nothing in this stage: its shipped body already removes the transaction from the watermark under TxnMapMu. The writeup says the same of BusTub's starter. You come back to it in stage 7.

Pitfall

TransactionManager.Watermark(), GetUndoLog and GetUndoLogOptional (in transaction_manager_impl.go) take TxnMapMu.RLock themselves. Go's mutexes are not reentrant, so calling any of them while your goroutine holds TxnMapMu blocks forever, in either mode (the warm-up question). Inside Begin and Commit, use m.RunningTxns directly. This matters most in stage 6's garbage collection. Every test call into your code is bounded, so a deadlock fails the test with a message instead of hanging the run.

Idiom

In BusTub, Transaction declares friend class TransactionManager, so the manager writes read_ts_ and commit_ts_, two std::atomic<timestamp_t> fields, while everyone else only has getters. Go has no friend classes; the same effect comes from the package. Transaction's fields readTs, commitTs and state are unexported atomic.Int64 values, and transaction_manager.go is in package concurrency, so it calls txn.readTs.Store(…) directly. Executors in package execution can only read them through ReadTs(), CommitTs() and TransactionState().

Why does Commit compute its timestamp as lastCommitTs.Load() + 1 and store the new value at the end of its TxnMapMu section, instead of calling lastCommitTs.Add(1) at the start?

  • So that no transaction can begin with the new timestamp as its read timestamp before the commit is finished.
  • Because two concurrent Add calls could return the same commit timestamp.
  • Because atomic.Int64.Add is reported by the race detector.
  • Because AddTxn panics when a read timestamp is above the watermark's commit timestamp.

A version of Begin reads lastCommitTs just before it takes TxnMapMu, and uses that value as the read timestamp. What does TestTxnTsConcurrentBeginCommit report?

  • Two transactions receive the same id.
  • A deadlock between Begin and Commit.
  • A worker panicked with read ts < commit ts in AddTxn.
  • Nothing: an atomic load is safe without the latch.

The last commit timestamp is 9, and three transactions are running with read timestamps 4, 4 and 7. The one at 7 commits; then both at 4 abort. What does the watermark report after each step?

  • 4, then 9
  • 4, then 10
  • 7, then 10
  • 7, then 7

Build it: timestamps and the watermark (stage 1)

You edit concurrency/watermark.go (AddTxn, RemoveTxn) and concurrency/transaction_manager.go (Begin, Commit). Run every command from go_db_internals/intro_to_db. The rules, in plain words:

  • A transaction's read timestamp is the last commit timestamp at the moment it begins, read inside Begin's TxnMapMu section.
  • A commit timestamp is the last commit timestamp plus one, computed under commitMu. Store it in the transaction before UpdateCommitTs(txn.CommitTs()), and publish it as the new last commit timestamp last, still under TxnMapMu.
  • The watermark is the lowest read timestamp of the running transactions, or the last commit timestamp if none runs. Several transactions may share a read timestamp. AddTxn and RemoveTxn must be amortized O(1) or O(log N).
  • Leave Abort as it is, and don't call m.Watermark() while holding TxnMapMu.

    What should CurrentReads hold when two transactions begin with the same read timestamp? What is WatermarkTs worth while the map is empty, and does Watermark() ever read it then?

    The approach

    Keep the shipped panic check at the top. Then, if the map is empty or the new read timestamp is below WatermarkTs, set WatermarkTs to it. Finally increment the read timestamp's count.     One key fragment 
    w.CurrentReads[readTs]++ // a count per read ts, not a set
  • What to think about

    Which removals can change the minimum? When the minimum disappears, where is the next one, and why is it never below the old one? What happens when the map becomes empty?

    The approach

    Decrement the count; if it is still positive, you are done. Otherwise delete the key. If the map is now empty, there is nothing to track (Watermark() returns CommitTs). If the removed timestamp was not the minimum, the minimum stands. Otherwise step a candidate up from the removed timestamp, one at a time, until it is a key of the map, and make that the new WatermarkTs. Every key is above the old minimum, so the walk ends. Don't look for the minimum with a range over the map: that is O(N) per call.

    One key fragment 
    next := readTs + 1
for w.CurrentReads[next] == 0 { // absent keys read as 0
	next++ // only forward: amortized O(1)
}
