P3 Stretch: TopN

Answer ORDER BY … LIMIT N with one pass and N tuples of memory: implement a TopN executor around a heap capped at N that the TopN check can watch, and the optimizer rule that turns a Limit over a Sort into a TopN.

This lesson is optional, and Project 3 is complete without it. The Fall 2025 writeup has no TopN task, but BusTub at d49b823 still ships everything for one: the test file p3.17-topn.slt, whose header reads # 0 pts and # Fall 2025 - TopN Not Implemented, the executor stub, a check executor that watches the executor's memory, and an empty rule OptimizeSortLimitAsTopN that the default rule list already calls. The algorithm is Lecture #11's top-N heap sort, which Unit 5, Lesson 1 traced. Doing this stage also makes go test -race -count=1 ./... pass without the -skip flag of the previous lesson.

Warm-up: retrieval from earlier lessons

  • 5 passes, 160 I/Os.
  • 2 passes, 64 I/Os.

Unit 5, Lesson 7: why does BusTub's rule list run NLJAsHashJoin after MergeFilterNLJ?

  • Hash joins are cheaper to estimate after a merge.
  • MergeFilterNLJ turns hash joins back into nested loop joins.
  • The order doesn't matter, because every rule is applied bottom-up.
  • Until the filter is merged into the join, the join's predicate is just true, with no equality to hash on.

Unit 4, Lesson 8: BusTub's C++ index iterator has no Close method. Why does the Go iterator need one?

  • Go has no destructors, so Close drops the read guard the iterator holds on its current leaf.
  • Close flushes the leaf the iterator wrote to.
  • Close removes the tombstones the scan passed over.
  • Close unpins every page from the root to the leaf.

Why a TopN plan

Without the rule, ORDER BY … LIMIT N is planned as a Limit over a sort, and your external merge sort orders the whole input before the Limit keeps the first N rows. This is the plan with the starter's rule, on one of p3.17's queries:

bustub> explain (o) select * from test_simple_seq_2 order by col1 desc limit 5;
=== OPTIMIZER ===
Limit { limit=5 }
  ExternalMergeSort { order_bys=[("Descending", "Default", "#0.0")] }
    SeqScan { table=test_simple_seq_2 }

With the rule, the same query becomes one node, which keeps the order-by items and N:

=== OPTIMIZER ===
TopN { n=5, order_bys=[("Descending", "Default", "#0.0")]}
  SeqScan { table=test_simple_seq_2 }

(The missing space before the final brace is BusTub's.) A TopN executor reads its input once and keeps only the best N rows seen so far. For a million rows and N = 10 it holds 10 tuples and writes no pages, where the merge sort writes and reads every page in each of its passes. Lecture #11's slide 10 calls a query with an ORDER BY and a LIMIT the ideal scenario for heap sort, as long as the top N elements fit in memory.

#11 Sorting & Aggregation Algorithms, "Top-N heap sort" (17:16), slides 9–10: the heap built one value at a time for ORDER BY sid ASC FETCH FIRST 4 ROWS WITH TIES.

BusTub's TopN is the plain LIMIT version of that example: it returns exactly N rows (or all of them, if there are fewer) and never extends the heap for ties. p3.17 is CMU's test of both pieces. Each of its queries carries the option ensure:topn, which first runs explain (o) and fails the record unless the plan contains a TopN; the last query asks for two with ensure:topn*2, and its plan nests one TopN in another:

bustub> explain (o) select * from (select * from test_simple_seq_2 order by col1 desc limit 5) order by col1 asc limit 3;
=== OPTIMIZER ===
TopN { n=3, order_bys=[("Ascending", "Default", "#0.0")]}
  TopN { n=5, order_bys=[("Descending", "Default", "#0.0")]}
    SeqScan { table=test_simple_seq_2 }

A heap capped at N

The TopN keeps the best N rows in a heap whose root is the worst of them: the row that sorts last by the ORDER BY. For each row from the child:

  • while the heap holds fewer than N rows, push the row;
  • once it holds N, compare the row with the root. If the row sorts before the root, it replaces the root and the heap is repaired; otherwise the row is dropped.

The root is the only row ever compared or removed, which is why it must be the worst one. For an ascending ORDER BY that makes the heap a max-heap, and for a descending one a min-heap by value: in both cases it is a max-heap by "sorts later". Each row costs at most one comparison with the root and O(log N) work to repair the heap, so M input rows cost O(M log N). When the child is exhausted, the heap holds the answer in no particular order, and the executor sorts those N rows (or pops them, worst first, and reverses) before Next returns them.

For ORDER BY v ASC LIMIT 3 over 5, 2, 7, 2, 9, 1: the heap fills with 5, 2 and 7, root 7. The second 2 sorts before 7 and replaces it, leaving 5, 2, 2 with root 5. 9 sorts after 5 and is dropped. 1 replaces 5. The heap ends as {1, 2, 2}, and the output is 1, 2, 2.

Idiom

C++ would use std::priority_queue with a comparator. Go's container/heap has no heap type of its own: it runs the heap algorithms on any type that implements heap.Interface, which is sort.Interface (Len, Less, Swap) plus Push(x any) and Pop() any. heap.Push, heap.Pop and heap.Fix keep the smallest element by Less at index 0, so a "max-heap" is a Less that answers the reverse question. Push and Pop change the slice's length, so they need pointer receivers, and you call heap.Push(&h, x), never h.Push(x): the method only appends, while the function also restores the heap order.

NumInHeap and the TopN check

Nothing in a query's result shows whether an executor kept N rows or all of them, so BusTub checks the memory directly. When a record has ensure:topn, the runner turns on EnableTopNCheck, and CreateExecutor builds the TopN with a TopNCheckExecutor between it and its child: TopN, then the check, then the scan. The check passes every Next call through to the scan, but first it calls the TopN's NumInHeap (BusTub's GetNumInHeap, documented as "The size of top_entries_ container, which will be called on each child_executor->Next()") and returns an error in two cases:

  • the heap holds more than N tuples: Cannot store more than N elements (the TopN heap holds %d tuples, N is %d);
  • while the heap is filling up, it didn't grow by exactly one since the last call: Did you implement GetNumInHeap() properly? (the TopN heap went from %d to %d tuples).

The check calls NumInHeap while your Init is still running, between two of its Next calls to the child. So the heap must live in a field of the executor, not in a local variable of Init, and an executor that keeps every row and trims to N only at the end fails as soon as the check finds more than N rows in it. BusTub wrote the growth check for a one-tuple-at-a-time model. With batches of common.BatchSize (20) tuples, the check sees an empty heap on the first call, and one full batch later the heap already holds N tuples (or the child is exhausted) whenever N ≤ 20, so the growth condition never comes into play. Every TopN that runs with the check, in p3.17 and in the unit tests, has N ≤ 20.

The rule

OptimizeSortLimitAsTopN in optimizer/sort_limit_as_topn.go follows the shape of every rule in the package, which the writeup describes: first apply the rule to the children, then check whether the current node matches. The match is a LimitPlanNode whose child is a SortPlanNode, and the result is a TopNPlanNode with the Limit's output schema, the Sort's child and order-by items, and the Limit's count. Everything else stays as it is, including a Sort over a Limit, which is a different query: it sorts the first N rows of an unsorted input.

The rule is only in OptimizeCustom, the default list in optimizer_custom_rules.go. It runs after OptimizeOrderByAsIndexScan, so an ORDER BY on an indexed column has already become an ordered index scan and there is no Sort left to merge. With set force_optimizer_starter_rule=yes, the starter list runs instead, without the rule, and the query above keeps its Limit over ExternalMergeSort.

One side effect: p3.16-sort-limit.slt and p3.18-integration-1.slt run under the default rules and contain ORDER BY … LIMIT queries, so once your rule works, those queries go through your TopN executor instead of your merge sort. The merge sort still runs every ORDER BY without a LIMIT, and its unit tests call it directly, but rerun go test -race -run '^TestSort' -timeout 300s ./... after this stage.

Check your understanding

A TopN for ORDER BY a DESC LIMIT 3 holds a = 90, 70 and 80. The next row has a = 75. What happens?

  • The row is pushed, and the heap holds four rows until the child is exhausted.
  • The row is dropped, because 75 is smaller than the best row, 90.
  • It replaces 70, the root, and the heap holds 90, 80 and 75.
  • It replaces 90, the root.

An Init pushes every child tuple into the heap and trims it to N only after the child is exhausted. What does p3.17's first query, select * from test_simple_seq_2 order by col1 desc limit 5 over 10 rows, report?

  • An error from the TopN check: the heap holds 10 tuples and N is 5.
  • The right five rows, because the result is trimmed before Next returns it.
  • "TopN not found", because the plan no longer has a TopN.
  • An error saying the heap didn't grow by one per call.

Which plan does OptimizeSortLimitAsTopN rewrite into a TopN?

  • A Sort with no Limit above it.
  • A Limit over a SeqScan.
  • A Sort over a Limit.
  • A Limit over a Sort that sits under a Projection.

The rule works, and you run a query with set force_optimizer_starter_rule=yes. Which executor sorts the rows of its ORDER BY … LIMIT 5?

  • The TopN executor, because the rule runs in every rule list.
  • The external merge sort, under a Limit.
  • An index scan, always, when the starter rules are forced.
  • The Limit executor sorts and truncates in one step.

Build it: TopN (stretch stage S1)

You edit execution/topn_executor.go (the struct's fields, Init, Next and NumInHeap, plus a heap type of your own) and optimizer/sort_limit_as_topn.go. Leave SetChildExecutor as it is: the factory uses it to put the check between the TopN and its child. Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • Init initializes the child, starts from an empty heap and reads the whole child. The heap never holds more than N tuples, at any moment the check can look.
  • NumInHeap returns the number of tuples the heap holds now, during Init and after it.
  • Next returns the kept tuples in ORDER BY order, under the batch contract: clear both slices, append up to batchSize tuples with one common.RID{} each, return true for every non-empty batch including the last partial one, and false once all are out. Return the child's errors; don't panic.
  • A second Init starts over with an empty heap.
  • What to think about

    Which entry must be cheapest to look at and to replace? container/heap keeps the element that is smallest by Less at index 0: which question must your Less answer so that this element is the one that sorts last? Which stage-10 type already decides whether one entry sorts before another?

    The approach

    A struct with a TupleComparator and a []SortEntry. Len and Swap are the usual slice methods. Less(i, j) asks the comparator whether entry j sorts before entry i, the reverse of the ORDER BY. Push appends an entry and Pop removes and returns the last one, both with pointer receivers.

    One key fragment 
    // reversed: the entry that sorts last rises to index 0
func (h topNHeap) Less(i, j int) bool { return h.cmp.Less(h.items[j], h.items[i]) }
  • What to think about

    When the heap is full, which single entry do you compare the new one with, and what happens on each outcome? What should happen for N = 0? Where must the heap live so that NumInHeap, called by the check between your calls to the child, sees its current size? And once the child is exhausted, in which order are the kept entries?

    The approach

    Return the error of e.child.Init() if there is one. Build the comparator with NewTupleComparator(e.plan.OrderBys) and store a fresh heap in a field. Loop over the child's batches with common.BatchSize; for each tuple, make a SortEntry with GenerateSortKey(t, e.plan.OrderBys, e.child.OutputSchema()). Below N entries, heap.Push it; at N, replace the root when the new entry sorts before it and call heap.Fix on index 0, else drop it. After the loop, put the kept entries into an output slice in ORDER BY order, by sorting a copy or by popping (worst first) and reversing.

    One key fragment 
    } else if e.cmp.Less(entry, e.heap.items[0]) { // better than the worst kept entry
    e.heap.items[0] = entry
    heap.Fix(&e.heap, 0)
}
  • What to think about

    NumInHeap is called during Init by the check and after Init by TestTopNHeapNeverAboveN: what must it never exceed in either case? What does Next need to remember between calls? Where is the read position reset?

    The approach

    NumInHeap returns the heap's Len(). Next clears both slices, copies up to batchSize tuples from the output slice starting at a position field, appends common.RID{} for each, advances the position, and returns whether it appended anything. Init resets the output slice and the position.

    One key fragment 
    func (e *TopNExecutor) NumInHeap() int {
    return e.heap.Len()
}
