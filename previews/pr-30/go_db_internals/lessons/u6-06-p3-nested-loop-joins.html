P3.5 Nested Loop and Nested Index Joins

Implement inner and left nested loop joins that re-initialize the right child for every left tuple, treat a NULL predicate as false, pad unmatched left tuples with typed NULLs and resume across batch boundaries; then implement the nested index join, which probes the inner table's B+tree once per outer tuple.

Unit 5, Lesson 3 costed the nested loop family on paper: the naïve join rescans the inner table for every outer tuple, and the index nested loop join replaces that scan with an index probe. BusTub plans every join as a nested loop join, and one pre-built optimizer rule turns some of them into index joins, so this lesson's two executors run every join query until the next lesson adds hash joins. The algorithms are short. The work is in the batch model: a join emits a variable number of tuples per input tuple, and its state must survive the end of a batch.

How BusTub plans a join

The writeup says the DBMS uses NestedLoopJoinPlanNode for all joins by default, whether the SQL says FROM a, b WHERE …, INNER JOIN … ON or LEFT OUTER JOIN … ON. The plan has two children, a Predicate and a JoinType, which is common.JoinInner or common.JoinLeft in every test. Its output schema is all the left child's columns followed by all the right child's columns. The shell shows one of CMU's test queries:

bustub> explain (o) select * from test_simple_seq_1 s1 left join test_simple_seq_2 s2 on s1.col1 + 5 = s2.col1;
=== OPTIMIZER ===
NestedLoopJoin { type=Left, predicate=((#0.0+5)=#1.0) }
  SeqScan { table=test_simple_seq_1 }
  SeqScan { table=test_simple_seq_2 }

In a join predicate, #0.c is column c of the left tuple and #1.c is column c of the right tuple. You evaluate it with EvaluateJoin(&left, leftSchema, &right, rightSchema), which the writeup points to, and which returns a types.Value that can be true, false or NULL. A pair matches only when the value is true: NULL counts as false, exactly as in FilterExecutor.matches, which tests !v.IsNull() && v.AsBool(). So the left row whose key is NULL never matches anything, not even a right row whose key is NULL.

Two rule lists decide what happens to the join next. The default list contains NLJAsHashJoin, whose starter version returns its input, so until Lesson 7 every join stays a nested loop join. Files that start with set force_optimizer_starter_rule=yes (p3.10, p3.11 and p3.13 among this lesson's) use the starter list, which contains the pre-built NLJAsIndexJoin instead. That rule is where the nested index join of the second half comes from.

The nested loop join, one batch at a time

The writeup asks for "the simple nested loop join algorithm from class": for each tuple in the outer table, consider each tuple in the inner table and emit the ones that satisfy the join predicate. BusTub says left and right where the lecture says outer and inner. In pseudocode:

for each left tuple l:
    re-initialize the right child
    for each right tuple r:
        if predicate(l, r) is true: emit (l, r)
    if l is a left join's tuple and matched nothing: emit (l, NULLs)

The right child is an executor, not a table, and the only way to read an executor again is to call its Init. Re-initializing it for every left tuple is what makes this the naïve join of Lecture #12; reading the right side once into memory and looping over the copy would be a different algorithm, and the tests forbid it. TestNestedLoopJoinReinitializesRight counts the right child's Init calls and fails unless there is at least one per left tuple.

CMU's .slt files check the same thing with the record option +ensure:nlj_init_check. It wraps both children of every nested loop join in an InitCheckExecutor that counts calls, and after the query the engine compares the right child's Init count with the number of batches the left child returned. When the right side was initialized too rarely, the query fails with BusTub's assertion text:

nlj check failed, are you initializing the right executor every time when there is a left tuple? (off-by-one is okay)

Because that check counts left batches, a join over a small left table passes it even when the right child is read only once. An NLJ that buffered its right side in memory passed every .slt file of this stage, and only the unit test caught it:

--- FAIL: TestNestedLoopJoinReinitializesRight (0.00s)
    nested_loop_join_executor_test.go:105: the right child was initialized 1 times for 7 left tuples: initialize it again for every left tuple
    nested_loop_join_executor_test.go:116: ExecutionEngine.Execute with the NLJ check: Execute returned (false, nlj check failed, are you initializing the right executor every time when there is a left tuple? (off-by-one is okay)), want (true, nil)

Re-initializing also has consequences one level down. Whatever sits under the right side gets Init many times: p3.12-repeat-execute.slt puts a sequential scan, an aggregation (Lesson 5's Init must start from an empty table) and an index scan there. And a join can be the right child of another join, so your own Init must reset all of the join's state as well as initializing both children.

Keeping state across batches

The loop above emits as it goes, but Next must stop when its batch holds batchSize tuples and continue in the next call from exactly that point. One left tuple can have more matches than fit in a batch, and one batch can hold the matches of several left tuples. The doc comment on Next puts it this way: keep enough state to pick up where the last call stopped. That state is:

  • the left child's current batch and your position in it, plus whether the left child is exhausted;
  • the current left tuple, whether there is one, and whether it has matched any right tuple yet;
  • the right child's current batch and your position in it, plus whether the right child is exhausted for this left tuple.

With those fields, Next is one loop that runs while the output batch has room. If there is no current left tuple, take the next one (fetching a new left batch when the current one is used up, and stopping when the left child is exhausted), re-initialize the right child, and reset the right-side state. If the right batch is used up, fetch the next one; if the right child is exhausted, the current left tuple is finished: pad it if it is a left join's tuple with no match, and clear it. Otherwise test the next right tuple against the predicate. The same pattern, a child's batch plus an offset into it, is what FilterExecutor keeps in childTuples and childOffset. TestNestedLoopJoinAcrossBatches joins 45 by 30 rows with batch sizes 20, 7 and 1, so an off-by-one at a batch boundary shows up as a missing or repeated row.

Left joins and typed NULLs

A left join keeps every left tuple. When the right child runs out and the current left tuple has matched nothing, the join emits it once, followed by one NULL per right column. Each NULL has the type of its column, types.NewNullValue(rightSchema.Column(i).Type()), so an INTEGER column prints integer_null and a VARCHAR column varlen_null. CMU's files compare those strings:

query rowsort +ensure:nlj_init_check
select * from test_simple_seq_1 s1 left join test_simple_seq_2 s2 on s1.col1 + 5 = s2.col1;
----
0 5 15
...
5 integer_null integer_null

An empty right child is the extreme case: an inner join returns nothing, and a left join returns every left tuple padded. An empty left child returns nothing for either join type.

The nested index join

The pre-built rule NLJAsIndexJoin (in the starter rule list only) rewrites a nested loop join when three things hold: the predicate is one equality between a left column and a right column, in either order; the right child is a SeqScan; and the scanned table has an index on that column. Then each left tuple's key can be looked up in the index instead of scanning the right table:

bustub> set force_optimizer_starter_rule=yes;
bustub> create table t1(v1 int);
bustub> insert into t1 (select * from __mock_table_123);
bustub> create index t1_v1 on t1(v1);
bustub> explain (o,s) select * from test_simple_seq_2 t2 left join t1 on t1.v1 = t2.col1;
=== OPTIMIZER ===
NestedIndexJoin { type=Left, key_predicate=#0.0, index=t1_v1, index_table=t1 } | (t2.col1:INTEGER, t2.col2:INTEGER, t1.v1:INTEGER)
  SeqScan { table=test_simple_seq_2 } | (t2.col1:INTEGER, t2.col2:INTEGER)

The node has a single child, the outer side. The inner table is not a child at all: the plan names it with InnerTableOID and IndexOID and gives its schema as InnerTableSchema. KeyPredicate is the left side of the equality, rewritten to tuple index 0 because you evaluate it on the outer tuple alone, with Evaluate(&outer, childSchema). Anything else keeps the nested loop join: on t1.v1 + 1 = t2.col1 is not a column on both sides, t1 left join test_simple_seq_2 … on t1.v1 = t2.col1 has no index on its right table, and on t1.v1 = t2.col1 and t2.col2 > 10 is an AND, not one equality.

The writeup's hint gives the per-tuple work: fetch the tuple from the outer table, construct the index probe key by using key_predicate, and then look up the RID in the index to retrieve the corresponding tuple for the inner table. In this course's API:

  1. In Init, find the index and the table in the catalog: Catalog().GetIndexByOID(plan.IndexOID) gives an *catalog.IndexInfo with the Index and its KeySchema, and GetTableByOID(plan.InnerTableOID) gives the *catalog.TableInfo whose Table is the heap.
  2. Evaluate the key predicate on the outer tuple. A NULL key matches nothing.
  3. Build a one-column key tuple with table.NewTuple([]types.Value{v}, indexInfo.KeySchema) and call Index.ScanKey(key). Keys are unique (the warm-up's B+tree rule), so it returns at most one RID.
  4. Fetch the row with Table.GetTuple(rid), which returns the tuple's meta and the tuple. Skip it if meta.IsDeleted: TestNestedIndexJoinSkipsDeletedInner marks a row deleted in the heap while its key is still in the index.
  5. Emit the outer columns followed by the inner table's columns, or, for a left join with no live match, the outer columns followed by NULLs of InnerTableSchema's column types.

The test of the output layout compares types as well as strings: in TestNestedIndexJoinOutputLayout the outer row (5, 7) joins the inner row ("five", 5, NULL), and the test expects INTEGER:5, INTEGER:7, VARCHAR:five, INTEGER:5, INTEGER:integer_null. The writeup also promises that CMU will not test strange edge cases involving NULLs in indexes, and neither does this course beyond "a NULL probe key matches nothing".

Idiom

Even with at most one match per outer tuple, give the nested index join the same resumable shape as the nested loop join: the outer batch and a position in it, and the current outer tuple's matches with a position. Then a batch can end between any two output tuples. Holding the matches as a slice you reset with s = s[:0] reuses its backing array for the next outer tuple, so the probe loop doesn't allocate a new slice per tuple.

Build it: the nested loop join (stage 7)

You edit execution/nested_loop_join_executor.go: Init, Next and the fields you add to NestedLoopJoinExecutor. Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • Next follows the batch contract: clear *tuples and *rids first, append up to batchSize tuples with one RID each (the zero common.RID{}, since joined tuples come from no table), return true for every non-empty batch including the last partial one, and false once the join is exhausted, on every later call too.
  • Return the children's errors; don't panic.
  • Re-initialize the right child for every left tuple. Don't keep the right side in memory.
  • A pair matches only when EvaluateJoin returns true; NULL is false.
  • Output tuples are the left columns followed by the right columns, built with table.NewTuple(values, e.OutputSchema()). A left join emits each unmatched left tuple once, padded with NULLs of the right columns' types.
  • What to think about

    List what Next must remember between calls, for the left side and for the right side. If this join is itself the right child of another join, its Init runs many times: which of those fields would carry stale values into the next run?

    The approach

    Add the left batch (tuples and RIDs) with a position and a "left exhausted" flag; the current left tuple with a "have one" flag and a "matched" flag; the right batch with a position and a "right exhausted" flag. In Init, call e.left.Init() and e.right.Init(), returning their errors, then truncate the batches, zero the positions and clear the flags. The plans in the tests only carry common.JoinInner and common.JoinLeft; returning an error for any other type keeps a surprise loud.

    One key fragment 
    e.leftTuples, e.leftRIDs = e.leftTuples[:0], e.leftRIDs[:0]
e.leftPos, e.leftDone = 0, false
e.haveLeft = false
  • What to think about

    The loop runs while the output batch has room. In each round, which of three situations are you in: no current left tuple, the right batch used up, or a right tuple waiting to be tested? What happens when the left child returns false: is the batch you have so far still returned?

    The approach

    Clear the output slices. Loop while len(*tuples) < batchSize. If there is no current left tuple: when the left position has reached the end of the left batch, stop if the left child is exhausted, otherwise call e.left.Next (on false, mark it exhausted and stop); then take the tuple at the position, advance, mark it current and unmatched, call e.right.Init() and reset the right batch. If the right position has reached the end of the right batch, call e.right.Next: on true reset the position and continue; on false the left tuple is done, so clear "have one". Otherwise take the next right tuple, evaluate the predicate with EvaluateJoin, and on true mark the left tuple matched and append the combined tuple. After the loop, return len(*tuples) > 0.

    One key fragment 
    v := pred.EvaluateJoin(&e.cur, ls, r, rs)
if v.IsNull() || !v.AsBool() {
	continue // NULL counts as false
}

Success prints ok intro_to_db/execution.

  • What to think about

    At which point of the loop do you know for sure that a left tuple has no match? What type must each NULL have, and where do you find it? What if the right child is empty from the start?

    The approach

    In the branch where e.right.Next returns false, before clearing the current left tuple, check the join type and the "matched" flag; if it is a left join and nothing matched, append the left values followed by types.NewNullValue(rs.Column(i).Type()) for each right column. A helper that combines a left tuple with a right tuple, or with NULLs when the right tuple is nil, serves both branches.

    One key fragment 
    for i := 0; i < rs.ColumnCount(); i++ {
	values = append(values, types.NewNullValue(rs.Column(i).Type()))
}

Build it: the nested index join (stage 8)

You edit execution/nested_index_join_executor.go. The batch contract and the error rule are the same as above. The rules that differ:

  • The executor has one child, the outer side. The inner table and its index come from the catalog, by plan.InnerTableOID and plan.IndexOID.
  • The probe key is plan.KeyPredicate evaluated on the outer tuple. A NULL key matches nothing. Skip inner tuples whose meta says IsDeleted.
  • Output tuples are the outer columns followed by the inner table's columns (plan.InnerTableSchema). A left join pads an unmatched outer tuple with NULLs of those columns' types.
  • What to think about

    Which catalog lookups take an OID? What should Init do if one of them returns nil? Which state does Next need, given that an outer tuple produces zero or one output tuples here?

    The approach

    Get the catalog from e.ExecutorContext().Catalog(), then GetTableByOID(e.plan.InnerTableOID) and GetIndexByOID(e.plan.IndexOID); store both, and return a common.NewException error if either is nil. Keep the same resumable state as the nested loop join for the outer side (batch, position, exhausted flag, current tuple), plus the current tuple's matches and a position in them. Reset all of it, then return e.child.Init().

    One key fragment 
    cat := e.ExecutorContext().Catalog()
e.innerTable = cat.GetTableByOID(e.plan.InnerTableOID)
e.indexInfo = cat.GetIndexByOID(e.plan.IndexOID)
  • What to think about

    What is the key's schema: the outer schema or the index's? Where is the outer tuple's value in the key predicate's tuple indexes? What does GetTuple return for a row that a delete marked, and what should the join do with it?

    The approach

    Write a lookup helper: evaluate e.plan.KeyPredicate.Evaluate(&outer, e.child.OutputSchema()); return no matches if the value is NULL; otherwise build the key tuple over e.indexInfo.KeySchema, loop over e.indexInfo.Index.ScanKey(key), call e.innerTable.Table.GetTuple(rid) and keep the tuples whose meta is not deleted.
