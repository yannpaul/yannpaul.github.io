P3.8 Window Functions

Compute window aggregates and RANK over partitions and a shared ORDER BY, read BusTub's WindowFunc plan with its placeholder columns, implement the window function executor, and pass the whole Project 3 suite.

A window function computes a value for every row from a set of related rows, and keeps every row in the output, where GROUP BY would collapse each group into one row. You wrote such queries in DuckDB in Unit 0, Lesson 2. This is the last required stage of Project 3, and it reuses two pieces you already wrote: the sort comparator from stage 10 orders the rows, and the aggregation rules from stage 6 combine them. When its tests pass, you run the whole suite and Project 3 is done.

Warm-up: retrieval from earlier lessons

Unit 5, Lesson 2: a sorting aggregation computes AVG(gpa) per group while it scans the sorted tuples. What does its running total hold for the current group?

  • The average of the tuples seen so far.
  • The group's minimum and maximum.
  • The pair (COUNT, SUM), divided only when the group is emitted.
  • Every value of the group, so the average can be computed at the end.

Unit 5, Lesson 5: Lecture #13's slide 5 lists the build side of a join as a pipeline breaker. What makes an operator a pipeline breaker?

  • It cannot finish until all of its children have emitted all their tuples.
  • It has two or more children.
  • It always writes its input to disk.
  • It evaluates an expression on every tuple.

Unit 0, Lesson 2: slide 38 finds the student with the second-highest grade in each course by computing RANK() in a derived table and filtering rank = 2 outside it. Why not filter in the same query's WHERE?

  • RANK can only be computed over numeric columns.
  • The derived table makes the query faster.
  • WHERE can't refer to a column alias, but it could refer to RANK() directly.
  • A window function can't appear in WHERE; DuckDB rejects the query.

What a window function computes

The writeup's conceptual model has three steps. Split the rows by the PARTITION BY clause. Sort each partition by the ORDER BY clause inside OVER. Then, for each row of a sorted partition, compute the boundaries of its frame, the set of rows the function is computed over, and output the function's value on that frame. All three clauses are optional, and a window frame clause such as ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING would set the frame explicitly. BusTub supports no frame clause: its planner rejects one with BusTub currently only support window function with default window frame settings. That leaves three cases, which the writeup shows with an AVG(salary) per department:

  • PARTITION BY dept_name ORDER BY user_name: each row's frame runs from the first row of its partition to the current row, so the value is a running aggregate. In dept2, sorted by name, the salaries 50, 100 and 60 give the averages 50, 75 and 70.
  • PARTITION BY dept_name with no ORDER BY: the frame is the whole partition, so every row of a partition gets the same value, 200 for dept1 and 70 for dept2.
  • OVER (): no partition clause either, so the whole input is one partition and every row gets 135.

BusTub's window functions are count(*), count, sum, min, max and rank. AVG is only the writeup's illustration: the planner refuses it with unsupported window_call avg with 1 args.

The test file, p3.20-window-function.slt, uses a table t1 holding −99999, 99999, 0, 1, 2 and 3. With OVER (), all five aggregates give 6 -99999 99999 6 6 on all six rows. With OVER (ORDER BY v1) they become running values in ORDER BY order:

count(*)  min      max     count  sum
1         -99999   -99999  1      -99999
2         -99999   0       2      -99999
3         -99999   1       3      -99998
4         -99999   2       4      -99996
5         -99999   3       5      -99993
6         -99999   99999   6      6

The writeup notes that an ORDER BY inside OVER also changes the order of the output rows, and that this is not required: "The test case will not check the order of output rows as long as columns within each row are matched." So you may sort the rows first when there is an ORDER BY, and keep the child's order when there is none, which is what the starter's doc comment asks for.

RANK and ties

RANK() gives each row its position in the sorted partition, except that rows with equal ORDER BY keys share a rank, and the rank after a tie skips the tied positions. After the test file inserts another 1 and another 3 into t1, rank() over (order by v1) gives:

-99999 1
0 2
1 3
1 3
2 5
3 6
3 6
99999 8

One way to state the rule: a row's rank is one more than the number of rows in its partition that sort strictly before it. In a sorted partition, that means the rank changes only when the key changes, and then it jumps to the row's position (counting from 1). The planner makes sure a rank has something to sort by: rank() over (partition by v1) fails with order by clause is mandatory for rank function. The writeup only says "Be aware that there might be ties and please refer to test cases for the expected behavior", and the test cases above are the specification.

How BusTub plans a window query

All the window functions of a SELECT go into one WindowFunc plan node, which sits directly over the node that produces the rows. Here is the plan of a query with a running sum and a rank over the same window, on the t2 table from the test file:

bustub> explain select v1, v2, sum(v2) over (partition by v1 order by v2), rank() over (partition by v1 order by v2) from t2;
...
=== OPTIMIZER ===
WindowFunc {
  columns=#0.0, #0.1, placeholder, placeholder, ,
  window_functions={
    2=>{ function_arg=#0.1, type=sum, partition_by=["#0.0"], order_by=[("Default", "Default", "#0.1")] },
    3=>{ function_arg=1, type=rank, partition_by=["#0.0"], order_by=[("Default", "Default", "#0.1")] }
  }
} | (t2.v1:INTEGER, t2.v2:INTEGER, __unnamed#0:INTEGER, __unnamed#1:INTEGER)
  SeqScan { table=t2 } | (t2.v1:INTEGER, t2.v2:INTEGER)

Read it with plans.WindowFunctionPlanNode open in execution/plans/window_plan.go:

  • Columns has one expression per output column. Columns 0 and 1 are ordinary expressions over the child's tuple (#0.0 is v1). Columns 2 and 3 are placeholders: a ColumnValueExpression with ColIdx() −1, which the plan text prints as placeholder. A placeholder only marks where a window function's value goes; evaluating it would read column −1. The trailing , , is BusTub's formatting.
  • WindowFunctions is a map[int]WindowFunction from a placeholder's column index to its function: Type, the argument Function, PartitionBy and OrderBy. For rank and count(*) the planner puts the constant 1 in Function; the unit tests build rank plans with a nil Function, so never evaluate it for a rank.
  • Every window column has type INTEGER, because the placeholders are INTEGER columns.
  • There is no Sort node under the WindowFunc. The executor sorts the rows itself.

For simplicity, the writeup says, "BusTub ensures that all window functions within a query have the same ORDER BY clauses." The planner enforces it: select sum(v2) over (order by v2), sum(v2) over () from t2 fails with order by clause of window functions are not compatible, and so does a pair ordered by different columns. The PARTITION BY clauses may differ, though. The last query of the test file computes sum(v2) over (partition by v1 order by v2) and sum(v2) over (order by v2) side by side, and expects each row's two values to differ: (2, 400) gives 400 within its partition and 1000 over the whole table. So the executor sorts once, by the shared ORDER BY, and partitions separately for each function.

The rest of the query is planned around the node. A WHERE clause is evaluated below it, and an outer ORDER BY becomes an ExternalMergeSort above it:

bustub> explain (o) select v1, sum(v2) over (partition by v1 order by v2), count(*) over (order by v2), rank() over (order by v2) from t2 where v1 > 0 order by v1;
=== OPTIMIZER ===
ExternalMergeSort { order_bys=[("Default", "Default", "#0.0")] }
  WindowFunc {
    columns=#0.0, placeholder, placeholder, placeholder, ,
    window_functions={
      1=>{ function_arg=#0.1, type=sum, partition_by=["#0.0"], order_by=[("Default", "Default", "#0.1")] },
      2=>{ function_arg=1, type=count_star, partition_by=[], order_by=[("Default", "Default", "#0.1")] },
      3=>{ function_arg=1, type=rank, partition_by=[], order_by=[("Default", "Default", "#0.1")] }
    }
  }
    SeqScan { table=t2, filter=(#0.0>0) }

To filter on a rank, as in Unit 0's second-highest grade, the rank is computed in a subquery and an outer WHERE becomes a Filter node above the WindowFunc. A window function must be a select-list item of its own: sum(v2) over (order by v2) + 1 fails with should not parse window expressions here.

NULLs

The doc comment of WindowFunctionExecutor says the aggregates "follow the rules of SimpleAggregationHashTable": count(*) starts at 0 and counts every row, the others start at NULL and skip NULL inputs. A partition whose argument values are all NULL therefore gets integer_null from count as well as from sum, min and max. Standard SQL, and DuckDB, would give 0 for that count; BusTub's count starts at NULL instead. A NULL in a PARTITION BY expression behaves like a NULL group key in stage 6: all rows whose key is NULL form one partition. And a NULL in the ORDER BY key sorts by your stage-10 comparator, first in ascending order unless the query says otherwise. After two more rows, (NULL, 7) and (3, NULL), go into t2, the reference prints:

Pitfall

Standard SQL's default frame with an ORDER BY includes the current row's peers, the rows with the same ORDER BY key, so tied rows get the same running value. The writeup and the doc comment define the frame as the rows from the start of the partition up to the current row, and the reference solution adds the rows one at a time. The two only differ on ties, and p3.20 never has a tie in a running aggregate, so either passes. What does BusTub do with SELECT SUM(v1) OVER (ORDER BY v1), SUM(v2) OVER () FROM t1?

  • The executor sorts the rows once for each function.
  • It computes the second sum over the rows in v1 order, treating OVER () as compatible.
  • The planner rejects it: the two window functions have different ORDER BY clauses.
  • The planner makes two WindowFunc nodes, one per ORDER BY.

select v1, sum(v2) over (partition by v1 order by v2), count(*) over (order by v2), rank() over (order by v2) from t2 where v1 > 0 order by v1: which nodes does the optimized plan have?

  • Two WindowFunc nodes, one for each PARTITION BY, over the scan.
  • One WindowFunc node over the filtered SeqScan, and one ExternalMergeSort above it for ORDER BY v1.
  • An ExternalMergeSort on v2 below the WindowFunc node, and another on v1 above it.
  • One WindowFunc node and no sort node at all.

Build it: the window function executor (stage 11)

You edit one file, execution/window_function_executor.go: the struct's fields, Init and Next, plus any unexported helpers you add. Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • The executor is a pipeline breaker. Init initializes the child, reads all of its rows and computes every output row; Next only hands them out. A second Init starts over.
  • With an ORDER BY, sort the rows by it (all window functions share it) and output them in that order; without one, keep the child's order.
  • With an ORDER BY, an aggregate covers the rows from the start of the row's partition to the row itself; without one, the whole partition. Rank is the position, with ties sharing a rank.
  • Evaluate the non-placeholder columns on each child tuple with the child's schema, and never evaluate a placeholder. Build each output tuple with the executor's output schema.
  • The batch contract: Next clears *tuples and *rids, appends up to batchSize tuples, each with one RID (common.RID{}, since these rows don't come from a table), returns true for every non-empty batch including the last partial one, and false once everything is out. Return errors from the child; don't panic.
  • What to think about

    Why can't the first output row be computed before the child's last row has arrived, even for OVER ()? The child clears and refills the batch slice on every call: what may you keep from it, and what must you copy out? What must a second Init reset so that rows from the first run don't come out again?

    The approach

    Return the error of e.child.Init() if there is one. Then call e.child.Next with a batch slice, a RID slice and common.BatchSize until it returns false, appending the batch's tuples to a local slice each time. Reset the fields that hold the output rows and the read position at the start of Init. This is the same build loop as your aggregation executor's.

    One key fragment 
    if !ok {
    break
}
rows = append(rows, batch...) // copies the Tuple values out of the reused slice
  • What to think about

    The planner guarantees one ORDER BY for all window functions, but some may have none (OVER () can't be mixed with an ORDER BY, so in practice either all have it or none). Where do you find it? Which stage-10 helpers already compare two rows exactly as an ORDER BY wants, NULL placement included? Why is a stable sort the better choice?

    The approach

    Loop over e.plan.WindowFunctions and take the first non-empty OrderBy; Go's map order is random, but the clauses are all equal. If there is one, build a SortEntry per row with GenerateSortKey(row, orderBys, e.child.OutputSchema()), sort the entries with sort.SliceStable and NewTupleComparator(orderBys).Less, and put the tuples back in that order. The writeup suggests reusing the sort executor's code; an in-memory sort is what this stage needs, since the rows are already in memory.

    One key fragment 
    cmp := NewTupleComparator(orderBys)
sort.SliceStable(entries, func(i, j int) bool { return cmp.Less(entries[i], entries[j]) })
  • What to think about

    What is the value of an empty frame for count(*), and for the other four? What does one more input row do to each, and what does a NULL input do? With an ORDER BY, row i gets the value after folding rows 0 to i; without one, every row gets the value after the last row. Which output columns do you evaluate, against which schema, and which may you never evaluate?

    The approach

    For each entry col, wf of e.plan.WindowFunctions, compute a []types.Value with one value per row. Start from 0 for WindowCountStarAggregate and an INTEGER NULL for the others, and fold each row's wf.Function.Evaluate(&row, childSchema) with the rules of your CombineAggregateValues (plans.WindowFunctionType is a separate enum from plans.AggregationType, so a small switch of your own is simplest). Running: record the value after each row; whole: record the final value on every row. Then, for each row, fill one value per entry of e.plan.Columns and build the tuple with table.NewTuple(values, e.OutputSchema()). Next copies up to batchSize of those tuples into the cleared slices from your read position.

    The approach

    For each window function, evaluate its PartitionBy expressions on each row into an AggregateKey.
