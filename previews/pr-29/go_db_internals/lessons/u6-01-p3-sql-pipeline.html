P3.0 The SQL Pipeline: Postgres Parser, Binder, Planner, EXPLAIN

Pull Project 3's code and build its cgo parser, follow a SQL statement from text to rows through the binder, planner, optimizer and executors, read BusTub's EXPLAIN output, and run the three kinds of tests you will use for the rest of the project.

Unit 5 described query execution and optimization on paper. Project 3 makes you write the executors, the operators that turn a plan into rows, plus two optimizer rules. Everything around them is already built: a SQL front end above, and your own Project 1 buffer pool and Project 2 B+tree below. In this stage you write no code: you get the project building, take the pipeline apart in the shell, and learn to read plans and test failures. Its checkpoint passes on the starter by design.

Warm-up: retrieval from earlier lessons

Unit 5, Lesson 5: BusTub's execution engine runs while (executor->Next(&tuples, &rids, BUSTUB_BATCH_SIZE)) and appends each batch to the result. A scan has 7 matching tuples left when the engine calls it, and the batch size is 20. What must its Next do?

  • Return false with the 7 tuples in the batch, since the table is now exhausted.
  • Keep scanning until it has 20 tuples, so that every batch is full.
  • Return true with the 7 tuples, then return false with an empty batch on the next call.
  • Return the 7 tuples one per call, each with true.

Unit 5, Lesson 7: BusTub's planner turns FROM t1, t2 WHERE t1.a = t2.b into a Filter over a nested loop join. Why must MergeFilterNLJ run before NLJAsHashJoin?

  • Until the filter merges into the join, the join's predicate is just true, so there is no equality to hash on.
  • MergeFilterNLJ computes the table sizes that NLJAsHashJoin needs to pick a build side.
  • A hash join can't have a Filter above it, so the filter has to disappear first.
  • NLJAsHashJoin only visits the root node, so the join must be pulled up first.

Unit 5, Lesson 8: how does BusTub's optimizer learn how many rows a table has?

  • From an equi-depth histogram kept in the catalog.
  • By sampling a few pages of the table when the query is planned.
  • From a row count the catalog updates on every insert and delete.
  • From a suffix in the table's name, such as _1m; other tables have no estimate.

cgo and the first build

The SQL parser is not written in Go. The binder package calls pg_query_go, which wraps libpg_query: PostgreSQL's own parser, extracted from the PostgreSQL source as a C library. Go compiles and links that C code through cgo, the part of the Go toolchain that lets Go packages call C. Two things must be in place:

  • go env CGO_ENABLED prints 1. That is the default on a Mac. If yours prints 0, run go env -w CGO_ENABLED=1.
  • A C compiler. The Xcode Command Line Tools from Lesson 0 provide clang; xcode-select -p prints their path if they are installed.

Without cgo, the build stops in the binder, and every package that imports it fails too:

# intro_to_db/binder
binder/binder.go:38:26: undefined: pg_query.Parse
binder/binder.go:55:23: undefined: pg_query.Scan

The first build downloads the pg_query_go module and compiles the C parser, which takes about a minute. Go caches the result, so later builds are fast. Run one warm-up build now, so that the minute doesn't land in the middle of a test run:

time go build ./...

The first test run with -race compiles the parser once more for the race-enabled build, which takes about 40 seconds; after that it is cached too. Only binder and the packages that import it (planner, bustub, sqllogictest, cmd/shell) need cgo. The packages you edit, execution and optimizer, don't import the binder.

From SQL text to rows

Lecture #15 draws the path from a SQL string to a plan as four steps. BusTub follows it with one extra stage between the binder and the optimizer, a planner, and without the statistics and cost model, which BusTub doesn't have (Unit 5, Lesson 8).

One statement, such as SELECT colA FROM __mock_table_1 WHERE colA > 97;, passes through these packages in order:

StepPackageWhat it producesBusTub source
Parsebinder (Binder.ParseAndSave)PostgreSQL's parse tree, from pg_query.Parsebinder/binder.cpp, transformer.cpp
Bindbinder (Binder.BindStatement)a bound statement: names resolved against the catalog, * expanded into columns, expressions typedbinder/bind_*.cpp
Planplannera tree of plan nodes (execution/plans), one per operator, each with an output schemaplanner/*.cpp
Optimizeoptimizerthe same tree rewritten by a list of rulesoptimizer/*.cpp
Executeexecutiona tree of executors built by CreateExecutor, run by ExecutionEngine.Executeexecution/*.cpp, executor_factory.cpp

The parser checks grammar only: it knows nothing about tables. BusTub parses with DuckDB's fork of libpg_query, so both versions accept a PostgreSQL grammar, and this course's binder translates PostgreSQL 17's parse tree node by node into the same bound statements BusTub builds. The grammars differ in one place that the tests hit. DuckDB accepts a trailing comma before FROM, as in select colC, colA, colB, from temp_2, and two of CMU's test records rely on it; PostgreSQL reports a syntax error. So ParseAndSave first runs PostgreSQL's tokenizer and deletes any comma token that directly precedes a FROM token, then parses. Commas inside string literals are not tokens of their own, so they are left alone.

The binder turns names into catalog references. It checks that __mock_table_1 exists, that it has a column colA, and what type each expression has; SELECT nosuch FROM __mock_table_1 fails here with column nosuch not found. The planner then turns the bound statement into a plan: a Projection over a Filter over a scan. The optimizer rewrites that plan with rules (Unit 5, Lesson 7). Finally the execution engine builds one executor per plan node and pulls batches of tuples from the root.

Two more packages hold the rest together. bustub is the database instance (BusTub's BusTubInstance): its ExecuteSQL runs each statement in its own transaction, sends SELECT, INSERT, UPDATE and DELETE down the pipeline above, and handles CREATE TABLE, CREATE INDEX, EXPLAIN, SET and the backslash commands itself. Below the executors sit catalog (tables and indexes by name and OID), storage/table (the table heap: tuples in a linked list of pages), storage/index (an adapter that makes your B+tree an index), and types (values, columns and schemas). The shell cmd/shell and the test runner sqllogictest are both thin wrappers around an instance.

A few things to notice in that run:

  • On a real table the scan is a SeqScan, and the WHERE clause has moved into it as filter=. The pre-built rule MergeFilterScan folds a Filter into the SeqScan below it, so your sequential scan has to evaluate that predicate itself (Lesson 2). It doesn't merge into a MockScan, which is why the mock query kept its Filter.
  • CREATE TABLE and CREATE INDEX work on the starter: they only need the catalog, your buffer pool and your B+tree. Inserting needs the insert executor, which is stage 2.
  • The optimizer has two rule lists. By default it uses the "custom" list in optimizer_custom_rules.go; set force_optimizer_starter_rule=yes switches to the starter list, as some of CMU's test files do. ORDER BY v1 already becomes an IndexScan, because OrderByAsIndexScan is pre-built. WHERE v1 = 1 stays a SeqScan until you write SeqScanAsIndexScan in stage 5; its starter version returns the plan unchanged.
  • The INSERT reached a stub that panics. The instance recovers every panic and reports it as internal error (panic) with the frames of this module's code, and the shell carries on. Inside a test, the same panic fails only the test that hit it.

Reading plan text

Each line of a plan is one plan node, and a node's children are the lines indented under it. Data flows upward: the most indented scans produce tuples, and the root's output is the query's result. With schemas on, | (…) after a node is its output schema, the columns of every tuple it produces. The writeup is strict about it: "your executor implementations must produce tuples with schema exactly as specified in the plan node".

An expression such as #0.1 is a column value expression: the number before the dot is the tuple index, and the number after it is the column index in that tuple. In a node with one child, the tuple index is always 0, so #0.1 is the child's second column; in the Agg above, aggregates=["#0.1"] is the max of the join's second column. A join evaluates its predicate on a pair of tuples, so there #0.0 is column 0 of the left child's tuple and #1.0 is column 0 of the right child's. (#0.0=#1.0) is colA = colE. Constants print as themselves: (#0.0>97) is colA > 97.

Quoted lists

This port prints plans exactly as BusTub at d49b823 does, and BusTub's formatting library quotes the elements of a list: Projection { exprs=["#0.0", "#0.1"] }. The writeup's examples were written with an older version and show exprs=[#0.0, #0.1] for the same plan.

Executors work in batches

Unit 5, Lesson 5 placed BusTub among the processing models: the vectorized model, pulled from the root, with whole row tuples in each batch. In Go the interface is execution.Executor:

type Executor interface {
	Init() error
	Next(tuples *[]table.Tuple, rids *[]common.RID, batchSize int) (bool, error)
	OutputSchema() *types.Schema
	ExecutorContext() *ExecutorContext
}

BusTub's Next(std::vector<Tuple> *tuple_batch, std::vector<RID> *rid_batch, size_t batch_size) becomes a method that fills two slices through pointers. ExecutionEngine.Execute calls Init on the root, then Next with common.BatchSize, which is 20, until it returns false. Every executor you write follows the same contract, and the unit tests check it on every call:

  • Clear both slices first (*tuples = (*tuples)[:0]), then append up to batchSize tuples, each with its RID. Tuples that don't come from a table carry the zero common.RID{}.
  • Return true for every non-empty batch, including a last batch that is only partly full. Return false with an empty batch once the executor is exhausted, and keep returning false after that.
  • Init may be called again after the executor ran, and must then start over: a nested loop join re-initializes its right child once per left tuple. Pipeline breakers, such as aggregation, do their build phase in Init.
  • Return errors; don't panic. Where BusTub throws an exception, Go returns an error, usually a *common.Exception from common.NewException.

An executor pulls from its children the same way, batch by batch. When a child's batch holds more tuples than fit in the output batch, the executor has to keep the rest for its next call. The pre-built FilterExecutor (execution/filter_executor.go) shows how: it stores the child's last batch and an offset into it. Read it before you start Lesson 2.

Idiom

BusTub's executors throw C++ exceptions, and an exception from deep inside an executor tree unwinds to the instance. Go code returns errors instead, so Init returns error and Next returns (bool, error), and a parent passes a child's error straight up: if err != nil { return false, err }. Panics are for bugs. The instance recovers them so that one bad statement doesn't kill the shell, but they are reported as internal errors, never as query errors. Project 4 adds one more kind: an error for which common.IsExecutionException is true fails the statement quietly, as a write-write conflict should.

How the tests are organised

Every stage's checkpoint is one command, run from go_db_internals/intro_to_db, that collects three kinds of tests by their shared prefix:

  • Executor unit tests in execution/*_test.go call your executor directly, on small tables in a small buffer pool, and check the batch contract on every Next call: cleared slices, 1 to batchSize tuples, one RID per tuple, false with an empty batch at the end. Every call has a time limit, so an executor that never releases a page latch fails its test instead of hanging.
  • Rule tests in optimizer/*_rule_test.go (stages 5, 9 and S1) hand your rule a plan and check what it returns.
  • SQL logic tests: CMU's own test files, sqllogictest/testdata/p3.*.slt, copied byte for byte from BusTub. A Go port of BusTub's bustub-sqllogictest runs them, one fresh in-memory instance per file. Each stage's Test<Prefix>SQL runs that stage's files as subtests named after them. The writeup says CMU provides all of its test cases and has no hidden ones, so these files are the whole SQL test suite.

An .slt file is a list of records separated by blank lines; # starts a comment. statement ok runs SQL and expects no error. query runs SQL and compares its output, columns separated by spaces, with the lines after ----; query rowsort sorts both sides first, for queries whose row order isn't fixed. Options that start with + run extra checks before the query: +ensure:index_scan, for example, runs explain (o) on it and fails unless the plan contains an IndexScan. This is stage 0's whole file, p3.00-primer.slt:

Check your understanding

The optimized plan for a join over two mock tables reads NestedLoopJoin { type=Inner, predicate=(#0.0=#1.0) }, with MockScan { table=__mock_table_1 } and MockScan { table=__mock_table_3 } as its children, in that order. __mock_table_3 has the columns (colE, colF). What is #1.0?

  • colB, the second column of __mock_table_1.
  • colE, column 0 of the right child's tuple.
  • colF, column 1 of __mock_table_3.
  • The constant 1.0, compared with column 0.

An executor has 45 tuples to produce, and its parent calls Next with batchSize 20 until it returns false. Which sequence of results follows the contract?

  • (true, 20), (true, 20), (false, 5)
  • (true, 20), (true, 25), (false, 0)
  • (true, 20), (true, 20), (true, 5), (true, 0)
  • (true, 20), (true, 20), (true, 5), (false, 0)

On the starter, with an index t1v1 on t1(v1) and force_optimizer_starter_rule=yes, EXPLAIN (o) of SELECT * FROM t1 ORDER BY v1 shows an IndexScan, but SELECT * FROM t1 WHERE v1 = 1 shows SeqScan { table=t1, filter=(#0.0=1) }. Why the difference?

  • The ORDER BY rule is pre-built, while the rule for point lookups is a stub that returns the plan unchanged.
  • The table is empty, so the optimizer decides a sequential scan is cheaper for the WHERE query.
  • The starter rule list has no rule for WHERE clauses at all.
  • The binder can't resolve v1 inside a WHERE clause until the index is used.

The planner produced Projection { exprs=["#0.0", "#0.1"] } over Filter { predicate=(#0.0=3) } over SeqScan { table=test_simple_seq_2 }. EXPLAIN (o) shows a single node, SeqScan { table=test_simple_seq_2, filter=(#0.0=3) }. Which pre-built rules produced it?

  • SeqScanAsIndexScan alone, which absorbed both nodes into the scan.
  • EliminateTrueFilter removed the Filter, and MergeProjection removed the Projection.
  • MergeProjection removed the identity Projection, and MergeFilterScan moved the predicate into the SeqScan.
  • None: the SeqScan executor removes the nodes above it when it runs.

Your Mac's Go reports CGO_ENABLED=0. What happens when you run go build ./... after the pull?

  • It builds, using a pure-Go fallback parser in pg_query_go.
  • The binder fails with undefined: pg_query.Parse, and so does every package that imports it.
  • Every package fails, including execution and optimizer.
  • It builds, and the first SQL statement panics at run time.

    Run \dt, then the query, then EXPLAIN of it, and read the three sections. Then try the same WHERE clause on test_simple_seq_2, a real table, with EXPLAIN (o,s), and see where the predicate went.

    One key fragment 
    EXPLAIN SELECT colB FROM __mock_table_1 WHERE colA = 5;
EXPLAIN (o,s) SELECT col2 FROM test_simple_seq_2 WHERE col1 = 5;
  • What to think about

    Which pre-built rule uses an index for ORDER BY? Which rule would use it for WHERE v1 = 1, and what does its starter version return?

    The approach

    Create t1(v1 INT, v2 INT) and an index on v1. Explain an ORDER BY query and a point lookup, then set force_optimizer_starter_rule=yes and explain them again; show force_optimizer_starter_rule; prints the current value. Write down the plans: after stage 5 the point lookup should change.

    CREATE TABLE t1(v1 INT, v2 INT);
CREATE INDEX t1v1 ON t1(v1);
EXPLAIN (o,s) SELECT * FROM t1 WHERE v1 = 1;
