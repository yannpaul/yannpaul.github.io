P3.3 Index Scan and the SeqScan→IndexScan Rule

Write IndexScanExecutor, which reads a table through your B+tree by point lookups or in key order, and the optimizer rule SeqScanAsIndexScan, which turns a sequential scan with an equality predicate on an indexed column into an index scan, without leaving a leaf latched.

So far every query reads the whole table. This stage is the first where your Project 2 tree answers SQL: WHERE v1 = 2 becomes one lookup in the index instead of a scan of every page, and ORDER BY v1 walks the leaves in key order. It takes two pieces: the executor does the reading, and an optimizer rule decides when to use it. The rule is the first plan rewrite you write yourself, after the pre-built ones you have been reading in EXPLAIN output since Lesson 1.

Warm-up: retrieval from earlier lessons

Unit 4, Lesson 8: a goroutine stops an index scan after the first entry and forgets Close. The same goroutine then calls tree.Remove on a key in that first leaf. What happens?

  • The garbage collector drops the iterator's guard, and Remove proceeds.
  • Remove upgrades the iterator's read latch to a write latch and proceeds.
  • Remove waits forever for a write latch that the goroutine itself holds in read mode.
  • Remove panics with a message that the leaf is already latched.

Unit 5, Lesson 5: a table of 100 students has an index on age and an index on dept. The query has WHERE age < 30 AND dept = 'CS' AND country = 'US'; 99 students are under 30 and 2 are in CS. Which index should the DBMS use?

  • The age index, because range predicates suit a B+tree best.
  • The dept index, then check the age and country predicates on the 2 tuples it returns.
  • Neither: only an index on country would help.
  • Both, always, intersecting their record IDs.

Unit 5, Lesson 7: the Project 3 writeup says most optimizer rules build plans "bottom-up". What does that mean for a rule's code?

  • It enumerates join orders from single tables upward, as System R does.
  • It reorders the executors so that the leaves run first.
  • It only ever looks at the leaves of the plan tree.
  • Before checking whether a node matches, it applies itself recursively to the node's children.

What stage 5 covers

An IndexScanPlanNode has four fields: TableOID, IndexOID, FilterPredicate (nil if none) and PredKeys, a list of constant expressions. Its output schema is the table's. The writeup asks the executor to support two kinds of query:

  • Point lookups, SELECT … FROM t WHERE <index column> = <value>, including "several point lookups on the same index". The plan has PredKeys: look each key up in the index and return the matching tuple. Your rule creates these plans.
  • Ordered scans, SELECT … FROM t ORDER BY <index column>, ascending only. The plan has no PredKeys: walk the whole index in key order. The pre-built rule OrderByAsIndexScan creates these plans when a Sort sits directly on a SeqScan and its keys are an index's columns.

Here is what both look like once the stage is done, on CMU's p3.05 table with indexes t1v1 (OID 0) and t1v2 (OID 1):

The index adapter

The catalog's GetIndexByOID(plan.IndexOID) returns an *catalog.IndexInfo whose Index field is an index.Index interface. The writeup says the object is always a BPlusTreeIndexForTwoIntegerColumn and that you can cast it; in Go that cast is a type assertion, info.Index.(*index.BPlusTreeIndexForTwoIntegerColumn), with the ok form so that a wrong type becomes an error. The adapter is pre-built and wraps your tree:

MethodDoes
ScanKey(key table.Tuple) []common.RIDthe RID stored under the key, as a slice of zero or one (your GetValue)
BeginIterator() *btree.IndexIteratoran iterator at the smallest key (your Begin)
BeginIteratorAt(key btree.GenericKey)an iterator at the first key ≥ key (your BeginAt)
Key(key table.Tuple) btree.GenericKeythe tree's key bytes for a key tuple
KeySchema(), KeyAttrs()the key's columns, and which table columns they come from

A tree key is 8 bytes (index.TwoIntegerSizeBTree): the key tuple's bytes, one or two little-endian INTEGERs, padded with zeros. GenericComparator compares the INTEGER columns as signed int32s, so negative keys come first, and p3.05 relies on that with keys −10 and −20. Your iterator's Entry() returns the key and the RID; IsEnd, Next and Close are the methods you wrote in Unit 4, Lesson 8.

To look a key up, you need it as a key tuple. Each of the plan's PredKeys is a constant expression, so it evaluates without a tuple: keyExpr.Evaluate(nil, types.NewSchema(nil)) returns its types.Value, as the Values executor does with its rows. table.NewTuple([]types.Value{v}, info.KeySchema) then lays the value out in the key's schema, and ScanKey takes it from there.

The index holds RIDs, not tuples. For each RID, fetch the tuple with tableInfo.Table.GetTuple(rid), which returns its meta and a copy that carries the RID. Skip it if its meta says deleted, as the writeup asks ("do not emit tuples that are deleted"), and skip it if a FilterPredicate is present and isn't true for it, with NULL as false, exactly as in your sequential scan. TestIndexScanSkipsDeleted marks tuples deleted in the heap without touching the index, so the meta check is the only thing that hides them.

A repeated key returns one row

WHERE v1 = 2 OR v1 = 2 is a legal query, and the rule turns it into point lookups with PredKeys 2 and 2. Looking each key up and returning what you find gives the row twice; SQL's answer is one row. The writeup's hint is to "think about how to handle queries of the form WHERE v1 = 1 OR v1 = 1", pointing at the aggregation's hash keys. The simplest fix is to remember which RIDs you have already collected, in a map[common.RID]bool (a common.RID is a comparable struct, so it works as a map key), and skip repeats. CMU's .slt files never repeat a key, so only the unit test checks this:

--- FAIL: TestIndexScanRepeatedKey (0.00s)
    index_scan_executor_test.go:65: rows with a = 3 or a = 3:
         got  ["3, 30" "3, 30"]
         want ["3, 30"]

Point lookups may come back in any order; the tests compare them as sets, and the .slt records use rowsort. An ordered scan must return rows in key order.

Pins, latches and closing the iterator

Your Project 2 iterator holds a read guard on its current leaf: a pin, and a read latch. If the index scan keeps that iterator open between its Next calls, the leaf stays latched while the executors above it run. The executor above can be an insert into the same table, which writes into the same index:

bustub> EXPLAIN (o) INSERT INTO t1 SELECT v1 + 1000, v2 FROM (SELECT * FROM t1 ORDER BY v1);
=== OPTIMIZER ===
Insert { table_oid=32 }
  Projection { exprs=["(#0.0+1000)", "#0.1"] }
    IndexScan { index_oid=0 }

The insert gets a batch, then calls InsertEntry, which needs a write latch on the leaf where the new key goes. With 100 small keys there is only one leaf, and the scan's iterator holds it in read mode. Everything runs on one goroutine, so the insert waits for itself, the situation of the warm-up's first question. Here it is as an .slt file run against an index scan that keeps its iterator open (the timeout lowered to 10 seconds with -slt.timeout=10s):

--- FAIL: TestSQLLogicFile (10.03s)
    stages_test.go:98: lazy.slt:12: did not finish within 10s (a deadlock or an endless loop?); the rest of the file is skipped
        --- SQL
        insert into t1 select v1 + 1000, v2 from (select * from t1 order by v1);

Even without the latch, an open iterator would see the keys 1000 and up that the insert adds ahead of it, which is the Halloween problem from Lesson 3 in index form. Both go away if the executor reads the index completely in Init: collect every RID in order, close the iterator (defer it.Close() right after creating it), and serve batches from the slice of RIDs in Next. The heap's iterator in Lesson 2 needed no such care, because it holds no guard between calls. TestIndexScanReleasesIterator checks the result: after the scan returns false, no page is pinned, and an InsertEntry into the index finishes within its time limit. Point lookups through ScanKey hold nothing after they return.

Idiom

In BusTub the iterator's destructor releases the leaf when the iterator goes out of scope, so a C++ executor that stores an iterator member releases it whenever the member is replaced or the executor is destroyed. Go has neither destructors nor a guarantee about when an unreachable iterator is collected, so every iterator you open needs a Close on every path: at the end of the scan, on a re-Init in the middle of a scan, and when a parent stops early (a LIMIT, in stage 10). Collecting the RIDs in Init with a defer it.Close() covers all three with one line.

The rule: SeqScanAsIndexScan

By the time your rule runs, MergeFilterScan has moved the WHERE clause into the SeqScan's FilterPredicate; both rule lists call OptimizeSeqScanAsIndexScan last, right after it. The rule looks at that predicate, and if it selects rows by equality on a column with an index, it replaces the scan. The writeup lists the shapes it must handle:

  • one equality on the indexed column: v1 = 1;
  • the same, flipped: 1 = v1;
  • several point lookups on the same index, joined by OR: v1 = 1 OR v1 = 4, in any nesting and any mix of sides.

Everything else stays a SeqScan. The writeup names v1 = 1 AND v2 = 2 ("you do not need to split the predicates"), and the rule tests add ranges (>, >=, <, <=, !=), a column compared with a column (v1 = v2), an OR that mixes an equality with a range (v1 = 1 OR v1 > 4), an OR across two columns (v1 = 1 OR v2 = 4, even when both columns have indexes), a column without an index, and a scan without a predicate. From the shell, with indexes on both v1 and v2:

bustub> EXPLAIN (o) SELECT * FROM t1 WHERE v1 = 5 AND v2 = 10;
=== OPTIMIZER ===
SeqScan { table=t1, filter=((#0.0=5)and(#0.1=10)) }

bustub> EXPLAIN (o) SELECT * FROM t1 WHERE v1 = 8 OR v2 = 30;
=== OPTIMIZER ===
SeqScan { table=t1, filter=((#0.0=8)or(#0.1=30)) }

bustub> EXPLAIN (o) SELECT * FROM t1 WHERE v1 > 3;
=== OPTIMIZER ===
SeqScan { table=t1, filter=(#0.0>3) }

When the predicate matches, the rule needs the column's index. The pre-built helper o.MatchIndex(scan.TableName, colIdx) returns the OID of an index whose only key column is table column colIdx, with its name and an ok flag. The new node is plans.NewIndexScanPlanNode(scan.OutputSchema(), scan.TableOID, indexOID, scan.FilterPredicate, keys): the scan's schema, the original predicate kept as the filter, and the constant expressions as PredKeys, in any order and duplicates allowed (the executor removes repeated rows).

The predicate is an expression tree, and three node types matter. An *expressions.LogicExpression has a LogicType (expressions.And or expressions.Or) and two children. An *expressions.ComparisonExpression has a CompType (expressions.Equal, expressions.LessThan, …) and two children, read with ChildAt(0) and ChildAt(1). The leaves are *expressions.ColumnValueExpression (ColIdx() is the column) and *expressions.ConstantValueExpression. A type switch over these, recursing into OR nodes, covers every shape; any node it doesn't expect means "leave the scan alone".

How rules recurse

A rule receives the root of the plan. The SeqScan can be anywhere below it: under a Projection (SELECT v3 FROM t1 WHERE v2 = 40), under an Update or a Delete (which is how p3.05's update … where v1 = 2 gets an index), or as either child of a join. So every rule starts the same way, as the pre-built ones in optimizer/ do: apply itself to the children, rebuild the node over the results, and only then look at the node. The package doc in optimizer/doc.go points to two unexported helpers in optimizer_internal.go. optimizeChildren(plan, rule) does the first step: it applies rule to each child and returns plan.CloneWithChildren of the results. withOutputSchema(plan, schema) copies a node with another output schema; this rule doesn't need it, since the IndexScan keeps the scan's schema, but the leaderboard's column pruning will. merge_filter_scan.go is the closest example: about twenty lines, and your rule has the same skeleton.

bustub> EXPLAIN (o) SELECT v3 FROM t1 WHERE v2 = 40;
=== OPTIMIZER ===
Projection { exprs=["#0.2"] }
  IndexScan { index_oid=1, filter=(#0.1=40) }

bustub> EXPLAIN (o) UPDATE t1 SET v3 = 0 WHERE v1 = 3;
=== OPTIMIZER ===
Update { table_oid=32, target_exprs=["#0.0", "#0.1", "0"] }
  IndexScan { index_oid=0, filter=(#0.0=3) }

  • The row twice, once per key.
  • The row once.
  • An error, because the plan has duplicate keys.
  • No rows, because the duplicates cancel.

  • An IndexScan under the Projection, as with a recursive rule.
  • An IndexScan alone, because the Projection is merged away.
  • The SeqScan under the Projection stays a SeqScan.
  • An optimizer error, because the plan isn't the expected shape.

An index scan opens its iterator in Init and reads entries from it lazily in Next. It runs under INSERT INTO t1 SELECT v1 + 1000, v2 FROM (SELECT * FROM t1 ORDER BY v1), and t1's 100 keys fit in one leaf. What happens?

  • The insert waits for a write latch on the leaf that the scan holds in read mode, and the statement never finishes.
  • The insert upgrades the scan's latch and inserts 100 rows.

  • The buffer pool reports a deadlock and the statement fails with an error.

Build it: index scan executor (stage P3.3a)

You edit execution/index_scan_executor.go. Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • With PredKeys, look each key up with ScanKey and return each matching tuple once, even if a key repeats. Without them, return every tuple in key order, through the index's iterator.
  • Skip deleted tuples, and tuples for which a FilterPredicate isn't true (NULL counts as false).
  • Close every iterator you open; no leaf may stay latched or pinned after the scan, and Init may be called again in the middle of a scan.
  • The batch contract from Lesson 1: clear, up to batchSize, true for every non-empty batch, then false for good.
  • What to think about

    Which of the plan's two OIDs gives the heap and which gives the tree? What does Next work from: an iterator, or something you prepared in Init? What must a second Init clear?

    The approach

    Keep the *catalog.TableInfo, the *index.BPlusTreeIndexForTwoIntegerColumn, a slice of RIDs to fetch and a position in it. In Init, look up the table with GetTableByOID and the index with GetIndexByOID (errors if either is nil), assert the index's type (an error if it isn't a B+tree), truncate the RID slice and set the position to 0.

    One key fragment 
    tree, ok := idxInfo.Index.(*index.BPlusTreeIndexForTwoIntegerColumn)
if !ok {
	return common.NewException("index " + idxInfo.Name + " is not a B+tree index")
}
  • What to think about

    A PredKey is an expression: what do you evaluate it on, given it has no column references? Which schema lays out a key tuple? What does ScanKey return for a key that isn't in the tree? How do you notice that a RID is already in your list?

    The approach

    If len(e.plan.PredKeys) > 0: make a set of RIDs. For each key expression, evaluate it with a nil tuple and an empty schema, build a one-value tuple with the index's KeySchema, and append each RID from ScanKey that isn't in the set yet (then add it). That finishes Init for a point lookup.

    One key fragment 
    v := keyExpr.Evaluate(nil, types.NewSchema(nil))
key := table.NewTuple([]types.Value{v}, idxInfo.KeySchema)
for _, rid := range tree.ScanKey(key) { /* skip RIDs already seen */ }
  • What to think about

    What does your iterator hold while it is open, and which executors may run between two of your Next calls? What would happen to an INSERT into the same index above you? Which Go statement guarantees the Close on every return path?

    The approach

    Get an iterator with BeginIterator() and defer its Close at once. Loop until IsEnd, taking the RID from Entry() and calling Next. When Init returns, the RIDs are in key order in your slice and no leaf is latched.

    One key fragment 
    it := tree.BeginIterator()
defer it.Close()
for ; !it.IsEnd(); it.Next() { /* append the RID from it.Entry() */ }
  • What to think about

    This is your sequential scan's Next with a different source of positions. What replaces the table iterator? Where can the tuple for a RID come from, and what tells you it was deleted?

    The approach

    Clear the slices. While the batch has room and the position is inside the RID slice, take the next RID, advance, get (meta, tuple) from the heap's GetTuple, skip deleted tuples, apply the filter like your scan does, and append the tuple and RID. Return whether the batch is non-empty.

    One key fragment 
    rid := e.rids[e.pos]
e.pos++
meta, t := e.tableInfo.Table.GetTuple(rid)

Build it: the SeqScanAsIndexScan rule (stage P3.3b)

You edit optimizer/seqscan_as_indexscan.go; its starter body returns the plan unchanged. The rules, in plain words:

  • Rewrite bottom-up: optimize the children first, then look at the node.
  • Rewrite a SeqScan whose predicate is column = constant, constant = column, or an OR tree of those on one column, when MatchIndex finds a single-column index on that column. Leave every other plan as it is.
  • The IndexScan gets the scan's output schema and table, the index's OID, the scan's original predicate as its filter, and the constants as PredKeys.
  • What to think about

    Which node types can appear in a qualifying predicate, and at which positions? How do you handle 1 = v1 without writing the equality case twice? An OR of three equalities is two OR nodes; how does recursion keep that simple? Where do you notice that two equalities name different columns?

    The approach

    Recurse with a type switch. A LogicExpression qualifies only if it is an OR and both children qualify. A ComparisonExpression qualifies only if it is Equal and one child is a ColumnValueExpression and the other a ConstantValueExpression, in either order; record the column the first time and require the same column after that, and append the constant. Anything else fails, which covers AND, ranges, v1 = v2 and arithmetic.

    One key fragment 
    case *expressions.LogicExpression:
	return e.LogicType == expressions.Or &&
		match(e.ChildAt(0), &col, &keys) && match(e.ChildAt(1), &col, &keys)
  • What to think about

    Which pre-built rule has almost the same skeleton? What do you return when the node isn't a SeqScan, has no predicate, doesn't match, or has no index on the column? Which schema and which predicate does the new node keep?

    The approach

    Start with optimized := optimizeChildren(plan, o.OptimizeSeqScanAsIndexScan). If optimized is not a *plans.SeqScanPlanNode or its FilterPredicate is nil, return it. Run your helper; if it fails, return optimized. Call o.MatchIndex(scan.TableName, col); if nothing is found, return optimized. Otherwise return a new IndexScan node.

    One key fragment 
    return plans.NewIndexScanPlanNode(scan.OutputSchema(), scan.TableOID, indexOID,
	scan.FilterPredicate, keys)
