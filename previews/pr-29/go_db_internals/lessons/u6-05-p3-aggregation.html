P3.4 Aggregation

Build the hashing aggregation executor: drain the child in Init, fold each row into its group with CombineAggregateValues, follow BusTub's NULL rules for count(*), count, sum, min and max, put NULL group keys into one group, and emit group-bys then aggregates batch by batch.

Unit 5, Lesson 2 compared two ways to compute GROUP BY, sorting and hashing, and found that Project 3 uses hashing with a table that fits in memory. That table is pre-built. What is left for you is the part that decides the answers: how one row changes a group's running aggregates, which rows count as the same group when a key is NULL, and what an empty input produces. The aggregation is also the first executor you write that is a pipeline breaker, so it is where the split between Init and Next starts to matter.

Unit 0, Lesson 2: what does HAVING filter, and when?

  • Input rows, before they are grouped.

What the plan asks for

Every query with an aggregate or a GROUP BY gets an AggregationPlanNode, printed as Agg. Here is a small table and one aggregate query, run in the shell (go run ./cmd/shell from go_db_internals/intro_to_db) once this stage works:

bustub> create table t(a int, b int);
bustub> insert into t values (1, 5), (1, null), (null, 3), (null, 4), (2, null);
bustub> explain (o) select a, count(*), count(b), sum(b) from t group by a having count(*) > 1;
=== OPTIMIZER ===
Projection { exprs=["#0.0", "#0.2", "#0.3", "#0.4"] }
  Filter { predicate=(#0.1>1) }
    Agg { types=["count_star", "count_star", "count", "sum"], aggregates=["1", "1", "#0.1", "#0.1"], group_by=["#0.0"] }
      SeqScan { table=t }

The node has three lists, which the Go plan exposes as fields:

  • GroupBys: one expression per GROUP BY item, here #0.0, the column a of the child's tuple.
  • AggTypes: one plans.AggregationType per aggregate, out of CountStarAggregate, CountAggregate, SumAggregate, MinAggregate and MaxAggregate. BusTub has no AVG.
  • Aggregates: the expression each aggregate reads, in the same order. count(*) reads the constant 1, whose value nobody looks at.

The output tuple of a group is its group-by values followed by its aggregates, in plan order. The writeup states that layout, and the operators above the Agg depend on it: here column #0.0 is a, #0.1 is the count(*) that HAVING added, #0.2 the count(*) of the SELECT list, #0.3 is count(b) and #0.4 is sum(b). The HAVING clause became a Filter above the aggregation, as the writeup says it would, and the projection on top picks the four columns the query asked for. Your executor never sees HAVING.

Init is the build phase

No group's aggregates are final until the child's last tuple has been read, so the aggregation is a pipeline breaker (Unit 5, Lesson 5). The writeup's hint asks you to decide whether the build phase belongs in Init or in Next; the doc comment on AggregationExecutor.Init settles it for this course: Init initializes the child and builds the hash table from all of its tuples. Next then only walks the finished table.

The build is a loop you have seen in the pre-built executors: call the child's Next with a batch of up to common.BatchSize tuples until it returns false, and for each tuple call InsertCombine(e.makeAggregateKey(&t), e.makeAggregateValue(&t)). Both helpers are pre-built: one evaluates the group-by expressions on the tuple, the other evaluates the aggregate expressions. InsertCombine is pre-built too. It hashes the key, looks in that bucket for a key that is Equal, creates the group with GenerateInitialAggregateValue if there is none, and then calls the one method of the table you write, CombineAggregateValues.

Init can run more than once. The engine calls it once, but a nested loop join calls Init on its right child for every left tuple (next lesson), and p3.12-repeat-execute.slt puts aggregations exactly there: select * from __mock_table_123, (select count(*) as cnt from t1) must print cnt = 2 on all three rows. So Init starts from an empty table every time, never adding to the groups of the previous run. TestAggregationReInit runs the same executor three times and also checks that each Init initialized the child once.

Combining one row into a group

CombineAggregateValues(result, input) receives the group's running aggregates in result.Aggregates and one row's aggregate inputs in input.Aggregates, both indexed like AggTypes. It updates result in place. The starting values come from GenerateInitialAggregateValue: 0 for count(*) and an INTEGER NULL for the other four. The writeup explains the choice: on an empty table, CountStarAggregate returns zero and every other aggregate returns integer_null.

AggregateStarts atA non-NULL inputA NULL input
count(*)0adds 1adds 1
count(x)integer_nullNULL becomes 1, otherwise adds 1no change
sum(x)integer_nullNULL becomes the input, otherwise adds itno change
min(x), max(x)integer_nullNULL becomes the input, otherwise keeps the smaller (larger) oneno change

Run on the table above, the rules give:

bustub> select a, count(*), count(b), sum(b) from t group by a;
+--------------+-----------+--------------+--------------+
| t.a          | <unnamed> | <unnamed>    | <unnamed>    |
+--------------+-----------+--------------+--------------+
| 1            | 2         | 1            | 5            |
| integer_null | 2         | 2            | 7            |
| 2            | 1         | integer_null | integer_null |
+--------------+-----------+--------------+--------------+

Look at the last row. Group 2 has one row and its b is NULL, so count(b) never leaves its starting value and prints integer_null. Standard SQL says 0 there: DuckDB returns (2, 1, 0, None) for the same query. This is a BusTub convention, and the course keeps it because CMU's tests expect it: p3.07-simple-agg.slt checks that select count(v1) from t1 on an empty table prints integer_null, and TestAggregationNullInputs expects "2, 2, integer_null, integer_null, integer_null, integer_null" for a group whose values are all NULL.

Pitfall

The arithmetic on types.Value treats NULL the way SQL does: Add, Min and Max with a NULL operand return NULL. Calling cur.Add(in) or cur.Min(in) on a group's starting value would therefore keep it NULL forever. Check IsNull() on both sides first. The starting NULL is also INTEGER-typed even when the column is a VARCHAR, so for min and max replace a NULL running value with the input rather than comparing against it; then compare inputs with CompareLessThan and CompareGreaterThan, which return a types.CmpBool.

Empty input, with and without GROUP BY

An empty child gives an empty hash table: no row ever reached InsertCombine, so no group exists. What the executor returns then depends on the plan:

  • Without GROUP BY (len(plan.GroupBys) == 0), SQL still returns one row, the aggregates of nothing: count(*) 0 and NULL for the rest. The executor must produce that row itself, from GenerateInitialAggregateValue, because the table has no group to iterate over.
  • With GROUP BY, there are no groups and therefore no rows. p3.08-group-agg-1.slt runs select v5, min(v1), sum(v2), count(*) from t1 group by v5 on an empty table and expects an empty result, with the comment "no groups, no output".
bustub> select count(*), count(b), min(b) from t where a = 99;
+-----------+--------------+--------------+
| <unnamed> | <unnamed>    | <unnamed>    |
+-----------+--------------+--------------+
| 0         | integer_null | integer_null |
+-----------+--------------+--------------+
bustub> select a, count(*) from t where a = 99 group by a;
+-----+-----------+
| t.a | <unnamed> |
+-----+-----------+

The extra row must come once per run, and again after a new Init: TestAggregationReInit runs the query without GROUP BY twice, and inside a nested loop join the right child's Init is called many times.

NULL group keys form one group

The writeup's hint: "Group-by columns can also have NULL values. You may want to consider modifying the way aggregate keys are compared." In a comparison, NULL = NULL is NULL, not true. GROUP BY uses a different notion of sameness and puts all the NULLs of a column into one group, which is why the output above has a single integer_null row for a.

The pre-built AggregateKey.Hash skips NULL values, so every NULL key lands in the same bucket. The starter AggregateKey.Equal is BusTub's operator==, which compares each value with CompareEquals and requires types.CmpTrue. For a NULL that comparison returns types.CmpNull, so a key holding a NULL equals nothing, not even itself, and InsertCombine creates a new group for every such row. The doc comment on Equal says so and asks you to change it, which is the change the writeup's hint means. In this course AggregateKey lives in your file, so that every line you may change is in a learner file; in BusTub it is in aggregation_plan.h.

types.Value has the comparison you need: CompareExactlyEquals reports true when both values are NULL or when CompareEquals is CmpTrue. With the starter Equal and everything else working, CMU's test file shows the symptom: __mock_table_4 has ten rows whose colH is NULL, and they come out as ten groups of one.

DISTINCT is an aggregation

The planner has no separate DISTINCT operator. SELECT DISTINCT becomes an aggregation that groups by every selected column and computes no aggregates:

bustub> explain (o) select distinct a from t;
=== OPTIMIZER ===
Agg { types=[], aggregates=[], group_by=["#0.0"] }
  Projection { exprs=["#0.0"] }
    SeqScan { table=t }
bustub> select distinct a from t;
+--------------+
| t.a          |
+--------------+
| 1            |
| integer_null |
| 2            |
+--------------+

This is Lecture #11's hashing aggregate in its DISTINCT form: the hash table only has to discard duplicates. If your loops handle an empty AggTypes and your Equal handles NULLs, DISTINCT needs no code of its own; TestAggregationDistinct checks that two (NULL, 3) rows come out once. Because DISTINCT always has group-bys, the empty-input row never applies to it.

Build it: aggregation (stage 6)

You edit one file, execution/aggregation_executor.go: AggregateKey.Equal, SimpleAggregationHashTable.CombineAggregateValues, and AggregationExecutor.Init and Next, plus any fields you add to the executor (the struct already has aht and ahtIterator, BusTub's suggested members). Run commands from go_db_internals/intro_to_db. The rules, in plain words:

  • Next follows the batch contract: clear *tuples and *rids first, append up to batchSize tuples with one RID each (the zero common.RID{}, since groups don't come from a table), return true for every non-empty batch including the last partial one, and false once the groups are exhausted, on every later call too.
  • Return errors from the child; don't panic.
  • Each output tuple is the group-by values followed by the aggregates, built with table.NewTuple(values, e.OutputSchema()).
  • count(*) counts every row; count, sum, min and max skip NULL inputs and stay integer_null until they see a non-NULL one.
  • Without GROUP BY an empty input gives one row of initial values; with GROUP BY it gives none. NULL group keys belong to one group.
  • What to think about

    Which index of input.Aggregates goes with which entry of h.aggTypes? For each type, what happens when the input is NULL, and what happens when the running value is still its starting NULL? Which of the five types ignores the input's value entirely?

    The approach

    Loop over h.aggTypes with its index i, and switch on the type. CountStarAggregate: add one. For the other four, skip the row when the input is NULL. Otherwise, if the running value is NULL, it becomes 1 for CountAggregate and the input for the others. If it isn't NULL, count adds one, sum adds the input with Add, and min/max replace it when CompareLessThan/CompareGreaterThan of the input against it is types.CmpTrue. Write each new value back into result.Aggregates[i].

    One key fragment 
    case plans.MinAggregate:
	if in.IsNull() {
		continue
	}
	if cur.IsNull() || in.CompareLessThan(cur) == types.CmpTrue {
  • What to think about

    Which arguments does NewSimpleAggregationHashTable need, and where in the plan are they? What must be true of the table after a second Init? How will Next know, later, that it owes the caller one row of initial values?

    The approach

    Call e.child.Init() and return its error. Set e.aht to a new table built from e.plan.Aggregates and e.plan.AggTypes (or Clear the old one). Then loop: call e.child.Next into batch slices kept as fields, with common.BatchSize; stop when it returns false, return any error; for each tuple, InsertCombine its key and value. Afterwards set e.ahtIterator = e.aht.Begin(), and record in a field whether the "empty input without GROUP BY" row is due: no group-bys and an iterator already at the end.

    One key fragment 
    for i := range e.childTuples {
	t := &e.childTuples[i]
	e.aht.InsertCombine(e.makeAggregateKey(t), e.makeAggregateValue(t))
}
  • What to think about

    Where does each output value come from: the iterator's Key() or its Val()? When does a batch end: at batchSize, at the end of the table, or both? After the extra row for an empty input has been returned, what must the next call return?

    The approach

    Clear both slices. If the empty-input row is due, clear the flag, append a tuple made from e.aht.GenerateInitialAggregateValue().Aggregates with a zero RID, and return true. Otherwise, while fewer than batchSize tuples are in the batch and the iterator isn't at the end, build a value slice from Key().GroupBys followed by Val().Aggregates, append the tuple and a zero RID, and advance the iterator. Return whether the batch is non-empty.

    One key fragment 
    values := make([]types.Value, 0, len(key.GroupBys)+len(val.Aggregates))
values = append(values, key.GroupBys...)
values = append(values, val.Aggregates...)
