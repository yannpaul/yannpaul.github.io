Hiding Latency

Four techniques that don't remove round-trip time — they make sure the player never has to feel it.

Lesson 1 ended on a floor nobody can engineer away: an authoritative server can't confirm anything faster than one network round trip. If a shooter waited for that round trip before showing your bullet leaving the gun, it would feel broken — even a great connection makes that wait noticeable. Real games don't remove the wait. They hide it, with four distinct techniques that each solve a different piece of the same problem.

The problem, split into three pieces

Gabriel Gambetta's framing (the standard reference for this whole lesson) splits "latency ruins the game" into three separate sub-problems, because each needs a different fix:

  1. My own input feels laggy — I press a key, and nothing visibly happens until a full round trip later.
  2. Other players move unevenly — I only get updates about them each server tick, and just replaying pos­itions verbatim looks jerky, or ahead of where the server actually has them.
  3. Hits feel unfair — by the time my "I shot them" message reaches the server, the target has already moved on the server's clock.

One technique addresses each of the first two; a fourth exists specifically for the third. All four assume the client-server model and tick rate from Lesson 1.

1. Client-side prediction: fixing my own input

The fix for problem 1 is direct: don't wait. The client applies the local player's own input immediately, running the same movement/physics rules the server will eventually use, and shows the result right away — before the server has even seen the input. Because the client is running the real rules, its guess about its own action is usually exactly right. This is why moving and shooting feel instant even though, underneath, nothing has been confirmed by anyone yet.

This is optimistic execution: proceed as if the operation will succeed, and only pay the cost of a correction on the rare occasion it doesn't. It's the same trade optimistic concurrency control makes over pessimistic locking — assume no conflict, verify after the fact, and only fall back to a slower path when the assumption turns out wrong.

2. Server reconciliation: correcting without a snap

Client-side prediction creates a new problem: sometimes the client's guess is wrong (another player's stray hit slowed you down, unseen terrain, a desync). When the server's real result disagrees with what the client already showed, the naive fix — just overwrite local state with the server's answer — causes a visible snap backward, and worse, it can silently drop player input the client had already sent for the *next* tick, before the correction arrived.

The actual fix, server reconciliation: the client keeps a short buffer of its own recent, not-yet-acknowledged inputs. When a correction arrives, the client resets to the server's authoritative state, then replays exactly those buffered inputs on top of it — reproducing wherever the player would legitimately be now, correction included, with no lost input and (ideally) no visible jump.

Why does server reconciliation replay the client's buffered inputs on top of a correction, instead of just snapping straight to the server's authoritative state?

  • Replaying is a way to reduce the round-trip time to the server.
  • The client doesn't trust the server's state is actually more current than its own.
  • Without replaying, any input sent after the corrected tick but before the correction arrived would be lost.
  • Replaying saves bandwidth by not re-sending the same inputs to the server.

3. Entity interpolation: smoothing everyone else

Prediction and reconciliation only work for the local player, because only the local client knows its own input the instant it happens. For every other player, the client has no early information at all — it only learns where they are when a server update arrives, once per tick.

The naive approach — snap each remote player straight to their latest reported position — looks jerky, since ticks arrive in discrete jumps rather than smooth motion. Entity interpolation fixes this by deliberately rendering other entities slightly in the past: the client buffers the last two (or more) authoritative positions it received and smoothly interpolates between them, arriving at "now" only once the *next* update has already confirmed where the entity actually was headed. The cost is a small, fixed extra delay in what you see of other players — worth it, because delay reads as reasonable while jitter reads as broken.

This mirrors a read replica deliberately serving slightly stale data to smooth over replication lag, rather than blocking until the freshest write propagates. Entity interpolation makes the same trade explicitly, in a domain (rendering) where "slightly stale but smooth" beats "current but jumpy."

4. Lag compensation: making hits fair

The last problem is different in kind: it's not about what a client displays, it's about what the *server* decides really happened. Say a player fires at a target that's moving. On the shooter's own screen (already delayed by network and possibly further behind by entity interpolation) the target looked like it was in one spot. By the time that "I fired" message reaches the server, real server-clock time has moved on and the target has actually moved further.

Valve's Source engine (Half-Life 2, Counter-Strike, Team Fortress 2) documents a concrete, shipped fix: the server keeps a rolling history — roughly one second — of every player's recent positions and animation state. When a hit needs to be checked, the server temporarily rewinds *its own* copy of the world back to the exact moment the shooter's client actually fired, checks the hit against what the shooter genuinely saw, then restores the present. This is lag compensation, and it's why a competent shooter doesn't require you to visibly "lead" your shots against a moving target.

The trade lag compensation makes

Rewinding the world to favor the shooter's view is also exactly why you can sometimes be shot "behind cover" in a badly-tuned shooter — from the server's rewound perspective, at the moment the shot was actually fired, you hadn't ducked behind that wall yet. Every fairness mechanism in this lesson is a trade, not a free fix; this one trades a little unfairness to the target for a lot of fairness to the shooter.

Lag compensation is implemented entirely on the server, unlike the other three techniques in this lesson. Why does it have to live there rather than on either client?

  • Only the server holds the authoritative history of where everyone actually was, and only the server's hit decision can't be biased by either player's own client.
  • Clients don't have enough memory to store even one second of position history.
  • Running it on the server is the only way to reduce round-trip time for both players at once.
  • The shooter's client can't tell what direction it fired in without server help.

Putting the four together

TechniqueFixesRuns on
Client-side predictionMy own input feeling laggyClient (local player only)
Server reconciliationCorrecting prediction without snapping or losing inputClient, driven by server corrections
Entity interpolationOther players' motion looking jerkyClient (remote players only)
Lag compensationHits feeling unfair given network delayServer only

Notice the pattern: three of the four exist entirely to manage the *client's* experience of a delay that can't be removed. Only lag compensation changes what the *server* itself decides. That split — client-side illusion vs. server-side decision — is a preview of Lesson 8's whole point: the server is the only place a decision that matters is allowed to be made.
