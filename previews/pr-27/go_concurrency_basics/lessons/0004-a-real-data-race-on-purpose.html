A Real Data Race, On Purpose

Rebuild Lesson 3's channel-based duTop from memory first. Then deliberately break it, and watch what actually happens — not just what the textbook says happens.

Every lesson so far has told you a data race is dangerous. Today you cause one on purpose, in code you already trust, and see for yourself that it doesn't crash, doesn't always misbehave, and doesn't announce itself — which is exactly why go run -race exists as a separate, deliberate step, not something you'd notice by just running the program and watching.

Warm-up — repeat from Lessons 1–3
  • Checkpoint

    go run -race . du top --path scratch --n 10 prints the same three sorted lines it always has, no warnings — your known-good baseline before you break anything.

New: breaking it back to a shared append

Set your Lesson 3 duTop aside for a moment (comment it out, or copy it to a scratch file — you'll want it back at the end). Today's version starts each goroutine the way Lesson 2 warned you not to: computing a size, then calling append directly on one shared dSizes slice, with nothing coordinating who appends when.

  • Stuck? Show the function 
    func duTop(root string, n int) error {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return err
	}

	var dSizes []dirSize
	var wg sync.WaitGroup
	for _, d := range dirs {
		wg.Add(1)
		go func(name string) {
			defer wg.Done()
			p := filepath.Join(root, name)
			s, err := sizeOf(p)
			if err != nil {
				return
			}
			dSizes = append(dSizes, dirSize{p, s})
		}(d.Name())
	}
	wg.Wait()

	sort.Slice(dSizes, func(i, j int) bool { return dSizes[i].Size > dSizes[j].Size })
	n = min(len(dSizes), n)
	for _, d := range dSizes[:n] {
		fmt.Printf("%10d %q\n", d.Size, d.Name)
	}
	return nil
}

    This compiles and runs cleanly — that's the point. Nothing here is a syntax problem.

Build a scratch directory with several entries — the more there are, the more likely two goroutines actually overlap:

  • Stuck? Show the commands 
    mkdir -p race-test/{a,b,c,d,e,f,g,h}
for d in a b c d e f g h; do head -c 10 /dev/zero > race-test/$d/f.bin; done
  • Checkpoint

    You should see 8 lines most of the time — and, on at least one run, 7, or some other number less than 8. Nothing crashes, no error prints. An entry's result simply never made it into dSizes that time, because two goroutines' concurrent append calls collided — one append can silently overwrite or lose another's write when both are racing to grow the same underlying array. If you don't see it drop a line in five or six tries, that's not proof it's safe — it's exactly the danger this lesson is about: a race that only sometimes shows itself.

  • Stuck? Show the command 
    go run -race . du top --path race-test --n 10
    Checkpoint

    A WARNING: DATA RACE block prints, naming two goroutines both reading and writing at the same memory address, with a stack trace pointing directly at your append line in both. This is the tool doing exactly what Lesson 7 of Go CLI Basics described: it only reports a race that actually happened during this run, but when it fires, it's not a false alarm — it's telling you precisely where two goroutines touched the same memory unsafely.

Idiom

append isn't one atomic operation — it reads the slice's current length and capacity, decides whether the backing array needs to grow, possibly allocates a new one, copies data, and writes the new element and the new length back into the slice header your variable holds. When two goroutines run all of that concurrently against the same shared slice variable, they can both read the same starting length, both decide independently where their new element goes, and one goroutine's write can be silently overwritten by the other's — not a crash, just quietly wrong data. This is precisely why Lesson 2 insisted on indexed writes into a pre-sized slice (each goroutine owns a distinct memory location, so there's nothing to collide over) and why Lesson 3's channel moved the only append call into a single goroutine that never runs concurrently with itself.

  • Checkpoint

    go run -race . du top --path race-test --n 10 now reliably prints all 8 lines, every time, with no warning — the same fixture that just silently dropped data a moment ago.

A data race is not "usually fine, occasionally slow." It's undefined behavior that happens to look fine most of the time on your machine, today, with this input size — and silently wrong the rest of the time. -race is how you find out which one you actually have, instead of hoping.

Something unclear — why append specifically is unsafe here when indexed writes weren't, why the plain (non--race) run doesn't always show the corruption, what would happen with a much larger number of entries, anything else? Ask your teacher (me) before moving on.
