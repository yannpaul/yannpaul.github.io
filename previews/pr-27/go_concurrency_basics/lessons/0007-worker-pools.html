Worker Pools: Bounded Concurrency

Rebuild Lesson 6's select-guarded duTop from memory first. Then ask what happens when "one goroutine per entry" means ten thousand goroutines, not ten.

Every duTop so far starts exactly len(dirs) goroutines. For a directory with a dozen subdirectories, that's fine. For one with fifty thousand, you'd launch fifty thousand goroutines at once, all hammering the filesystem simultaneously — and on a real machine, more concurrent disk I/O than the disk can actually serve doesn't make the work finish faster, it just adds contention. A worker pool fixes the number of goroutines doing the work, no matter how much work there is.

Warm-up — repeat from Lessons 1–6

    go run -race . du top --path scratch --n 10 prints your known-good sorted lines well within the timeout, no warnings.

New: a fixed number of workers, pulling from a queue

Instead of one goroutine per entry, start a small, fixed number of worker goroutines up front — say, four. Feed all the entry names into a jobs channel. Each worker loops, pulling one name off jobs at a time, computing its size, and sending the result — exactly the same as before, except now only four sizes are ever being computed at once, regardless of whether there are ten entries or ten thousand.

  • Stuck? Show the constant 
    const maxWorkers = 4
  • Stuck? Show the code 
    jobs := make(chan string, len(dirs))
for _, d := range dirs {
	jobs <- d.Name()
}
close(jobs)

    Sizing the buffer to len(dirs) means every send here completes immediately — nothing is waiting to receive yet, and nothing needs to. Closing jobs right after filling it doesn't discard the buffered values; a closed channel still delivers everything already sent before signaling "no more" to a range over it.

  • Stuck? Show the code 
    results := make(chan sizeResult, len(dirs))
var wg sync.WaitGroup
for w := 0; w < maxWorkers; w++ {
	wg.Add(1)
	go func() {
		defer wg.Done()
		for name := range jobs {
			p := filepath.Join(root, name)
			s, err := sizeOf(p)
			results <- sizeResult{Name: p, Size: s, Err: err}
		}
	}()
}

    A for range over a channel keeps pulling values until the channel is closed and drained — that's what makes each worker keep working until jobs is genuinely exhausted, then exit its loop and return, letting wg.Done() fire.

  • Stuck? Show the code 
    go func() {
	wg.Wait()
	close(results)
}()

    This has to run in its own goroutine — calling wg.Wait() directly in duTop's main body would block before you ever start receiving from results, and the workers would deadlock trying to send into a channel nobody's draining yet.

  • Stuck? Show the full function 
    const maxWorkers = 4

func duTop(root string, n int) error {
	dirs, err := os.ReadDir(root)
	if err != nil {
		return err
	}

	jobs := make(chan string, len(dirs))
	for _, d := range dirs {
		jobs <- d.Name()
	}
	close(jobs)

	results := make(chan sizeResult, len(dirs))
	var wg sync.WaitGroup
	for w := 0; w < maxWorkers; w++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for name := range jobs {
				p := filepath.Join(root, name)
				s, err := sizeOf(p)
				results <- sizeResult{Name: p, Size: s, Err: err}
			}
		}()
	}

	go func() {
		wg.Wait()
		close(results)
	}()

	var dSizes []dirSize
	var firstErr error
	for r := range results {
		if r.Err != nil {
			if firstErr == nil {
				firstErr = r.Err
			}
			continue
		}
		dSizes = append(dSizes, dirSize{r.Name, r.Size})
	}
	if firstErr != nil {
		return firstErr
	}

	sort.Slice(dSizes, func(i, j int) bool { return dSizes[i].Size > dSizes[j].Size })
	n = min(len(dSizes), n)
	for _, d := range dSizes[:n] {
		fmt.Printf("%10d %q\n", d.Size, d.Name)
	}
	return nil
}

Idiom

The shape here — a buffered jobs channel filled and closed up front, a fixed number of workers ranging over it, a separate goroutine closing results once wg.Wait() returns — is one of the most common concurrency patterns in real Go code, precisely because it decouples how much work there is from how much concurrency you allow. maxWorkers is the one number you'd tune based on what you're bottlenecked on: CPU-bound work usually wants roughly runtime.NumCPU() workers, while I/O-bound work like this (waiting on disk, or a network call) can often support more workers than CPU cores, since most of each worker's time is spent waiting, not computing.

You now have every raw ingredient — goroutines, channels, select, and bounded pools. Lesson 8 shows you how little of it you'd actually hand-write in most real code, once a well-tested library exists for exactly this shape.
