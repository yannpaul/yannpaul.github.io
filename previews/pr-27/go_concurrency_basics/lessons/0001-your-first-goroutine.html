Your First Goroutine

A small standalone demo today — not burrow yet. Lesson 2 applies this for real.

This course exists because burrow du top scans one subdirectory at a time, in a plain loop, even though each subdirectory's size is completely independent of every other one — exactly the shape of problem goroutines exist for. But the first thing to learn about a goroutine has nothing to do with speed: it's that starting one and waiting for it are two completely separate steps, and forgetting the second one is the single most common first mistake. Today is that lesson, small and isolated, before Lesson 2 puts it to real use.

Before you start

    cd /path/to/your/burrow
go build ./...
./burrow du top --path . --n 5
    Checkpoint

    Builds cleanly, prints a sorted size report, same as before. Don't touch main.go yet — today's work happens in a throwaway scratch file, not burrow itself.

  • Stuck? Show the commands 
    mkdir goroutine-demo
cd goroutine-demo
go mod init goroutine-demo

New: starting a goroutine doesn't wait for it

Prefixing any function call with the go keyword starts it as a goroutine — an independently running unit of work that the Go runtime schedules on its own — and the line right after go keeps running immediately. Nothing waits. Nothing pauses. If main has nothing else to do, it simply exits, and every goroutine still running when that happens is torn down with it — no error, no warning, no partial cleanup.

  • Stuck? Show the code 
    package main

import "fmt"

func main() {
	go func() {
		fmt.Println("hello from a goroutine")
	}()
	fmt.Println("hello from main")
}
  • Stuck? Show the command 
    go run .
    Checkpoint

    You'll almost certainly see hello from main print every single time, and hello from a goroutine never print at all. main finishes its one remaining line and exits before the goroutine — which has to be scheduled onto a thread from scratch — ever gets a chance to run. Nothing here is guaranteed by the language (in principle the scheduler could interleave differently), but on real hardware this outcome is overwhelming, and consistent, and that's the point: go genuinely does not wait.

Idiom

A goroutine is not an OS thread, and this course avoids calling it one. The Go runtime multiplexes potentially thousands of goroutines onto a small pool of real OS threads, starting and scheduling them far more cheaply than the operating system would a thread — which is exactly why "just start ten thousand goroutines" is a normal, unremarkable thing to write in Go, where it would be unthinkable with OS threads directly. See Rob Pike's talk "Concurrency Is Not Parallelism" (linked below) for the deeper point this course will keep returning to: concurrency is about structuring independent pieces of work, not, by itself, about making anything run faster.

New: making main actually wait — sync.WaitGroup

To make main wait for a goroutine on purpose, use a sync.WaitGroup — a counter safe to touch from multiple goroutines at once. The shape is always the same three calls: Add(n) increases the counter by n, Done() decreases it by one, and Wait() blocks until it reaches zero.

  • Stuck? Show the code 
    package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println("hello from a goroutine")
	}()
	wg.Wait()
	fmt.Println("hello from main")
}
  • Stuck? Show the command 
    go run .
    Checkpoint

    Every run now prints hello from a goroutine followed by hello from main — always in that order, every time. main is now genuinely blocked at wg.Wait() until the goroutine's deferred Done() fires, so it physically cannot reach its own print first.

  • Stuck? Show the command 
    go run -race .
    Checkpoint

    Identical output, no warnings — this demo has nothing two goroutines touch at once, so there's nothing to catch. You'll see -race earn its keep in a later lesson, on purpose.

Idiom

Two WaitGroup mistakes worth naming now, before they cost you an hour later. First: always call Add from the goroutine that's starting the work, never from inside the goroutine itself — if Wait() happens to run before a self-Adding goroutine gets scheduled, the counter can still be zero and Wait() returns immediately, as if nothing were running at all. Second: a missing Done() — say, an early return before it, or a panic — leaves the counter permanently above zero, and Wait() blocks forever. That's exactly why this workspace's standing habit is defer wg.Done() as the very first line inside the goroutine: a deferred call still fires on any exit path, including a panic.

That's the whole lesson: go starts something and does not wait; WaitGroup is how you make something wait on purpose. Lesson 2 puts this exact pattern to work on burrow's real bottleneck.

Something unclear — why the unfixed demo's ordering isn't guaranteed even though it's reliable in practice, the two WaitGroup mistakes, why goroutines aren't threads, anything else? Ask your teacher (me) before moving on.
