Packages Beyond main

A small standalone demo today — not burrow yet. Lesson 2 applies this for real.

Every Go file you've written so far starts with package main — the one special package that produces something runnable. But package main is just one package among many a module can have, and understanding what a package actually is, and how visibility works between them, is the whole foundation Lesson 2 needs to pull real logic out of burrow's main.go. Today: a second package, from scratch, small enough to see the whole mechanism at once.

Before you start

  • Stuck? Show the commands 
    mkdir -p greetdemo/greet
cd greetdemo
go mod init greetdemo

    Two directories: greetdemo/ (the module root, where main.go will live) and greetdemo/greet/ (a second package).

New: a directory is a package

A Go package is a directory of .go files that all declare the same package name at the top. There's no separate "create a package" command — you make a directory, put a file in it with a package clause, and that directory is now importable by anything in the same module.

  • Stuck? Show the code 
    // Package greet builds greeting messages.
package greet

var defaultName = "friend"

func Hello(name string) string {
	if name == "" {
		name = defaultName
	}
	return "Hello, " + name + "!"
}
  • Stuck? Show the code 
    package main

import (
	"fmt"

	"greetdemo/greet"
)

func main() {
	fmt.Println(greet.Hello("Ada"))
	fmt.Println(greet.Hello(""))
}
    Checkpoint

    go run . prints Hello, Ada! then Hello, friend!. The import path greetdemo/greet is your module's name (from go.mod) plus the package directory's path — nothing about it references your filesystem's absolute path.

Idiom

Notice greet.go's doc comment — // Package greet builds greeting messages. — sits directly above the package clause with no blank line between them. That's not decoration; a comment in exactly that position is a package's doc comment, shown by go doc and by pkg.go.dev for any package published publicly. Get in the habit of writing one for every package you create, even one this small — it's the first thing anyone (including future you) sees when trying to understand what a package is for before reading its code.

New: exported versus unexported

Go's entire visibility rule is capitalization, checked by the compiler, not a convention you can accidentally violate without consequence. A name starting with an uppercase letter (Hello) is exported — visible to any package that imports this one. A name starting with lowercase (defaultName) is unexported — visible only inside the package that declares it, full stop.

  • Stuck? Show the line to add 
    fmt.Println(greet.defaultName) // add this line temporarily
    Checkpoint

    go build . refuses to compile, with exactly this error: name defaultName not exported by package greet. This isn't a linter warning or a style suggestion — the build fails outright. Remove the line again before moving on; go run . is back to printing its original two lines.

Idiom

Default to unexported. Start every new function, type, and variable lowercase, and only capitalize it the moment something outside the package genuinely needs to call or read it. Once a name is exported, it becomes part of your package's public contract — other code (possibly code you don't control, once a package is shared) can come to depend on it, which makes it harder to freely rename or remove later. An unexported identifier has no such obligation: you can change it freely, because nothing outside the package could have depended on it in the first place. Hello is exported here because main genuinely needs to call it; defaultName stays unexported because nothing outside greet has any legitimate reason to read it directly.

That's the whole mechanism: a directory with a package clause is a package, and capitalization is the entire visibility rule the compiler enforces. Lesson 2 puts this to work for real — pulling actual logic out of burrow's main.go into its own package, then building a second binary that reuses it.

Something unclear — why the doc comment has to sit directly above package with no blank line, what "not exported" actually means for the compiler versus a style linter, when you'd choose to export something versus keep it unexported, anything else? Ask your teacher (me) before moving on.
