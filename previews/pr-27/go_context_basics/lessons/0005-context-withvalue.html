context.Context in Go · Lesson 5 of 7

context.WithValue

A small standalone demo today — not burrow's cancellation path. This is a different, unrelated job a context can do.

Everything so far has been about Done() and Err() — cancellation and deadlines. A context.Context can also carry arbitrary key/value data through a call chain, the same way it carries cancellation: attach it once, and any function holding that context down the chain can read it back, no matter how many calls deep. That sounds like a convenient way to avoid threading a parameter through five function signatures — and that instinct is exactly what this lesson pushes back on.

New: attaching and reading a value

context.WithValue(parent, key, value) returns a child context carrying that key/value pair alongside everything the parent already carries. ctx.Value(key) reads it back — from that context, or from anything derived from it. The key should never be a bare string or int: use an unexported type defined specifically for this purpose, so nothing outside your own code could ever accidentally construct an equal key.

  • Stuck? Show the code 
    package main

import (
	"context"
	"fmt"
)

// unexported key type — prevents collisions with keys defined in other
// packages, even if they happen to use the same underlying value.
type ctxKey int

const requestIDKey ctxKey = 0

func withRequestID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, requestIDKey, id)
}

func requestIDFrom(ctx context.Context) (string, bool) {
	id, ok := ctx.Value(requestIDKey).(string)
	return id, ok
}

func logSomething(ctx context.Context, msg string) {
	if id, ok := requestIDFrom(ctx); ok {
		fmt.Printf("[req=%s] %s\n", id, msg)
	} else {
		fmt.Printf("[no request id] %s\n", msg)
	}
}

func main() {
	ctx := context.Background()
	logSomething(ctx, "before attaching a request id")

	ctx = withRequestID(ctx, "abc-123")
	logSomething(ctx, "after attaching a request id")

	func(ctx context.Context) {
		func(ctx context.Context) {
			logSomething(ctx, "three calls deep")
		}(ctx)
	}(ctx)
}
    Checkpoint

    Prints [no request id] before attaching a request id, then [req=abc-123] after attaching a request id, then [req=abc-123] three calls deep — the value survives being passed through two more layers of ordinary function calls with no extra parameters anywhere.

New: why a bare string key is a real, demonstrable bug

The unexported-type requirement above isn't caution for its own sake. ctx.Value(key) finds a match using ordinary == comparison — and two bare strings with the same text are always equal, even if they were written by two completely unrelated pieces of code that have never heard of each other.

  • Stuck? Show the code 
    func componentA_attach(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, "requestID", id) // plain string key
}

func componentB_attach(ctx context.Context, retryCount int) context.Context {
	return context.WithValue(ctx, "requestID", retryCount) // same string, unrelated meaning
}

func main() {
	ctx := context.Background()
	ctx = componentA_attach(ctx, "abc-123")
	fmt.Println(ctx.Value("requestID")) // "abc-123"

	ctx = componentB_attach(ctx, 3)
	fmt.Println(ctx.Value("requestID")) // component A's value is gone
}
    Checkpoint

    The second print shows 3, not abc-123 — component B's completely unrelated value silently overwrote component A's, because both used the identical string key. Worse: if component A had read it with an unchecked type assertion (ctx.Value("requestID").(string)) instead of the comma-ok form, this would panic at runtime — interface conversion: interface {} is int, not string — the moment component B's code ran anywhere upstream, for a reason that would look nothing like its actual cause.

Idiom

An unexported type defined inside your own package fixes this completely — not by convention, but by the language itself. Two types declared in different packages are different types to the Go compiler even if they're both defined as int with the same underlying value; == on two interface values compares both the dynamic type and the value, so pkgA.Key(0) and pkgB.Key(0) can never be equal to each other, no matter what either package does. This is exactly why every serious use of context.WithValue defines its own private key type rather than reaching for a string or a shared constant — it turns an entire category of accidental collision into something the type system rules out, rather than something you have to remember to avoid.

Idiom

context.WithValue is for request-scoped metadata that genuinely crosses API boundaries you don't control the full call chain of — a trace ID threaded through a web framework's middleware and handlers, say. It is not a general substitute for passing a parameter. If a function's caller always has a value ready to hand it directly, pass it as a real, typed, named parameter — the compiler checks that it's present and correctly typed, go doc shows it, and a reader doesn't have to guess what a function silently expects to find buried in a context. Reach for WithValue only when threading an explicit parameter through every intermediate function would mean touching code that isn't yours to change.

You've now used a context for both of its two real jobs: carrying cancellation, and — much more narrowly — carrying request-scoped data across a boundary you don't control.
