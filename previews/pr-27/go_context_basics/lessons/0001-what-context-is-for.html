What context.Context Is For

A small standalone demo today — not burrow yet. Lesson 2 applies this for real.

Go Concurrency Basics' Lesson 6 gave duTop a timeout with a package-level constant and a bare select against time.After. That works, but it's a dead end: nothing about it can be passed into another function, canceled early on purpose, or combined with a second, independent reason to stop. context.Context is the standard library's real answer to all three. Today, before touching burrow at all: the smallest possible demo of what a context actually is and does.

New: a context you can cancel, and a goroutine watching for it

A context.Context is an interface carrying a cancellation signal through your code. context.WithCancel(parent) returns a new context plus a cancel function; calling cancel closes that context's Done() channel. Anything holding the context — even a completely different goroutine — can watch for that with <-ctx.Done(), which blocks until the moment it happens.

  • Stuck? Show the code 
    package main

import (
	"context"
	"fmt"
	"time"
)

func watch(ctx context.Context) {
	<-ctx.Done()
	fmt.Println("watch: context is done, reason:", ctx.Err())
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())

	go watch(ctx)

	fmt.Println("main: doing some work")
	time.Sleep(200 * time.Millisecond)

	fmt.Println("main: calling cancel")
	cancel()

	time.Sleep(50 * time.Millisecond) // let the goroutine print before main exits
}
    Checkpoint

    The order is always: main: doing some work, then (after the 200ms sleep) main: calling cancel, then watch: context is done, reason: context canceled. The goroutine was genuinely blocked at <-ctx.Done() the entire time — it only unblocks the instant cancel() actually runs, not before.

Idiom

context.Background() is the root of every context tree — no deadline, never canceled on its own, carries no values. Every context you create in this course starts from it (directly, or indirectly through a context that itself started from it). Resist the temptation to call context.Background() partway down a call chain just to "get a context" when you don't have one handy — that silently throws away whatever cancellation or deadline the real caller further up already set up. A context should be threaded down from wherever it was first created, not manufactured fresh partway through.

New: calling cancel more than once is safe

  • Stuck? Show the code 
    package main

import (
	"context"
	"fmt"
)

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	cancel()
	cancel() // calling a second time is a documented no-op, not an error
	fmt.Println("still fine:", ctx.Err())
}
    Checkpoint

    No panic, no error — it just prints still fine: context canceled and exits 0. The second cancel() call did nothing, which is exactly the documented behavior, not a lucky accident.

Idiom

Because a second call to cancel is guaranteed safe, defer cancel() immediately after creating a canceling context is this workspace's standing habit from here on — even in a function where the context might already have been canceled some other way (a timeout elapsing first, say) by the time the deferred call actually runs. Skipping the defer isn't merely untidy: until cancel runs, or the context's parent is itself canceled, the resources behind that context (an internal timer, for a timeout-based one) can't be released. That's a real, specific leak, not a style nitpick.

That's the whole mechanism: a context carries a cancellation signal, Done() is how you watch for it, Err() is how you learn why, and calling cancel is always safe to do more than once. Lesson 2 replaces duTop's hand-rolled timeout with exactly this, using context.WithTimeout to cancel automatically instead of waiting for you to call cancel yourself.

Something unclear — why Done()'s channel doesn't carry a value, why calling context.Background() partway down a call chain is a problem even though it compiles fine, what happens if you never call cancel at all, anything else? Ask your teacher (me) before moving on.
