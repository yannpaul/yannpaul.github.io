Good to know

A real pygame program, run on your own computer, opens a window that stays open until you close it. A browser-based version like OneCompiler's usually can't do that — it runs your code for a while and shows you a picture or a short recording of what happened, then stops on its own after some seconds. That's expected here, not a bug. If your square stops moving after a while even though you didn't touch anything, that's just the tool ending the run — click "run" again to see more.

Get a window showing anything at all

Every pygame program starts the same way: turn pygame on, describe a window, then run a loop that keeps redrawing that window until something tells it to stop. That loop is called the game loop, and literally every moving pygame program — this one included — is built around it.

  • Stuck? Show the lines 
    import pygame

pygame.init()

  • This is called the display Surface — the rectangle of pixels you'll draw everything onto.

    Stuck? Show the lines 
    WIDTH, HEIGHT = 400, 400
screen = pygame.display.set_mode((WIDTH, HEIGHT))
  • Stuck? Show the line 
    clock = pygame.time.Clock()

  • The tiny loop inside the loop (checking pygame.event.get()) is called the event loop — it's how you notice the player clicked the window's close button.

    Stuck? Show the loop 
    running = True
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

    screen.fill((20, 20, 30))
    pygame.display.flip()
    clock.tick(60)

pygame.quit()

    screen.fill(...) paints the whole Surface one flat color — three numbers for red, green, and blue, each 0–255. pygame.display.flip() is what actually shows the Surface on screen; nothing you draw is visible until you call it. clock.tick(60) pauses just long enough to cap the loop at 60 times per second.

  • Checkpoint

    The output area shows a solid dark navy square — your 400×400 window, filled with the color (20, 20, 30). Nothing moves yet, and there's no error message. If you see red error text instead, re-check every line above against your hints before continuing.

Draw the square

Now put an actual square on that window — sitting still, in the corner, for now.

  • Stuck? Show the lines 
    SIZE = 40
x, y = 0, 0
  • Stuck? Show the line 
    pygame.draw.rect(screen, (255, 120, 40), (x, y, SIZE, SIZE))

    pygame.draw.rect takes the Surface to draw on, a color, and a rectangle described as (left, top, width, height).

    Checkpoint

    Run it again: an orange square now sits in the top-left corner of the window, staying perfectly still.

Make it move

  • Stuck? Show the line 
    dx, dy = 4, 4
  • Stuck? Show the lines

    Checkpoint

    Run it: the square now slides diagonally down and to the right, and eventually slides right off the window and out of view. That's expected — you haven't taught it about walls yet. That's next.

Bounce off the walls

A bounce is just: notice the square reached an edge, then flip the sign of its velocity on that axis. Nothing about the square's position needs to jump — only the direction it's heading changes.

  • The square's left edge is at x; its right edge is at x + SIZE. It's hit a wall when the left edge reaches 0 or the right edge reaches WIDTH.

    Stuck? Show the lines 
    if x <= 0 or x + SIZE >= WIDTH:
    dx = -dx
  • Stuck? Show the lines 
    if y <= 0 or y + SIZE >= HEIGHT:
    dy = -dy
  • Checkpoint

    The orange square bounces off every edge of the window and never leaves view — it just keeps going, changing direction each time it touches a wall, for as long as the program keeps running.

Idiom

In pygame, (0, 0) is the top-left corner of the window, not the bottom-left like graph paper. x grows to the right as you'd expect, but y grows downward. That's why a positive dy in this lesson moves the square down, not up — if your square seems to bounce the "wrong" way vertically, this is almost always why.

Here's the whole thing end to end, for reference once every piece above is checked off and working on your own:

Show the complete program 
import pygame

pygame.init()

WIDTH, HEIGHT = 400, 400
screen = pygame.display.set_mode((WIDTH, HEIGHT))
clock = pygame.time.Clock()

SIZE = 40
x, y = 0, 0
dx, dy = 4, 4

running = True
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False

    x += dx
    y += dy

    if x <= 0 or x + SIZE >= WIDTH:
        dx = -dx
    if y <= 0 or y + SIZE >= HEIGHT:
        dy = -dy

    screen.fill((20, 20, 30))
    pygame.draw.rect(screen, (255, 120, 40), (x, y, SIZE, SIZE))
    pygame.display.flip()
    clock.tick(60)

pygame.quit()

Now play with it

You have a working proof-of-concept. Before moving on to anything new, try changing a few numbers and predicting what will happen before you run it each time:

  • Change dx, dy = 4, 4 to bigger or smaller numbers — what happens to the speed?
  • Change one of them to a negative number to start — which direction does it head first?
  • Change the color tuple in pygame.draw.rect — pygame colors are (red, green, blue), each 0–255.
  • Change SIZE to make a bigger or smaller square — does it still bounce correctly?
Something unclear — why pygame.display.flip() is needed at all, why the bounce check comes right after moving instead of before, anything else? Ask your teacher (me) before moving on. A good question now is worth more than pushing ahead confused.
